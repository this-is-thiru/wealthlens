# ADR: W-337a — the mapping layer (closes D-928 C1)

**Decision under test (D-928 C1a):** Spring Data JPA (Hibernate) with Flyway, against **C1b** (Spring Data JDBC) and
**C1c** (jOOQ).

**Result: C1a confirmed, not reopened.** `insurance` and `auth` ported to parallel JPA entities on branch `w-337`
(`UserDetailJpa`, `RefreshTokenJpa`, `InsuranceJpa`, `PolicyDetailsJpa`), proven against a real PostgreSQL 18 Testcontainer
in `PostgresMappingProbeIntegrationTest` (6/6 green): the encrypted and searchable columns (`EncryptedColumn`,
`SearchableColumn`, JPA `AttributeConverter`s on the same `FieldCipher` Mongo's `EncryptedField`/`SearchableIdentifier`
use — proven cross-compatible, the copier's premise, D-928 C3a), an embedded list, an atomic conditional update
(`RefreshTokenJpaRepository.spend`, exactly-once under real concurrency), an expiry swept with no TTL index, a
transaction (committed and rolled back), and money/dates/instants exact.

**Scope, per the owner's choice between a full cutover and a parallel probe:** the live `UserDetail`/`RefreshToken`/
`InsuranceEntity` and their services are untouched — MongoDB stays primary. `PostgresJpaConfig` is off by default
(`app.postgres.enabled=false`), so nothing about the running app changes. The real cutover is W-337c's.

## What the probe found, for W-337b/c to reuse

- **Spring Boot 4 split JPA/JDBC out of `spring-boot-autoconfigure`.** The MySQL-era plan's dependency names
  (`flyway-core` + `flyway-mysql`) and class packages no longer exist. Correct for this version:
  `spring-boot-starter-data-jpa`, `spring-boot-starter-flyway` + `org.flywaydb:flyway-database-postgresql` (runtime),
  `org.postgresql:postgresql` (runtime); `DataSourceProperties` is now `org.springframework.boot.jdbc.autoconfigure`,
  `EntityManagerFactoryBuilder` is now `org.springframework.boot.jpa` (and its constructor takes
  `Function<DataSource, Map<String,?>>`, not a plain `Map`), and Hibernate's Spring bean container is
  `org.springframework.orm.jpa.hibernate.SpringBeanContainer` (not the older `orm.hibernate5` package).
- **A second `DataSource`/`EntityManagerFactory`/transaction manager must be fully hand-built**, not left to Boot's
  auto-configuration: once any `DataSource` bean exists, Boot's own JPA auto-configuration activates against it
  (`@ConditionalOnSingleCandidate(DataSource.class)`), and would otherwise entity-scan the whole app and collide with
  the manually-wired beans. Defining `DataSource`/`EntityManagerFactoryBuilder`/`LocalContainerEntityManagerFactoryBean`/
  `PlatformTransactionManager` beans of those exact types (any name) makes Boot's `@ConditionalOnMissingBean`
  auto-configuration back off — proven by a clean app-context boot with both stores present. The existing
  `MongoDbTransactionConfig`'s bean needed `@Primary` so every untouched `@Transactional` in the app still resolves to it
  now that a second transaction manager exists.
- **Hibernate instantiates a `@Convert` converter by reflection** unless told to ask Spring instead — the same problem
  `MongoConfig.mongoCustomConversions` solves for `@ValueConverter` (D-447). Fixed by setting
  `hibernate.resource.beans.container` to a `SpringBeanContainer` when building the entity manager factory.
- **A custom `@Modifying @Query` method is not itself transactional**, unlike an inherited `JpaRepository` method
  (`save`, `findBy…`): it throws `TransactionRequiredException` unless called from inside an existing transaction. The
  real port's services will need `@Transactional("postgresTransactionManager")` (or the equivalent) on any method that
  calls one, not just the repository's own annotations.
- **`@ElementCollection` defaults to lazy**, unlike Mongo's embedded list, which always arrives with its parent
  document. Needs `fetch = FetchType.EAGER` to behave the same way outside of an open session.
- **The JPA `AttributeConverter` contract does not skip `null`** the way it was assumed to (unlike what the Mongo
  `MongoValueConverter`s here rely on) — Hibernate calls a `@Convert` converter for a `null` embeddable/element-collection
  field in this version, so `EncryptedColumn`/`SearchableColumn` null-check explicitly.
- **PostgreSQL's default collation is already case-sensitive** (unlike Azure SQL's, which needed D-934 C2's explicit
  collation to avoid matching ciphertext case-insensitively) — nothing to decide here.

## Not done here (left for W-337b/c)

Date and enum encrypted forms (`EncryptedField`'s other two branches) — no insurance/auth field needs them; a Flyway
layout for the other 37 collections; the live services' cutover; the copier (W-337g); `LoginIndexInitializer`'s removal
(it still runs, since the Mongo entities are untouched).
