## Plan for W-236 — the Gazette watch (design first, with the owner)

**For:** a new Gazette instrument that may change a shipped pack — a Finance Act, an Income-tax Rules amendment, a CBDT
notification — is noticed within a day and put in front of the owner as a lead, so a pack is never silently out of
date. The job **never writes a pack**; a lead is not law until its Gazette copy is read (strict-Gazette rule).

### What I read (session 50)

- **`DR 19` E8** (`19-engineering-foundations.md:480` – `:500`): `GazetteWatch` — daily, singleton across the cluster,
  *"checks the gazette index; opens a ticket. Never writes a pack"*. W-236's row: undesigned — which index, how
  "touching" is decided, where a ticket goes (`03-WORK-ITEMS.md:1516`, D-449 C1a).
- **The job framework exists** (W-137, D-449): `taxplanning/jobs/` — `TaxJob`, `TaxJobRunner` (a Mongo lease per job,
  TTL, a fencing holder), `JobFailure` dead-letter, `TaxJobSchedule` behind `app.tax.jobs.enabled`.
- **How the Gazette can be read** (sessions 12 – 16, memory "egazette-locate-by-scan"): no index API is known to me;
  PDFs sit at `https://egazette.gov.in/WriteReadData/<year>/<number>.pdf`, the number rising with publication date;
  each first page carries the ministry, department, date line and title in English. This is how every Gazette copy in
  `sources/` was found. A search page exists on the site; whether it can be queried by a program is **not verified**.
- **Reading a PDF needs no new library:** iText 5.5.13 (`pom.xml:26`) has `com.itextpdf.text.pdf.parser.PdfTextExtractor`.
- **No outbound HTTP client is used in `main` today**; Spring's `RestClient` comes with `spring-web`.
- **What a pack is founded on:** each lock's `instruments` (Act, Finance Act, Rules, with Gazette ids), and each rule
  version's `provision2025` / `provision1961` section references.

### Choices (recommended first)

**C1 — the index.** (a) **Scan by number:** keep a cursor (`tax_gazette_cursor`: year, last number read); each run
fetches the following numbers' PDFs, reads page 1, stops after 20 consecutive misses (the end of what is published)
or 400 numbers (a cap per run), and advances the cursor; a new calendar year starts a new folder. Proven by hand on
this site; about one minute per 100 PDFs. (b) The site's search form — unverified; I would probe it first and come
back. (c) A non-Gazette source (incometaxindia.gov.in notifications) — not Gazette, so leads only, and the site was
unreachable from here before (D-159).

**C2 — "touching a shipped pack".** (a) **Two tiers:** a lead when page 1 names the *Ministry of Finance (Department of
Revenue)* and *income-tax* (or the Central Board of Direct Taxes, or a Finance Act); and on each lead, the shipped rule
ids whose `provision2025` / `provision1961` sections the text names, listed as *possibly affected* — for triage, never
a verdict. (b) Section matches only — misses a new instrument that cites no section on page 1.

**C3 — where a lead goes.** (a) **A Mongo collection `tax_gazette_leads`** (number, URL, date line, title, matched
terms, possibly affected rules, found at; unique on URL so a re-run adds nothing), a `SUPER_USER` read endpoint
`GET /tax-planning/admin/gazette-leads`, and a WARN log line per lead — no secret, no third-party write. (b) Also open a
YouTrack WL issue per lead — needs a write token in production config (a secret, a runbook entry) and an outbound call
to `youtrack.cloud`. (c) YouTrack only.

**C4 — how it calls out.** (a) **`RestClient` with a generic `User-Agent` (`WealthLens-GazetteWatch/1.0`, no email in any
header or URL)**, 10 s timeouts, one request at a time, a pause between requests; the
whole watch behind its own flag `app.tax.gazette-watch.enabled`, **off** in every profile until you turn it on.
(b) On with the other jobs.

### Build (C1a – C4a), in outline — the steps are re-planned once these are chosen

2. `GazetteLeadController` (`SUPER_USER`, read only).
3. Config: `app.tax.gazette-watch.*` (enabled false, base URL, caps, pause) in the three profile yamls.
4. Runbook: how to seed the cursor (the year and a recent number), turn the flag on, read the leads; a removal is not

5. Tests: matcher on page-1 texts of real Gazette copies in `sources/` (Finance Act 2026, Rules 2026, a non-tax notice

### Risks and unknowns
- **Unverified:** whether egazette.gov.in serves an automated client from a cloud host daily without blocking; the
  first enabled run is the test, and its outcome goes in the runbook's log.
- A long instrument's English may begin after page 1 (memory: ITR-form notices at p.47) — tier one may miss it; reading
  pages 1 – 3 trades bandwidth for recall. Proposed: page 1 only, to start.
- Choosing the seed number per year is manual (C1a); a wrong seed only delays leads.

### The build in detail (after C1a – C4a; session 50)

**Module boundaries.** The job runs in `taxplanning` (where `jobs/` lives). Tier two needs each shipped rule's cited
sections, which sit inside `taxengine.rules` — not visible to `taxplanning` (`taxplanning/package-info.java`: only
`taxengine :: *` named interfaces). So the engine's `api` (`TaxCalculator`, already exposing `ruleChecksums`,
`packVersions`) gains one read: `List<ProvisionCitation> provisionsCited(TaxYearId year)` — each rule version's
`provision2025` / `provision1961` reference reduced to `(act, section, ruleId)` (`act` = `2025` or `1961`; `section`
the number and letters after `s.`, e.g. `202`, `80C`; a reference naming several sections gives several rows). A
read of shipped facts, no law in code.

**The pieces** (`taxplanning/gazette/`):
1. `GazetteCursor` — one document `{_id: "egazette", year, last_number, updated_at}` in `tax_gazette_cursor`.
2. `GazetteLead` — `tax_gazette_leads`: `url` (unique index), `year`, `number`, `date_line`, `title`, `matched_terms`,
   `possibly_affected` (rule ids with the section), `found_at` (UTC).
3. `GazetteFirstPage` — fetches one number with `RestClient` (User-Agent `WealthLens-GazetteWatch/1.0`, 10 s timeouts),
   returns *absent* on 404, the page-1 text otherwise (iText `PdfTextExtractor`); any other failure throws — the
   runner records it in `tax_job_failures` and the cursor is not advanced past it.
4. `GazetteMatcher` — tier one: the text names *Ministry of Finance* and *Department of Revenue*, and one of
   *income-tax*, *Central Board of Direct Taxes*, *Finance Act* (case-insensitive, whitespace-normalised); tier two: each
   *"section N"* / *"s. N"* in the text against `provisionsCited` of every shipped year, keyed by the Act the text names.
   The words are the job's search terms, held in `app.tax.gazette-watch.terms`, not code (facts, not rules).
5. `GazetteWatch implements TaxJob` — `name` `gazette-watch`, timeout 60 min. Reads the cursor (none → logs *"seed
   the cursor"* and returns, never guesses); for each next number, in the cursor's year folder and — once that folder
   has 20 misses in a row and the clock's year is later — the next year's folder (numbers continue across years:
   2025/265620, 2026/271439); stops at 20 misses in a row, 400 fetched, or a lost lease; saves a lead per match
   (`insert`, a duplicate URL skipped); advances the cursor after each number read.
6. `GazetteWatchController` — `GET /tax-planning/admin/gazette-leads` (newest first) and
   `PUT /tax-planning/admin/gazette-cursor` (`{year, lastNumber}`, validated: a known year folder, a positive number),
   both `SUPER_USER`.
7. Schedule: `TaxJobSchedule` runs it on `app.tax.jobs.gazette-watch-cron` (daily, 05:00) only when
   `app.tax.gazette-watch.enabled` is true — `false` in all three profile yamls (C4a).
8. Runbook §1.w: when, who, the seed call (with a read-only check before and after: `GET` the leads, the cursor
   document), turning the flag on, reading the first run's outcome; safe to re-run (unique URL, cursor forward only);
   the way back: the flag off.

**Choices left (recommended first):**

**D1 — seeding the cursor.** (a) **The `PUT` endpoint above**, validated and recorded with the caller; (b) a `mongosh`
insert in the runbook — no code, no validation.

**D2 — the page-1 test fixtures.** (a) **The first page's text of three real Gazette copies, extracted once and
committed as test resources** — Finance Act, 2026 (271439, a lead), Income-tax Rules, 2026 (271092, a lead), and one
non-tax notice from the same weeks (not a lead) — each with its URL and sha256 in a `_source` line; (b) synthetic texts
— proves the matcher against what I imagine a Gazette says.

**Tests** (each expected value from the texts themselves, by hand): the matcher on the three fixtures (lead / lead / not;
tier-two rules named for the Rules' sections); `provisionsCited` on the shipped packs (e.g. `SAL-STANDARD-DEDUCTION-NEW-TAX-REGIME`
cites 2025 s.19); the watch against a JDK `HttpServer` serving iText-made PDFs at numbers n+1, n+3 with gaps — the
cursor's advance, the 20-miss stop, the year roll, a re-run adding nothing, a 500 recorded and the cursor held; the
controller's role checks (integration). **No test calls egazette.gov.in.** Probes: drop a term → the Finance Act
fixture stops being a lead; remove the unique index → the re-run test fails.

### Revision 1 — the approved rule fails on real Gazette copies (R13; session 50; for approval)

Before any code, step D2a's fixtures were fetched and read (`sources/2026-11-07-gazette-watch-window.md`). The approved
design is wrong on the two instruments that matter most:

- **The Finance Act, 2026** (271439) is published by the *Ministry of Law and Justice (Legislative Department)*; page 1
  never says *Ministry of Finance* or *Department of Revenue* — C2a's tier one misses it.
- **The Income-tax Rules, 2026** (271092, 2,508 pages) carries only the Gazette header on page 1; its English half
  begins near page 1,530 — nothing on page 1 identifies it. C1a's *"reads page 1"* misses it.
- **Measured over 100 consecutive numbers** (271400 – 271499, 30 – 31 March 2026): the approved page-1 rule flags **0**;
  a whole-document rule flags **18** — the Finance Act and 17 Department of Revenue / CBDT instruments — and leaves out
  the two customs-side notices that merely name a Finance Act.

**What changes (recommended first):**

**E1 — the rule.** (a) **Read the whole document, stopping at the first page that names *Central Board of Direct
Taxes*, or names both *Income-tax Act* and *Department of Revenue*** — a lead; the terms in config as before. Catches the
Act (by its CBDT mention) and the Rules (page 1,533); flags 18 of 100 in a busy week, none of the non-tax notices.
(b) Any of income-tax / CBDT / Finance Act anywhere — 20 of 100, the extra two customs notices. (c) Keep page 1 — 0 of
100.

**E2 — the cost of reading whole documents.** Most notices are 2 – 6 pages; an Act is ~120, the Rules 2,508 (29 MB,
53 s to the first match with pypdf). (a) **Keep the 400-numbers-per-run cap and add a byte cap per document (40 MB,
over it → a lead marked *"too large to read; open it"*)**, so nothing is silently skipped; the run's 60-minute lease
holds. (b) No byte cap.

**E3 — tier two (possibly affected rules)** reads the sections named on the matching page and the next two, not
page 1 — the place the instrument's own English is.

**Fixtures (D2a, revised):** single pages cut from the real copies, each with its URL and sha256 in a `_source` note —
the Finance Act's page naming CBDT, the Rules' page 1,533, all of 271421 (a two-page CBDT notification), 271497 (a
Department of Revenue notice naming a Finance Act — not a lead under E1a), and 271093 (health — not a lead). The
whole-document scan (first match, stop, byte cap) is tested against the fake server with generated multi-page PDFs.

Everything else in "The build in detail" stands (cursor, leads collection, endpoints, flag off, runbook §1.w).

### Build record

**Engine (`taxengine.api`):** `ProvisionCitation(act, section, ruleId)`; `TaxCalculator.provisionsCited()` — every
shipped year's rule versions, each `provision1961` / `provision2025` present in an Income-tax Act, its references read by
`CitedSections` (`s.` one section, `ss.` a list, `;` a further citation, sub-divisions dropped).

**`taxplanning/gazette/`:** `GazetteWatchSettings` (`app.tax.gazette-watch.*`, terms in config), `GazetteCopies` (GET
only — the site answers HEAD with 404 even for a copy it holds; 404 absent, any other non-2xx a failure; a body over the
size cap read no further), `GazetteMatcher` (whole copy, page by page, first page meeting the terms; tier two from
"section N of the Income-tax Act, 1961 / 2025" on that page and the next two), `GazetteWatch` (cursor, misses, year roll,
cap, lease), `GazetteCursor`, `GazetteLead` (unique `url`), `GazetteWatchService`, `GazetteWatchConfig`;
`controller/GazetteWatchController` (`SUPER_USER`); `TaxJobSchedule` runs it daily only when the flag is on;
`JobIndexInitializer` creates the lead index. Config in the three profile yamls and the integration-test yaml (flag
`false` everywhere). Runbook §1.w. `02-TECH-SPEC.md` layout and Changes.

**Fixtures (D2a, Revision 1):** five cuts of real copies under `src/test/resources/taxplanning/gazette/` with
`SOURCES.md` (URL, sha256, pages).

**Tests:** `CitedSectionsTest` (5, references copied from shipped rules), `ProvisionsCitedTest` (1, six citations read by
hand from the rule files), `GazetteMatcherTest` (5 — Finance Act page, Rules p.1533, 271421 leads; 271497, 271093 not;
tier two: `1961 s.2 CG-TERM-LISTED-SECURITY`, `1961 s.10 OS-DEATH-GRATUITY`, none for 2025 s.533 — all from the rule
files), `GazetteWatchIntegrationTest` (6 — no cursor refused; leads and cursor 104 after three misses; rerun adds nothing;
year roll to 2027/105; a 500 holds the cursor at 499; too large → page-0 lead), `GazetteWatchEndpointIntegrationTest`
(3 — 403 for a user; cursor stored with its caller; 2008 refused 400). **No test reaches egazette.gov.in.** All matcher
expectations held on the first run: iText reads the real pages, 271421's English on its page 2.

**Probes, each reverted (`cmp`):** the Board term dropped → the Finance Act and Rules cases fail; `@Indexed(unique)`
removed → the rerun test finds two leads.

**Departures from the plan:**
1. `provisionsCited()` takes no year — it reads every shipped year, since `taxplanning` cannot list them.
2. Tier two matches *"section N of the Income-tax Act, YYYY"* only, not any "section N": the Finance Act's page also cites
   the Black Money Act's section 4, which a bare match would have pinned on an Income-tax rule.
3. The endpoint tests use the JDK's HTTP client: RestAssured 5.5.7 throws a NullPointerException inside its own response
   handling on these `/tax-planning/admin` paths although the server answers correctly (403, 200, 400 — read with the JDK
   client); `TaxPlanningControllerIntegrationTest` already avoids RestAssured on `/tax-planning`. Cause not established;
   not a defect of the endpoints.
4. A test's own state (the fake server's copies, a per-class instance under `@TestInstance(PER_CLASS)`) is cleared
   before each test — the first run of the rerun case failed on copies left by another case, not on the index.
5. The too-large note gave the cap in whole megabytes ("over 0 MB" at the tests' 100-byte cap) — it gives bytes.
6. `verify`'s JaCoCo gates not run separately; the new engine code is covered by the tests above.
