**What this item is for (one sentence, in my own words):** the only code that reads untrusted PDF bytes, iText's `PdfReader`, runs in a
child process that is killed at its time budget, capped in CPU and memory, and cut off from the network. A hostile PDF then cannot
hang, exhaust or reach out from the application.

### What the design, the code and the sources say

- **O6** (`14-operational-design.md`, "Parsing isolation"): "the parser runs with **no network egress** and a hard CPU and
  wall-clock budget — a PDF is untrusted input from an unknown generator". The same section adds that the parser is "the module's only
  attack surface that consumes arbitrary third-party bytes". **D-761 C4a:** isolation is required before `app.tax.documents.enabled`
  turns on. D-769 C2a kept that.
- **iText reads untrusted bytes in two places today, both inside the application:**
  - At upload, `DocumentBytes.pagesOf` (`documents/store/DocumentBytes.java`) opens `new PdfReader(plain)` to refuse a password
    and count the pages. It runs in the request thread.
  - In the job, `CertificateReading.read` (`documents/parser/CertificateReading.java`) opens `new PdfReader(content.bytes())` and
    calls `PrintedText.of(reader)`, which turns the pages into `Word(page, line, text, left, right, top, bottom)`.
    Everything after that is matching against the year's layout, on plain data.
- **The seam:** the untrusted part is bytes → (password?, pages, words). The layout matching (`CertificateReading.Matching`) needs
  the rule packs through `TaxCalculator`, and it stays in the application.
- **Today's budget:** `ParseDocuments.withinBudget` runs the parse in a daemon thread and waits `parse-budget` (PT30S, D-764 C3a).
  Past it, the thread is "abandoned, not stopped — that is W-131f's isolation" (its Javadoc).
- **No in-JVM sandbox:** Java 25 refuses a Security Manager. Run locally, `java -Djava.security.manager=allow -version` printed
  "Enabling a Security Manager is not supported". So isolation has to be a separate OS process.
- **The jar:** a Spring Boot 4.1.0 fat jar, `Main-Class: org.springframework.boot.loader.launch.JarLauncher` (its manifest), and it
  ships `org/springframework/boot/loader/launch/PropertiesLauncher.class` (`unzip -l`). PropertiesLauncher can start another main
  class from the same jar (`-Dloader.main`). This is from Spring Boot's documentation, not yet observed here (C5).
- **The image:** `eclipse-temurin:25-jre-alpine`, one container (`Dockerfile`), run as
  `docker run -d -p 8080:8080 --name wealthlens-container …` (`aws/runbook-daily.sh:7`). The app itself needs the network for Mongo
  Atlas, so cutting the network applies to the child only.

### Choices for the owner (recommended first)

- **C1 — the mechanism:**
  - **(a)** A child JVM per read, started from the same jar (`java -Xmx… -cp /app.jar -Dloader.main=<reader> PropertiesLauncher`).
    The PDF bytes go in on stdin, and the result comes back on stdout as JSON: a password refusal, the page count, and the words.
    Nothing runs between reads, so there is **no new server** and no new image. Each read pays a JVM start (time measured in C5).
  - (b) A separate always-on reader container with `--network none`, `--memory` and `--cpus`, talking over a Unix socket on a shared
    volume. Docker enforces the strongest isolation this way, but it is a second container, always running, with its own deploy steps.
  - (c) Keep reading in-process. **Not recommended:** it does not meet O6, and D-761 C4a keeps uploads off.
- **C2 — no network egress:**
  - **(a)** Start the child in its own empty network namespace (`unshare -rn`), **if** C5 shows the app's container allows it under
    Docker's default security profile. Otherwise, start it with every Java connection sent to a dead proxy
    (`-DsocksProxyHost=127.0.0.1 -DsocksProxyPort=9`), and record in the D-row that this second path stops Java code only, not native
    code. That gap would then be yours to accept.
  - (b) The dead-proxy setting only.
- **C3 — what goes into the child:**
  - **(a)** Both reads: the upload's password and page check, and the job's printed text. After this, iText never opens an untrusted
    file inside the application.
  - (b) The job's read only. The upload's page count stays in-process.
- **C4 — the limits:**
  - Wall clock: the existing `parse-budget` PT30S. Past it, the child is killed (`destroyForcibly`) and the attempt is `FAILED`, as
    today. The upload's check gets its own budget, `upload-read-budget`, at PT10S (**mine, unsourced**).
  - CPU: `ulimit -t 30` for the child, matching the budget (**mine**).
  - Heap: `-Xmx256m` (**mine**: measured in C5 on a 20 MiB, 50-page PDF; adopt or raise).
  - Output: at most 16 MiB read back, parsed strictly. Anything else is a `FAILED` attempt, or a 400 at upload saying the PDF could
    not be read. The child is treated as untrusted too.
- **C5 — the probe:** may I run a one-off CI workflow on a throwaway branch, as W-131e's probe ran? It would build the jar and the
  image, then check four things:
  - the child starts through PropertiesLauncher;
  - `unshare -rn` works inside the container (and whether alpine needs `util-linux` for it);
  - busybox's `ulimit -t` works;
  - the child's start time and peak memory.

### Five roles

- **Architect:** the untrusted surface becomes one small `main` with no Spring and no rule packs. The application trusts only checked
  JSON from it. No new module, no new server (C1a).
- **Product manager:** nothing visible changes. An upload may take about one JVM start longer (C5 measures it), and the switch can be
  turned on once this is done.
- **Senior engineer:** `ParseDocuments` loses its abandoned threads. Limits live in yaml, and the child's reply is size-capped and
  strictly parsed. Only `IOException` and `TimeoutException`-shaped failures are caught.
- **Automation tester:** misbehaving children (hang, flood, crash, garbage) are each a test. Every existing parser golden still passes,
  because the same words reach the same matching.
- **Manual tester:** on staging, a real Form No. 130 reads as before, and the start log names the isolation in force (namespace or
  proxy).

### Risks or ambiguities

- **C2's namespace** may be refused by Docker's default security profile. Then only the proxy fallback is left, and its gap is yours to
  accept.
- **Upload latency** of one JVM start, unmeasured until C5.
- **Memory:** one child at a time (the job reads documents one after another), plus one per concurrent upload. Unmeasured until C5.
