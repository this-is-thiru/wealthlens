### Findings

1. **The pipeline can't run from salary yet.** `inputs.components` and `salary.gross` have no nodes until

2. **The row's path is stale.** `S202_DEFAULT` is the regime code renamed to `NEW_TAX_REGIME` (D-051), and

3. **The runner can't live in `taxplanning`.** It needs `pipeline` and `node`, which aren't named

5. **No 2025-26 T1 rule is `UNVERIFIED`** (`W-052c`), so no case is `PROVISIONAL` now. The mechanism is

## Built — where the build departs from the plan (for review)

- **B1 — a defect in the shipped law data, found by the golden cases: `FIRST_SCHEDULE_RATES`'s pipeline
  had no `tax.afterrebate`.**
  - The ₹12,500 rebate (s.156(1); 1961 s.87A) could never run in the other regime. The pipeline went
    `tax.bybasis → tax.cess`, and `CessNode` requires `tax.afterrebate`, so every First Schedule case
    refused to run.
  - It has been there since `W-045f`, probably from the row ⚠ *"The relief branch exists only in the
    default regime"*, which `W-049` corrected for the rebate node but not for the regime's pipeline.
  - **Fixed:** `tax.afterrebate` is inserted after `tax.bybasis`, as in `NEW_TAX_REGIME`. The law layer
    moved, so the locks go to **2025-26 `law.2`** and **2026-27 `law.11`**; no rule checksum changed.
  - This is a pack change the plan said this item wouldn't make. It's the one change needed for T1-O1,
    O2, O3 and A1a–d to run, and it's exactly what the golden cases exist to catch (rule R3: *"if one
    fails, the code is wrong"*).
- **B2 — bite probe 1 (the rebate's regime check off).** T1-O2 fails against ₹13,000, and several cases
  error on `RebateNode`'s overlap guard (the rebates exceed the tax at slab rates). The plan predicted
  "≈₹10"; the actual effect is a failure plus refusals, since the new-regime rebate now meets the
  First Schedule tax.
