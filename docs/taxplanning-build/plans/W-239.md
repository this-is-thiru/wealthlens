## Plan for W-239 — third-party retention for landlords and lenders

**What this item is for (one sentence, in my own words):** the monthly `retention-purge` job deletes a landlord or
lender record once its retention has run out (`DR 14` O5 sets this as "the tax year plus 2 years"). Today nothing
ever deletes those records.

### Choices (recommended first)

**C1 — what "the tax year" is for a record no draft names.**
- **(a) Recommended:** the **later** of:
  - the latest tax year among the profile's stored drafts, of any status;
  - the tax year containing the record's last change (`updated_at`, or `created_at` if that is absent).

  The record is kept through the end of that tax year plus the period. Any draft of the profile may be the return
  the record supports. Without a reference, this is the shortest period that still covers O5's minimum for every
  such return. The second date keeps a record entered before the year's draft exists. Both inputs are stored facts.
  No date is written into code. Once the profile's last draft is purged, the record follows it ("erased with the
  draft").
- (b) Only the record's own last change. This is shorter, but it can delete a landlord before O5's minimum. For
  example, a landlord entered in 2025-26 and used in the 2026-27 draft would be deleted after 31-03-2028, a year
  early for 2026-27.
- (c) Build F3's reference first (a `landlordId` on `Tenancy`, a `lenderId` on the loans), then anchor on the last
  draft naming the record. This changes the input schema and the API, so it is a separate item. Under (a) I
  **place it as a backlog row** (W-239a, `·`, Phase 14 after W-239). It is what would shorten (a)'s retention to
  the exact year.

**C2 — what is deleted.** **(a) Recommended:** the whole record (name, address, PAN, relationship / kind).
`DR 14:21` classes all of these as third-party data, and F3 says "they carry the shortest retention". (b) Blank the
PAN only, which is the literal reading of `:144`. That would leave a name and an address with no purpose.

**C3 — the period.** **(a) Recommended:** `app.tax.retention.third-party-after: P2Y` in all three profile yamls, a
third component of `RetentionPeriods`. It is product policy (O5 marks it `RECOMMENDATION`), so it is configuration
like D-449's periods, not rule-pack data.

**Expected values, by hand (for the tests).** The clock is 2029-04-01:
- **Case 1.** The profile's drafts are 2025-26 and 2026-27. A landlord was last changed on 2025-06-01, which is in
  2025-26. The anchor is max(2026-27, 2025-26) = 2026-27, which ends on 31-03-2027. Adding P2Y gives 31-03-2029.
  2029-04-01 is after that, so the landlord is **deleted**.
- **Case 2.** Same as case 1, but the clock is 2029-03-31. That is not after 31-03-2029, so the landlord is
  **kept**. This is the boundary case.
- **Case 3.** The profile has no drafts. A lender was last changed on 2027-05-10, which is in 2027-28. 2027-28 ends
  on 31-03-2028, plus P2Y gives 31-03-2030. With the clock at 2029-04-01 the lender is **kept**.
- **Case 4.** The profile's latest draft is 2028-29. A landlord was changed in 2024-25. The anchor is 2028-29, which
  gives 31-03-2031, so the landlord is **kept**. This proves the draft side of the max.
- **Case 5.** The lease is lost before the first removal. Nothing is deleted.
- **Case 6.** Another profile's records are untouched.

**Probe.** Remove the draft side of the max. Case 4 must then fail: its anchor becomes 2024-25, which gives
31-03-2027, so the landlord would be deleted. Then restore the file byte for byte (`cmp`).

### Five roles

- **Architect:** the change stays inside `taxplanning` and adds no new module dependency. The anchor is computed
  from stored facts. The period is configuration, and no legal date is in code. The seam is `RetentionPurge`, with
  the same lease discipline as the draft pass.
- **Product manager:** after its period, a landlord or lender disappears from `GET …/landlords` / `…/lenders`.
  Nothing computed changes, because no computation reads these records. The api-collection is unaffected, since no
  request shape changes. Stored data from before this item is purged on the first run if it has expired.
- **Senior engineer:** no new field or parameter without a caller. `thirdPartyAfter` is read by the purge. Names
  reuse "retention", "purge" and "third-party" from O5.
- **Automation tester:** cases 1 – 6 and the probe above. I will grep the tests for `RetentionPeriods(` and
  `purgeArchivedAfter` so every constructor call is updated.
- **Manual tester:** on staging, create a landlord, then set its `audit_metadata.updated_at` back on a **copy**
  database only (the owner runs this). Run the purge, or wait for the 1st of the month. Then
  `GET /tax/user/{email}/profiles/{profileId}/landlords` (`TaxProfileReferenceController.java:26`, `:69`) returns `[]`. Edge cases: a profile with no drafts, a
  record with no `updated_at`, and the 31 March boundary.
