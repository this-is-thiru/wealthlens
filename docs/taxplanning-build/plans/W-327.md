## Plan for W-327 — a plain "why" for lines with no limit (F37.3): split first

**What this item is for (one sentence, in my own words):** when a trace line's `limitedBy` is not a limit the content
explains, the explanation prints the engine's text after the sentence, as written. That text uses component codes,
unformatted figures and internal ids. This item makes that "why" plain words too: the node publishes the reason as
facts, and the content turns those facts into a sentence.

**Probe (run before this plan, then removed):** for one taxengine unit run (4,175 tests, all green), I logged every
`TraceLine.withLimitedBy` call: the rule, the node, the kind, the calling class and line, and the text. I then restored
`TraceLine.java`; `git diff` shows it unchanged. I classified each text against the shipped `byLimit` names.

| Finding | Count |
|---|---|
| `limitedBy` writes in the run | 388,387 |
| Producer sites (class:line) | 139. 7 of them are test classes, so **132 engine sites** |
| Sites that write only a limit name the content explains | 13. These already read in words (W-116) |
| Engine sites that write engine text | **119**, by family: salary 51 (including `employer.contrib.charges`), Chapter VIII and other sources 29, house property and set-off 22, capital gains 10, the bill 14 (tax by basis, surcharge, rebate, interest and fees, advance tax, credits) |
| Shared producers behind many sites | `RegimeVerdict.Disallowed.whyNot` (`RegimeVerdict.java:62`, reached from 15 sites); cap results (`AmountInExcess:32`, `AggregateWithCeiling:93`, and the other shapes in `rules/cap`); "not met: " + a condition's `describe()` (`RebateNode:94`, `DisabilityDeduction:97`); "not a perquisite: excluded by" + a rule id (4 sites) |

**What a user sees today**, taken from the probe:
- **Internal ids:** "… (calendar months, D-303)", "… D-229 …", "… — W-081b".
- **Codes:** "CLUB, less the recovery 0.00", "disallowed in the NEW_TAX_REGIME regime: …", "LONG_TERM_LISTED_EQUITY; slab".
- **Figures not in Indian notation:** "gross total income 100000.00", "10% of adjusted gross total income 450000.00".
- **Raw formulas:** "(PC 74000.00 ÷ 2 + PC1 + TP1 0.00) × I 0.00 ÷ F(avg) …".

Each site needs its node read to know which facts its reason carries. That is 119 sites, which is too large to review as one item.

**Choices for the owner:**
- **C1: the mechanism.**
  - **C1a (recommended):** `TraceLine` gains an optional structured reason: a reason code plus its typed facts (money, a date, a tax year, a rule, a component, a regime, a count, a share). `limitedBy` stays as it is: it is the audit text published as `ComputedTax.Step.limitedBy` and recorded in the trace snapshots. The content file gains one template per reason code. The renderer prefers the reason and fills its facts by type: money through `Money.inIndianNotation`, codes through a display name. With no reason, it falls back to `limitedBy`, as today. That lets each family move on its own. The compiler refuses a reason code with no template.
  - C1b: replace `limitedBy` with the structured reason, and render the audit text from it too. That changes the published `limitedBy` and both snapshot twins in one step, so nothing can move family by family.
- **C2: display names for codes** (heads, capital-gains parts, charge codes, regimes, components):
  - **C2a (recommended):** reuse a `displayName` where the pack already has one (components, regimes, disallowance sets). Add a content `terms` map for the rest, and have the compiler refuse a code the reasons can name that has no word.
  - C2b: labels in Java. That puts wording in code, against SC-2 and the extendability standard.
- **C3: citations and internal ids in the plain "why":**
  - **C3a (recommended):** the plain sentence states the fact and drops citations and design ids (`D-303`, `W-081b`, section numbers). The citation stays in `limitedBy` and in the line's provenance, both of which are already published with the step.
  - C3b: keep section citations in the sentence, and drop only internal ids.
- **C4: the split.**
  - **C4a (recommended):** five items, each with its own plan, probe, red test, review and commit, in this order:
    - **W-327a, the mechanism and the shared producers:** C1a to C3a; the regime disallowance (15 sites), cap results, "not met", and "excluded by". This one item turns much of the visible text into words, because those producers sit behind many sites.
    - **W-327b, salary:** the remaining salary and employer-contribution sites (about 51 less those W-327a covers).
    - **W-327c, Chapter VIII and other sources:** about 29 sites.
    - **W-327d, house property, set-off and capital gains:** about 32 sites.
    - **W-327e, the bill** (about 14 sites), **then the coverage pin:** a test that fails when an engine site writes `limitedBy` text with no reason. Each sub-item greps for its family's sites that the run did not reach.
  - C4b: one item for all 119 sites.

**Numbers I will use:** none. The figures above are counts from the probe.

**Design sections I read:** `20-product-gaps.md` F37 (lines 289 – 310: "every trace line has a template; templates live in the rule pack … no template ⇒ the rule ID is shown, never a blank"); D-671, D-673 (where W-327 was placed), D-676.

**What I am NOT doing here:** any code, template or wording. This plan places W-327a – e on the board, in order, on approval. `batch-small-items` does not apply, because these are not small.

**Files I will modify on approval:** `03-WORK-ITEMS.md` (five rows), STATE (board, D-row), CHECKPOINT.

**How I will verify:** the board, `FinishedPlanTest` and `ParkedRowsTest`. Each sub-item names its own tests when it is planned.

**Post-deployment actions (R15):** none.

**Roles:**
- **Architect:** the reason becomes a fact the node publishes, and the wording is content (the standard's "facts, not rules"). `limitedBy` keeps its audit role untouched, so no consumer moves before its family does.
- **PM:** the visible change is the end of internal ids and codes in the user's "why". W-327a alone covers the most common texts (the regime disallowance and cap results).
- **Senior engineer:** a new value type on `TraceLine` crosses only `taxengine`. Its id grammar is checked against `rules/id` before W-327a names it.
- **Automation tester:** each sub-item probes its sites and has a red test, and W-327e's pin makes coverage a build check.
- **Manual tester:** a draft under the new regime shows "not allowed under the new tax regime" in words, not `NEW_TAX_REGIME` and a section list.

**Risks:**
- The probe sees only sites the unit tests reach. Each sub-item greps for its family's other `withLimitedBy` calls.
- Five items is a long run. W-327a carries most of the visible gain, so the rest could be reordered behind other board work if you prefer.
