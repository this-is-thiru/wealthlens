## Plan for W-239a — drafts name the landlords and lenders they rely on

**What this item is for (one sentence, in my own words):** a draft records which of the profile's landlords and
lenders it relies on. Retention can then keep a record until two years past the last tax year a draft names it,
instead of W-239's stand-in (the profile's latest draft of any kind).

### What I read (session 78)

- **The row** (`03-WORK-ITEMS.md:1554`), D-505, and `plans/W-239.md` C1c.
- **`DR 15` F3** (`15-review-findings.md:653-680`): the records are *"referenced by id from `DraftInputs`"*.
- **`DraftInputs`** (`taxplanning/workspace/DraftInputs.java:18`) is `(entered, filing, brought)`, and `blank()` is
  at `:20-22`. It is `taxplanning`'s own record, not the engine's.
- **The engine inputs carry no reference.** `Tenancy` is at `taxengine/input/Tenancy.java:18`. The loan records are
  `HousingLoan` (`:24`, inside `HouseProperty.java:42`), `EducationLoanInterest` (`:14`) and `PurposeLoanInterest`.
  `taxengine` is CLOSED and depends only on `shared` (CLAUDE.md module table), and no engine rule reads a
  landlord or lender id.
- **Editing.** A draft changes only through `DraftService.patch` (`DraftService.java:118-138`). It applies a JSON
  Patch to the stored tree and binds it (`requireBinds`, `:128`). `setInputsJson` is called only at `:79` (blank)
  and `:133`. Only `DRAFT` / `READY` drafts are editable (`DraftStatus.java:25-27`). `DraftService` already uses the
  profile package (`TaxProfileService`, `:4`, `:28`).
- **`inputs_json` is encrypted** (`FilingDraft.java:47-48`, `@ValueConverter(EncryptedField.class)`), so a Mongo
  query cannot find the drafts that name an id. They have to be read and parsed.
- **Landlords and lenders can only be created, listed and replaced, never deleted through the API**
  (`TaxProfileReferenceController.java:64-91`). Only retention and erasure remove them.
- **Retention today:** `ThirdPartyRetention` (D-505), which counts from the later of the profile's latest draft and
  the record's last change.
- **Tests:** `DraftIntegrationTest` (18 methods) and `TaxJobsIntegrationTest`. The api-collection has no "patch a
  draft" request (`ls "api-collection/Tax Profile"` shows only Compute / Optimise a Draft for drafts).

### Choices (recommended first)

**C1 — where the reference lives.**
- **(a) Recommended:** add a fourth component to `DraftInputs`, `thirdParties`, holding
  `ThirdParties(List<String> landlordIds, List<String> lenderIds)`: the records this draft relies on. This is what
  F3 says, the engine stays untouched, and it is set by the existing patch:
  `{"op":"add","path":"/thirdParties/landlordIds/-","value":"<id>"}`. A stored draft without the field reads as
  naming nothing, which is true: no draft could name one before this item.
- (b) Add a `landlordId` to `Tenancy` and a `lenderId` to the loans. This puts a `taxplanning` store id into the
  CLOSED engine's vocabulary, where no rule reads it. That is a speculative field, so I rejected it.
- (c) Per-item references keyed by the tenancy's position in the list. These break when the list is reordered.

**C2 — checking a name.** **(a) Recommended:** after a patch binds, every id the patch **newly** names must be a
landlord or lender of the draft's profile. Otherwise the patch is refused with a 400, e.g. *"landlord `<id>` is not
one of this profile's landlords"*. Ids the draft already named are not checked again, so a draft that names a record
retention has since deleted can still be edited elsewhere. The check is a new
`TaxProfileReferenceService.requireHeld(profileId, landlordIds, lenderIds)`, which already owns both repositories.
`DraftService` gains that one dependency.

**C3 — the retention rule from now on.** **(a) Recommended:**
- A record **named** by at least one stored draft: kept to the end of the later of the latest tax year of a draft
  naming it and the tax year of its last change, plus P2Y.
- A record **named by no draft**: kept to the end of the tax year of its last change, plus P2Y. This is O5's "the
  tax year" taken literally, and it removes W-239's stand-in.

There is no deployed database with real users yet (W-239 and this item are "before the one deploy"). Staging
records named by no draft follow the second rule on the first run, and runbook §1.y's count shows that.

**Expected values, by hand.** The clock is 2029-04-01 unless stated.
- **A, named.** A landlord last changed on 01-06-2025 (2025-26) is named by the 2026-27 draft. The profile also has
  a 2028-29 draft that does not name it. The year is max(2026, 2025) = 2026-27, which ends 31-03-2027, plus P2Y =
  31-03-2029. It is **kept** on 31-03-2029 and **deleted** on 01-04-2029. Under W-239 it would have been kept to
  31-03-2031, so this case is the one that tells the old rule from the new.
- **B, unnamed.** A lender last changed on 01-06-2025 is named by no draft, and the profile has a 2028-29 draft.
  2025-26 ends 31-03-2026, plus P2Y = 31-03-2028, so it is **deleted**. W-239 would have kept it.
- **C, named late.** A landlord last changed on 01-07-2024 is named by the 2028-29 draft. That gives 31-03-2031, so
  it is **kept**.
- **The W-239 tests that change:**
  - `…whenTheProfileHasALaterDraftThanTheRecordsLastChange_keeps…` becomes case C, kept only because the draft
    names it.
  - The boundary test names the landlord from `draft-2026` so its 31-03-2029 boundary holds.
  - The no-date and lost-lease tests are unchanged.
- **Patch checks:**

  2. Naming another profile's landlord gives 400, and the revision does not move.
  3. Naming an unknown lender id gives 400.
  4. A draft already naming an id that no longer exists, patched at another path, gives 200.
  5. A stored draft whose JSON has no `thirdParties` binds as naming nothing.

### Five roles

- **Architect:** `taxengine` is untouched. `workspace` → `profile` is already a dependency (`DraftService.java:4`)
  inside one module. The reference is a stored fact ("this draft relies on X"), and the period stays configuration.
  The seams are `DraftService.patch` and `ThirdPartyRetention`.
- **Product manager:** a client can now say which landlords and lenders a draft relies on, and a wrong id is
  refused with a readable message. An old client that never sends the field is unaffected. A record nobody names
  now goes two years after its own year rather than living as long as the profile drafts, as O5 intends.
- **Senior engineer:** no field without a reader, since retention reads `thirdParties`. One word for the concept
  ("third party", as in D-505). `DraftService` stays within the field and method limits.
- **Automation tester:** the hand figures A – C, patch checks 1 – 5, and both probes. I will grep the tests for
  `new DraftInputs(` and `DraftInputs.blank` so every constructor call is updated.
- **Manual tester:** create a landlord, add it with the patch above, and `GET` the draft to see the id. Patch in
  another profile's landlord id and expect a 400. Edge cases: an id named twice in one patch (stored as given, and
  the check passes once), an empty list, and a frozen (`ACTED_ON`) draft, which is already refused with a 409.

**Risks or ambiguities I noticed:**
- Under C3a an `ACTED_ON` draft can outlive a record it names (8 years against 2), leaving an id that no longer
  resolves. That is O5's design ("the tax year plus 2 years"), and C2a never re-checks an old name.
- Retention now parses every draft of a profile that holds third parties, once a month. That is the same order of
  work as the staleness sweep.
