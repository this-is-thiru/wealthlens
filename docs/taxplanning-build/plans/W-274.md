## Plan for W-274 — fractional quantities are compared exactly

**What this item is for (one sentence, in my own words):** a holding of fractional units can be sold in full and
leaves nothing behind, because quantities are compared within the tolerance the code already defines rather than
exactly (G-2, G-5, PS-4, PS-11).

**Findings (each read this session, 2026-11-11):**

1. **The tolerance exists:** `DoubleUtil.equal(a, b)` — `|a − b| < 1e-9` (`shared/util/math/DoubleUtil.java`). V2's
   delete of an emptied lot already uses it (`PortfolioService.java:460`).
2. **Exact comparisons on the sell path:** `validateTransaction` refuses when `existingQuantity < requested`
   (`:498`); both allocation loops run `while (sellQuantity > 0)` (`:622` V1, `:674` V2) and take a whole lot only
   when `sellQuantity >= assetQuantity` (`:641`, `:679`); V1 deletes emptied lots on `== 0` (`:483`).
3. **What that does** (W-264a, both runs): units 0.1 + 0.7 sum to 0.7999999999999999, so a sale of 0.8 is refused —
   both flows (scenario 6); V1 selling 0.3 of 0.1 + 0.2 leaves 0.19999999999999998 against the 0.2 lot, takes the
   partial branch and stores a lot of 2.7755575615628914E-17 that is never deleted and shows as held (scenario 10).
   The loops have no `hasNext()`; only the exact validation keeps them from running off the end (PS-4).
4. **PS-11:** the holdings price is `totalValue / totalQuantity` (`:597`), unguarded; a group of only zero-quantity
   lots would give `NaN`. Such lots exist only as residue like scenario 10's.
5. **Stored residue:** V1 sales before this fix may have left near-zero lots in `assets`; how many is not known.

**Choices for the owner:**

- **C1 — the comparison.**
  - **C1a (recommended):** use `DoubleUtil.equal` at all four points: refuse a sale only when it exceeds the holding
    by more than the tolerance; a lot within the tolerance of the remaining sale is taken whole (set to exactly 0);
    the loop stops when what remains is within the tolerance of 0; V1 deletes emptied lots as V2 does. The loops keep
    `next()` unguarded on purpose — after this validation, running off the end is a defect that should fail loudly,
    not a sale silently left part-allocated.
- **C2 — PS-11's divide.**
  - **C2a (recommended):** the holdings views leave out lots with nothing left (within the tolerance), as the
    capital-gains held view already does (W-262), so no group divides by zero.
  - C2b: leave it; C1a stops new residue.
- **C3 — residue already stored.**
  - **C3a (recommended):** runbook 3.13, read-only: count `assets` lots with `0 < quantity < 1e-9`; a correction is
    its own row.
  - C3b: no check.

**Files I will modify:** `PortfolioService` (validation, both loops, V1's delete, the views' filter for C2a); tests —
W-264a scenarios 6 (V2 0.1 + 0.7, sell 0.8) and 10 (V1 0.1 + 0.2, sell 0.3) as the first tests, V1 twin of 6, a sale
over the holding by more than the tolerance (0.8 of 0.7 held) still refused, the views leaving out a stored residue
lot; `post-deployment-runbook.md` 3.13 (C3a), so WL-A-2 is republished.

**Numbers I will use:** the existing tolerance, 1e-9 (`DoubleUtil.EPSILON`); fund units are entered to at most a few
decimal places, so a real difference is never that small.

**What I am NOT doing:** moving quantities to `BigDecimal` (B-3, decided against, `money-representation-analysis.md`);
correcting stored residue.

**How I will verify:** first tests red then green; probe: validation back to exact → scenario 6 fails; the affected
classes; `./mvnw validate`.

**Post-deployment actions (R15):** runbook 3.13, read-only, owner, any time; safe to repeat; nothing to undo:
`db.assets.countDocuments({ quantity: { $gt: 0, $lt: 1e-9 } })`.

**Five roles:**
- **Architect:** one tolerance, already defined, used everywhere a quantity is compared on the sell path.
- **Product manager:** a fund holding sells in full; nothing invisible is left behind.
- **Senior engineer:** the whole-lot branch absorbs the float residue, so a lot ends at exactly 0.
- **Automation tester:** scenarios 6 and 10 in both flows, the still-refused over-sale, a probe.
- **Manual tester:** buy 0.1 and 0.7 units, sell 0.8: accepted, nothing held.

**Risks or ambiguities:** a sale exceeding the holding by under 1e-9 units is accepted and allocates the whole
holding — far below any unit a fund issues.
