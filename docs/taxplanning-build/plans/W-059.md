## Plan for W-059 — the component registry on the timeline (Phase 7 opens)

**What this item is for (one sentence):** pay components become pack data that a year's rule pack
carries, so Phase 7's nodes can partition and sum a declared set rather than whatever codes arrive
(`D-CLOSEDSUM`).

**This plan raises an ordering problem that needs your decision (C1) before anything is built.**

### What I read

- **The `W-059` row:** *"`components.json` for both years — `DR 10` E4, `DR 15` F-part — every code
  has `cashNature`"*. There's no erratum. Appendix D's audit stops at `W-058`, so no Phase 7 row has been
  checked against the code.
- **`DR 10` E4** (`10-extensibility.md:224-300`): a registry, not an enum. `ComponentDefinition(code,
  displayName, head, kind, cashNature, treatment, feedsInto, salaryBaseFor, …)`. Reachability extends I3:
  *"every `ComponentCode` must be `feedsInto` at least one rule, or be explicitly marked
  `informationalOnly`"*.
- **`DR 05` M2** (`05-domain-model.md:269-330`): the *"initial contents of components.json"*, 44 codes
  across every head — cash salary, perquisites, employer and employee contributions, professional tax,
  retirement receipts, house property, other sources, capital gains.

- **Code already built (Phase 2/3):**
  - `rules/component/ComponentDefinition` — its constructor **refuses** a component with empty

  - `CashNature` {CASH, NON_CASH, CASH_OUTFLOW}, `ComponentKind`, `TaxTreatment`, `ComponentLifecycle`,

  - `RegistryJson.components` reads `exec/components.json` (`cashNature` is required, so "every code has
    `cashNature`" is already enforced at load);
  - `PackValidator` requires every `feedsInto` / `salaryBaseFor` rule to **exist in the pack**;
  - `ComponentCodes` is generated and empty.
- **The gap:** `RulePackCompiler` writes `exec/components.json` as an **always-empty** array, and
  `TimelineReader` has no components directory. Its Javadoc: *"Directories are added with their first
  content and its reader (D-053) — `exec/components` … have none yet"*.
- **What components would feed:** rulebook R7/R8 — `SAL-DEF-001` (what "salary" includes, s.17(1)),
  `SAL-DEF-HRA-001` / `-GRAT-` / `-NPS-` (the salary bases), `SAL-STDDED-001/002`, `SAL-PTAX-001`. **None
  is in the pack.** They're `W-064` (salary.json rows) and `W-062` (`SalaryBaseNode`), both later than this
  item.

### Findings

1. **A component can't truthfully exist before the rule it feeds.** The constructor and `PackValidator`
   together mean every component must name an existing rule in `feedsInto`, or claim it feeds none
   (`informationalOnly`). With no salary rule in the pack, authoring BASIC now means either naming a rule
   that doesn't exist (refused at load) or claiming BASIC feeds nothing (false). This is `D-084`'s problem
   (data before its consumer) in a stricter form: here the domain type itself refuses it, not a test.
2. **`SAL-DEF-001` has no shape yet.** It's an inclusion list ("salary includes wages; annuity …"), and a
   `RuleVersion` must carry a cap, a relief, a rounding or conditions (`W-049a` A3). How a definition
   becomes a row is `W-064`'s question, not one to settle here.
3. **The plumbing is missing, and it doesn't depend on content:** a timeline directory, the reader, the
   compiler emitting a year's live components (`ComponentLifecycle.isLiveIn`), the lock covering them, and
   `ComponentCodes` regenerating. It can be proven on a fixture timeline, as `rulepacks-fixture/` already
   proves rules.
4. **The row's scope is every head.** `DR 05`'s list spans five heads. Phase 7 is the salary head;
   perquisites and contributions are Phase 8, other sources `W-079`, capital gains `W-088`.
5. **Standing rules (D-043):** no section is modelled here, so there's no coverage or catalogue change.
   Both years, and concept IDs, apply to whichever item authors content (C1).

### Choices (recommended first)

- **C1 — the ordering (finding 1).**
  - **(a) recommended: W-059 builds the plumbing; each component arrives with the first rule that reads
    it.**
    - W-059: `exec/components/<CODE>.json`, one file per component like `law/rules/`; `TimelineReader`
      reads it; `RulePackCompiler` emits the components live in the year; the lock and `ComponentCodes`
      follow. It's proven on a fixture timeline with two or three components, and ships **no** content.
    - An erratum on the Phase 7/8 rows: each item that authors a rule consuming a component also authors
      that component, for both years, with `cashNature` sourced. So `W-064` brings BASIC, DA and the other
      cash-salary components with `SAL-DEF-001` / `SAL-STDDED-*`, and `W-063` brings PROFESSIONAL_TAX with
      `SAL-PTAX-001`. No component ever exists without its consumer, and the invariant stays whole.
  - **(b)** Author the salary components now as `informationalOnly: true`, flipping each as its rule
    arrives. It's quicker, but every row would state something false for several items. That needs an
    explicit exception from you, like D-084's, and "informationalOnly" would then mean two things.
  - **(c)** Move `W-064` (the salary rule rows) ahead of W-059. That pulls finding 2, how a definition
    becomes a row, forward into an item that isn't about it.
- **C2 — scope (finding 4), under (a):** plumbing only, so scope is moot here. Each head's components land
  with that head's items; the erratum names them. Under (b) or (c), the salary head only: the 12 cash-salary
  codes and PROFESSIONAL_TAX from `DR 05` M2.
- **C3 — "`DR 15` F-part":** an erratum that the reference is unresolved. `DR 10` E4 and `DR 05` M2 are the
  specs actually used.
