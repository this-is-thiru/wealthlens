## Plan for W-240 — branch coverage of the tax engine to X5.5's figures

**What this item is for (one sentence, in my own words):** raise `taxengine`'s branch coverage to 90 % and
`taxengine.rules`' to 85 % (`DR 07` X5.5), with tests whose expectations are worked by hand, and raise the JaCoCo
minimums to match.

**This item is mis-sized (§7).** This plan asks only for the split. No test is written under W-240 itself.

### What I measured (session 78, `backend/target/site/jacoco/jacoco.csv` from W-239a's full verify)

| Scope | Missed / total branches | Covered | X5.5 | Most that may be missed | Must cover |
|---|---|---|---|---|---|
| `taxengine` outside `rules` | 550 / 3,220 | 82.92 % | 90 % | 322 | **≥ 228** |
| `taxengine.rules` | 580 / 2,526 | 77.04 % | 85 % | 378 | **≥ 202** |

How the "Most that may be missed" column was worked: 3,220 × 0.10 = 322 and 2,526 × 0.15 = 378.9, so the
whole-branch limits are 322 and 378. The figures have moved since W-144 measured 533 / 2,890 and 560 / 2,425
(`03-WORK-ITEMS.md:1555`), because the engine has grown.

Where the misses are:
- **Outside `rules`:**
  - `input`: 310 of 909 missed. Of these, the `Employer*` classes miss 103 across 14 classes, and the other 51
    classes miss 207.
  - `node` 111, `pipeline` 59, `election` 32, `optimise` 17.
- **Inside `rules`:** `definition` 108 (45 classes), `json` 96, `condition` 58 (`Condition` alone 27), `regime` 50
  (`RegimeSpec` 17), `pack` 42, `timeline` 41.

The gates are `check-taxengine` and `check-taxengine-rules` (`pom.xml:295-345`). Their branch minimums are 0.81
and 0.76, set by D-461 as a ratchet.

**Size.** Roughly 430 branches over more than 100 classes. Most are refusals in records' compact constructors, so
each is a test case with a hand-worked message. Even with parameterised tests that is several times §7's 300
lines, and more than one session.

### Choices (recommended first)

**C1 — the split.**
- **(a) Recommended:** four items in Phase 14 after W-240, each closing a measured slice. Each item raises its
  gate's branch minimum to the floor of what it measured (the D-461 ratchet), so the coverage gained can never be
  lost again.

  | Item | Slice | Missed now | Target | Gate after |
  |---|---|---|---|---|
  | **W-240a** | `input`, the 14 `Employer*` classes | 103 | ≥ 90 covered | `check-taxengine` branch to its new floor |
  | **W-240b** | the other `input` classes, until `taxengine` outside `rules` reaches **90 %** | 207 | ≥ 228 − W-240a's | **0.90**, X5.5 met |
  | **W-240c** | `rules.condition` + `rules.regime` | 108 | ≥ 95 covered | `check-taxengine-rules` branch to its new floor |
  | **W-240d** | `rules.definition`, then `rules.json` if needed, until `rules` reaches **85 %** | 108 (+96) | ≥ 202 − W-240c's | **0.85**, X5.5 met |

  W-240 is marked `—` (split), as earlier splits were.
- (b) Split by package instead, one item per package. That makes 10 or more items, several of them under 40
  branches.
- (c) Keep the ratchet as it is and close the gap opportunistically. That leaves X5.5 unmet before the deploy the
  row names.

**C2 — unreachable branches.** **(a) Recommended:** when a missed branch cannot be reached by any input, the slice
removes that branch rather than testing around it (CLAUDE.md §2, no dead weight), with a `path:line` and the
reason. It counts toward the slice's target only by shrinking the total. (b) Leave it, and raise the coverage by
covering other branches.

### Five roles

- **Architect:** no production change, except a branch C2a proves unreachable. The gates stay scoped as D-461 set
  them.
- **Product manager:** nothing changes for users. The deploy is safer, because the refusals of malformed input are
  proven.
- **Senior engineer:** parameterised refusal tests keep each slice within §7. Test names follow
  `method_whenCondition_expected`.
- **Automation tester:** every refusal's expected message is read from the record's contract, never copied from
  a run. Every slice ends with the ratchet raised and a failing-minimum probe.
- **Manual tester:** nothing to run by hand. The JaCoCo HTML report (`backend/target/site/jacoco/index.html`)
  shows each package's figure.

**Risks or ambiguities I noticed:** the totals move whenever the engine grows. Each slice re-measures before it
plans, and its target is stated against that fresh measure, not against this table.
