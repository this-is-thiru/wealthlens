### The problem the plan has to solve

A row's conditions are ANDed and tested against one `ConditionContext`. If the senior row gains an `ItemFactIs`,
`isSenior` must not test it: tested with no item, it throws ("The item carries no fact …",
`ItemFacts.code`). Testing the senior row per item instead would hide the time-deposit nil line for a non-senior.
For a non-senior no row would reach the item, so it would no longer count as deposit interest at all, and T6-6's
second line would vanish.

### Choices (recommended first)

- **C1 — testing person and item apart:**
  - **(a) recommended:** a `Condition` says whether it reads the item, through `isAboutItem()`:
    - one `default` method on the sealed interface, as an exhaustive pattern `switch` over the permits: the three
      `Item…` predicates are true, `AllOf` / `AnyOf` / `Not` are true when any limb is, and the rest are false;
    - `DepositInterestDeduction` tests the senior row's other conditions for the person (`isSenior`), as today;
    - each row's item conditions are tested per item, with `ctx.conditions().about(facts)`.

    A row's conditions keep their single list. A limb mixing person and item facts counts as about the item and is
    tested with both, which is safe, because the context then carries both.
  - **(b)** a positional convention: "the senior row's last condition is its item limb". No algebra change, but
    nothing enforces it.
  - **(c)** test whole rows per item. The time-deposit nil line would disappear for non-seniors, which breaks D-318
    C3a (trace lines unchanged).
- **C2 — which items are "deposit interest" (the nil line's population and `entered`):**
  - **(a) recommended:** an item either row's item conditions reach. Today that is savings and deposit interest, the
    same two kinds, so `entered` and every line are unchanged.
  - **(b)** only the senior row's reach, because s.153(2)(b) is "any account". That holds today, but it ties the
    savings row to the senior row's list.
