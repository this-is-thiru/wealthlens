## Plan for W-238d — basic pay movable, the provident fund following it

**For:** a user whose employer pays into a recognised provident fund. Moving basic moves that contribution with it
(A2.2 C8), and the optimiser must price the two together. Row `03-WORK-ITEMS.md` W-238d (D-489 finding). Parent
W-238 (closed, D-490).

### What I read (session 66)

- **Basic is not refused today.** `AllocationSpace` refuses the RPF as a movable fund (`api/AllocationSpace.java:36-39`)
  but nothing refuses `BASIC` in `movable`. Named, basic moves alone: the RPF contribution and `EMPLOYEE_PF` stay as
  entered, which breaks C8 silently. W-238a's "basic is not movable" (`plans/W-238.md:64`) is a note, not a check.
- **What already follows basic.** `BASIC.json` is in seven salary bases (`SAL-SALARY-FOR-HRA`, `-GRATUITY`,
  `-EMPLOYER-PENSION`, `-EMPLOYEE-PENSION`, `-ENTMT`, `-ACCOM`, `-RPF`). The pipeline re-reads them on every priced
  allocation, so HRA and the NPS sub-cap need no code. Only the two contributions do.
- **What does not.** The RPF contribution is an `EmployerFundContribution` (`input/EmployerFundContribution.java`).
  `EMPLOYEE_PF` is a component, `CASH_OUTFLOW`, feeding `DED-SCHEDULE-XV` (`exec/components/EMPLOYEE_PF.json`).
- **The design's rule.** C8: `x_PF_EMPLOYER = 12% × x_BASIC` "in the usual case", sourced to the EPF scheme, outside
  the tax rulebook (`03-advisory.md:166`). The pack holds no EPF rate. I have not read the EPF scheme, so I cite no
  rate, ceiling or paragraph here.
- **The search.** `Allocation.moved` takes the whole difference from the residual (`optimise/Allocation.java:33-38`).
  `Saturation.of` bounds a move at `amount + residual` (`optimise/Saturation.java:26`). Both assume one item moves.
  `Money.scaledBy(Money, Money)` exists (`rules/money/Money.java:116`).

### Choices (recommended first)

**C1: how much follows.**
- **(a) Recommended: the user's own ratio.** Each follower moves in proportion to basic, at the ratio entered:
  `suggested = entered × suggestedBasic ÷ enteredBasic` (`Money.scaledBy`). The rate comes from the user's facts, so
  there is no law in Java or the pack (CLAUDE.md §4). The limitation: an employer that pays on a capped wage, whose
  contribution does not move with basic, is described wrongly. I propose a row for it (below).
- (b) The EPF rate and wage ceiling as versioned rule data. That needs Gazette sourcing of the EPF scheme first, so
  it would be its own item.

**C2: what follows.**
- **(a) Recommended: the employer's RPF contribution and `EMPLOYEE_PF`,** where entered for the residual's
  employment. The employee's share is withheld from the same basic and lowers take-home (C3). If it stayed put, the
  answer would overstate cash in hand.
- (b) The employer's RPF only, as the row is worded. The employee's share would then be a new finding.

**C3: refusals.** **(a) Recommended:**
- `BASIC` movable with a follower entered but basic nil: no ratio.
- `BASIC` movable where the employment has dearness allowance that counts for retirement. Whether PF follows DA too
  is not in the facts, so the item refuses rather than guesses. A row is proposed.
- The RPF named in `movableFunds`: the message changes to "name `BASIC` movable; the contribution follows it".
- A follower entered twice for the employment.
- (b) No DA refusal: follow over basic + DA. That guesses an employer's terms.

**C4: how a follower is published.**
- **(a) Recommended: a new list, `Optimisation.followingChanges`,** of `FollowingChange(name, current, suggested,
  follows)`. Basic's own `Change` carries the move whole. Its `savingAlone` is priced with the followers applied, and
  its `cashImpact` counts the residual's Δ × (1 + ratio) and the larger employee withholding. `Change` and
  `FundChange` are unchanged, so old readers see the same fields.
- (b) Put followers into `changes` and `fundChanges` with an empty `savingAlone`. That reads as a move a user could
  make alone, which they cannot.

### Shape (names checked at build)

- `Allocation.moved` applies basic's followers by their ratios. The residual funds basic plus the employer's share;
  the employee share is not CTC, so it is not taken from the residual.
- `Saturation` bounds basic at the residual's zero, which is `residual ÷ (1 + employer ratio)`, not `amount + residual`.
- The ratios are read once in `AllocationPricing.over`. Each method ≤ 60 lines, ≤ 7 parameters.

### Hand figures (TY 2026-27, new regime; slabs as `plans/W-238c.md` cases 1 – 2)

   0.12), `BASIC` movable, floor nil.
