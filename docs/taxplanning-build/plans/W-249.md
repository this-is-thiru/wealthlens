## Plan for W-249 — erasure once the purpose is no longer served

**For:** an account is erased when its purpose has lapsed, not only when its owner asks. Act s.8(7)(a) asks erasure
"on withdrawal of consent *or* once the specified purpose is no longer served, whichever is earlier"
(`sources/2026-11-07-data-protection.md` row 6). W-237d erases on request only (D-474, C6a).

### What I read (session 58)

- **The row** (`03-WORK-ITEMS.md:1527`): needs the owner's rule for when an account's purpose lapses; once given it is
  data and reuses W-237d's hold and `account-erasure` job.
- **The law gives WealthLens no period.** Rules r.8(1) – (2) set a lapse period and 48 hours' notice only for the Third
  Schedule's classes (e-commerce, online gaming, social media at stated user counts); WealthLens is in none (row 11).
  r.8(3) sets a *minimum* of one year from the last processing (row 12). So any period is the owner's ruling, not law.
- **What the app can observe today:** nothing records a sign-in. `UserDetail` holds only email, password, roles
  (`auth/entity/UserDetail.java:12-17`). `privacy_processing_log` records every request with `principal` and
  `recorded_at` (`shared/privacy/ProcessingRecord.java:29-53`), but `LogRetention` erases it after
  `app.privacy.log-retention` = P1Y (`LogRetention.java`, `application.yaml:57`), so it cannot show inactivity longer
  than a year. No email channel exists (no `JavaMailSender` in `backend/`), so no warning can be sent before erasure.
- **What W-237d gives:** `AccountErasureService.request/due/erase/reapply`; every `PersonalDataHolder`; the hold refuses
  login, token and re-registration (D-474); `reapply` re-erases any request with `erased_at` after a restore (W-237f).

### Choices (recommended first)

**C1 — when an account's purpose lapses. Your ruling; I cannot source a number.**
- **(a) Recommended: after a period with no sign-in, which you give** (e.g. `P2Y`, `P3Y` — your number, recorded as your
  ruling in D-480 and the yaml comment, never as law). Stored as `app.privacy.purpose-lapse`; startup refuses a period
  shorter than `erasure-hold` (r.8(3)'s year from the last processing). Published in the privacy notice, so a user knows.
- (b) **No lapse rule:** the notice states the purpose as "tracking your portfolio while you keep the account", so it lapses
  only when you ask erasure, which W-237d already does. W-249 closes as a decision, no code. Weaker: an abandoned account
  is kept forever, and "whichever is earlier" reads as if lapse can come before a request.

**C2 — what counts as activity (if C1a).**
- **(a) Recommended: a successful sign-in.** `auth` stores the fact `last_signed_in_at` on `user_details` at login and at
  registration. An account registered before W-249 has none; the job fills an absent value with its own run time (a
  `$set` only where absent, so a second run changes nothing) — every existing account gets a full period from deploy,
  and no one-time runbook command or removal ticket is needed. The field's Javadoc says so: for those accounts it is
  "first counted", not a real sign-in.
- (b) Any request in the processing log. Not possible past a year: the log is erased at P1Y.

**C3 — what happens at lapse.**
- **(a) Recommended: erase directly, recorded as an erasure.** The `account-erasure` job, before its due requests, finds
  accounts with `last_signed_in_at + purpose-lapse ≤ now`, records an `AccountErasureRequest` with a new fact
  `cause` = `PURPOSE_LAPSED` (existing rows read as `REQUESTED`), `requested_at` = the lapse moment, and erases at once
  through the same holders. No hold: r.8(3)'s year from the last processing has already passed (C1a refuses less). The
  row is the proof of erasure, `reapply` covers it after a restore, and `LogRetention` removes it a year later, as today.
- (b) Lapse opens a normal request and the one-year hold follows. Not recommended: a returning user is locked out for a
  year (the hold refuses login), and erasure lands a year later than the rule says.

### Build (if C1a – C3a)
1. `PrivacySettings` gains `purposeLapse` (refused if ≤ `erasureHold`); `PrivacyNotice` carries it; three yamls with your
   period and its D-480 comment; test yaml.
2. `auth`: `UserDetail.lastSignedInAt` (`@Field("last_signed_in_at")`), set by `AuthService.addUser` and on login
   (`generateToken`); `RegisteredUsers` gains `lapsedBefore(cutoff)` and `countFrom(nowUtc)` (fill where absent),
   implemented in `RegisteredUserDirectory`.
3. `AccountErasureRequest.cause` (`ErasureCause` enum: `REQUESTED`, `PURPOSE_LAPSED`; absent reads `REQUESTED`);
   `AccountErasureService.eraseLapsed(nowUtc)`; `AccountErasure.run` calls it first, checking the lease per account.
4. Runbook entry (no command: the job fills the field; a read-only check before and after); WL-A-2 republished.

### Tests (dates by hand)
- `purpose-lapse` P2Y in the test yaml (a test value). Signed in 2027-06-10T08:00Z → at 2029-06-10T07:59Z nothing
  erased; at 08:00Z every holder holds nothing for the person, another user untouched, a request row with
  `cause PURPOSE_LAPSED`, `requested_at` = `erased_at` = 2029-06-10T08:00Z. A second run changes nothing.
- A sign-in at 2028-01-01 moves the lapse to 2030-01-01. An account without the field: first run sets it to the run time,
  erases nothing; a second run leaves it unchanged.
- Startup refuses `purpose-lapse` P6M (< P1Y) and P1Y (equal). The notice shows the period. `reapply` after a snapshot
  older than a lapse erasure re-erases it.
- **Probes:** skip the login update → the moved-lapse test fails; drop the absent-only filter → the second-run test fails;
  relax the startup check → its test fails. Restore by `cmp`.

### Out of scope
A warning before erasure (no email channel exists; r.8(2)'s 48 hours does not bind WealthLens) — placed as a row if you
want one. Encrypting `last_signed_in_at` (W-253 covers identifiers; a time is not one).

### Review lenses

  The period is data, the cause is a fact (CLAUDE.md §4).
- **PM:** the notice tells users the rule; nothing changes for active users.
- **Senior engineer:** idempotent fill and erase; lease checked per account; one more `user_details` write per login.
- **Automation tester:** the dated cases and probes above, integration tier against Mongo.
- **Manual tester (staging):** set `purpose-lapse` per the runbook check, sign in, read `last_signed_in_at`; read

### Post-deployment (R15)
Nothing to run: the first `account-erasure` run fills `last_signed_in_at`. Read-only check before (count of
`user_details` without it = all) and after the first run (0). **Nothing is erased for at least the lapse period after
deploy.** Second run safe. Way back: drop the field (`$unset`), no data lost.

### Risks
- Whether a job's processing (AMC billing, corporate actions) after the last sign-in restarts r.8(3)'s year. I take the
  user's sign-in as the last processing that serves the purpose; your call.
- The notice must carry the rule before the first lapse can fall — guaranteed, since the earliest lapse is a full period
  after deploy.
