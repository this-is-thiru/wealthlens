## Plan for W-131d1 — the document flow: upload, parse view, confirm, behind a switch

> **Approved as recommended — C1a – C6a** (owner, session 104, 2026-11-17). Built; review: "commit and push" (D-766). Every path:line below was read this session at `5d3a9af6` + D-765.
> **Probe in the build's first step:** a multipart upload through the integration test's RestAssured against the switch, and
> the relock with `EMPLOYEE_PAN`. A shape that does not hold is an R13 stop.

**What this item is for (one sentence, in my own words):** give a person three endpoints:
- upload a certificate for one of their profiles;
- see what was read from it;
- confirm it.

All three are behind `app.tax.documents.enabled` (off in every profile yaml). A certificate whose PAN is not the profile's
is refused at confirmation, and the notice names what is stored.

### What D-765 decided, and what the code offers

  `StoredConfirmation`, `ParseDocuments` and `TaxJobRunner`.

### Choices for the owner (recommended first)

- **C1 — the endpoints** (T8, under `/tax/user/{email}`):
  - **(a)**
    - **`POST /documents`**, multipart: `file`, `profileId`, `taxYear` (start year), `documentType`. Returns the
      document: id, type, year, pages, upload time.
      - The same bytes again under the profile return the stored document (M7), marked as not new.
      - Refused (400): a form no parser reads, a year with no layout for it, or a file outside W-131b's limits.
    - **`GET /documents/{documentId}/parse`** returns:
      - `WAITING` before an attempt exists; otherwise the latest attempt, with its outcome, each field (path, text read,
        value as text, confidence, page), the unread text and the notes;
      - the employee PAN's state: `MATCHES`, `DIFFERS` or `NOT_READ`, without printing either PAN;
      - whether it is confirmed.
    - **`POST /documents/{documentId}/confirm`**, `{attemptId, accepted: [paths], corrected: {path: text}, rejected: [paths]}`.
    - A document of another account, or of a held profile, is "This account holds no such document", the same in every
      case.
  - (b) Paths under `/profiles/{profileId}/documents` (T8 names `/documents`).
- **C2 — corrected values:**
  - **(a)** Text, read by the field's kind in the layout:
    - AMOUNT as rupees (`950000`, `950000.50`);
    - YES_NO as `yes` / `no`;
    - PERIOD as `2026-04-01/2027-03-31`;
    - TEXT as given.

    Text that does not read is a 400 naming the row.
  - (b) Typed JSON per kind.
- **C3 — what a confirmation must be:**
  - **(a)**
    - for the document's latest attempt, not a FAILED one, and not already confirmed;
    - every path one the layout declares; an accepted path one that was read with a value;
    - the PAN (corrected, else read) present and equal to the profile's (B9-73).

    Each refusal is a 400 in words. `confirmedBy` is the path's email.
  - (b) Any attempt, re-confirmable.
- **C4 — parsing after an upload:**
  - **(a)** Where `app.tax.jobs.enabled` is true, a background thread runs `ParseDocuments` through the runner once the
    upload is stored; the minute's schedule covers a skipped run (W-131c).
  - (b) Parse inside the upload request, which needs no job but holds the request for up to PT30S.
- **C5 — recorded reads:**
  - **(a)** `ReadSubject.DOCUMENT`, recorded on each parse view, and `ProfileRemoval` also deletes the records naming
    the profile's documents.
  - (b) Not recorded.
- **C6 — the notice:**
  - **(a)** The `tax-planning` description ends "…, your requests to erase a profile, and the salary certificates you
    upload (Form No. 130), what was read from them and what you confirmed". This goes in the three yamls and the
    integration-test yaml, so their notice stays one.
  - (b) Other wording; give it.
