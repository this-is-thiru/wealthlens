## Plan for W-328 — the processing-log tests wait for the record

**What this item is for (one sentence, in my own words):** the processing-log tests stop reading the log once,
straight after the response, and instead wait for the record the filter writes after the response, so they stop
failing at random.

**Probe (two runs, each reverted, `cmp` clean; 2026-11-14):**
- **Reproduced.** `login_whenThePasswordIsWrong_recordsTheAttemptWithTheRefusal` was repeated 200 times in one JVM.
  Repetitions 1 – 28 passed and 29 – 200 all failed with `Expected size: 1 but was: 0`, and no server error was
  logged. My reading: once the JVM is warm, the client gets the 401 and reads Mongo before the insert lands. A busy CI
  run gets there sooner, which fits run 43606808789.
- **The cause, confirmed.** The same 200, polling for the record for up to 2 s instead of reading once: 200 / 200
  passed. The record landed between 0.8 ms and 31 ms after the response (median 3.6 ms).
- **The design stays.** `ProcessingLogFilter` inserts after `filterChain.doFilter` on purpose (W-237e: a failed write
  cannot change what the person was told). The fix belongs in the tests.
- **Every read that follows a request** in `ProcessingLogIntegrationTest`: the `records()` checks at `:118`, `:146`,
  `:158`, `:173` and `:250`; the stored document at `:135`; and "records nothing" at `:186`, which can pass falsely
  before a late write. The erasure-run reads (`:199`, `:216`) follow no request, so they are unaffected. No other
  test reads `ProcessingRecord` (grep).
- **Awaitility** 4.3.0 is managed by the Spring Boot 4.1.0 BOM (`spring-boot-dependencies`, `awaitility.version`), and
  it is already in the local Maven repository.

**Choices for the owner:**
- **C1: how the tests wait.**
  - **C1a (recommended):** Awaitility, test scope, with its version from the Boot BOM (no version in our pom). It
    polls up to 5 s for a record, and gives a clear timeout message.
  - C1b: a small hand-written poll in the test class. No dependency, but it is ours to keep right (interval,
    deadline, message).
- **C2: "records nothing" (`:186`).**
  - **C2a (recommended):** check that the log stays empty for 500 ms (Awaitility `during`). The slowest write
    seen was 31 ms.
  - C2b: make a named request after the anonymous one, wait for its record, and then check that it is the only one.
    No fixed wait, but the two writes are not ordered, so it can still pass falsely.

**Files I will modify:**
- `backend/pom.xml` (test dependency `org.awaitility:awaitility`, no version).
- `ProcessingLogIntegrationTest` (the 7 reads above wait; one helper for the wait).
- **Docs:** STATE (board, D-row), CHECKPOINT.

**Numbers I will use:** the 5 s ceiling and the 500 ms "stays empty" window are mine, chosen well above the 31 ms
measured. They are test timings, not law.

**What I am NOT doing:** changing `ProcessingLogFilter` or the order it writes in; other integration tests.

**How I will verify:**
- `ProcessingLogIntegrationTest` (10 tests), then once with `login_whenThePasswordIsWrong…` repeated 200 times in a
  probe that is reverted: 200 / 200, where it was 28 / 200 before.
- `./mvnw validate`. Full tiers on the pipeline.
- **Red check:** take the wait out of `:158` again under the 200-repetition probe, and it fails as before.

**Post-deployment actions (R15):** none.

**Roles:**
- **Architect:** the filter's write-after-response is a decided design; the tests now respect it.
- **PM:** a red pipeline no longer stops item work for a test that is not broken.
- **Senior engineer:** one test dependency, one helper, seven reads.
- **Automation tester:** the 200-repetition probe gives a before-and-after, and the red check shows the wait is what
  makes it pass.
- **Manual tester:** none; there is nothing to see in the product.

**Risks:**
- The 500 ms window adds about half a second to one test.
- A real failure to write would now take up to 5 s to show, then fail with the same message.
