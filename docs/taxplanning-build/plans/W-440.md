### 2. Choices for the owner

- **C1 — the parts, in order.** **C1a (recommended):** W-440a the duplicate fixed on today's upload (no samples needed);
  W-440b the instrument registry, keyed by ISIN (W-383 (1)); W-440c one parser per broker export, from the samples; W-440d each
  imported trade through V2. W-355 and W-356 then build on W-440b. **C1b:** parsers first, registry later (identity by the
  broker's symbol until then — renames keep hiding matches).
- **C2 — W-440a's key.** **C2a (recommended):** a row's key from what the trade *is* — user, broker, account holder, asset type,
  stock code, side, date, quantity and price, written canonically (no `double` formatting) — plus its occurrence among rows of
  the same file equal in all of those, so two identical rows in one file are both kept (W-275's scenario 15 still holds) and any
  later file carrying them records nothing again. **Risk, stated:** rows recorded before the change carry the old key, so a
  file sent before the change and sent again after it would record its rows again; the build looks up the old key too, or the
  runbook backfills the new key onto stored upload rows (an idempotent write, a backup first, CLAUDE.md §6) — the probe (§3b row 14)
  and §3c take the first: the old key is looked up too. **C2b:** refuse a file that repeats a stored trade, naming the rows.
- **C3 — strictness.** **C3a (recommended):** a broker file is refused whole when any row fails a check, naming the row,
  column and value; nothing is recorded from it. **C3b:** record the good rows and report the rest.
- **C4 — the generic template upload.** **C4a:** keep it beside the broker import. **C4b:** retire it once every broker you use
  is served.
- **C5 — the source file.** **C5a (recommended):** keep nothing of the file but its digest and the per-row identity on each
  trade (the files hold personal data). **C5b:** store each import's raw rows for audit (then it needs erasure, W-237 family).

**What the samples settle, and what they contradict:**
1. **Identical rows inside one order are real.** Fyers: one EMAMI sell order (one exchange order id, one time) is three rows,
   two of them identical (`1.00` at `634.00`); one FINEOTEX order is two rows at two prices. A Fyers row's identity is
   therefore the order ids, the time, quantity and price **and its occurrence among equal rows of the file**.
2. **Upstox's `Amount` is not quantity × price.** 2025-06-12: `Amount` 500.03, 4.67 × 107.16 = 500.4372; 2025-04-02 (a
   sell): 6,960.52 against 6,958.695. A check that the two agree would refuse every row; which one is the cost is **C6**. The
   holdings the app stores today take quantity × price (the owner's MOTILAL OSWAL lots: 240.65 × 8.31 + 112.23 × 8.91 =
   2,999.7708, the stored `totalValue`).
3. **No file names an instrument the way the app's stored lots do.** Stored lots use the owner's own codes (Upstox
   `CONS_MIRAE_FUND`, where the file says `F769K01BL5`), the scheme name without the plan suffix (Zerodha
   `EDELWEISS NIFTY SMALLCAP 250 INDEX FUND - DIRECT PLAN`, where the file says `… INDEX FUND- DIRECT PLAN GROWTH - GROWTH`),
   and exchange symbols for Fyers (`BARBEQUE`, where the file says `BARBEQUE NATION HOSP. LTD`). Imported under the file's
   names, a sell would find no lot (as W-356 found for renames). **So the registry (W-440b) comes before any parser:** every
   file value — ISIN, scrip code, shortened name — and every stored code is an alias of one registry instrument, and an import
   meeting an alias the registry lacks is refused, naming it.
4. **A Fyers row says nothing of its exchange**, and the app requires `NSE` or `BSE` on every equity trade (D-826). The
   exchange is not inferred from an order id's digits; **C7**.
5. **Not in these samples:** a buy from Fyers, equity from Upstox, a Zerodha sell of MF, two identical MF buys on one day, an
   intraday or F&O row, an auction trade. A parser accepts only what a sample has shown; anything else is refused until a
   sample shows it.

**Duplicate keys, from the columns above** (each with the broker and the user):
- Zerodha equity: exchange + `Trade Date` + `Trade ID` + `Order ID`.
- Zerodha MF: ISIN + `Trade Date` + `Order ID`.
- Fyers: `Exchange order ID` + `OMS order ID` + `Date & time` + side + quantity + price + occurrence among equal rows.
- Upstox MF: scrip code + date + side + quantity + price + `Amount` + occurrence among equal rows.

**Unproven, and the occurrence count depends on it:** that a later, overlapping export holds every row of each day the earlier
one held. Each preamble states its range as dates without times, which is consistent with it but does not prove it. The build
proves it on two real overlapping downloads per broker before the occurrence count is trusted; until then a file whose
occurrence counts disagree with stored rows of the same day is refused, naming the day.

**Checks each parser makes, refusing the whole file (C3a) and naming the row, column and value:**
- The preamble's markers and the header row exactly as above (order and spelling).
- Every row's date inside the preamble's range; the file's broker is the one the user names on the upload.
- Each column's type as the sample shows it (Zerodha's ids text, numbers numeric; Upstox's date a serial; Fyers' numbers parse
  with separators and its ids in `="…"`); an id in scientific notation or with lost digits refused.
- Values only from the sets the samples show: side, segment (`EQ`/`MF`; `MF`; `Equity`), product type `Delivery`,
  exchange (`NSE`/`BSE`; `BSE`; `BMF`), `Auction` false, Upstox `Instrument Type` `MF` with `Strike Price` 0 and no
  `Expiry`.
- Fyers: `Total value` = Qty × price to the paisa.
- Every instrument resolves through the registry.

### 3a. Choices the samples add

- **C6 — Upstox MF cost.** **C6a:** `Amount` as the cost (and the sale value), quantity and NAV kept as given. **C6b:**
  quantity × price, as stored today. The two differ by paise on every row; **owner to rule** — the samples cannot say which the
  fund house charged.
- **C7 — Fyers' exchange.** **C7a:** the owner downloads a Fyers report that names the exchange, if one exists (to be shown by a
  sample). **C7b:** the upload names the exchange for the whole file, refused if the file mixes them — which this export cannot
  show. **C7c:** each registry instrument carries the exchange the owner trades it on for that broker.

- **C8 — a period already entered by hand.** The owner's stored trades and the broker's file can differ (finding 7), so an
  exact key cannot recognise them. **C8a:** each broker import starts from a date the owner names per broker; earlier rows in a
  file are refused, naming the date. **C8b:** the owner's stored history for a broker is replaced by the broker's files — a data
  correction through the runbook (backup first, read-only counts before and after, CLAUDE.md §6), redoing every sale and
  corporate action on those lots; its own item. **C8c:** match stored trades within a tolerance — rejected: a tolerance is a
  guess at what "the same trade" means.
- **C9 — charges on trades before the first rate card.** **C9a:** import them with no charges and say so on the trade
  (`NO_SCHEDULE`), the cost basis the price alone. **C9b:** refuse them until W-383 (2) ships earlier cards. **C9c:** the
  owner enters each trade's charges from the contract note — a field the broker files do not have.
