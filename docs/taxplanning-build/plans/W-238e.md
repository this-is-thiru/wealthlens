### What I read (session 67)

- **The rules a fund feeds.** Five rows have conditions that read `employer.fund`:

  - `SAL-INCLUDES-PENSION-CONTRIBUTION`;
  - `PERQ-RPF-CONTRIBUTION`.

    `EmployerContributionNode` (`node/EmployerContributionNode.java:105-146`), not through a condition.
  - So scanning conditions alone would give superannuation **no rules at all**, even though the aggregate limit is
    the one rule its contribution feeds.

### Re-plan (R13, session 67) — C2a measured does not give "feeds"

No code was written. The approved C1a C2a C3a stand, except for C2.

**What the trace check found.** I dumped the trace of W-238c's draft (basic 16L, special 8L, new regime): first with
no fund, then with NPS 2,24,000, superannuation 7,50,000 and RPF 2,70,000. This was a temporary test, deleted after;
the output is in the session scratchpad.

- **A trace line names no item.** `TraceLine` carries `node, rule, kind, in, out, limitedBy, provenance`
  (`trace/TraceLine.java:43-50`). So "the lines that take this fund" can only be measured by comparing two runs.
- **The NPS salary line is traced under the wrong-looking rule.** It is traced under `SAL-SALARY-INCLUDES`, not
  `SAL-INCLUDES-PENSION-CONTRIBUTION`. `GrossSalaryNode` names the head-total rule on every added line
  (`node/GrossSalaryNode.java:70-79`). The pension rule only decides which funds count (`:98-105`). So the plan's
  case 1 figure cannot come out of the trace.
- **The accretion line is present at nil.** `PERQ-EMPLOYER-ACCRETION` is in the trace with no contribution at all.
  So presence alone does not say a fund fed it.
- **A comparison picks up more than "feeds".**
  - It needs one more election per fund change: the answer with that fund at nil. `Priced` keeps no trace.
  - Any rule that appears only when a figure turns non-nil (a rebate, a surcharge) would show up as "fed" by a
    fund that only lowered income.

**C2 again (recommended first):**
- **(c) Recommended: a fund row in the pack.** Add `exec/funds/<EmployerFund>.json`, like a component row, with an
  authored `feedsInto`, `_note` and provenance. `PackValidator` checks at build that:
  - every named rule exists;
  - every rule whose conditions read `employer.fund` for that fund is listed.
  A rule reached by a node, such as the aggregate limit, is listed by hand, with the node line in the `_note`.
  The fact lives in the pack, not Java (§4). It costs no pipeline runs. And it gives W-238e1's liquidity the row it
  needs: the row text says "a contribution has no component row".
  - Expected `feedsInto`, TY 2026-27, read from each rule's own conditions and the node lines above:
    - NPS: `DED-NPS-EMPLOYER-GOVT`, `DED-NPS-EMPLOYER-NEW-TAX-REGIME`, `DED-NPS-EMPLOYER-OTHER`,
