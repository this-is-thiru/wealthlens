**What this item is for (one sentence, in my own words):** the one-time rewrites that update raw rows by a collection name
convert a stored string `_id` of 24 hex digits into an `ObjectId`, so on prod's data they match nothing and report success
— make them match the `_id` as stored, and prove each with a test on such an id.

**Evidence (read this session):**
- W-334c2 row 6 on prod's copy: `POST /privacy/stored-fields/encrypt?dryRun=false` re-keyed the 15 logins but encrypted
  **0** of 817 `transactions`, 529 `assets`, 163 `trade_outcomes`, 11 `lastly_performed_corporate_action`, 7
  `profit_and_loss`, 6 `corporate_action` rows — no error, 0 conflicts (`m1-start-1.log:151`).
- Every `_id` in those six collections is a `string` (owner's `$type` query, run log).
- `StoredFieldEncryption.java:121` builds `where("_id").is(row.get("_id"))` and `:131` sent it through
  `mongoTemplate.updateFirst(query, update, collectionName)` — a query with no entity type, which Spring Data's query
  mapping converts to an `ObjectId` when the string is a valid one. The existing tests use ids like `"plain-1"`, `"p1"`
  (`StoredFieldEncryptionIntegrationTest.java:45`, `ProfitAndLossSplitReshapeIntegrationTest.java:210`), never converted.
- **Probe, red then green:** a new test inserting a `transactions` row with `_id` `"65f0a1b2c3d4e5f6a7b8c9d0"` got
  `encryptedRows` 0 (Expected 1, Actual 0); with the update sent unmapped
  (`mongoTemplate.execute(collection, c -> c.updateOne(query.getQueryObject(), update.getUpdateObject()))`) it is 1, and
  `StoredFieldEncryption…`, `StoredActorEncryption…`, `StoredIdentifierEncryption…IntegrationTest` pass 14 / 0 — the
  conflict case (`StoredIdentifierEncryptionIntegrationTest.java:120`) included, so the duplicate-key translation still works.
- **The same pattern** is at `ProfitAndLossV2Backfill.java:125` (runbook §2.8) and `ProfitAndLossSplitReshape.java:69` (§2.6),
  both `updateFirst(Criteria.where("_id").is(rawId), update, COLLECTION)` on `profit_and_loss`, whose `_id`s are strings.
