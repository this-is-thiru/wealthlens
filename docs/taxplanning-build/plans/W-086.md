- **How `netProfit` is made** (`TradeOutcomeRecorder:131–134`): sell value less **all** sell charges, less buy value

- **The charge catalogue** (`data/charges/charge-catalogue.json`) flags each code `deductibleForCapitalGains`: STT,
  AMC and account opening `false`; brokerage, exchange, SEBI, stamp duty, DP, GST, exit load `true`.
  `ChargeDeductibilityService` excludes an unknown code, *"never assumed deductible"*.
- **Rows without a breakup:** `TransactionBasedTradeOutcomeMigration` → `TradeMatchingService` builds rows with broker
  charges but no breakup, so their deductible charges read 0.
- **Two year formats in one collection:**
  - `TradeOutcomeRecorder`, `ProfitAndLossService` and `PortfolioService` write `TLocalDate.financialYear` →
    `"2025-2026"`;
  - `TradeMatchingService.deriveFinancialYear` (the migration) writes `"FY2025-26"`.

  W-085's `CapitalGainsSummary` Javadoc gives `FY2025-26` as the example, which is the migration's format, not
  `portfolio`'s.
- **`TradeOutcomeRepository`** has `findByEmail` and `findByEmailAndSourceBuyLotIdIn`. The collection is indexed
  `{email, sell_date}`.

### Findings

1. **The gain to publish is the sale value less the cost less the deductible charges,** per row:
   `sellPrice × sellQuantity − corporateActionAdjustedBuyPrice × buyQuantity − deductibleBuyCharges −
   deductibleSellCharges`. That is `portfolio`'s own quantification (R-10: `portfolio` owns "the amount"), using the
   flags it already keeps. `netProfit` would deduct STT, so the published gain would be too small.
2. **A row with charges but no breakup cannot be quantified.** Its deductible part is unknown, and reading it as 0
   would overstate the gain silently.
3. **Rows must be selected by sell date, not by the year string,** or the migration's rows are missed.

### Choices (recommended first)

- **C1 — the gain:**
  - **(a) recommended:** finding 1, canonicalised with `TMoney`. User-entered misc charges are **not** deducted:
    they have no code, so the catalogue cannot say whether they are deductible, and an unknown charge is excluded
    (`ChargeDeductibilityService`'s rule).
  - **(b)** as (a), but misc charges deducted.
  - **(c)** `netProfit`. That deducts STT, which the catalogue flags non-deductible.
- **C2 — a row with charges and no breakup:**
  - **(a) recommended:** refuse the summary, naming how many disposals and the first row's sell date and stock, so
    the user re-records them. This is the same blocking stance X1.3 takes for `UNCLASSIFIED`.
  - **(b)** publish it with nothing deducted. That overstates the gain silently.
- **C3 — the service:**
  - **(a) recommended:** `portfolio/service/CapitalGainsSummaryService.summaryFor(String email, String
    financialYear)` (`@Service @Log4j2 @Transactional(readOnly = true) @RequiredArgsConstructor`).
    - The year is `portfolio`'s `"2025-2026"` form. Anything else is refused, naming the expected form.
    - It reads `TradeOutcomeRepository.findByEmailAndSellDateBetween` from 1 April to 31 March (C4).
    - It groups by (classification, asset type, sub-class), summing with `TMoney`.
    - Every classification is published, `UNCLASSIFIED` and `SPECULATIVE` included (X1.3).
    - An empty year gives no buckets.
  - **`asOf`** is the time of the read (`Instant.now()`).
  - **`portfolioComputationRef`** is `"trade_outcomes:" +` a SHA-256 over the rows' sorted `id`, classification and
    gain. So a later read of changed data gives a different reference: the pin F4.1 needs.
- **C4 — the query bounds:** Spring Data MongoDB's `Between` excludes both ends, as I recall its reference documentation (`$gt` / `$lt`); I have not checked it here. I'll pass 31 March of
  the previous year and 1 April of the next, so 1 April and 31 March are included, and an integration test proves it.
- **C5 — the consumer, so nothing is left unplaced:**
  - **(a) recommended:** **W-087** grows to *"`MoneyBridge` and `CapitalGainsAdapter`"*: the adapter in
    `taxplanning.portfolio` calls this service and maps to `CapitalGainsInput`, and the bridge is used only there
    (`only_the_adapter_converts`). That gives W-086 a consumer in the next item, and the modulith test then covers
    the first real import.
  - **(b)** a separate row W-087a after W-087.
- **C6 — the two format defects:**
  - W-085's Javadoc example is corrected to `2025-2026` here, as a comment-only change.
  - For the migration's `"FY2025-26"` rows: **(a) recommended:** place **W-086a** after W-086, *"`TradeMatchingService`
    writes `TLocalDate.financialYear`, and a migration rewrites the `FY…` rows"*. **(b)** leave it to `portfolio`'s own
    backlog, recorded in the D-row only.
