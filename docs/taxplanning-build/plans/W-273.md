## Plan for W-273 — holdings merge account holders into one row

**What this item is for (one sentence, in my own words):** the holdings views show one row per stock, broker **and
account holder**, so one person's shares are never shown as another's at a blended price (G-7, PS-14).

**Findings (each read this session, 2026-11-11):**

1. **The key.** `groupedWithCharges` (`PortfolioService.java:542`) groups lots by `stockWithCodeAndBroker()`
   (`:845`): `asset.getStockCode() + asset.getBrokerName().name()` — no account holder, no delimiter (PS-14). It is
   the only grouping key left; PS-14's second one (`stockCodeWithBroker` over `AssetResponse`) no longer exists.
2. **Every holdings view goes through it:** `GET /stocks/all`, `GET /mfs`, `POST /stocks` (date range) and the assets
   export (`getExportEntities`). The row copies the first lot's fields (`combineAllDetailsOfEntities`), so it names
   one holder for both. Proven: W-264a scenario 12 — "Self" 10 @ 100 and "Spouse" 10 @ 200 shown as one row, holder
   "Self", 20 @ ₹150.
3. **The assets export has no account-holder column** (`PortfolioExportColumns.ASSETS`; `ExcelHeaders` has no such
   header), so two rows that differ only by holder would look identical there.
4. **Seen, not in scope:** the upload never sets an account holder (`AssetRequestParser` reads no such column), so
   uploaded lots carry none; they group together as one holder, which is what they are today.

**Choices for the owner:**

- **C1 — the key.**
  - **C1a (recommended):** a private record `Holding(stockCode, brokerName, accountHolder)` as the grouping key — a
    record cannot collide the way a concatenation can (PS-14), and a missing holder is one value of its own.
- **C2 — the export.**
  - **C2a (recommended):** add `ACCOUNT HOLDER` to the assets export (`ExcelHeaders.ACCOUNT_HOLDER`, field
    `accountHolder`), after `STOCK CODE`, so the split rows can be told apart.
  - C2b: leave the export as it is.

**Files I will modify:** `PortfolioService` (key), `PortfolioExportColumns`, `ExcelHeaders` (C2a); tests — W-264a
scenario 12 as the first test (two rows: Self 10 @ ₹100, Spouse 10 @ ₹200), a delimiter case (stock `AB` at a broker
whose name continues it is not constructible with the `BrokerName` enum, so PS-14's collision is covered by the
record's equality rather than a scenario), the export carrying the holder; any export test counting columns.

**Numbers I will use:** none beyond the scenario's own figures.

**What I am NOT doing:** the upload's missing holder (seen in finding 4 — I will place it as a row if you want it
fixed); per-row charge totals beyond what the grouping already gives.

**How I will verify:** scenario 12 red then green; the export's holder column read back; probe: holder dropped from
the key → scenario 12 fails; the affected classes; `./mvnw validate`.

**Post-deployment actions (R15):** none — a view, nothing stored.

**Five roles:**
- **Architect:** a holding's identity stated once, as a record.
- **Product manager:** a family's holdings are shown per person; the spreadsheet says whose each row is.
- **Senior engineer:** one key, no string concatenation.
- **Automation tester:** scenario 12 with distinct prices; a probe.
- **Manual tester:** buy one stock for Self and Spouse at one broker; `/stocks/all` shows two rows.

**Risks or ambiguities:** a client that summed one row per stock and broker now gets more rows — the correct shape.
