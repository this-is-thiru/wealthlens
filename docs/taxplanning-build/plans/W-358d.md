## Plan for W-358d — login hardening, validation, logs: the split

> Planned in session 114 (2026-11-21), after W-362 put `m1.5` on staging and prod. W-358d (D-850) holds four unrelated changes, so,
> like W-358c (D-855), it is split first and each part gets its own plan with its probe before it is built. **Stop point: nothing is
> built until the owner answers C1 – C2.**

**What this item is for (one sentence, in my own words):** a sign-in cannot be guessed at without limit, a stored password moves to a
better hash without anyone resetting it, every request body is checked the same way before it reaches a service, and the logs carry a
request id but never a person's email.

### What the code is today (measured this session)

| Part | Today | Where |
|---|---|---|
| Rate limiting | none: `POST /api/v1/public/auth/login` accepts any number of attempts; no rate-limit library on the classpath (no Bucket4j, no Caffeine) | `AuthController:30`; `dependency:tree` |
| Account existence | registration answers "User with email … already exists" and "The account … is being erased", so anyone can test whether an address has an account | `AuthService:47`, `:51` |
| Password hashing | one `BCryptPasswordEncoder` bean; stored hashes carry no `{id}` prefix; nothing upgrades a hash. Spring Security 7.1.0's `PasswordEncoderFactories` defaults to `bcrypt` and offers `argon2` (BouncyCastle, now 1.85 on the classpath), `scrypt`, `pbkdf2` | `InvestmentTrackerConfig:14`; `javap` of `spring-security-crypto` 7.1.0 |
| Bean Validation | `spring-boot-starter-validation` on the classpath, but **no** `@Valid` / `@Validated` in main code and **no** `jakarta.validation.constraints` annotation; checks live in records' compact constructors (`RefreshRequest`), request methods (`EmployerRequest.applyTo`) and services, each refusing with `IllegalArgumentException` → 400 | `grep`; `ControllerAdviser` has no `MethodArgumentNotValidException` handler |
| Request id | none: no MDC, no correlation id, no response header | `grep MDC` |
| Emails in logs | **17** log statements write an email (e.g. `TradeOutcomeService:23` "Saved trade outcome for email: {}", `UserRecordsErasureService:62`, `PortfolioQueryService:67`); **5** exception messages carry one and `ControllerAdviser` logs each refusal's message (`AuthService:47, :51, :80`, `AccountErasureService:56`, `TransactionBasedTradeOutcomeMigration:81`). Logback masks a PAN-shaped token in every line (D-447 C4a), not an email | `grep`; `logback-spring.xml` |

### The split (C1)

| Part | What | Why it stands alone |
|---|---|---|
| **W-358d1 — logs** | a request id on every log line (MDC, and a response header a caller can quote); no email in any log line: the 17 statements and 5 messages reworded, and a guard (runtime masking in `logback-spring.xml` as for PANs, a test that fails on an email in a captured log line, or both — decided in its plan) | code only, nothing stored |
| **W-358d2 — sign-in hardening** | login attempts limited (per account and per address; the limit, the window and where the counts live decided in its plan); registration and sign-in answer the same whether or not an account exists | code only, or one small collection if counts must survive a restart |
| **W-358d3 — password hashes** | a delegating encoder: hashes stored today keep matching, each is rehashed to the chosen algorithm at its next sign-in (`UserDetailsPasswordService`); the algorithm and its cost decided in its plan | **writes stored data** (`user_details` passwords, one at each sign-in): a runbook entry with a read-only count of hashes not yet upgraded |
| **W-358d4 — request validation** | `@Valid` on every `@RequestBody`, constraints on the request types, `MethodArgumentNotValidException` answered as a `ProblemDetail` naming each field; checks that duplicate a constraint removed (the list measured in its plan); a guard that no body is read without `@Valid` | code only; 50 bodies of 35 types, the largest part |

- **C1a (recommended):** the four parts above, each its own plan (probe first), D-row and commit; the parent W-358d closes when the four do.
- **C1b:** one item, one plan, one commit — it would mix a stored-data change (d3) with three code-only ones.

### The order (C2)

- **C2a (recommended):** d1 → d2 → d3 → d4. d1 first: email in logs is personal data written today on every database the app runs
  against (DPDP, the same reason PANs are masked). d2 next: it guards the only route that takes a password. d3 after d2 (both touch
  sign-in). d4 last: the largest, and no data at risk.
- **C2b:** another order (name it).

**Files I will create / modify:** none in this split; each part's plan lists its own.
**Numbers I will use:** the counts in the table (17, 5, 50 bodies of 35 types, 0 `@Valid`), each measured this session.
**Design sections I read:** D-850, D-855 (the W-358c split this follows), D-447 C4a (PAN masking), D-854 (refresh tokens).
**What I am NOT doing:** MFA, passkeys (D-850: parked until a frontend); any part's design before its own plan.
**How I will verify:** per part, in its plan.
**Post-deployment actions (R15):** d3 adds a runbook entry; d1, d2, d4 add "Next deploy" lines for callers (a header; 429 on too many
attempts; field-level 400s).
**Five roles:** Architect: four independent changes, each small enough to prove. PM: the privacy fix first. Senior engineer: no part waits
on another but d3 on d2. Automation tester: each part red first and guarded. Manual tester: the api-collection's sign-in and one body per
module.
**Risks or ambiguities:** d4's 50 bodies (35 types) may need their own split once measured; a rate limit kept in memory resets on a restart
(acceptable for one local instance; d2's plan weighs it).
