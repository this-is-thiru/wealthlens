## Plan for W-275 — an upload drops a row identical to an earlier one

**What this item is for (one sentence, in my own words):** every row of an uploaded sheet is recorded, identical rows
included, while sending the same file again still records nothing twice — and the answer says which happened (G-9).

**Findings (each read this session, 2026-11-11):**

1. **Why the row is dropped.** Upload rows carry no `idempotencyKey`, so `TransactionService.recordTransaction` falls
   back to the trade fingerprint within the 60 s window (`TransactionService.java:73-74`; `application.yaml`
   `window-seconds: 60`) and treats the second identical row as a retry of the first. Proven: W-264a scenario 15 —
   two identical rows, answer "All transactions uploaded successfully", one transaction.
2. **The fingerprint exists for client retries**, and an upload can be retried too (a re-sent file after a timeout);
   today a whole-file retry within 60 s is absorbed by the same window — and one after it is recorded twice.
3. **A supplied key is exact and has no window** (`:56-62`), checked by `findByEmailAndIdempotencyKey`; the index on
   `idempotency_key` is unique and sparse **across all users** (`TransactionEntity.java:126`), so a derived key must
   include the user. `AssetRequest.asTransaction` does not copy the key onto a held-back temporary, so redrive is not
   mistaken for a replay.
4. **The answer ignores each row's outcome.** `uploadTransactions` (`PortfolioService.java:234-252`) discards what
   `processTransaction` returns (`REPLAYED_MESSAGE` for a repeat) and answers "All transactions uploaded successfully".
5. **Rows come back in sheet order** (`AbstractRequestParser.parse`), and a sheet with any bad row is refused whole,
   so a row's position in the parsed list is its position in the sheet.

**Choices for the owner:**

- **C1 — how a row is told from a repeat.**
  - **C1a (recommended):** each row gets a key the server derives: `upload:` + SHA-256 of (user, quarter, the
    file's bytes) + `:` + the row's position. Two identical rows in one file differ by position, so both are
    recorded; the same file sent again — at any time, not only within 60 s — yields the same keys, so nothing is
    recorded twice. Uses `TradeFingerprint.sha256`.
  - C1b: upload rows skip the fingerprint check only — identical rows recorded, but a re-sent file records every row
    again.
- **C2 — the answer.**
  - **C2a (recommended):** say how many rows were recorded and how many were already recorded by an earlier send of
    the same file, beside the existing held-back list.
  - C2b: unchanged.

**Files I will modify:** `PortfolioService.uploadTransactions` (keys per row, counts in the answer); tests — W-264a
scenario 15 as the first test (two identical rows: two transactions, 20 held), the same file sent twice (second send:
nothing new, answer says 2 already recorded), the same file by two users (each records its own — the unique index);
CLAUDE.md is silent on upload idempotency, so no change there.

**Numbers I will use:** none.

**What I am NOT doing:** the parser's empty-cell shift (W-276); upload validation (W-277); the account holder (W-285).

**How I will verify:** first tests red then green; probe: the position left out of the key → scenario 15 fails; the
affected classes (`PortfolioIntegrationTest`'s upload tests, `TransactionIntegrationTest`); `./mvnw validate`.

**Post-deployment actions (R15):** none — rows uploaded before this carry no key and are unaffected.

**Five roles:**
- **Architect:** the server derives identity from what it was sent, which is exact, instead of guessing from a time
  window.
- **Product manager:** two equal fills in a broker statement are both recorded; uploading the same statement twice
  never doubles a holding, and the answer says so.
- **Senior engineer:** one digest of the file per upload, one key per row; the existing key check does the rest.
- **Automation tester:** identical rows, a re-sent file, two users with one file; a probe.
- **Manual tester:** upload a sheet with two identical rows: two trades; upload it again: "2 already recorded".

**Risks or ambiguities:** a user who edits nothing but re-sends a file meaning to record it twice gets nothing new —
by design; changing any cell makes it a different file.
