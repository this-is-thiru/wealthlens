## Plan for W-238f — HR support for a suggested change, as product data

**For:** a user reading a suggestion to move pay. They should see how likely an employer is to agree to the change.
This is reported and is never a veto (A2.2 C10). Row `03-WORK-ITEMS.md` W-238f (W-238b C4a, D-490). Design:
`03-advisory.md` A2.6 (`hrSupportLikelihood`).

### What I located (session 69)

- `POST /tax/user/{email}/drafts/{draftId}/optimise` returns the engine's `Optimisation` as it is
  (`DraftComputationController.java:42-45`). `Change`, `FundChange` and `FollowingChange` are `taxengine` result
  records (`taxengine/api/Optimisation.java:50,68,89`). HR support has no legal source, so it may not enter
  `taxengine` or the pack.
- The pack's component rows (`rulepacks/timeline/exec/components/*.json`): 19 of 51 are `SALARY`/`CASH`, 4 are
  `EMPLOYEE_CONTRIBUTION`, and the rest are `QUALIFYING_PAYMENT` or `STATUTORY_DEDUCTION`, all `CASH_OUTFLOW`. Only
  the 19 `SALARY` rows and the three `EmployerFund`s (`taxengine/input/EmployerFund.java`) are the employer's to agree
  to. W-238g decides what happens to the others.
- The legacy `taxplanning/enums/HrSupportLikelihood` (HIGH, MEDIUM, LOW, EMPLOYER_DISCRETION, NOT_APPLICABLE) is used
  only by the legacy path (`RestructuringEngine`, `AllowanceRecommendation`, `AllowanceCatalogueEntity`). W-159
  deletes that path. A second class with the same simple name would be a defect (CLAUDE.md §3).

### Choices (recommended first)

**C1: the shape of the answer.**
- (a) A `taxplanning` view, `DraftOptimisation`, holds the engine's `Optimisation` unchanged plus `hrSupport`: one
  entry per moved name (each `Change.component` and `FundChange.fund`) with its value. A `FollowingChange` takes no
  entry of its own, because it moves only with what it follows (W-238d). The endpoint returns the view.
- (b) Mirror `Change` and `FundChange` in `taxplanning` with an `hrSupport` field each. This matches A2.6's layout,
  but it copies two engine records field by field.

**C2: the vocabulary.**
- (a) Reuse `HrSupportLikelihood`. Move it out of `enums/` into the new code's package, and amend W-159's row so the
  enum stays when the legacy path goes. This keeps one word for one concept.
- (b) A new enum with your own values and a new name (not `HrSupportLikelihood`).

**C3: coverage.**
- (a) A table (`data/tax-planning/hr-support.json`, read at start) must give a value for every `SALARY` component in
  the pack and every `EmployerFund`. A build-time test fails when the pack gains one without a value. A name
  with no entry (a non-`SALARY` row, until W-238g) is shown as having no value given. No default is filled in.
- (b) A value is required for every component row (51 + 3), including those that are not pay.

**C4: the values.** These are yours. The item says so, and copying the legacy catalogue is not offered (W-238b C4c).

### Build steps (after approval and the values)

1. Write the table and its loader, which refuses at start a value or name it does not know. Write the coverage test,
   then prove it with a deliberate gap and revert.
2. Write the view and the service join, with unit and integration tests whose values come from your table. Update the
   api-collection `Optimise a Draft` and `02-TECH-SPEC.md:99`.
3. Close-out: STATE board line 65, the decision row, CHECKPOINT. The runbook is unchanged, since a resource file needs
   no database action.

### Roles, briefly
- Architect: product data in `taxplanning`. The engine and pack are untouched, and no new cross-module import.
- PM: the user sees the employer's likely stance beside each change, never a refusal.
- Engineer: a startup refusal plus a build-time coverage test, so no value is ever silently missing.
- Automation tester: expected values are read from the owner's table by hand.
- Manual tester: one draft moving HRA into the employer's NPS, with both entries shown.
