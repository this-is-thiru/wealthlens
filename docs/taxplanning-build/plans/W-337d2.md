### Core findings from probing the code before planning (`probe-before-plan.md`)

1. **Null-safe scope matching in `ChargeScheduleRepository.findOpenScheduleForScope` (`ChargeScheduleRepository.java:46-49`):** Mongo's `'exchange': null` matches null fields, whereas SQL `s.exchange = :exchange` returns false when `:exchange` is null. The JPQL query must use explicit null-safe predicates `((:param IS NULL AND col IS NULL) OR col = :param)` for all 5 nullable scope dimensions (`brokerName`, `assetType`, `segment`, `exchange`, `planCode`), using `CAST(s.assetType AS string)` / `CAST(s.segment AS string)` so the existing `String` method signature stays unchanged (zero unit-test mock churn).
2. **2-level nesting in `ChargeScheduleEntity.rules` / `ChargeInstrumentEntity.rules` (`ChargeRule.java:32-173`):** `ChargeRule` contains `Set<ChargeEvent> events`, `List<ChargeSlab> slabs`, and `List<String> baseCodes`. No query in the codebase ever filters inside `rules` — the engine always loads whole cards/profiles. A `ChargeRuleListConverter` (`TEXT` JSON column `rules_json` via Jackson `JsonMapper`) keeps both tables single-table and avoids 4 deeply-nested join tables.
3. **`UserChargeEntity.amountByCode` (`UserChargeEntity.java:140-141`, `UserChargeRepository.java:27-41`):** queried dynamically by charge code (`amount_by_code.? > 0`) in `existsChargeForScripOnDate`, `existsChargeForOrder`, and `existsChargeForDay`. Mapping it as an eager `@ElementCollection` `Map<String, Double>` in child table `user_charge_amounts` (`user_charge_id` FK, `charge_code`, `amount`) lets all 3 deduplication queries run in pure JPQL (`JOIN u.amountByCode a ... KEY(a) = :chargeCode AND VALUE(a) > 0`).
4. **Seeded reference table preservation:** `AbstractIntegrationTest.SEEDED_REFERENCE_COLLECTIONS` (`AbstractIntegrationTest.java:57`) already lists `"charge_catalogue"`, so Postgres `TRUNCATE` in `cleanDatabase()` already preserves `charge_catalogue` between tests.
5. **Cross-module erasure:** `UserRecordsErasureService` (still in `portfolio` / Mongo) calls `userChargeService.deleteByEmail(email)` and `chargeAccountService.deleteByEmail(email)`, both of which run inside `@Transactional("postgresTransactionManager")` on their respective services.

### Decisions (for approval with this plan)

- **C1 — `ChargeScheduleEntity.rules` and `ChargeInstrumentEntity.rules` (`List<ChargeRule>`).** **C1a (recommended):** store as `rules_json TEXT` via a JPA `AttributeConverter<List<ChargeRule>, String>` (`ChargeRuleListConverter` using Jackson `JsonMapper`) — no query ever filters inside rules, keeps both tables single-table, and avoids 4 nested child tables for `rules` → `events`/`slabs`/`baseCodes`. **C1b:** normalize into 4 child tables (`charge_schedule_rules`, `charge_schedule_rule_events`, `charge_schedule_rule_slabs`, `charge_schedule_rule_base_codes`, plus the same 4 for `charge_instruments`).
- **C2 — `UserChargeEntity.amountByCode` (`Map<String, Double>`).** **C2a (recommended):** `@ElementCollection(fetch = FetchType.EAGER)` child table `user_charge_amounts (user_charge_id, charge_code, amount)` so `existsChargeForScripOnDate`, `existsChargeForOrder`, and `existsChargeForDay` run in pure JPQL with `KEY(a)` / `VALUE(a)`. **C2b:** store `amount_by_code` as JSONB and use Postgres native JSONB queries.
