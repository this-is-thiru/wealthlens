## Plan for W-337g — the copier: MongoDB → PostgreSQL (size check + decisions)

> Planned in session 122 (2026-11-25), next after W-337f (D-952). **Stop point (Stage 2 EXPLAIN):** nothing is built
> until the owner answers C1 – C6.

**What this item is for (one sentence, in my own words):** a one-time copier inside the app that reads every MongoDB
collection the `m1.6.1` build writes and fills the PostgreSQL tables of W-337b – f with the same rows — ciphertext and
keyed digests carried as they are (D-928 C3a) — idempotent by key, proven by counts, digests and a read-back through
the app's own repositories, so W-337i can move dev, staging and prod.

### Core findings from probing before planning (`probe-before-plan.md`)

1. **Column names follow the Mongo field names.** For every flat field the target column is the Mongo key
   (`@Field` name) or, for a field without `@Field`, the snake_case of the Java key Mongo stored; `_id` → `id`
   (an `ObjectId` or a 24-hex string, `StoredId.java:16` — both become the hex text). The 12 that differ, all at
   `m1.6.1`: `PolicyDetails.broker_name`→`broker`, `AssetEntity` and `TransactionEntity`
   `corporate_action`→`corporateActionType`, `AssetEntity.comments`→`comment`, `TradeOutcomeEntity`
   `ca_adjusted_buy_price`→`corporateActionAdjustedBuyPrice` and `is_ca_derived`→`corporateActionDerived`,
   `FinancialReport.capital_gains`→`monthlyReport`, `MonthlyReport.first_half_report`/`second_half_report`
   →`first/secondFortnightReport`, `tax_year`→`taxYearStart` on `StoredDocument`, `FilingDraft`,
   `TaxYearWorkspace`. Each target column is confirmed against its `CREATE`/`ALTER` at build time, never assumed.
2. **Ciphertext can be copied as it is** — `EncryptedField` ↔ `EncryptedColumn`/`EncryptedDateColumn` and
   `SearchableIdentifier` ↔ `SearchableColumn` all store `FieldCipher`'s same text form
   (`EncryptedField.java:23`, `EncryptedColumn.java:24`, `SearchableColumn.java:27`); a searchable value is
   deterministic, so a copied digest still matches a query. GridFS bytes are already `FieldCipher.encryptBytes`
   output (W-337f finding #5), copied as they are into `tax_document_bytes.bytes`.
3. **Dates.** *(Amended by D-954 while building W-337g1: every copied time is written in UTC — a local-held time,
   every audit time, read in UTC; a UTC-held one read in `app.copier.written-zone`.)* `m1.6.1` stored a `LocalDate` as a Mongo `Date` at midnight **UTC**
   (`LocalDateToDateConverter` at `m1.6.1`: `atStartOfDay().toInstant(ZoneOffset.UTC)`), so the copier reads it
   back in UTC; a system-zone read would move every date a day back in IST. `LocalDateTime`s were stored UTC
   (CLAUDE.md, `TLocalDateTime.atUtc()`).
4. **The JSON columns are not the Mongo sub-document shape.** `JsonColumnConverter` writes Jackson's form of the Java
   class (`JsonMapper.builder().build()`, `JsonColumnConverter.java:14`) — camelCase keys, Jackson's date form —
   whereas Mongo holds the sub-document under its `@Field` names. Each of the 16 JSON columns needs its sub-document
   keys renamed by the `m1.6.1` names (including the 3 renames inside the P&L tree, finding #1) and its dates
   re-formed; only the read-back (C4) proves each one.
5. **A missing Mongo field must not become NULL** in a primitive-backed column (V9's NOT NULL zero defaults, D-952;
   "a NULL there makes the row unreadable"): an absent key is left out of the `INSERT`, so the column default applies.
6. **Defect found, not in this item — W-337e stores corporate-action copies' audit emails in plaintext.**
   `CorporateActionEntity.auditMetadata` is an `AuditColumns` (`CorporateActionEntity.java:83-85`), whose
   `createdBy`/`updatedBy` are encrypted only by JPA's `@Convert(SearchableColumn)` (`AuditColumns.java:24-31`).
   Inside `CorporateActionListConverter`'s JSON (`assets.corporate_actions`, `transactions.corporate_actions`,
   `trade_outcomes.applied_corporate_actions`) Jackson ignores `@Convert` and has no `@JsonIgnore` to stop it, so
   the admin's email is written in clear — the regression W-341 closed on Mongo, where `AuditMetadata`'s
   `@ValueConverter(SearchableIdentifier)` applied inside embedded copies. It also decides what the copier writes
   there (C5). `AssetRequestConverter` already shows the fix pattern (`AssetRequestConverter.java:39-41`).
7. **The source must be fixed for the run.** The app writes on request and on the jobs (off since W-336); a copy taken
   while the app serves can miss a write. Leaving the copier out of a serving app removes that case (C2).

### Decisions (for approval with this plan)

- **C1 — how a row is mapped.** **C1a (recommended):** raw: read each collection as `org.bson.Document`, write with
  JDBC; a flat field goes to the column of its name (finding #1, with the 12 renames as an explicit table), values
  copied verbatim (ciphertext unchanged, D-928 C3a); `audit_metadata` → the four audit columns; each child table and
  JSON column has its own small mapping. **C1b:** typed: decrypt into the JPA entities and save through the
  repositories — re-encrypts every field (new nonces), and needs the 40 `m1.6.1` Mongo-mapped classes back in the code
  to read the source; not recommended.
- **C2 — how it runs.** **C2a (recommended):** a Spring profile `copier` that starts the app with no web server
  (`spring.main.web-application-type: none`), runs the copy and its checks in an `ApplicationRunner`, logs one report
  line per collection and exits non-zero on any mismatch; the owner runs it from a terminal with the source and target
  environments' settings. Nothing serves while it copies (finding #7). **C2b:** an admin route — needs a zone module,
  route tests and an api-collection entry, and the app serves while it copies; not recommended.
- **C3 — idempotence.** **C3a (recommended):** one target transaction per source document, writing its row and its
  child rows with `INSERT … ON CONFLICT (id) DO NOTHING`; a second run, or one after a run that failed part-way,
  skips what is there and finishes the rest. A precheck refuses a target holding an `id` the source lacks (a target not
  fresh). **C3b:** truncate the target and reload each run — also idempotent, but a destructive write on every run;
  not recommended.
- **C4 — what proves the copy.** **C4a (recommended), all three per collection, any failure stops with the
  collection named:** (1) counts — rows per table, and child rows per table against the summed array lengths; (2) a
  SHA-256 digest of every copied row read back by JDBC against the same digest of the mapped source values — proves
  nothing was truncated or re-typed on the way in; (3) a read-back — every copied row loaded through its JPA
  repository, which proves each JSON column parses, each cipher field decrypts and no NULL sits in a primitive column.
  **C4b:** counts only — would have missed V9's NULL trap and every JSON shape error; not recommended.
- **C5 — the plaintext audit emails in corporate-action JSON (finding #6).** **C5a (recommended):** place **W-401**
  (fix `CorporateActionListConverter` to encrypt the copy's `createdBy`/`updatedBy` as `AssetRequestConverter`
  does, with a red test), built before W-337g2; the copier then writes Mongo's ciphertext into those JSON copies
  unchanged. **C5b:** the copier decrypts them to match today's plaintext form — writes personal data in clear; not
  recommended.
- **C6 — the split.** **C6a (recommended):**
  1. **W-337g1** — the engine and the 22 flat collections: the `copier` profile and runner, `_id`, dates, the 12
     renames, `audit_metadata`, absent fields, GridFS → `tax_document_bytes`, the precheck, C4's three checks; the
     runner refuses to start while any of the 40 collections lacks a specification, so it cannot run half-built;
     idempotence integration test (Mongo + Postgres containers: copy, copy again, copy after an injected failure — same
     rows each time).
  2. **W-337g2** — the 18 collections with embedded data: the 12 child tables and 16 JSON columns (C5's W-401 first);
     the runbook entry (precheck, run, report, way back) and the removal ticket.
  **C6b:** one item (≈ 1,500 lines with tests); not recommended.

### Build scope (if approved; W-337g1 first)

1. `shared/migration/` (a new sub-package, owned by `shared`, which may see every module's tables through JDBC, not
   their classes): `MongoCopier` (the run), `CollectionCopy` (one collection's specification: source name, target
   table, renames, embedded mappings), `CopyReport`; `application-copier.yaml`.
2. A specification per collection — 22 in W-337g1, 18 in W-337g2 — each with the read-back repository named.
3. `MongoCopierIntegrationTest` (idempotence, part-way failure, every C4 check made to fail once by a deliberate
   corruption, then reverted) and per-collection cases seeded from `m1.6.1` shapes written by hand from the
   `m1.6.1` classes — never from the copier's own output (CLAUDE.md §5).
4. `post-deployment-runbook.md`: one entry (W-337g2) — before: source collection list equals the 40 + GridFS (an
   unknown collection stops it), target fresh; run: `java -jar … --spring.profiles.active=<env>,copier`; after: the
   report; second run safe; way back: drop and re-create the target schema (Flyway), nothing on Mongo is written.
5. Removal: W-337j already removes the copier with the Mongo starter (its row); a YouTrack issue is opened at
   W-337g2's close-out.

**Five roles:**
- **Architect:** a one-way, one-time bridge; values copied, not reinterpreted; no app code depends on it, so W-337j
  removes it whole.
- **PM:** no behaviour change for a user; the move's risk is a lost or unreadable row, and C4 names every such row.
- **Senior engineer:** no decryption in transit (C1a); a run can be repeated after any failure (C3a).
- **Automation tester:** test rows written by hand from the `m1.6.1` shapes; each check proven able to fail.
- **Manual tester:** the copier's report on dev first (W-337i), then the api-collection against dev.

**Risks or ambiguities:**
1. **Size (§7)** — the split C6a; W-337g2 may need to split again if the P&L tree's mapping runs long.
2. **Shapes older than `m1.6.1`.** A row written by an earlier build may hold a key `m1.6.1` no longer names; the
   copier counts unknown keys per collection and stops on any (an unmapped key would be data dropped in silence).
3. **Finding #6 is from reading, not a run;** W-401's red test is what proves it.
4. **W-337f flags still open** (CHECKPOINT): `GazetteCursor` never fills `created*`, native lease acquire leaves audit
   columns null — the copier copies `audit_metadata` where the source has it, so those columns stay null as on Mongo.
