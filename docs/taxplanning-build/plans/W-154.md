refused, and how the row's amount is worked out are today chosen in Java by the item's kind, setting, use or owner.

data, not new code (audit P4, N1; D-313).

### Risks or ambiguities

1. **Q4 spans three item types.** `PERQ-SPECIFIED-EMPLOYEE` would reach household benefits (by arrangement), the
   employer's car (by owner) and children's education (always). An `AnyOf` over facts one item does not carry throws
   (`ItemFacts.code`). W-154b's plan has to choose between one gating row per item type and a common fact
   (`perquisite.provided_by_employer`) that every item publishes. The choice is stated there.
2. **Q9 is about a car's position among several.** It is a fact of the employment's cars, not of one car. W-154e
   has to publish it as an item fact (for example "another of the employer's cars precedes this one") so a row can
   condition on it. The order rule — the first entered — is today's (D-113) and is not changed.
3. **Q5's voucher fallback is "otherwise".** A voucher is valued in full only where `PERQ-MEAL-VOUCHER` does not
   apply in the regime. With conditions alone, `PERQ-MEAL` reaching vouchers too would make two rows apply in the
   old regime. W-154c chooses between an `AT_MOST_ONE` set with an ordered fallback and stating the regime on
   `PERQ-MEAL`'s voucher condition. Neither changes a figure.
4. **Nil and refusal lines may change their row.** Tea / snacks and remote food are nil lines citing `PERQ-MEAL`
   today; a telephone, `PERQ-OTHER-BENEFIT`. If those become rows of their own, the row id on the line moves, which
   C4a forbids without a D-321-style exception. The sub-plan asks before moving one.
5. **W-154e may be mis-sized on its own.** If its plan finds it over §7, it proposes e1 / e2.
