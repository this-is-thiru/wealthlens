### The question: does a data definition add anything?

What the Java decides is which arithmetic applies to which kind of share. Today that kind is chosen by **which
record the taxpayer enters**. Each record holds only the prices its method reads: an unlisted share has no opening
price to enter, and a listed traded share has no banker's value. So:

- **Moving the choice to rows**, with a `security.valuation` fact (the record's name) selecting a row whose
  definition names a method, gives a one-to-one map from record to method. No row could ever name another method for
  a record, because the record would lack that method's prices. The rows would restate the input's shape. That is
  the same law held twice, which C4a of D-325 says is to be avoided.
- **A Rule that changes the method** (for example a closing price only, or a volume-weighted price) changes what is
  entered, so it is a new or changed record and new arithmetic whichever way this is built. Data cannot absorb it.
- **What is data already**, and should be: the window of days (`PERQ-SPECIFIED-DATE`) and the perquisite's own rate
  (`PERQ-SPECIFIED-SECURITY`, 100%). Neither is in Java.

The three branches are therefore dispatch by an input shape that evaluates only the data it carries: the audit's
"not a finding" column for L3.
