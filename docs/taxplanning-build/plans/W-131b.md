## Plan for W-131b — a document's bytes: stored encrypted, within O6's limits

> **Approved as recommended — C1a – C6a** (owner, session 104, 2026-11-17). Built; review: "commit and push" (D-763). Every path:line below was read this session at `069eec4a`.
> **Probe run** (a throwaway integration test, deleted): `GridFsTemplate` is a bean in the test context; it stored 3 bytes
> under a name, read them back (length 3) and deleted them (`findOne` null after). With no bucket named, it writes to
> `fs.files` / `fs.chunks`.

**What this item is for (one sentence, in my own words):** keep an uploaded PDF's bytes outside Mongo's documents (O6), so
W-131c's job can read them and erasure and retention can remove them:
- encrypted with the application's key;
- refused on the way in when they are not a PDF, too large or too long.

### What the design and the code say

- **O6** (`14-operational-design.md:161`):
  - "Size | 20 MB per file, 50 pages";
  - "Types | PDF only at launch";
  - "Encryption | at rest with a per-tenant key; the object store is not readable without the application";
  - "Password-protected | prompt; **never persist the password**";
  - "Storage location | outside Mongo (GridFS or an object store); Mongo holds the metadata and the SHA-256".
- **O9:** "Document store unavailable | upload 503". `ServiceUnavailableException` already maps to 503
  (`shared/exception/ControllerAdviser.java:100`).
- **D-761 C2a:** GridFS, encrypted before writing.
- **The cipher:** `FieldCipher` (`shared/protection/FieldCipher.java`) seals with AES-256-GCM under the data key, a fresh
  nonce per value. Its public methods take and return **text** (`encrypt(String)`, `decrypt(String)`); the sealing
  itself (`run`) works on bytes.
- **The content:** `DocumentContent(byte[] bytes)` with `sha256()` (`documents/parser/DocumentContent.java`).
  `IngestedDocument` requires `pageCount >= 1`.
- **Passwords:** the parser already refuses a password-protected PDF: "The PDF is protected by a password: upload it without
  one" (`CertificateReading.java:59` – `:61`, iText's `BadPasswordException`).
- **Erasure and retention** go through `DocumentRemoval` (W-131a), whose `ProfileRemoval` caller is `@Transactional`.

### Findings

1. **GridFS writes may not join Mongo transactions.** This is my understanding of Spring Data's `GridFsTemplate`, **not yet
   verified**; the build's first integration case (a rolled-back erasure) settles it. If they do not, bytes deleted inside
   `ProfileRemoval`'s transaction are gone even if it rolls back, leaving a document whose bytes are lost.
2. **A crash between storing bytes and storing the document leaves bytes no document names.** The same holds for a delete
   that runs after a commit and fails.
3. **A password-protected PDF has no page count until opened**, and `IngestedDocument` needs one.
4. **Encrypting 20 MB as text** would mean Base64 (a third larger) and a 27 MB string.

### Choices for the owner (recommended first)

- **C1 — encrypting bytes:**
  - **(a)** `FieldCipher.encryptBytes(byte[])` / `decryptBytes(byte[])`, the same AES-256-GCM and key, sealing bytes
    directly (key id, nonce, ciphertext). This is a `shared` change with its own unit tests: round trip, a fresh nonce,
    tampering refused.
  - (b) Base64 through the text methods.
- **C2 — where the bytes go:**
  - **(a)** A bucket of their own, `tax_document_bytes` (`.files`, `.chunks`), through a `GridFsTemplate` built
    for it; each file named by its document id, so no reference is stored on `StoredDocument`.
  - (b) The default `fs` bucket.
- **C3 — the limits on the way in** (`DocumentBytes.store`, before anything is written):
  - **(a)**
    - PDF only: the bytes start `%PDF-`;
    - at most 20 MB (20 × 1,048,576 bytes);
    - it opens, and has 1 to 50 pages.

    A password-protected PDF is refused with the parser's own words, "upload it without one" (finding 3). The password is
    never asked for, so never persisted; O6's "prompt" becomes a later item. Each refusal is an `IllegalArgumentException`
    (400). The limits are `app.tax.documents.max-bytes` and `max-pages` in the three profile yamls, from O6.
  - (b) Java constants.
- **C4 — deleting bytes** (finding 1):
  - **(a)** `DocumentRemoval` deletes the bytes **after the transaction commits** (a transaction synchronisation), or at
    once when none is active.
  - (b) Inside the transaction.
- **C5 — bytes no document names** (finding 2):
  - **(a)** `DocumentRetention` also deletes files in `tax_document_bytes` whose name is no stored document's and that
    are older than one day (so an upload in flight is never taken). It is idempotent and runs monthly with the purge.
  - (b) Leave them.
- **C6 — the store unreachable** (O9):
  - **(a)** A failure to reach Mongo while writing or reading bytes (`DataAccessResourceFailureException`) becomes
    `ServiceUnavailableException` (503). Nothing broader is caught.
  - (b) Let it be a 500.

### Files (C1a – C6a)

- **`documents/store`:** `DocumentBytes` (`store`, `read`, `remove`), its `GridFsTemplate` bean, `DocumentSettings`
  (max bytes, max pages); `DocumentRemoval` (bytes after commit).
- **`jobs`:** `DocumentRetention` (orphans).
- **The three yamls:** `app.tax.documents.max-bytes: 20971520`, `max-pages: 50`.
- **Tests:**
  - `DocumentBytesTest` (unit, real PDFs built with iText in the test): not a PDF, 20 MB + 1 byte, 51 pages and a
    password are each refused; exactly 20 MB and 50 pages pass the checks.
  - `DocumentStoreIntegrationTest`:
    - store, then read back equal;
    - the raw chunk does not contain `%PDF-`;
    - erasure leaves no file; a rolled-back erasure leaves the file;
    - an orphan older than a day is swept, one younger kept.
  - The erasure and retention tests' fixtures gain bytes.
  - A unit test for the 503 mapping, with the template mocked to throw.
