## Plan for W-088m1 — rule sets: a node reads a set of rows, and the data says which row applies

**What this item is for (one sentence):** nodes stop naming individual rule rows. Each row belongs to a **rule set**
declared in the pack, and the set's declared selection picks the row by the existing regime applicability and
conditions. Then an alternative row (a new regime's variant, a new person-based case) is added as data with no Java
change (D-251; review E1).

**Behaviour unchanged:**
- every number, line and trace row id is the same;
- the golden cases and node tests pass untouched;
- both locks are recomputed for the new pack content.

### Design

1. **The pack:**
   - `law/rule-sets.json` declares each set: `id` (`RS-…`), `selection` (`EXACTLY_ONE` | `ALL_THAT_APPLY`), `_note`.
   - Each rule row gains `ruleSet` (the set's id), and `ruleSetPosition` where the set is ordered (`ALL_THAT_APPLY`
     keeps the trace order).
   - `RuleRow` gains `RuleSetId ruleSet` and `OptionalInt position`.
   - `RulePack` gains `Map<RuleSetId, RuleSet>`.
2. **Every row is in exactly one set.** A step with one row today is a one-row set, so a later alternative is data.
3. **Engine:**
   - `ComputationNode.rules()` becomes `ruleSets(): Set<RuleSetId>`.
   - `NodeContext.ruleSet(id)` returns the set's **applicable** rows: published, in force, in this regime, and with
     conditions that hold. It applies the declared selection:
     - `EXACTLY_ONE`: refuses none or several, naming the set, the regime and the rows;
     - `ALL_THAT_APPLY`: returns them in position order.
   - The trace still names the **row** that applied, never the set.
   - Generated `RuleSetIds` constants, as `RuleIds` are generated today; nodes reference only `RuleSetIds`.
4. **I3 becomes:** every set is declared by some node, and every row is in a set. A row no node can reach, because it
   is in an undeclared set, is reported as today.
5. **Validator:**
   - a row naming an undeclared set;
   - a set with no rows in a year's pack;
   - positions missing or repeated in an ordered set, or present in an unordered one.

1. **A third selection, `AT_MOST_ONE`.** Several nodes check whether the year holds a row at all, and an "exactly one"
   set would refuse that. It covers 11 one-year rows, the 7 salary bases and the 6 car columns, in each case where the

2. **A per-set `SelectionGround`.** Only the slab ladder chooses by conditions. Every other set chooses by regime, so
   the rebate's "not met" lines and similar traces are unchanged.
3. **`rule-sets.json` is optional at load.** The synthetic and broken fixture timelines compile byte-identically, so
   their locks keep encoding their intended defects. "Every row is in a set" is enforced by `PackValidator`, which every
   shipped pack passes through.
4. **New helpers:**
   - `NodeContext.ruleIdOf`;
   - `RulePack.membersOf`, to recognise a row by its set, never to choose one;
   - `SalaryBases.of(RuleSet, …)`, because the bases stay keyed by row so traces don't change;
   - node-local `GoverningRow`, a row's id with its governing version, so two helpers carry the id without another
     parameter;
   - `OtherSourcesNode.Lines.row` / `optionalRow`.
5. **Six helpers gained a `ctx` parameter** (`transportLimit`, `bands`, `commutedPensionShare`, `RentPaidDeduction.line`,
   `DonationDeduction.bar`, `LeaveTravelExemption.line`), and `GrossSalaryNode.added` gained the row. This adds to S1's
   list; W-088p owns it.
6. **Two of my migration bugs were caught by the unit tier and fixed:**
   - `ChapterEightNode:167` tested `Collections.disjoint(rowIds, setIds)`, which is always disjoint, so 8 Chapter VIII
     tests and 7 T5 golden cases failed;
   - `AllowanceExemption.PER_CHILD.contains(rowId)` was always false, so 5 tests failed.

   Both now go through `RulePack.membersOf`. A follow-up scan for the same mix of set ids and row ids found no other
   case.
7. **`NodeHarnessTest`'s stub node now reads its row through `RS-RATE-SLAB`,** so the test pins the new regime. The
   expected row is unchanged.
