## Plan for W-238h — a fund move with no retirement-fund history

**For:** a user asking the optimiser to move pay into the employer's NPS or superannuation contribution without
having entered the funds' history. Today the whole optimisation is refused as soon as one probe takes the
aggregate past the limit, even where the answer lies at or below it. Row `03-WORK-ITEMS.md` W-238h (W-238c
finding, D-491). Design: `03-advisory.md` A2.2 C5 (the aggregate cap, "or accept the excess as a perquisite").

### What I located (session 71)

- `EmployerContributionNode.aggregateAndAccretion` throws a plain `IllegalArgumentException` when the excess
  over the `PERQ-EMPLOYER-CONTRIBUTION` cap is above nil and no `RetirementFundHistory` is entered
  (`taxengine/node/EmployerContributionNode.java:110-116`). The accretion formula needs PC1, TP1, I and the
  balances, which only the taxpayer can enter (`RetirementFundHistory.java:6-17`).
- `Saturation.of` bisects from nil to `amount + residual` (`optimise/Saturation.java:24-36`, `Allocation.java:53-57`).
  With a residual of 8L, the first probe for superannuation is 4L and later probes pass 7.5L. Each probe is a whole
  computation (`AllocationPricing.totalIncome`), so the throw ends the optimisation. The greedy and exhaustive
  passes price candidate combinations the same way (`SalaryOptimiser.java:77-150`). Two funds, each at its own
  saturation, can cross the limit together.
- A draft keeps `EnteredFacts` whole (`taxplanning/workspace/DraftInputs.java:18`), and `EnteredFacts` carries
  `Optional<RetirementFundHistory>` (`EnteredFacts.java:125`). So a history can be entered today. No integration
  test enters one through a draft yet; step 1 adds one.
- D-491's engine cases supply a history with nothing accrued (`TaxCalculatorOptimiseTest` `NOTHING_ACCRUED`), so
  the accretion is nil. Without a history the answer ought to be the same, which gives an independent check.

### Choices (recommended first)

**C1: the approach.**
- (a) Keep the search to what the engine can price. The node throws a typed refusal,
  `FundHistoryRequiredException`, which extends `IllegalArgumentException`, so every other caller still gets a 400
  exactly as now. The optimiser catches only that type. An allocation that raises it is not priced and not
  admissible in greedy or exhaustive. In saturation it counts as "stops falling", which is monotone because a larger
  contribution only adds to the aggregate. The limit is never read or written in Java; the engine's own refusal
  marks the edge. When a history is entered, nothing is cut and the search runs over everything, including excess
  accepted as a perquisite (C5).
- (b) Ask on the way in: refuse whenever a fund is movable and no history is entered. This is simpler, but it
  blocks an NPS move that never nears the limit, for a user who has no fund statement to hand.

**C2: how the answer says so.**
- (a) `Optimisation.unpriced`, an `Optional<UnpricedNotice>` holding the facts: the input missing
  (`retirementFundHistory`) and the rule that needs it (`PERQ-EMPLOYER-ACCRETION`, from the node's rule id).
  It is present only when some allocation tried was cut. `taxplanning` passes it through unchanged.
- (b) A text notice, like `discrepancy`.

**C3: an entered history that already puts the entered pay above the limit.** No choice is needed, only a
statement of what happens. The pay as entered is priced first, unchanged, so it is refused as now with the typed
refusal's message. Nothing is cut there.

### Build steps (after approval)

1. Tests first, with expected values taken from D-491's hand figures:
   - Engine: superannuation movable with no history gives 0 → 7,50,000, bill 2,92,500 → 1,20,900, saving
     1,71,600, residual 50,000, with the notice present. The same case with `NOTHING_ACCRUED` gives the same answer
     with no notice.
   - Engine: NPS and superannuation both movable with no history gives an answer, not a refusal.
   - Engine: pay as entered already above the limit with no history is refused naming the history.
   - Node: the typed refusal is thrown where the plain one was.
   - Integration: a draft moving superannuation with no history gives 200 and the notice. A draft entering a history
     gives no notice.
2. Add the typed exception, throw it from the node, and handle it in `AllocationPricing` (price and total income,
   remembered); `admissible` skips an allocation not priced; the saturation edge. Add `UnpricedNotice` to `Optimisation`. Update javadoc,
   `02-TECH-SPEC.md` row 99 and the api-collection docs, if the example needs it.
3. Probes, each restored by `cmp`: the catch removed (refusals come back), and the saturation edge treated as
   "keeps falling" (the bisection crosses the edge).
4. Verify: targeted tests, `DraftComputationIntegrationTest`, then one detached `./mvnw clean test verify`.
5. Close-out on "commit it": board line 65, D-497, STATE, CHECKPOINT. The runbook is unchanged: no stored data,
   flag or seed.

**Numbers:** none introduced. The test figures are D-491's (TY 2026-27), with the 7,50,000 limit measured through
the pack row, never written in Java.

**Not doing:** a form to collect the history (it is already an entered fact), W-238i, W-238j, W-238k.

**Risks:** catching a typed exception inside the search could hide a real defect if any other path threw that type.
Only the node throws it, and a test pins that.

### Roles, briefly
- Architect: the engine's own refusal marks the edge, so no limit appears in Java and no new cross-module import is
  needed. The API gains one optional field.
- PM: a fund move gets an answer where it used to get a 400, and the user is told what entering the history would
  add.
- Engineer: one typed exception, one catch site, remembered with the prices.
- Automation tester: the expected values come from D-491's hand figures. Two probes.
- Manual tester: optimise a superannuation move on a draft without a history (200, notice), then with one (no
  notice).
