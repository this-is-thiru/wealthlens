## Plan for W-202 — request bodies accept unknown JSON properties silently

**What this item is for (one sentence, in my own words):** a client that sends a field the server does not have,
whether misspelled, renamed or removed, today gets a 200 with that field dropped. This item decides whether the API
answers such a request with a 400 instead, as CLAUDE.md's "Nothing silent" asks, and does it safely if so.

**Source:** `03-WORK-ITEMS.md` W-202; `plans/W-201.md` C3; D-405.

**Board (R4):** `… W-201 D  W-202 ·  W-194 · …`. W-202 is the first open item. The resume check matched: last item
commit `809f51aa` (W-201), tree clean.

### What I found (2026-10-30)

- **The behaviour, measured:** W-201's probe posted `{"filters": […]}` to `/stocks/download`. It got 200, and the
  filter was dropped (D-405).
- **Where it comes from:** Spring Boot's auto-configured JSON mapper. There is no `spring.jackson` key in the three
  profile yamls, no mapper bean, and no `@JsonIgnoreProperties` anywhere in `src/main`.
- **What a global switch would reach:**
  - **Request bodies only.** The app makes no outbound HTTP calls (`grep RestClient|RestTemplate|WebClient|HttpClient
    src/main`: none), so no third-party response would be read through it.
  - **Not the seeders.** `ChargeSeederService:101` and `PolicySeederService:56` each build their own mapper, so they are
    untouched.
- **Clients:**
  - **No UI is in this repo.** Whether a front end or another client calls this API from elsewhere is **unknown to
    me**. See C2.
  - **`api-collection`, a heuristic survey** (scratchpad script: each POST/PUT/PATCH body's top-level keys against its
    `@RequestBody` class's fields):
    - 22 requests have a body; 8 matched cleanly with no unknown key.
    - **1 sends an unknown key:** `Charges Engine/Publish a rate card.yml` → `POST /charge-schedules` →
      `ChargeScheduleEntity`, key `currency`.
    - 13 could not be matched by the script: bodies with comments or templating, and paths it does not resolve
      (`/finances/…`, `/entity-test1/…`, two corporate-action PUTs). They need a check by hand, or a run against the
      app.
- **Found beside it — the seed files do the same:**
  - All **39** shipped card files carry `"currency": "INR"`, and `ChargeScheduleEntity` has no `currency` field.
  - They seed without error, so `ChargeSeederService`'s own mapper drops unknown keys silently as well.
  - A misspelt rule field in a card file would vanish without a word. That is the same "nothing silent" fault, on the
    data side. See C3.

### Choices (recommended first)

- **C1 — the decision:**
  - **(a) recommended:** request bodies refuse an unknown property with a **400** naming it.
    1. **One setting.** `spring.jackson.deserialization.fail-on-unknown-properties: true` in `application.yaml`
       (inherited by staging and prod). This is the Spring Boot property name, but I have not yet run it on this
       Boot / Jackson 3 version; step 2 proves it before anything else.
    2. **A committed integration test**, `RequestBodyStrictnessIntegrationTest`: an unknown key → 400, with the
       message naming the key, through `ControllerAdviser`. It is shown to **fail first**, with the property off, then
       pass with it on.
    3. **`ControllerAdviser`:** it already maps `HttpMessageNotReadableException` to 400 (`ControllerAdviser:22`, with
       `IllegalArgumentException`), so the status needs no new code. What remains is the message. The test asserts
       that it names the unknown field in words a client can act on. If the raw Jackson text does not, the handler's
       message is shaped there, and no new handler is added.
    4. **The collection:** every request brought to its DTO. The 13 unmatched requests are checked by hand, and
       `Publish a rate card` loses `currency` (or C3 decides otherwise).
    5. **Both tiers green.** An integration test that posts a stale key would now fail and show itself.
  - **(b)** Stay lenient. Record the reason (D-406), and add a CLAUDE.md line saying unknown properties are ignored.
- **C2 — clients outside this repo** (your knowledge, not mine):
  - Does a front end or any other client call this API?
  - If yes, C1a needs its own field survey before release, or it may answer 400 to requests that work today.
  - **(a)** No other client, so C1a is safe.
  - **(b)** Yes, and you'll name it, so I survey it first.
  - **(c)** Yes, but unknown, so C1a ships behind a profile flag, first on staging.
- **C3 — the seed files' unknown keys** (`currency` in 39 cards; the seeder's lenient mapper):
  - **(a) recommended:** place a row, **W-203**, after W-202:
    - make `ChargeSeederService` (and `PolicySeederService`) refuse an unknown key;
    - decide `currency`: drop it from the 39 cards, or model it;
    - prove by a misspelt field.
  - **(b)** Fold it into W-202.
  - **(c)** No row.

### The five roles

- **Architect:** one framework setting, and the error mapped at the one advice class. Seeders are untouched (W-203).
- **Product manager:** a client's typo becomes a clear 400 naming the field, instead of a silently wrong result. The
  risk is any unseen client sending stale fields (C2).
- **Senior engineer:** read `ControllerAdviser`'s handling of `HttpMessageNotReadableException` before writing. The
  message must be human-readable (CLAUDE.md), not Jackson's stack text.
- **Automation tester:** the strictness test fails first, with the property off, then passes. Both tiers run in full,
  because integration tests that post raw JSON may carry stale keys.
- **Manual tester:** `POST /charges/simulate` with an extra `"foo": 1` answers 400 and names `foo`; without it, it
  answers as before.
