## Plan for W-088n — input facts, not legal bands (split proposal)

**What this item is for (one sentence):** the inputs state what the taxpayer knows: a car's engine capacity and
whether it is electric, and a city's population. The Rules' 1.6-litre column and census bands move from Java enum
values into rule data (review E2, D-250).

**This plan proposes a split (§7: mis-sized). Approving it places W-088n1 – n2 and writes W-088n1's plan. Nothing is
built.**

### What I read (session 23, 2026-10-19)

- **The two enums:**
  - **`CarEngine`** (`input/CarEngine.java`) is `UP_TO_1600_CC`, `ABOVE_1600_CC` or `ELECTRIC`. It is read as
    `EmployerVehicle.engine` (`Optional`, empty for an other automotive conveyance), and `MotorCarPerquisite:160`
    passes its name as the item fact `vehicle.engine`. Six car rows test it with `ItemFactIs` (W-088m2).
  - **`PopulationBand`** (`input/PopulationBand.java`) is `ABOVE_FORTY_LAKH`, `FIFTEEN_TO_FORTY_LAKH` or
    `ANY_OTHER_PLACE`. It is read as `EmployerAccommodation.band` and becomes a location code for
    `PERQ-ACCOM-OWNED`'s `PercentOfBaseByLocation` cap (`PerquisiteNode:137–141`).

    That shape is HRA's too (`SAL-HOUSE-RENT-ALLOWANCE`): a list of places per percentage. Here its "places" are the
    band names.
- **Sources:**
  - 1.6 litres: `DR 01` `PERQ-CAR-2026` (`01-rulebook.md:782–784`), "≤ 1.6 litres or electric vehicle | > 1.6
    litres"; the electric row's `_note` (TY 2026-27 only, D-113 C5a).
  - The bands: `PERQ-ACCOM-OWNED`'s `_note` and `plans/W-071a.md:18–21` (S4 r.15(2) Table I Sl. 2(a), p.1541; Rules
    1962 r.3(1) as substituted by G.S.R. 615(E)): "exceeding forty lakhs as per 2011 census … exceeding fifteen lakhs
    but not exceeding forty lakhs … other areas", the same in both years.
- **Who builds these inputs:** only tests. Real call sites: `MotorCarPerquisiteTest` 16, `PerquisiteNodeTest` 8,
  `NodeContextRuleSetTest` 5, `EmployerVehicleTest` 4, `EmployerAccommodationTest` 3, `SalaryHeadPipelineTest` 2,
  `InputsFingerprintTest` 1. No production adapter yet.
- **No test pins the shape's trace text** ("at ABOVE_FORTY_LAKH"); grep finds none.
- **`AllOf` stops at the first failing limb** (`rules/condition/AllOf.java:9–12`), so a limb that settles the answer
  can precede one whose fact is absent.

### Proposed split (C0)

| Row | What | Why separate |
|---|---|---|
| **W-088n1** | **The car's facts.** `ItemFacts` gains quantities; one predicate, `ItemFactAtMost(fact, limit)`, inclusive ("does not exceed"); "exceeds" is `Not(AtMost)`. `CarEngine` becomes a record of facts: `electric`, and `cubicCapacityCc`, present exactly when not electric. `MotorCarPerquisite` supplies `vehicle.electric` and `vehicle.capacitycc`. The six rows' conditions: small = `AllOf(electric is false, capacity at most 1600)`; large = `AllOf(electric is false, Not(at most 1600))`; electric = `electric is true` (TY 2026-27 only, as now). Relocked. | Condition algebra plus the car; no shape change |
| **W-088n2** | **The city's population.** `EmployerAccommodation.cityPopulation` replaces `band`. A cap shape `PercentOfBaseByPopulation(base, population, bands[{exceeding, percent}], otherwise)` holds Table I Sl. 2(a): over 40,00,000 → 10%, over 15,00,000 → 7.5%, else 5%. `PERQ-ACCOM-OWNED` takes it in place of `PercentOfBaseByLocation`. The row id is unchanged; its trace's limit text names the population and the band. `PopulationBand` is deleted. Relocked. | A new cap shape and its JSON, independent of n1 |

The values: 1600 cc is 1.6 litres (1 litre = 1000 cc). 40,00,000 and 15,00,000 are forty and fifteen lakh persons
(1 lakh = 1,00,000).

### Choices (recommended first)

- **C0 — split:**
  - **(a) recommended:** n1 then n2, replacing W-088n's position, before W-088o.
  - **(b)** one item, about 400 lines with tests.
- **C1 — quantity predicates (n1):**
  - **(a) recommended:** `ItemFactAtMost` only. The Rules say "does not exceed" and "exceeding", which are `AtMost` and
    its negation. `ItemFactAtLeast` would have no caller (CLAUDE.md §2), so the WI row's pair becomes one.
  - **(b)** both.
- **C2 — the engine's facts (n1):**
  - **(a) recommended:** `electric` plus `cubicCapacityCc`, the two facts the Table turns on.
  - **(b)** a fuel-kind enum (petrol, diesel, CNG, electric …). The law asks one of those questions; the enum would be
    a list for nobody.
- **C3 — where the population bands live (n2):**
  - **(a) recommended:** a `PercentOfBaseByPopulation` shape on the same row, so the receipt's row id is unchanged.
  - **(b)** three rows in `RS-PERQ-ACCOM` chosen by `ItemFactAtMost` on the population. This splits
    `PERQ-ACCOM-OWNED` into three ids, so receipts are not comparable.
  - **(c)** a definition row mapping a population to the existing band codes. This keeps the old shape and adds a rule
    id and an indirection.

### How W-088n1 would be verified (detail in its own plan)

- Every golden case and node test gives the same values and the same trace row ids. Only input construction changes:
  `UP_TO_1600_CC` becomes 1,500 cc; `ABOVE_1600_CC` becomes 2,000 cc.
- Boundary cases: 1,600 cc → small; 1,601 cc → large.
- The probe: the small row's limit set to 1599 → the 1,600 cc case fails.

### What I am NOT doing

- Building any of it before the split is approved.
- `CommutingCity` (review E8: accepted, the Rules' own undefined category).
- Naming the census in data. Both years' Tables say 2011; a later Table that names another census is a new version's
  note, and the stated population is "as the Table's census counts it".

### Risks or ambiguities

- **The census is part of the fact.** The taxpayer must state the 2011 figure, not today's. The input's Javadoc and
  the shape's describe will say so. If a Table ever names a different census, the input needs the census named
  alongside. Raised then, not built now.
