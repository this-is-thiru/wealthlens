## Plan for W-305 — an unreadable request body is answered with Jackson's text

**What this item is for (one sentence, in my own words):** a request body the server cannot read should be refused
with a message naming the field and what it accepts, not with the parser's own text, which shows library settings
and controller signatures (W-264b G-3, D-614).

**Findings (read this session, 2026-11-13):**

1. **The cause.** `ControllerAdviser:29 – 32` handles `HttpMessageNotReadableException` together with
   `IllegalArgumentException` and answers `ex.getMessage()`. The status is already 400 (W-263); only the wording is
   wrong. This covers every JSON route.
2. **Probe run (the core change applied, then stashed as "W-305 probe (handler)"; the tree is unchanged).** These are
   the real routes on the Testcontainers harness, with what was answered:

   | Body sent | Today (report §1) | With the change |
   |---|---|---|
   | none | "Required request body is missing: public … ChargeSimulationController.simulate(…)" | "The request body is missing" |
   | `{"price": }` | Jackson's parse text | "The request body is not valid JSON (line 1, column 11)" |
   | `{"price":"abc"}` | "JSON parse error: Cannot deserialize value of type `double` …" | "Field 'price' must be a number, but was 'abc'" |
   | `{"nope":1}` | "Unrecognized field \"nope\" …" | "Field 'nope' is not one this request accepts" |
   | `{"brokerName":"NOPE"}` | Jackson's enum text | "Field 'brokerName' must be one of [UPSTOX, FYERS, ZERODHA], but was 'NOPE'" |
   | `{"transactionDate":"2026-13-01"}` | Jackson's date text | "Field 'transactionDate' must be a date as yyyy-MM-dd, but was '2026-13-01'" |
   | `[]` to an object route | Jackson's text | "The request body must be a JSON object" (a list route says "array") |
   | `{"quantity":null}` | "… FAIL_ON_NULL_FOR_PRIMITIVES …" | "Field 'quantity' must be a number" |
   | a rule without `perLot` (`/charge-schedules`) | "… FAIL_ON_NULL_FOR_PRIMITIVES …" | "Field 'rules[0].perLot' must be true or false" |
   | V2 trade `{"quantity":"ten"}` | Jackson's text | "Field 'quantity' must be a number, but was 'ten'" |

   Reading the cause: the handler takes Jackson's exception (`ex.getCause()`), not the deepest cause. The deepest
   one for a date is Java's `DateTimeParseException`, which carries no field. The first probe took the deepest cause
   and dates fell through; that is fixed in the stash.
3. **The classes used all exist in Jackson 3.1.4** (the version in `dependency:tree`): `JacksonException` with
   `getPath()` and `Reference`; `exc.StreamReadException` with `getLocation()`; `databind.exc.InvalidFormatException`
   with `getValue()`; `MismatchedInputException` with `getTargetType()`; `UnrecognizedPropertyException`.
4. **The wording reuses W-263's `accepted(type)`** (`ControllerAdviser`, the method under "What a parameter of
   {@code type} accepts"), so a body field and a query parameter of one type read the same. One case is added:
   `double` and `Double` read "a number". Today they would read "a double", and no parameter uses them (W-263's tests
   cover `int`, `boolean`, `LocalDate`, `LocalDateTime`, an enum and `long`).
5. **One route takes a list body:** `BonusAllotmentDateCorrectionController:35` (`@RequestBody List<…>`). That is
   why the top-level wording follows the target type.
6. **Tests the change moves (probe run of all 28 classes that assert a 400: 447 tests, 1 failure):**
   `CorporateActionIntegrationTest.addCorporateAction_whenTheRequestStillCarriesDate_answers400NamingIt` (`:327`)
   expects `containsString("\"date\"")`, Jackson's quoting. It gets "Field 'date' is not one this request accepts".
   Its intent, that the message names the field, holds. The expected value becomes `"'date'"`. Nothing else moves;
   `RequestBoundEntityBindingIntegrationTest:85` asserts on the mapper directly, not on the answer.

**Choices for the owner:**
- **C1: the wording.** **C1a (recommended):** as in the table above. C1b: one fixed sentence for every case ("The
  request body could not be read"). That is simpler, but the caller cannot tell which field to fix.
- **C2: an unknown field.** **C2a (recommended):** name it only. C2b: also list the accepted fields. A V2 trade has
  about 20, which makes a long message.
- **C3: the one moved test.** **C3a (recommended):** expect `'date'` with its comment unchanged.

**Files I will modify:**
- `shared/exception/ControllerAdviser.java`: its own handler `handleUnreadableBody`, and private `unreadable`,
  `path` and `isList`; `accepted` gains "a number". The parser's full text still goes to the log (`log(ex)`).
- `ControllerAdviserTest`: a stub route with a small record body, plus one test per case of the table: missing,
  malformed, wrong type, unknown field, enum, date, null into a primitive, nested path, an array to an object route,
  and an object to a list route. Each expected message is written from the field's name and type, as W-263's are.
  Red before.
- `CallerMistakeIntegrationTest`: report §1 scenarios 4 and 15 on the real routes (`/charge-schedules` with a rule
  missing `perLot`; `/charges/simulate` with `price` "abc" and with no body). Red before.
- `CorporateActionIntegrationTest:327` (C3a).
- `STATE.md`, `CHECKPOINT.md`.

**Numbers I will use, and where each comes from:** none. Every expected value is a message.

**Design sections I read:** report §3 G-3 and §1 scenarios 4 and 15, D-614, W-263's handler (D-532), and the CLAUDE.md
line "Messages are human-readable strings, never codes".

**What I am NOT doing:**
- Other handlers' wording (405 and 415 still pass Spring's text). If you want them reworded, I will place a row.
- `accepted` for `long` (reads "a long"); W-263's test pins it.
- W-306 and the rest.

**How I will verify:** red first on the new tests, by building them before the handler is restored from the stash.
Probe: put `ex.getMessage()` back in the new handler, and the new tests fail; then restore byte-identical. Locally,
the same 28 classes and `validate`. The tiers run on the pipeline.

**Post-deployment actions (R15):** none. There is no stored data and no flag.

**Five roles:**
- **Architect:** one handler in `shared`, no module change. The parser stays the guard that refuses (strict binding,
  `fail-on-unknown-properties`); only the answer changes.
- **Product manager:** every JSON route answers a bad body with the field and what it accepts. Status codes and API
  shapes don't change. The api-collection has no bad-body examples.
- **Senior engineer:** reuses `accepted`; no new type; nothing swallowed; the full cause is still logged.
- **Automation tester:** expected messages written from names and types, red first, one probe, 28 classes re-run.
- **Manual tester:** `curl -X POST …/charges/simulate -H 'Content-Type: application/json' -d '{"price":"abc"}'` with a
  token gives 400 "Field 'price' must be a number, but was 'abc'". With no `-d` it gives "The request body is
  missing". Edge cases: an empty body, `null` as the body, a nested list index, an unknown enum constant.

**Risks or ambiguities:**
- A Jackson failure outside the cases above answers "The request body could not be read". That is human-readable but
  general, and the log keeps the detail.
- "but was '…'" echoes the caller's own value back to them. It is the caller's own input, as in W-263's parameter
  messages.
