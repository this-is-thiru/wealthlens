**The user-visible history is preserved elsewhere, and is a different thing.** §2.6 moves the P&L's stored
`short_term_capital_gains` / `long_term_capital_gains` pair into its split rather than discarding it
(`post-deployment-runbook.md:571-586`) — that is the term-shaped figure a user saw. The per-trade label was internal:
no response ever carried it as a trade-level value, and the P&L exposed the aggregate, not the rows.

**The standard W-194 just set.** An audit record of a term is a decision recorded against the rule row and the pack
that made it, inside the computation (D-410). A bare `LONG_TERM` with a free-text reason on a trade is not that: it
cannot say which provision decided it, under which year's law, or in which computation.

**§2.5 already saves the values before deleting them.** Step 3 `mongoexport`s both fields to
`trade_outcomes-stored-terms-backup.json`; step 5's "way back" imports it.

### Choices (recommended first)

- **C1 — what happens to the labels:**
  - **(a) recommended: remove them, as §2.5 says, and make the backup file the history.** The values are a label
    from a law copy this repository is deleting, with no rule, pack or year — not an audit record (D-410), and not the
    figure a user ever saw (§2.6 preserves that). §2.5's step-3 file already holds every value; the runbook gains one
    sentence that the file is kept with the deploy record rather than treated as transient. No code, no new
    operation; W-168 and WL-35 unchanged.
  - **(b) keep them in place.** §2.5 is withdrawn and W-168 cannot ever be run (its removal would strand the data it
    was written for), so the endpoint and its integration test become standing code; the entity maps neither field, so
    "keeping" means a DBA can read them and the application cannot. The cost is permanent: live documents carry fields
    no code maps or writes, every export and backup carries them, and a later reader can mistake them for what the
    product decides today — while the values may be *wrong*, being the output of the duplicate law.
  - **(c) move them into a history subdocument, then unset the fields.** A migration copies both into a named place
    (e.g. `legacy_term_history: {capital_gains_type, classification_reason, copied_at, by}`) and §2.5 becomes that
    operation. History stays queryable and the active schema stays clean. Cost: a build (migration, endpoint, tests,
    runbook entry, W-168 rewritten) that preserves a possibly wrong label under a name that says so — the same
    question W-194 answered differently for the future, where the record carries its rule and pack.
- **C2 — if the answer is (a), the backup file:** the only choice is whether the runbook names it as something to
  keep. Recommended: yes, one sentence — otherwise the history exists only until someone clears the working directory.
