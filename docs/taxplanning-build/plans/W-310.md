## Plan for W-310 — a save that loses a race can be told the draft is unchanged

**What this item is for (one sentence, in my own words):** when two saves of one draft race at the same revision,
the loser should get the 409 that the design promises, naming the path both changed. Today, if the winner has not
committed yet, the loser is told "This draft has moved on to revision 0" with no conflicting path (D-620).

**Findings (read this session, 2026-11-13):**

1. **The contract.** Two concurrent `PATCH`es at one `If-Match` give "first 200, second **409** with
   `conflictingPaths`" (`11-filing-drafts.md:342`, T11-2). F5 says the client merges paths that do not overlap and
   asks only on a real collision (`:195 – 206`), so a `[]` from a race tells it, wrongly, that nothing overlaps.
2. **The path the loser takes.** `DraftService.patch` checks the revision (`DraftService:141 – 143`), then inserts
   the next revision (`:153`) under the unique key `{draft_id, revision_number}` (`DraftRevision:22`). The loser's
   insert fails. `DraftController:73 – 75` catches `DataIntegrityViolationException` and calls `conflictAfterRace`
   (`DraftService:238 – 241`), which reads the draft again in a new transaction.
3. **Why it can read revision 0.** The winner's insert is still uncommitted, so Mongo answers the loser with a
   write conflict, not a duplicate key. Spring Data MongoDB 5.1.0 turns a `MongoWriteException` that is not a
   duplicate key into a `DataIntegrityViolationException` (`MongoExceptionTranslator`, bytecode offset 280, read with
   `javap` this session), so the catch takes it. The read then runs before the winner commits, sees revision 0 and no
   later change set, and `stale` (`:243 – 252`) finds no overlap. This is read from code and bytecode. **Not yet
   reproduced:** the first step of the build reproduces it on purpose (C4).
4. **Seen once:** run 43363887553 attempt 1 (`9a08c25a`). Attempt 2 passed, and it was not in the six earlier failed
   runs, whose failures were the concurrent-buy tests (annotations read this session).
5. **An existing pattern.** `TradeCollisionRetry` (`portfolio/service`, W-269) runs a trade again outside its
   transaction when it collides, with Spring's `RetryTemplate` and a bounded policy (`:25 – 31`). It is
   trade-specific: its predicate looks only for `TransientTransactionError`, and its exhausted answer is
   `TradeCollisionException` ("…trade… not recorded").

**Choices for the owner:**

- **C1 — how the losing save is answered.**
  - **C1a (recommended):** run the save again when it collides, outside its transaction, with a new
    `DraftSaveRetry` (`taxplanning.workspace`). A re-run either sees the winner committed, and `patch`'s own revision
    check gives the real 409 with paths, or sees the winner aborted and applies, since its base is then current. That
    is the right answer both ways. The controller calls `DraftSaveRetry.patch` in place of `DraftService.patch`.
  - **C1b:** keep one attempt and have `conflictAfterRace` wait until the revision moves on. That is polling, and
    if the winner aborted it waits for nothing and then reports a conflict that never happened.
- **C2 — when every attempt collides** (the winner is held past the retry window).
  - **C2a (recommended):** 409 with the draft as last read and the message "Another save of this draft had not
    finished; read the draft and send again", never "moved on to revision N" for a revision that has not moved. The
    client re-reads; a resend at its base gets a true answer.
  - **C2b:** 503. The F5 client has no 503 path, and the save is a conflict, not an outage.
- **C3 — what counts as a collision.**
  - **C3a (recommended):** a `DataIntegrityViolationException`, which is what the controller catches today. That
    covers both the write conflict and a duplicate key against a committed winner, and a re-run of either lands in
    `patch`'s revision check. The aborted attempt wrote nothing, because the transaction rolled back.
  - **C3b:** only a failure labelled `TransientTransactionError`, as `TradeCollisionRetry` does. Then a duplicate
    key still takes the re-read path, which is correct there but means two paths to keep.
- **C4 — the tests.**
  - **C4a (recommended):** a deterministic race in `DraftIntegrationTest`. A thread holds a winning
    `DraftService.patch` open inside a `TransactionTemplate` on the `MongoTransactionManager`; `patch` is
    `@Transactional`, so it joins that transaction. The loser then `PATCH`es at `rev-0` over HTTP.
    - `patch_whenTheWinningSaveCommitsDuringTheRetry_namesTheConflictingPath`: the winner is released 100 ms after
      the loser is sent. Expected: 409, `"conflictingPaths":["/entered/employments/-"]`, "moved on to revision 1",
      two revisions stored. Red before: today the loser answers at once, with "revision 0" and `[]`.
    - `patch_whenTheWinningSaveOutlastsEveryRetry_saysItHadNotFinished`: the winner is released only after the
      loser has answered. Expected: 409 with C2a's message.

    Unit: `DraftSaveRetryTest`, covering a collision retried and then won, a collision on every attempt giving C2a,
    and any other failure (`BadRequestException`, `DraftConflictException`) thrown at once without retry. T11-2's
    test stays as it is.

**Numbers I will use, and where each comes from:** no legal figure. The retry policy copies `TradeCollisionRetry:25
– 31`: 5 re-runs, 20 ms doubling to at most 500 ms, 10 ms jitter, which is 620 ms at most. That is a choice, not a
sourced figure, as W-269 said of its own. The test's 100 ms release falls inside that window.

**Design sections I read:** `11-filing-drafts.md` F5 (`:193 – 219`) and T11-2 (`:342`); D-620.

**What I am NOT doing:**
- Not merging `TradeCollisionRetry` and `DraftSaveRetry` into one shared class. They differ in predicate and answer,
  and moving portfolio's class is a refactor beyond this item. Proposed only, if you want it.
- Not changing the 409 body shape (`serverChangeSets[]` and the rest of F5's body are out of scope).

**How I will verify:**

  `DraftServiceTest`; the unit tests in `taxplanning/workspace` are the binding tests and `JsonPatchApplierTest`.
- Red before: both C4a tests against today's code, and the unit tests against a `DraftSaveRetry` with no retry.
- Probe: set the policy to 0 re-runs → the commit-during-retry test fails, then restore byte-identical.
- `./mvnw validate`. Tiers on the pipeline.

**Post-deployment actions (R15):** none. No stored data, flag or index changes; the only change is the answer a
losing save gets.

**Five roles:**
1. **Architect:** the retry sits outside `DraftService`'s class-level `@Transactional`, so each attempt is its own
   transaction (as W-269). No new cross-module import.
2. **Product manager:** a user saving from two tabs is told the truth: which field collided, or that the other
   save had not finished. They are never told the draft is unchanged when it is not.
3. **Senior engineer:** one path for both race outcomes (C3a). Attempts are bounded, so a stuck winner cannot hold
   a request open for more than about 620 ms.
4. **Automation tester:** C4a replaces timing luck with a held transaction, so the race is the same on every run;
   both tests are shown red before the fix.
5. **Manual tester:** nothing to click through, since two simultaneous saves cannot be timed by hand. The C4a tests
   are the manual check.

**Risks or ambiguities:**
- *Unverified until C4a runs:* that Mongo answers the loser's insert with an immediate write conflict rather than
  blocking until the winner ends. If it blocks, the cause in finding 3 is wrong, and I stop and re-plan (R13).
- A re-run applying the loser's patch after an aborted winner is new behaviour. It is the F5 rule (the base is
  current), but no test covers it today. C4a does not hold a winner that aborts; say if you want a third test.
