## Plan for W-303 — exit load on the redemption value

**What this item is for (one sentence, in my own words):** a fund redeemed inside its exit-load window should be
charged the load on what the redeemed units fetch, not on what they cost. Today 40 units redeemed at ₹110 from a
₹100 lot pay ₹40.00, where the PRD's rule gives ₹44.00 (W-264b G-2, D-612).

**Findings (read this session, 2026-11-13):**

1. **The rule:**
   - `docs/charges-engine/prd.md:89`: exit load is a "% of redemption value, **conditional on holding period**".
   - `SlabChargeCalculator:18 – 19`: it "charges a percentage *of the redemption*".
2. **The cause is one line.** `ChargeEngine.lotContext` restates each lot's turnover as
   `lot.quantity() * lot.price()` (`:409`) and gives the lot context the lot's price (`:421`). The lot price is its
   **buy** price: the V2 path builds `new LotSlice(buy.quantity(), buy.date(), buy.price())`
   (`ChargeRecordingGatewayImpl:145`), and `/simulate` takes the same shape (`ChargeSimulationRequest:86`). The method's
   Javadoc states the wrong rule: "Turnover is restated from the lot's own quantity and price" (`:397 – 402`).
3. **Who reads `LotSlice.price` today:**
   - `ChargeEngine:409, 421` (the defect).
   - `ChargeSimulationService:114` (refuses a negative one).
   - Construction in the gateway, the tests and `ChargeGoldenFileTest:210`.

   After the fix, only that validation reads it.
4. **Existing tests the fix moves.** The sale context in `ChargeEngineTest` is 100 units at ₹1,000, turnover
   ₹1,00,000 (`:1172, :1177`).
   - `compute_whenRuleIsPerLot_emitsOneLinePerLot` passes lots 100 @ 900 and 50 @ 1,000. It asserts
     `900 + 500 = 1,400` (`:478`), which is 1 % of each lot's **cost**. On the redemption value it is
     1 % × 150 × ₹1,000 = **₹1,500**. That expected value is the defect written down, so it changes (C3).
   - Every other per-lot test passes lots priced at the sale price, so it is unchanged: `:493 – 500` gives 500,
     `:675` gives 500, and `:702` uses the principal basis. The same holds for the golden files, whose lots are at
     ₹100 on a ₹100 sale (`zerodha-mutual-fund-sell-*.json`), and for `ChargesIntegrationTest:328, 350`.
   - *Unverified until the build:* `ChargeFormulaEvaluatorTest:196` (a lot @ 900). It tests the evaluator, not
     `lotContext`, so I expect it unchanged, and I will report it either way.
5. **Stored rows.** `user_charges` keeps each sale's `turnover` and its lines, with `base_amount` and `amount`
   (`UserChargeEntity:129`, `ChargeLine:44, 48`). A stored exit load computed on cost cannot be recomputed from the
   row alone. The 2026-10-27 run log shows prod with `user_charges` 0 and staging with 328 rows. *Unknown:* how many
   carry an exit load today.

**Choices for the owner:**

- **C1 — what a lot's turnover is.**
  - **C1a (recommended):** the lot's quantity × the **sale** price. The lot context's `price` becomes the sale price
    too, so a formula reading `#price` inside a lot sees what the units fetched. Holding days still come from the
    lot. This is a one-method change in `ChargeEngine.lotContext`, and it covers V2 and `/simulate` together.
  - C1b: the gateway builds lots at the sale price. That fixes V2 only, and leaves `/simulate` and
    `lotContext`'s rule wrong.
- **C2 — `LotSlice.price`, which after C1a no charge reads.**
  - **C2a (recommended):** keep it as the lot's **acquisition price**, a fact about the lot ("facts, not rules"),
    and say so in the record's Javadoc. Removing it would break every `/simulate` caller that sends it, because
    `fail-on-unknown-properties: true` (`application.yaml:16`). It would also touch four golden files and about 25
    test constructions, for no behaviour change.
  - C2b: remove it. That is a breaking API change, with the api-collection request, the golden files and the tests
    updated.
- **C3 — the existing expected value that encodes the defect.** **C3a (recommended):** change
  `compute_whenRuleIsPerLot_emitsOneLinePerLot` from ₹1,400 to ₹1,500, with the hand computation in its comment.
  This is the one expected value that moves. It moves because the rule changes by your decision, not to make a
  build pass (R3).
- **C4 — stored exit loads.**
  - **C4a (recommended):** a read-only runbook count (§3.20) of `user_charges` rows per database whose
    `amount_by_code.EXIT_LOAD` is above zero. If it finds any, a correction row is placed with its own plan,
    because no recompute route exists (CE-4). No write now.
  - C4b: no runbook entry.

- **Who:** the owner, with `mongosh`.

**Five roles:**
- **Architect:** the rule lives in one place, the engine's per-lot context, so the trade path and `/simulate`
  cannot disagree. The lot keeps its cost as a fact.
- **Product manager:** a fund redeemed above cost pays the exit load the fund house charges on the redemption, not
  less, and one redeemed below cost no longer pays too much.
- **Senior engineer:** one method changes, and one expected value moves, with the reason stated.
- **Automation tester:** red first at both tiers, a probe, every per-lot test re-run, and the golden files
  unchanged.
- **Manual tester:** buy 40 units of PARAGPARIKHFLEXICAP at ₹100, redeem at ₹110 inside a year, and read
  `/user-charges/user/{email}`. EXIT_LOAD shows ₹44.00.

**Risks or ambiguities:**

  the trade as entered.
- C4: until §3.20 runs, the number of stored rows charged on cost is unknown.
