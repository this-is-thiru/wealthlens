## Plan for W-401 — encrypt the audit emails inside corporate-action JSON copies

> Planned in session 122 (2026-11-25), placed by D-953 C5a, before W-337g2. **Stop point (Stage 2 EXPLAIN):** nothing is
> built until the owner answers C1 – C2.

**What this item is for (one sentence, in my own words):** the corporate-action copies kept as JSON on `assets`,
`transactions` and `trade_outcomes` store the admin's email in clear since W-337e; store `createdBy` / `updatedBy`
encrypted in the same searchable form MongoDB held (W-341), so no personal data sits in clear and W-337g2 can copy
MongoDB's ciphertext into those columns as it is.

### Findings from probing before planning (`probe-before-plan.md`)

1. **Confirmed by a run, not only by reading.** A throwaway test (deleted) put a copy with `createdBy = admin@example.com`
   through `CorporateActionListConverter` and printed the column:
   `[{…,"auditMetadata":{"createdAt":"2026-01-01T00:00:00","createdBy":"admin@example.com",…},…}]`; reading it back gave
   `admin@example.com`. Jackson ignores `AuditColumns`' `@Convert(converter = SearchableColumn.class)`
   (`AuditColumns.java:24-31`), and `CorporateActionListConverter` (`CorporateActionListConverter.java:18-31`) adds nothing.
2. **The only gap of its kind.** At `m1.6.1` three embedded (not `@Document`) types carried encrypted fields: `PolicyDetails`
   (now a JPA child table, every field `@Convert(converter = EncryptedColumn.class)`, `PolicyDetails.java:15-58`),
   `AssetRequest` (encrypted by `AssetRequestConverter`, `AssetRequestConverter.java:39-41`) and `AuditMetadata` —
   embedded only in these corporate-action copies. So W-401 closes the last one.
3. **Where copies come from.** `CorporateActionService.java:255, 264, 352, 408, 490, 529`, `LotLedger.java:92`
   (`TJsonMapper.copy` of the `corporate_action` row, audit included), `TradeMatchingService.java:265`,
   `AssetsRebuild.java:166`. Nothing reads a copy's audit fields back (`getAuditMetadata()` in `portfolio` / `corporate`
   reads only the lot's own, `AssetsRebuild.java:167-168`), so the change is in storage only.
4. **No test pins the plaintext form:** no test names `CorporateActionListConverter` or `corporate_actions`, and none reads
   a copy's audit fields (grep over `src/test`).
5. **The pattern exists:** `AssetRequestConverter` — a Spring `@Component` converter (Hibernate asks Spring for it,
   `PostgresJpaConfig`'s `SpringBeanContainer`) with its own `JsonMapper`, encrypting the two identifiers with
   `FieldCipher.encryptSearchable` on a copy before writing and decrypting after reading.

### Decisions (for approval with this plan)

- **C1 — what the copies keep.** **C1a (recommended):** keep the audit fields, `createdBy` / `updatedBy` written with
  `encryptSearchable` — the form `m1.6.1`'s `SearchableIdentifier` gave them, so W-337g2 copies MongoDB's values unchanged.
  **C1b:** drop the audit fields from the copies — loses what W-341 chose to keep, and the copier would drop MongoDB's; not
  recommended.
- **C2 — how.** **C2a (recommended):** `CorporateActionListConverter` becomes a `@Component` taking `FieldCipher`, like
  `AssetRequestConverter`: it serializes the list, then replaces each entry's `auditMetadata.createdBy` / `updatedBy` in the
  JSON tree (the entities in memory are never changed), and on read decrypts them in the tree before binding. It stops
  extending `JsonColumnConverter`, whose mapper is private, and keeps its `null`-reads-as-empty-list behaviour.
  **C2b:** add a hook to `JsonColumnConverter` for every subclass — a generality with one user; not recommended.
