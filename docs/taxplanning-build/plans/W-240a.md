### Choices (recommended first)

**C1 — test shape.** **(a) Recommended:** one test class per record (`<Record>Test`, the repo's convention). Each
class has one `@Test` for an accepted baseline, and one `@ParameterizedTest` over a `@MethodSource` of named cases.
Each case is a `ThrowingCallable` that builds the record with **one** field made bad, plus the expected message
fragment. One method per record keeps it to about 300 lines across 13 files. The two existing classes gain that
method. (b) One `@Test` per refusal, as the existing classes do. That is about 75 methods and well past §7.

**C2 — the gate.** **(a) Recommended:** set `check-taxengine`'s BRANCH minimum (`pom.xml:295-325`, now 0.81) to
the measured figure after this item, floored to two decimals.

- **Each refusal:** the expected message fragment is taken from the record's own contract text at the line in the
  table (for example "Vehicle amounts may not be negative", `EmployerVehicle.java:75`), and the bad field is chosen

### Five roles

- **Architect:** test code and one build number. No module or dependency changes.
- **Product manager:** no user-visible change. The malformed-input refusals a client can hit through the draft
  patch are now proven.
- **Senior engineer:** one parameterised method per record, so there is no copy-paste per refusal. Names follow
  `construct_whenOneFieldIsBad_isRefusedNamingIt`.
- **Automation tester:** one case per operand, messages from the contract, and two probes. Before the full run, I
  grep for existing `<Record>Test` names to avoid duplicates.
- **Manual tester:** nothing to run by hand. The JaCoCo HTML for `taxengine.input` shows the `Employ*` rows at or
  near 100 %.

**Risks or ambiguities I noticed:** a refusal reached through an `||` whose earlier operand already throws counts
only when each operand is true alone. Cases are built to isolate one operand each, and the report will list any
branch still missed, with its line.
