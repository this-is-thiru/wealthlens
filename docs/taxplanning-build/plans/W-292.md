## Plan for W-292 — a transaction and a lot record the segment they were traded in

**What this item is for (one sentence, in my own words):** the request knows whether a trade was delivery or intraday,
but the stored transaction and lot drop it and fall back to `DELIVERY`. Every reader of those stores (lots, the
trade-outcome rebuild, the tax side's venues) then treats an intraday trade as delivery (D-585).

**Findings (read this session, 2026-11-12):**

1. **Neither conversion copies `segment`.** `AssetRequest.asTransaction` (`:95 – 122`) and `asAsset` (`:127 – 150`)
   set every other field. They skip `segment` (`:65`, default `DELIVERY`), so both entities keep their own default
   (`TransactionEntity:71`, `AssetEntity:76`). The callers are V1 and V2 buys (`PortfolioService:406`, `:431`), the
   transaction saves (`TransactionService:91`, `:122`) and the temporaries (`TemporaryTransactionService:51`).
2. **What it reaches today:**
   - Every live outcome row gets `buy_segment` from the lot: V2 `TradeOutcomeRecorder:196`, V1 `PortfolioService:698`.
     So it says `DELIVERY` for an intraday buy. The sale side comes from the request and is right.
   - The `trade_outcomes` rebuild (§2.2) takes both venues from the transactions (`TradeMatchingService:112`, `:211`).
     A rebuild therefore turns a correct intraday `sell_segment` into `DELIVERY`.
   - The tax side reads these venues (`CapitalGainsAdapter:97`; `CapitalGainsStt:72`, `CapitalGainsScope:52`).
   - The replay builds lots from transactions (`LotLedger.lotOf`, `:174`). It copies no segment, which matches live
     today.
3. **A related gap that W-292's row does not name:** the row-level `segment` on `trade_outcomes` is the value P&L
   files a sale under (`ProfitAndLossService.foldSale:397`, null → `DELIVERY` at `:431`). V2 sets it from the request
   (`TradeOutcomeRecorder:143`). V1's row (`PortfolioService:654`) and the rebuilt row (`TradeMatchingService:234`)
   never set it. So a V1 intraday sale, or any sale after §2.2 → §2.11, lands in the P&L under delivery.
4. **Runbook §3.15 (W-280) cannot match anything.** It looks for transactions with `segment: "INTRADAY"`, and none is
   stored that way. Stored data cannot recover a V1 intraday buy made before W-280 either: its `user_charges` row was
   priced as `DELIVERY` too. That is unknown, and it stays reported as unknown.
5. **V1's same-day merge ignores segment** (`PortfolioService:381`). An intraday buy and a delivery buy of one stock
   on one day are merged into one lot. Once lots carry a segment, the merged lot carries the first buy's.

**Choices for the owner:**

  - **C1a (recommended):** this item copies `segment` in `asTransaction`, `asAsset` and `LotLedger.lotOf`, as its row
    says. Finding 3 is placed as **W-295** (an outcome row records its sale's segment, V1 and rebuilt). Finding 5 is
    placed as **W-296** (V1 does not merge buys of different segments).
  - C1b: finding 3 is built here too; W-296 is placed.
- **C2 — data already stored.**
  - **C2a (recommended, the row as written):**
    - **§3.18 (read-only):** a count, per user, of transactions whose `user_charges` row says a different segment.
    - **§3.15:** its note is corrected to say it matched nothing before W-292 and still matches nothing for trades
      stored before it.
    - The correction (set `transactions.segment` from `user_charges`, then §2.12 → §2.2 → §2.11 per user) is placed
      as **W-297**, after W-295. Until W-295, §2.2 → §2.11 would still file those sales under delivery.
  - C2b: write that correction here as §2.14 (one-time, `mongosh`, backup, removal ticket). The per-user rebuilds
    wait for W-295.
