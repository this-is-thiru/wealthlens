## Plan for W-113 — the refund or payable forecast (F29)

**What this item is for (one sentence, in my own words):** answer "will I get money back after filing, or do I owe
now, and by when?" for a draft, as three separate figures (the year's liability, what the employer deducts, other
credits) and their difference, served at `GET /tax/user/{email}/drafts/{draftId}/forecast`.

**Design sections I read:** `01-PRD.md:190` (F29.1 – F29.5); `20-product-gaps.md` F29 (lines 31 – 66);
`23-architecture-consolidation.md` A6 (227 – 297) and A10 (419 – 435); `01-rulebook.md:1482` (`TDS-PROJ-001`);
`02-TECH-SPEC.md:366` (the route).

**What the code has (read this session):**
- `FilingPosition` (`taxengine/result/FilingPosition.java:36`) is `(basedOn, asOf, netPayable)`. **Nothing builds
  one.** `PipelineRunner.java:49` only names it in a comment.
- `ComputedTax` (`taxengine/api/ComputedTax.java:28`) already carries `bill`, `credits`, `advanceTax` (instalments
  with `dueOn` and `stillOwed`, `:61`), `interestAndFees`, `interestOnRefund` and `finalAmount` ("above nil payable,
  below nil refundable", `:22`).
- Tax at source is **one total**: `FilingFacts.taxAtSource` and `DraftInputs.Filing.taxAtSource`
  (`workspace/DraftInputs.java:59`). `CreditsNode` credits it with advance tax and self-assessment tax.
- **F12, the employer TDS projection (`TDS-PROJ-001`), is Tier Next** (`01-PRD.md:268`) and has no backlog row
  that builds it. F29's `employerWillDeduct` (DR 20 F29) presumes it.
- `ComputedTax.Step` (`:76`) has no amount, so a ranking by money cannot be built from the public trace.
  `ScenarioDiff`, the design's source for drivers, does not exist (`grep -rn ScenarioDiff` → one Javadoc mention in
  `TraceLine.java`).

**Choices for the owner:**
- **C1: what the employer deducts (F29.1).** No projection exists.
  - **C1a (recommended):** the draft states it. `DraftInputs.Filing` gets an optional `ofWhichByEmployer` (`Money`,
    null = not stated), the part of `taxAtSource` the employer deducts for the full year (from the payslip's
    projection, or Form 16 once issued). The engine is unchanged: `taxAtSource` stays the total it credits. If it
    is more than `taxAtSource`, the request gets a 400. If it is absent, the forecast shows the employer figure as
    "not stated" and counts all tax at source under other credits. This is backward compatible: no stored draft
    has the field, so no migration and no runbook entry.
  - C1b: build a coarse `TDS-PROJ-001` projection here. That is F12 brought forward, with the `TDS-SAL-*` law to
    read, and too large for one item.
  - C1c: leave the employer figure out. That fails F29.1.
- **C2: where the numbers come from (F29.5, A10).**
  - **C2a (recommended):** run the draft's computation on each GET, as `compare` does (`DraftComputationService.java:90`),
    store nothing, and read the figures off `ComputedTax`. This meets F29.4 (it recomputes on every input change
    and on the portfolio's `asOf`). There is no `tax_projections` collection, so erasure, retention and
    `cleanDatabase` need nothing. The cost is a full pipeline run per view, which F29.5 and A10 wanted to avoid. I'd
    add a forecast case to the W-143 benchmark profile. Errata on F29.5 and A10 would record this, and say that
    `FilingPosition` still has no builder.
  - C2b: materialise in `tax_projections` keyed `{draft_id, FORECAST}` and rebuild it on read when its revision or
    `asOf` day is stale (A10). That means a new collection, plus the `TaxAccountErasure` (`erasure/TaxAccountErasure.java:59`),
    `DraftRemoval` and `cleanDatabase` lines for it.
- **C3: which regime.**
  - **C3a (recommended):** the draft's `regimeElection` (`workspace/FilingDraft.java:52`) when set, otherwise the
    year's default (`taxCalculator.defaultRegime`). The response names the regime it used.
  - C3b: a required `?regime=` parameter, as `compute` takes it.
- **C4: the top three drivers (F29.3).** The design draws them from the diff between the employer's view and the
  return, and that diff needs F12.
  - **C4a (recommended):** defer F29.3 to a placed row **W-113a**, after F12. Its plan states which diff it ranks.
    The forecast states that drivers are not yet given. A ranking by the largest trace lines would put the slab
    rule first on every draft, and that explains nothing.
  - C4b: rank the forecast's own rule-carrying rows by amount: each `interestAndFees` row, plus the regime gap from
    `compareRegimes` when the other regime is cheaper.
  - C4c: add an amount to `ComputedTax.Step` and rank the trace by |out − in| (a taxengine API change).
- **C5: "payable now — by when" (F29.2).** If `finalAmount > 0`, the response gives the earliest advance-tax
  instalment on or after `asOf` with `stillOwed > 0` (its date comes from the pack's rule data, not a constant).
  If there is none, it gives the return's due date (`FilingFacts.dueDate`). If `finalAmount ≤ 0`, the response
  says "refund after filing" with no date, and shows the `interestOnRefund` rows separately.

**Numbers I will use, and where each comes from:** none of my own. Every figure is a field of `ComputedTax`, and
the instalment dates are the pack's. The identity
`liability − byEmployer − otherCredits = finalAmount` is asserted in a test.

**Worked case (by hand, for the tests):** take a bill of ₹87,750 with no interest (`plans/W-089.md` T13-1's
bill). Tax at source is ₹1,00,000, of which the employer deducts ₹90,000, and no advance tax was paid.
Liability = ₹87,750; employer = ₹90,000; other credits = ₹10,000; net = 87,750 − 90,000 − 10,000 = −₹12,250, so
the outcome is **refund after filing, ₹12,250**. If the employer figure is not stated, the response gives employer
"not stated" and other credits ₹1,00,000, and the net is the same.

**Roles:**
- **Architect:** the change stays inside `taxplanning` (compute and workspace). taxengine is untouched under C1a,
  C2a and C4a, and no new module dependency is added. Facts, not rules: the employer's figure is an entered fact,
  and the dates come from rule data.
- **PM:** this adds one new GET. Existing drafts and clients are unaffected. Before F12, the employer figure is
  only as good as what the user enters, and the response says that.
- **Senior engineer:** the forecast reuses the assembler and calculator. It is read-only, so it uses

- **Automation tester:** the tests cover the identity, all three outcomes, the next-unpaid-instalment date, the
  return due date when no instalment is owed, a 400 when the employer figure is over the total, the
  missing-employer case, a 400 for a draft not yet given a due date, and a 404 for a draft owned by someone else.
- **Manual tester:** an api-collection run on a seeded draft, once for a refund and once for a payable case,
  comparing the result by hand against `/compute`'s `finalAmount`.
