## Plan for W-118 — the claim playbook: each claim in a draft, how to make it, and what it is worth

> **Approved as recommended — C1a, C2a, C3a, C4a, C5a; the reason sentence adopted** (owner, session 97, 2026-11-14).
> Written ahead by the planning session for a later build session; not yet built. Build
> order: after W-117b (its `covers`, C1a, decides which trace lines an entry answers for). Every path and name below was
> read on 2026-11-14 at `d44536db`; grep each again before relying on it.

**What this item is for (one sentence, in my own words):** `GET /tax/user/{email}/drafts/{draftId}/claims` — for every
claim the draft's computation allows, the catalogue's playbook (what it is, the steps with real dates, whom to ask,
evidence, mistakes, what its absence from Form 16 means) and the tax it is worth, measured by a second run.

**Probe (2026-11-14; code and design read, no code run):**
- **Nothing reads the catalogue at run time.** `JsonPackAssembler` (`taxengine/rules/json/JsonPackAssembler.java:58-74`)
  parses `content/explanations.json` only; `RulePack` has no catalogue. `taxplanning` sees the engine only through its
  named interfaces (`api`, `input`, `result`, `money`, `id`), so the playbook must leave the engine as `taxengine.api`
  types, as `ComputedTax` and `DeductionRoom` do.
- **The compiled entry is not self-sufficient.** It names its `section`, but `content/sections/` is never compiled into
  a year's pack (`Timeline.sections`, D-060), and its texts hold `{{RULE-ID.field}}` placeholders whose values live in
  rule JSON the pack parses into typed definitions (no by-name access).
- **No Form 16 data exists** in any module (one Javadoc mention, `taxengine/input/RetirementEntry.java`). `DR 22` C3
  wants the verdict "next to every claim the reconciliation found in the computation but not in the document"; there
  is no document to reconcile against yet.
- **How a claim shows in a computation:** `ComputedTax.trace` is a list of `Step(sequence, node, rule, kind, limitedBy,
  in, out, explanation)` (`taxengine/api/ComputedTax.java`); a claim is present where a step's `rule` is an entry's lead
  or covered rule and its `out` is above nil.
- **Measured worth exists for adding, not for removing.** `DeductionRoomPricing` and `RentRoomPricing`
  (`taxengine/optimise/`) run the pipeline again with inputs filled in. Nothing runs it with a claim taken out.
- **One place decides whether a rule applies in a run:** `NodeContext.inRegime(rule, version)`
  (`taxengine/pipeline/NodeContext.java:383`), returning a sealed `RegimeVerdict` (`Applies`, `ExcludedByRow`,
  `Disallowed`). 20 of the 76 classes in `taxengine/node` call it. **Not established:** that every catalogue rule's
  line goes through it — that is the build's first step, below.
- **Dates for steps:** `DraftCalendarService` already works out `RETURN_DUE` and `DEDUCTION_PAID_BY` for a draft;
  `ClaimDeadlineCalendarTest` holds the link from `ClaimDeadline` to `DraftCalendar.Kind` (W-117a).
- **Banding is W-121's** (`DR 22` C6: invisible after rounding, below typical effort, material). This item returns
  the measured figure only.
- **Ripple to expect:** `new RulePack(` appears at 41 sites (1 main, 40 test) — a new component touches each, as
  W-116's `explanations` did.

**Choices for the owner:**
- **C1: how the worth of a claim is measured.**
  - **C1a (recommended):** a second run with the entry's rules withheld. `PipelineRunner.run` gains a set of withheld
    rules, `NodeContext.inRegime` answers a new `RegimeVerdict.Withheld` for them, and worth is the bill as it stands
    less the bill without the claim — the same `D-MARGINAL` measure F33 uses, general for every entry. Costs: one
    reason code with its sentence in `content/explanations.json` (the compiler refuses an unworded code), so both
    locks move.
  - C1b: remove the claim's inputs per family (rent, health payments, …), as the room pricing fills them. No verdict
    change, but new code for every entry added later.
- **C2: how the pack carries what the playbook needs.**
  - **C2a (recommended):** the compiler writes each kept entry whole: its section's `plainName` and `summary` beside
    it, and a `figures` map of each placeholder to the year's value from the rule version in force. A placeholder
    whose field is not an amount in every version is refused at build. Run time only formats and substitutes.
  - C2b: compile `content/sections/` into the pack as well and resolve placeholders at run time by reflection on the
    typed definitions.
- **C3: which claims the endpoint lists.**
  - **C3a (recommended):** `claimed` — entries with a line above nil in the draft's computation, each with its worth;
    and `notClaimed` — the year's other entries, without a worth. F33's completeness already prices what is missing.
  - C3b: only the claims in the computation.
- **C4: "missing from Form 16" without a Form 16.**
  - **C4a (recommended):** every claim carries its catalogue verdict as a fact ("if your Form 16 does not show this:
    …"); the response says in `notIncluded` that no Form 16 is compared yet. The comparison is placed as a new row
    when a Form 16 import is.
  - C4b: wait for a Form 16 import.
- **C5: a step's date.**
  - **C5a (recommended):** a step due at the tax year's end or the return's due date carries that date from the
    draft's calendar; the employer's cut-off and "none" carry no date, only the deadline's name.
  - C5b: names only.

**The model:**
- **Engine, `taxengine.api`** (new): `ClaimPlaybook(rule, covers, plainName, summary, channel, chapterViiiPart,
  ifMissingFromForm16, provision1961, provision2025, appliesTo, steps, askWhom, evidence, mistakes)` with nested
  `Step(order, instruction, actor, by, produces, warnsOfLateReturnBar)`, all strings (the catalogue's enums by name,
  as `ComputedTax` carries codes), texts with figures already substituted; `PricedClaim(playbook, allowed, worth)`.
  Both provisions are returned as facts; which Act a year falls under is not decided here.
- **Engine entry points on `TaxCalculator`:** `claimPlaybooks(TaxYearId)` (every entry of the year) and
  `priceClaims(EngineInputs)` (the entries with a line above nil, `allowed` = the sum of those lines' `out`, `worth`
  by C1).
- **Pack:** `RulePack` gains `claimCatalogue` (the year's entries as compiled, C2a); `JsonPackAssembler` reads
  `content/claim-catalogue.json`; `RulePack` refuses an entry whose lead rule the pack does not hold.
- **`taxplanning.compute`** (new): `DraftClaims(asOf, regime, revision, claimed, notClaimed, notIncluded)`,
  `DraftClaimsService` (loads the draft as `DraftCompletenessService` does, calls the two engine methods, adds dates
  from `DraftCalendarService`, C5a), and the endpoint on `DraftComputationController`.

**Build steps, in order:**
1. **Probe first (stop condition).** With C1a's change applied as a probe, a test over the shipped pack: for each
   catalogue rule (lead and covered), a run on a persona that claims it, with the rule withheld, shows that rule's
   line at nil. **If any rule's line survives**, its node does not ask `inRegime`: stop and report the rule and node
   before building further.
2. Compiler: `plainName`, `summary`, `figures` per entry (C2a); refusals with tests; relock.
3. `RulePack` + `JsonPackAssembler`; update the 41 construction sites.
4. `Withheld` verdict, its reason code and sentence; `PipelineRunner.run` overload; relock.
5. `TaxCalculator.claimPlaybooks` and `priceClaims`; api records.
6. `DraftClaims`, service, endpoint; api-collection entry (a submodule — parse its YAML, bodies can be escaped strings).

**Roles:**

- **PM:** closes F40.2 – F40.4's serving half: a person sees, per claim, what to do, by when, and what it is worth.

**Risks:**
- A catalogue rule whose node never asks `inRegime` (step 1). Fallback is C1b for that rule only, and you are told.
- Withholding one member of an aggregate (the investment ceiling, health limbs) must lower the aggregate, not just
  hide a line; step 1's test checks the bill moves, not only the line.
- Two claims can overlap (own NPS and the investment ceiling): worths are each "with all others as they stand" and
  need not add up; the response says so, as F33 does.
- Performance: one extra run per claimed entry. F33 does the same; budget N1 – N3 run only on the pipeline's benchmark
  job.
