## Plan for W-131 — documents reach users: storage, the parse job, the endpoints — findings and split

> **Approved as recommended — C1a – C5a** (owner, session 104, 2026-11-17; D-761). Every path:line below was read or grepped this session at
> `015496f4`. No probe: nothing shared changes until C1 is chosen. Each child plans and probes its own change.

**What this item is for (one sentence, in my own words):** let a user upload a Form No. 130 for TY 2026-27 (D-748), have
it parsed in the background, see what was read, and confirm it:
- stored encrypted, erased with the profile, and kept no longer than the law and DR 14 allow;
- so W-128's checks, W-129's assembly and W-130's reconciliation have real, confirmed certificates to work on.

### What the design and the row say

- **The row** (`03-WORK-ITEMS.md` W-131) asks for:
  - the endpoints, and the async job `ParseDocument` (DR 19 E8: "on upload … idempotent on `(documentId,
    parserVersion)`; a new attempt row per run");
  - `tax_documents` (unique `{sha256}`; `{profile_id, tax_year}`), `tax_parse_attempts` and
    `tax_document_confirmations` (`02-TECH-SPEC.md:331` – `:333`);
  - encryption of the read text and values, erasure with the profile and account, 8-year retention (O5), the bytes'
    storage (O6), the runbook entry, and the parse budget and isolation (O6, O9).
- **T8** (`02-TECH-SPEC.md:372`): `POST /documents` · `GET /documents/{id}/parse` · `POST /documents/{id}/confirm`
  under `/tax/user/{email}`.
- **O6** (`14-operational-design.md:161`): 20 MB and 50 pages; PDF only; "Scan before storage"; encryption at rest; never
  persist a password; parser "with no network egress and a hard CPU and wall-clock budget"; bytes outside Mongo (GridFS or
  an object store); a PAN mismatch "rejected before any field is consumed" (B9-73).
- **O5** (`:126`): documents 8 years; "computed from the rule pack". `TaxCalculator.longestCarryForward` already gives it.
  W-235 amended erasure: everything erased on request after a one-year hold.
- **O9:** a parser crash or timeout is a FAILED attempt and the document is kept.

### Findings

1. **The pieces exist:**
   - `EncryptedField` (`shared/protection`) for the read text and values;
   - `ProfileErasure` and `TaxAccountErasure` for erasure;
   - `TaxJob` and `TaxJobRunner` (`taxplanning/jobs`) for the job;
   - `DocumentParsers`, `IngestedDocument`, `ParseAttempt` and `DocumentConfirmation` (W-124, W-125);
   - `RetentionPurge` (`taxplanning/jobs`), which already reads `longestCarryForward`, for retention.

   No GridFS use exists outside the charge seeder.
2. **Two O6 demands need infrastructure the app does not have:** a malware scanner, and process isolation for the
   parser (no egress, a CPU budget). In-process, only a wall-clock budget and page/size caps are enforceable.
3. **The PAN check before any field is used** (O6, `14-operational-design.md:172`, citing B9-73): the employee's PAN
   against the profile's. `FORM_130.json` tags nine facts (CESS, EMPLOYER_TAN, EMPLOYMENT_PERIOD, REBATE,
   REGIME_OPT_OUT, SALARY_FROM_OTHER_EMPLOYERS, STANDARD_DEDUCTION, SURCHARGE, TAX_ON_TOTAL_INCOME); the employee's PAN is
   not one of them.
4. **Size.** Storage with encryption and erasure, the bytes, the job, the endpoints and the checks: several items (§7).

### Choices for the owner (recommended first)

- **C1 — the split:**
  - **(a)**
    - **W-131a:** the stored form — three collections, repositories, indexes, encryption of the read text and values,
      erasure with the profile and account, retention through `RetentionPurge`, the runbook entry.
    - **W-131b:** the bytes — storage in GridFS, encrypted, with the size, page and type limits.
    - **W-131c:** the `ParseDocument` job on `TaxJobRunner` — wall-clock budget, a timeout a FAILED attempt, idempotent
      on `(documentId, parserVersion)`.
    - **W-131d:** the endpoints, with the PAN check before use (B9-73), the confirmation, and a reconciliation read
      (W-130) for a draft.
  - Each gets its own plan and probe.
  - (b) Fewer, larger items.
- **C2 — where the bytes live:**
  - **(a)** GridFS: Mongo is already there. Encrypted with the existing key material before writing.
  - (b) An object store, which is a new dependency and new infrastructure.
- **C3 — the malware scan** (finding 2):
  - **(a)** Not at launch. Instead: PDF only, 20 MB and 50 pages, encrypted at rest, parsed only by the existing parser.
    The documents feature ships **off** behind `app.tax.documents.enabled` until a scanner is decided, as a placed row
    (**W-131e**).
  - (b) A scanner now (e.g. ClamAV), which brings new infrastructure.
- **C4 — parse isolation** (finding 2):
  - **(a)** In-process with a wall-clock budget, page and size caps, and no network call in the parser's code (iText reads
    bytes only). Process isolation with a CPU budget is a placed row (**W-131f**), required before the flag turns on.
  - (b) A separate process now.
- **C5 — the employee's PAN** (finding 3):
  - **(a)** A fact `EMPLOYEE_PAN` on Part A item 11 in `FORM_130.json` (W-131d), compared with the profile's PAN
    before any field is used.
  - (b) A path in Java.

### Five roles

- **Architect:** storage behind `taxplanning` only. Bytes outside documents' metadata (O6). The flag keeps an unscanned,
  unisolated upload from users.
- **Product manager:** the upload and confirm flow reaches users only when the flag turns on, after W-131e and W-131f.
  Until then it is buildable and testable but dark.
- **Senior engineer:** reuse `EncryptedField`, the erasure services and `TaxJobRunner`; no new infrastructure in
  W-131a – d.
- **Automation tester:** integration tests per child; erasure and retention proven.
- **Manual tester:** with the flag on in staging, an upload, a parse, a confirm, a reconciliation.
