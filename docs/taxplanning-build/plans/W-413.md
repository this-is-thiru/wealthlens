### Decisions (owner)

- **C1 — who makes the schema.** **C1a (recommended):** Flyway never makes it (`spring.flyway.create-schemas: false`). The
  schema must exist, as W-337h made it on all three hosts (runbook §2.19), and a host without it stops the app at start
  instead of working somewhere unexpected. That also catches staging's and dev's unpasted readback (W-337h) at the first
  start. The tests make it themselves when their container starts (`CREATE SCHEMA wealthlens`), so the history keeps no
  creation row and the baseline test is unchanged. **C1b:** Flyway makes it when absent. That is simpler for a new host,
  but the history then carries a creation row on a fresh database, the baseline test is changed to expect it, and a typo
  in a JDBC URL quietly makes a second schema.
- **C2 — where the schema is set.** **C2a (recommended, probed):** on the connection pool, `app.postgres.datasource.hikari.schema`.
  Every user of the datasource then agrees: Flyway, Hibernate, the copier's `current_schema()`, and the tests'
  `JdbcTemplate`. **C2b:** `?currentSchema=wealthlens` in each JDBC URL the owner types. There is no code change, but the
  schema lives in three secrets instead of the repo, and one forgotten URL sends that database to `public`.

   each host's `wealthlens` schema must exist before the PostgreSQL build first starts (prod: done; staging and dev:
   W-337h's readback).
