## Plan for W-283 — rebuild `profit_and_loss` (and `assets`) from what is stored

**What this item is for (one sentence, in my own words):** a `SUPER_USER` can recompute a user's derived portfolio
figures from stored source rows, dry run first, instead of hand-editing nested documents. Today the deploy runbook
says "correct the period by hand or accept it" (`post-deployment-runbook.md:140`) (B-4,
`docs/trade-ledger/backlog.md:59`).

**Findings (read this session, 2026-11-12):**

1. **What writes `assets`:**
   - `PortfolioService` — V1 buy (merges same-day lots, `:419`), V2 buy (one lot per buy, `:443`), and both sales
     (`:487 – 490`, `:510 – 513`).
   - Corporate actions, which rewrite lots in place: `saveCorporateActionProcessedStocks` (`:746`), called from
     `CorporateActionService:239, :312, :413, :445`.
2. **The flow that built a lot is not stored.** `trade_flow` exists only on a temporary transaction
   (`TransactionEntity:162 – 167`, set at `TemporaryTransactionService:51`). From `transactions` alone, a rebuild
   cannot tell a V1 merged lot from two V2 lots. It would also have to replay every corporate action in date order
   between the trades. Rebuilding `assets` is therefore a design problem, not an endpoint.
3. **The P&L is already a fold of stored rows, for V2:**
   - A V2 sale's capital gains are folded from its `trade_outcomes` rows (`ProfitAndLossService.recordSale`,
     `:361 – 384`, W-169).
   - Its charges, and a buy's (buys add charges only, `handleNormalBuyCase` `:331 – 351`), come from the pricing
     result, which is stored per trade as `user_charges`.
   - `trade_outcomes` can already be rebuilt from `transactions` (§2.2, D-284).
4. **V1 sales differ.** V1 saves its `trade_outcomes` row and separately updates the P&L through the deprecated
   `updateProfitAndLoss(ProfitAndLossContext)` (`PortfolioService:573 – 574`, `ProfitAndLossService:85`), with no
   charge summary. A fold of `trade_outcomes` may therefore not reproduce what V1 wrote. **Unverified** — the build
   measures it.
5. **Prior art to copy:** D-284's `trade_outcomes` rebuild.
   - `SUPER_USER`, `dryRun` default true, a report of what was examined and what was written.
   - Per-user idempotent: a user who already has rows is skipped.
   - Failures are named per user. The endpoint is a standing operation with its own runbook entry.

**Choices for the owner:**

- **C1 — scope.**
  - **C1a (recommended):** this item rebuilds **`profit_and_loss` only**. The capital-gains side is folded from
    `trade_outcomes` and the charges side from `user_charges`, per user, through
    `POST /portfolio/user/{email}/profit-and-loss/rebuild?dryRun=true` (`SUPER_USER`). The dry run reports, per
    financial year, the stored totals against the rebuilt ones. A real run replaces that user's P&L documents.
    Rebuilding `assets` is placed as **W-283a**, whose first step is a written design for lot shape (finding 2) and
    corporate-action replay.
  - C1b: both collections in this item, by replaying every transaction through the trade flows with the engine off.
    This is large, and lot shape is a guess for every V1 user.
  - C1c: park B-4; the manual correction stays.
- **C2 — V1 sales in the rebuild** (C1a).
  - **C2a (recommended):** fold every sale from its `trade_outcomes` rows, the same way V2 does. Those rows are what
    the tax side reads. Where a V1 sale's stored P&L differs, the dry run shows the difference before anything is
    written.
  - C2b: refuse a user with any V1 sale, which cannot be detected from a transaction (finding 2), so in practice
    any user with an old sale.

**Files I will create (C1a):**

- `portfolio/dto/…/ProfitAndLossRebuildReport` — the report (record).
- A `SUPER_USER` route on `PortfolioController` or a new `ProfitAndLossRebuildController`, matching D-284's shape.
- Tests: a unit test of the fold, and an integration test with V1 and V2 trades.

**Files I will modify:**

  to the rebuild, without changing what they compute.
- `post-deployment-runbook.md` — a §2 entry (standing, `SUPER_USER`), and `:140` pointed at it.
- `docs/trade-ledger/backlog.md` B-4.
- `api-collection` (a submodule).
- `AbstractIntegrationTest.cleanDatabase` if a collection is added (none is planned).

**Numbers I will use:** none from law. The integration test's expected totals are worked by hand from its trades
(prices, quantities and the charge rows it stores) and shown in the test.

**Design sections I read:** B-4 (`backlog.md:59 – 79`); D-284; runbook `:130 – 145` and §2.2 (`:1018`).

**What I am NOT doing:**
- Rebuilding `assets` (W-283a).
- Repricing anything (ADR-32: charges come from `user_charges` as recorded).
- Rebuilding `trade_outcomes`; the runbook entry says to run §2.2 first when its rows are also wrong.

**How I will verify:**
- A V2 user: rebuilt totals equal the stored ones, field for field.
- A V1 sale: the measured difference, if any, is reported.
- Dry run writes nothing.
- A second run is a no-op unless forced, or a user with a P&L is skipped as in D-284; I'll settle which in the D-row.
- A `USER` token gets 403.
- Probe: one fold step disabled makes the V2 equality fail.
- Then the targeted tests, the unit tier, and the integration tier once.

**Post-deployment actions (R15):** a standing §2 entry.
- **When:** after a manual correction to `transactions`.
- **Who:** the owner.
- **How:** back up that user's `profit_and_loss`, run §2.2 if needed, dry run, then a real run.
- **Checks before and after:** a read-only per-year count and total.
- **Second run:** safe.
- **The way back:** restore the backup.

**Five roles:**
- **Architect:** stays inside `portfolio`; reuses the P&L's own fold, so a rebuild and a live trade cannot compute
  differently. `assets` is deliberately left to a design item.
- **Product manager:** no user-facing change; the owner gets a safe correction tool, and the runbook's "by hand"
  step is replaced.
- **Senior engineer:** one class with one job; no new flags; failures named per user, as D-284 does.
- **Automation tester:** totals by hand; V2 equality, V1 difference, dry-run no-write, 403, and a probe.
- **Manual tester:** a curl dry run against staging for one user, with the expected per-year report shape in the
  runbook entry.

**Risks or ambiguities:**
- Finding 4 may show V1 P&L figures move on a rebuild; the dry run exists to show that first.
- The mapping from a stored `user_charges` row back to what `mergeChargeSummary` takes is not yet read.
- If no clean mapping exists, I stop and re-plan (R13).

**Added during the build (R13, owner C3a, D-575):** §2.8's skip list `pnl_backfilled_outcome_ids` was not mapped on
`ProfitAndLossEntity`. A rebuilt document would lack it, so a later §2.8 run would add every pre-deploy V2 sale again.
Any live save already dropped it. It is now a mapped field, and the rebuild fills it with every row it folds. The
runbook's §2.8 second-run note says so. Two tests and two probes cover it.
