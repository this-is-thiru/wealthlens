## Plan for W-088u8b — the `trade_outcomes` rebuild as a `SUPER_USER` operation

**What this item is for (one sentence):** the rebuild of `trade_outcomes` from raw transactions stops running at boot
whenever the collection is empty. It runs only when a `SUPER_USER` asks: dry run first, per user (skipping any user
who already has rows, so a re-run after a partial one completes it), the caller recorded as author, and a failing
user an error that names them (D-280, D-281, D-282).

### What I read (session 25, 2026-10-20, at `92991759`)

- **`shared/config/TradeOutcomeMigrationRunner`** (`CommandLineRunner`) calls
  `TransactionBasedTradeOutcomeMigration.migrateTransactionsToTradeOutcomes()` when `trade_outcomes` is empty or
  absent.
- **`portfolio/migration/TransactionBasedTradeOutcomeMigration`:**
  - `migrateTransactionsToTradeOutcomes` walks every distinct email in `transactions`. Per user, `migrateUser`
    saves `rebuiltRows(email)` (W-088u7 extracted it; `RebuildBuyChargeCorrection` uses it too).
  - A failing user is caught by `catch (Exception e)`, logged, and counted as skipped; the run carries on. Its
    `IllegalCatch` is suppressed in the baseline (`checkstyle-suppressions.xml:32`).
- **Author:** `TradeMatchingService.toTradeOutcomeEntity:319` stamps `buildAuditMetadata()`
  (`createdBy = "TransactionBasedTradeOutcomeMigration"`, `:346–354`). Spring auditing (`SecurityAuditorAware`)
  overwrites the audit fields when the entity is saved, as W-088u7's integration test found (`"unknown"` with no
  user). So inside a `SUPER_USER` request the caller is recorded, and the class-name stamp is dead weight. The only
  test touching it asserts `assertNotNull(entity.getAuditMetadata())` (`TradeMatchingServiceTest:748`); the field
  initializer keeps that true.
- **`TradeOutcomeRepository`:** has `findByEmail`, `deleteByEmail` and others, but no `existsByEmail`.
- **The trade-ledger docs rely on the rebuild as a recovery tool (C1):**
  - `docs/trade-ledger/migration.md` §3a (`:140–143`): to unwind a duplicated trade, delete the duplicate
    `transactions` rows, "**Drop the collection and restart**: `TradeOutcomeMigrationRunner` repopulates it".
  - `:166–169` and `backlog.md` B-4 (`:62–64`): `trade_outcomes` is "the one thing that rebuilds itself", the easy
    correction among the three derived collections.
  - So the rebuild is **not** one-time. It is the documented way to recompute `trade_outcomes` after a correction to
    `transactions`, which conflicts with WL-31 / W-088u9c (remove after use).
- **A cost of that recovery path today:** dropping the whole collection and rebuilding replaces V2's rows, which
  carry charge breakdowns and deductible charges, with rebuild rows that carry neither. The capital-gains summary
  then refuses those users (D-238 C2a). Per-user rebuilding narrows the damage to the user being corrected.

### Design

1. **`TransactionBasedTradeOutcomeMigration.rebuild(boolean dryRun)` returns `TradeOutcomeRebuildReport`.** It
   replaces `migrateTransactionsToTradeOutcomes` / `migrateUser`.
   - It walks the distinct emails in `transactions`, sorted.
   - A user with any `trade_outcomes` row is **skipped and listed**: whichever writer made the row, they are never
     duplicated.
   - Every other user's `rebuiltRows(email)` is saved, unless a dry run.
   - **Idempotent:** a re-run skips every user written before, so after a failed run it completes the rest, and
     after a full run it writes nothing.
2. **A failing user:** `IllegalArgumentException`, `IllegalStateException` and `DataAccessException` are caught by
   name and rethrown as `IllegalStateException("user <email>: <reason> — the users before are written; fix and
   rebuild again")`. No `catch (Exception)`, so suppression line 32 comes out.
3. **`TradeOutcomeRepository.existsByEmail(String)`**, a derived query.
4. **`POST /trade-outcomes/rebuild?dryRun=true|false`** goes on a new `portfolio/controller/TradeOutcomeRebuildController`.
   It is `SUPER_USER`, with `dryRun` defaulting to true, and returns the report with the caller. It is kept apart
   from `TradeOutcomeCorrectionController`, so each can be removed on its own.
5. **Author:** `TradeMatchingService.buildAuditMetadata` and its call are removed. The saved rows carry the caller
   through the auditing.
6. **`TradeOutcomeMigrationRunner` is deleted.**
7. **`TradeOutcomeRebuildReport`** (`portfolio/dto`):
   - `dryRun`, `auditor`;
   - `usersExamined`, `usersRebuilt`, `rowsWritten` (or would be);
   - `skipped`: email and the number of rows they already have.
8. **Docs:**
   - runbook (R15): §1.4 becomes "nothing at boot", and a new §2 step covers the rebuild — dry run, read the
     to-be-rebuilt list, write, verify;
   - `docs/trade-ledger/migration.md` §3a and `backlog.md` B-4: "drop and restart" becomes "delete the user's
     `trade_outcomes` rows, then `POST /trade-outcomes/rebuild` (dry run first)";
   - WI, STATE D-284, CHECKPOINT; WL-A-2 republished.

### Post-deployment actions (R15)

- **Runbook §2.2 (new), the rebuild, `SUPER_USER`:**
  - **When:** on a new database whose `transactions` came from elsewhere, or after a correction to `transactions`
    (with that user's `trade_outcomes` deleted first, backup first).
  - **On staging and prod as they stand:** the dry run should list, as to-be-rebuilt, only users with transactions
    and no rows at all. Read the list before writing.
  - **Steps:** dry run → read `usersRebuilt` and `skipped` → `?dryRun=false` → verify with `countDocuments` per user.
  - **Second run:** writes nothing. **Way back:** delete the written rows (`audit_metadata.createdBy` = the caller,
    `createdAt` = the run).
- **§1.4:** nothing at boot.

### Choices (recommended first)

- **C1 — is the rebuild one-time? (WL-31 / W-088u9c)**
  - **(a) recommended: no. Keep it as a standing operation.** Close WL-31 and W-088u9c as "not one-time" (D-284),
    because the trade-ledger correction procedure needs it. It stays manual, `SUPER_USER`, dry run first,
    idempotent: all D-280 asks for.
  - **(b)** keep WL-31: remove it after use. The trade-ledger docs then say a `trade_outcomes` correction has no
    tool, and is done by hand like `profit_and_loss`'s.
- **C2 — the author stamp:**
  - **(a) recommended:** remove `buildAuditMetadata`. The auditing records the caller, and the stamp was being
    overwritten anyway.
  - **(b)** keep it and also record the caller in `updatedBy`. That gives two sources for one fact.
