## Plan for W-268 — maintenance and test routes reach other users' data

**What this item is for (one sentence, in my own words):** stop an ordinary signed-in user from rewriting or
reading other users' portfolio records through three routes left over from maintenance and testing (G-11, G-12,
B-9 of W-264a's audit).

**Findings (each read this session, 2026-11-11):**

1. **`POST /portfolio/user/{email}/update`** — `SpecialController.java:17-20` calls
   `PortfolioService.updateTransactions` (`:847-861`), which `findAll()`s every user's assets, sets a missing
   `asset_type` to `MUTUAL_FUND`, saves all, then does the same to every transaction
   (`TransactionService.java:179-187`). Path check passes on the caller's own email. Proven: W-264a scenario 19.
   Callers: `api-collection/Update.yml`; `TransactionIntegrationTest.java:345` calls the service method directly.
   *Unverified:* whether this backfill has already run on staging and prod — no runbook entry names it
   (`grep asset_type post-deployment-runbook.md` shows only LAND_OR_BUILDING checks).
2. **`GET /portfolio/user/{email}/all/transactions`** — `PortfolioController.java:101-105` discards the email and
   returns `transactionService.allTransactions()` (`TransactionService.java:194-196`, `findAll()`). Proven:
   scenario 20. Callers: `api-collection/Transactions/All Transactions.yml`; `TransactionIntegrationTest.java:410`
   (one user, asserts `ADANIPORTS` present). The caller's own list already exists as `GET /transactions/user/{email}`
   (scenario 21).
3. **`POST /test/user/{email}/transact/sell`** — `TestController.java:22` hands client-supplied lots to the V2 sell
   allocation and saves nothing it mutates (B-9): P&L, charge records and trade outcomes are written for lots the
   caller made up. It was kept and repaired on purpose by W-205 (D-409, `HelperSellIntegrationTest`), and
   `api-collection/Test Req/Transact - New.yml` calls it.
4. **The guard already used for operator-only routes** is `@PreAuthorize("hasRole('SUPER_USER')")`
   (`ChargeScheduleController.java:59`, `ChargeAccountController.java:67`).

**Choices for the owner:**

- **C1 — `/update` (the backfill).**
  - **C1a (recommended):** remove the route, both `updateTransactions` methods and `SpecialController`; add a
    read-only runbook check counting `assets` and `transactions` with no `asset_type`. If any database shows
    some, a later row brings a scoped, idempotent backfill back through the runbook.
  - C1b: keep it behind `SUPER_USER`.
- **C2 — `/all/transactions`.**
  - **C2a (recommended):** answer the caller's own transactions only (`findByEmail`), so the existing request keeps
    working and means what its path says.
  - C2b: remove it; `GET /transactions/user/{email}` is the caller's list.
- **C3 — `/test/.../transact/sell`.**
  - **C3a (recommended):** put it behind `SUPER_USER`. W-205 kept it deliberately; this keeps it for the operator and
    takes it from ordinary users. B-9's "saves nothing" stays as the hook's documented nature.
  - C3b: remove it with `TestController`, `HelperSellIntegrationTest` and the request.

**Files I will create:** none beyond tests inside existing classes.

**Files I will modify (C1a, C2a, C3a):**
- `helper/controller/SpecialController.java` — deleted. `PortfolioService.java`, `TransactionService.java` —
  `updateTransactions` removed.
- `PortfolioController.java` — `/all/transactions` returns `transactionService.getUserTransactions(userMail)`
  (`TransactionService.java:148`); `allTransactions()` removed if no other caller.
- `helper/controller/TestController.java` — `@PreAuthorize("hasRole('SUPER_USER')")`.
- Tests: `TransactionIntegrationTest` (drop the backfill test; two-user case for `/all/transactions`),
  `HelperSellIntegrationTest` (SUPER_USER token; a USER token answers 403), W-264a scenarios 19 and 20 moved into
  `PortfolioGapAuditIntegrationTest` as this fix's first tests.
- `api-collection` (submodule): remove `Update.yml`; note SUPER_USER on `Transact - New.yml`.
- `post-deployment-runbook.md` — the read-only `asset_type` check (C1a), so WL-A-2 is republished.

**Numbers I will use:** none.

**What I am NOT doing:** the other portfolio fix rows; `/request` and `/request2` (scoped to the caller, scenario
32); auditing other modules' routes for the same pattern (W-264b – d).

**How I will verify:** scenarios 19 and 20 fail before the change and pass after; a USER token on the test hook
answers 403 and a SUPER_USER token 200; the affected integration classes run; `./mvnw validate`. Probe: restore
`findAll()` and see scenario 20 fail.

**Post-deployment actions (R15):** C1a adds one read-only check (when: before deploying W-268; who: owner; a second
run is safe; nothing to undo).

**Five roles:**
- **Architect:** the operator surface belongs behind one guard; nothing user-scoped by path may reach `findAll()`.
- **Product manager:** a user's records are seen and changed only by that user; nobody loses a working request
  except the backfill, which has no user purpose.
- **Senior engineer:** removal over guarding where nothing needs the code (C1a); the guard pattern already in use.
- **Automation tester:** the audit's failing scenarios become the first tests; probes as above.
- **Manual tester:** the report's request sequences for 19 and 20, repeatable against a local app.

**Risks or ambiguities:** if the backfill has not run somewhere, C1a leaves null asset types there until the
runbook check finds them — that is why the check comes with the removal.
