## Plan for W-285 — the upload records the account holder

**What this item is for (one sentence, in my own words):** a transaction entered by JSON carries its account
holder, but one uploaded from the workbook never does, so the same holder's lots split into two groups. The upload
should read an `ACCOUNT HOLDER` column, and the template should offer one (D-559).

**Findings (read this session, 2026-11-12):**

1. **The parser reads no holder.** `AssetRequestParser.simpleDataTypeMap` (`:29 – 47`) and `toRequest` (`:51 – 73`)
   cover 16 headers, and `ACCOUNT HOLDER` is not among them. Every uploaded request keeps `accountHolder` null
   (`AssetRequest:57`), and so does its transaction and lot (`asTransaction:116`, `asAsset:146`).
2. **A column the parser does not know is dropped silently.** `AssetRequestParserImpl.getCellDetail` reads a header
   missing from the map as `ExcelDataType.NULL` (`:120`, `:132`). So a workbook that carries `ACCOUNT HOLDER` today loses it
   without a word. Only a value with no header at all is refused (`refuseValuesUnderNoHeader`, `:111 – 117`).
3. **The header exists.** `ExcelHeaders.ACCOUNT_HOLDER = "ACCOUNT HOLDER"` (`:8`) is already used by the holdings
   export (`PortfolioExportColumns:40`). The template (`TRANSACTION_TEMPLATE`, `:87 – 101`, checked by
   `PortfolioExcelExporterTest:207 – 214`) does not carry it.
4. **JSON's meaning of "absent".** A JSON request may leave `accountHolder` out, and it is then null. Nothing in the
   trade path refuses that. Lots group on the holder as stored, null included (`LotLedger.sameHolding`,
   `PortfolioRepository` lookups).
5. **Not part of this item, found reading:** the upload also reads no `SEGMENT` and no `ACCOUNT TYPE`. An uploaded
   trade is therefore always delivery and always the user's own account (`AssetRequest:55`, `:65` defaults). An
   intraday or outsourced trade cannot be uploaded.

**Choices for the owner:**

- **C1 — what an absent or blank `ACCOUNT HOLDER` cell means.**
  - **C1a (recommended):** no holder (null), exactly what a JSON request without one means. A workbook made before
    the column existed keeps working unchanged.
  - C1b: refuse the row, naming it. Every uploaded lot then has a holder, but every existing workbook breaks.
- **C2 — the template.**
  - **C2a (recommended):** add `ACCOUNT HOLDER` after `BROKER NAME`, with the sample value `Self` (the value the
    tests' JSON trades use), and update `PortfolioExcelExporterTest`'s expected headings.
- **C3 — finding 5.**
  - **C3a (recommended):** place it as **W-301** (the upload reads no segment or account type), after W-285.
  - C3b: build it here. That would mean two more columns and two more meanings of "absent".

**Files I will modify (C1a, C2a, C3a):**
- `AssetRequestParser`: the map entry and `setAccountHolder`. A blank cell gives null, the same as `setBrokerOrderId`
  through `getOrDefault(…, CellDetail.def())`.
- `PortfolioExportColumns.TRANSACTION_TEMPLATE` and `EntityExportService.templateRow`.
- Tests:
  - `AssetRequestParserTest`: a row with `ACCOUNT HOLDER` `Lakshmi` gives `accountHolder` `Lakshmi`, red before; a
    row without the column gives null.
  - `PortfolioExcelExporterTest`: the expected headings gain `ACCOUNT HOLDER`, red before.
  - `PortfolioGapAuditIntegrationTest`: a workbook uploaded with `ACCOUNT HOLDER` `Lakshmi` stores a lot held by
    `Lakshmi`, red before (today the lot has no holder).
- `03-WORK-ITEMS.md` (W-301) and `STATE.md`.

**Numbers I will use:** none.

**Design sections I read:** D-559 (the row), D-557 / W-273 finding 4, D-528 (W-276, the blank-cell rule).

**What I am NOT doing:**

- correcting uploaded lots already stored without a holder, because the stored data does not say who held them;

  needs the app running, and you would do that.

**How I will verify:**
- The red tests run first.
- Probe: drop the map entry. The parser and upload cases must fail, because the column is then dropped again.
- Locally: the touched classes and `validate`. The tiers run on the PR's pipeline.

**Post-deployment actions (R15):** none. Stored lots are left as they are. The runbook gains no entry.

**Five roles:**
- **Architect:** the upload records the same fact a JSON trade does, with the same meaning of "absent".
- **Product manager:** uploaded and typed trades of one holder land in one holding.
- **Senior engineer:** one header, one setter and one template column.
- **Automation tester:** parser, template and upload cases, red first, plus a probe.
- **Manual tester:** download the template, fill `ACCOUNT HOLDER`, upload it, then export the holdings. The holder
  appears.

**Risks or ambiguities:**
- Lots already uploaded keep no holder. A later JSON trade with a holder groups apart from them. That is unchanged,
  and unknowable from stored data.
