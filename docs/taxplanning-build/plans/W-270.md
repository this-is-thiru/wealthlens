## Plan for W-270 — redrive applies every waiting trade through V1

**What this item is for (one sentence, in my own words):** a trade held back by a corporate action is, when redriven,
recorded by the flow it was entered through, so a V2 trade keeps its own lot and is priced by the charge engine (G-8).

**Findings (each read this session, 2026-11-11):**

1. **Both flows store a waiting trade the same way.** V1 and the upload reach `processTransaction`
   (`PortfolioService.java:95`), V2 its own copy (`:130`); both call `TemporaryTransactionService.filterOutTransaction`
   (`TemporaryTransactionService.java:39-49`), which saves a `TEMPORARY` `TransactionEntity` with the request
   (`asset_request`) and nothing saying which flow sent it.
2. **Redrive always uses V1.** `redriveTemporaryTransactions` calls `processTransaction` (`:281`), V1's path: a buy
   merges into a same-day lot (`buyStock`), is not priced by the charge engine, and a sale reads every lot regardless
   of date (G-3). Proven: W-264a scenario 13 — a waiting buy beside a same-day V2 lot came back merged, one lot of 20.
3. **No word for the flow exists** in the code (no `*Flow` type outside analytics' `CashFlow`); CLAUDE.md calls them
   "two live buy/sell flows", V1 (`/transaction`) and V2 (`/transaction/v2`).
4. **Temporaries stored before this change carry no flow**, and which flow sent them cannot be recovered from the
   stored document. How many exist on each database is not known.

**Choices for the owner:**

- **C1 — what is recorded.**
  - **C1a (recommended):** a new enum `TradeFlow { V1, V2 }` (`portfolio/dto/enums`), stored on the temporary as
    `trade_flow` — a fact (which flow received the trade), set by the server, never by the caller. V1 and the upload
    record `V1`, V2 records `V2`. Redrive sends a `V2` temporary through V2's path (lot per buy, charge engine, sale
    of lots dated on or before it) and a `V1` one through V1's.
  - C1b: the same, carried on the request (`AssetRequest`) instead — rejected by me as an option a caller could set.
- **C2 — a temporary with no `trade_flow` (stored before this change).**
  - **C2a (recommended):** redriven through V1, as every temporary is today, so nothing already waiting changes
    behaviour; a read-only runbook check counts them per database (§3), and the owner decides from the count.
  - C2b: refused at redrive ("entered before W-270; its flow is not known") until set by hand.

**Files I will create:** `portfolio/dto/enums/TradeFlow.java`.

**Files I will modify:** `TransactionEntity` (`trade_flow`, nullable for C2a); `TemporaryTransactionService.filterOutTransaction`
(takes the flow); `PortfolioService` — V2's body after validation becomes a private `processTransactionV2`, the twin
of `processTransaction`; redrive picks by the stored flow; tests (`TemporaryTransactionIntegrationTest` callers of
`filterOutTransaction`, W-264a scenario 13 as the first test, a V2 sale redriven sells only lots dated on or before it,
a temporary with no flow still redriven through V1); `post-deployment-runbook.md` §3 row 3.11 (C2a's count), so WL-A-2
is republished; CLAUDE.md's "Transaction flow" paragraph (the temporary records its flow).

**Numbers I will use:** none.

**What I am NOT doing:** validation on redrive (W-277, PS-1); V1's own sale-date gap (W-271); PS-8 (Q-1); any change
to which corporate actions block a trade (W-264c).

**How I will verify:** scenario 13 red then green (two lots after redrive); a V2-stored sale dated before a later lot
leaves that lot alone; a temporary without a flow merges as today; probe: redrive forced to V1 → scenario 13 fails;
the affected classes; `./mvnw validate`.

**Post-deployment actions (R15):** runbook 3.11, read-only: `db.transactions.countDocuments({ status: "TEMPORARY",
trade_flow: null })`; owner, after the deploy; safe to repeat; nothing to undo.

**Five roles:**
- **Architect:** the flow is a fact stored where the waiting trade is stored, set by the server; the redrive is a
  dispatch on it, not a third flow.
- **Product manager:** a trade comes back from waiting exactly as it would have been recorded had it not waited.
- **Senior engineer:** one private twin for V2's processing, so the public V2 path and redrive share it.
- **Automation tester:** scenario 13 is the proof; a probe shows it depends on the dispatch.
- **Manual tester:** a V2 buy blocked by a bonus, the bonus performed, redrive: the buy appears as its own lot with
  charges on `/user-charges`.

**Risks or ambiguities:** a V2 trade redriven now prices against the rate card for its own date, which is the same
pricing V2 would have done; nothing waiting today is re-priced (C2a).
