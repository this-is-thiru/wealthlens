## Plan for W-086a — one financial-year form in `trade_outcomes`

**What this item is for (one sentence):** make the transaction-based migration path write the financial year as the
rest of `portfolio` does (`TLocalDate.financialYear`, `2025-2026`), and rewrite the rows it already wrote as
`FY2025-26` (D-238 C6a).

**This plan raises choices C1–C3. Nothing is coded until you choose.**

### What I read (session 21, 2026-10-18)

- **The row:** *"`TradeMatchingService.deriveFinancialYear` writes `FY2025-26` where the rest of `portfolio` writes
  `TLocalDate.financialYear` (`2025-2026`) — use `TLocalDate.financialYear`, and a migration rewrites the `FY…`
  rows"*.
- **`TradeMatchingService`:**
  - `matchSellToLots` (l.173) computes `ChronoUnit.DAYS.between(lot.getBuyDate(), sell.getSellDate())`, and only
    then, at l.182, `deriveFinancialYear(sell.getSellDate())`.
  - `deriveFinancialYear` (l.329–339) returns `"UNKNOWN"` for a null date, else
    `String.format("FY%d-%02d", …)`.
  - So a null sell date already fails at l.173, and the `"UNKNOWN"` branch is unreachable from matching.
  - `TradeMatchingService` has one caller, `TransactionBasedTradeOutcomeMigration` (grep).
- **That migration** runs at startup through `shared/config/TradeOutcomeMigrationRunner` (a `CommandLineRunner`),
  only when `trade_outcomes` is empty.
- **Every other writer** (`TradeOutcomeRecorder:169`, `PortfolioService:785`, `ProfitAndLossService:245`) uses
  `TLocalDate.financialYear`.
- **No code queries `trade_outcomes` by `financial_year`** (grep: only the entity's `@Field`). So the `FY…` form is
  wrong only where a row's year is shown or compared. W-086 already selects by sell date.
- **`TradeMatchingServiceTest.shouldConvertToTradeOutcomeEntity`** passes `"FY2023-24"` through
  `toTradeOutcomeEntity`, a copy. Nothing tests the derivation.

### Choices (recommended first)

- **C1 — the writer:**
  - **(a) recommended:** `deriveFinancialYear` is deleted. `matchSellToLots` calls
    `TLocalDate.financialYear(sell.getSellDate())`.
  - This changes no reachable behaviour for a null date, which fails at l.173 first.
  - The copy test keeps its input string as it is: it tests a copy, not the form.
- **C2 — rewriting the stored rows:**
  - **(a) recommended:** a startup migration, the pair the codebase already uses:
    - `portfolio/migration/TradeOutcomeFinancialYearMigration` (`@Service`) finds the rows whose `financial_year`
      matches `^FY`, and sets each to `TLocalDate.financialYear(sell_date)`, one bulk update by id;
    - `shared/config/TradeOutcomeFinancialYearMigrationRunner` (a `CommandLineRunner`) calls it on every start. It is
      idempotent, since a second run finds no `FY` rows.
    - The year is taken from the row's `sell_date`, the fact it was derived from, not by reshaping the string.
    - An `FY` row without a sell date cannot exist (C1's l.173). If one is found, it is refused loudly, naming its id,
      and the start fails rather than leaving it half-migrated.
  - **(b)** an admin endpoint (`SUPER_USER`), as `/charges/seed` is. It needs a controller and a person to remember
    to call it.
- **C3 — records:** D-239; the W-086a WI note; no TS change (`portfolio` code only).
