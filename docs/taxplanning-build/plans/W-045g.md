## Plan for W-045g — the rule-pack compiler (D-034)

**What this item is for (one sentence):** build each tax year's rule pack **from the timeline**,
keeping only `PUBLISHED` versions that touch that year, and pin the result with a lock file, so that
an unreviewed edit to the timeline cannot silently change a year's law.

Package note: `taxrules/timeline/` is `taxengine/rules/timeline/` since `W-045b2`.

### What I found (read this session)

1. **Nothing in main code constructs a `RulePackProvider`.** `git grep "new ClasspathRulePackProvider"`
   finds only tests (`RulePackLoadTest`, `ClasspathRulePackProviderTest`, `PipelineRunnerTest`,
   `NodeHarnessTest`). There is no startup, so "fails startup" today means "fails when the provider
   loads the year". **No item in the backlog owns wiring the provider into the application**
   (`grep` over `03-WORK-ITEMS.md` and `02-TECH-SPEC.md`), so that is an unowned gap.
2. Loading the timeline from a JAR (inherited from `W-045f`) therefore has **no caller**. Under test
   the classpath is a directory, which `TimelineReader.read(Path)` already handles.
3. The provider's whole contract is **files per year**: `manifest.json` (layer versions and
   checksums) plus the layer files, handed to a `PackAssembler`. Six test roots use that format:
   the fixtures `rulepacks-fixture/2098-99`, `2099-00` (no rules; they test the provider's own
   contract, and **T9-21**'s "no Java change" year) and the broken packs `rulepacks-broken/2090`–`2093`
   (checksum, I1, I2, the 400001 trap).
4. `RuleIdNamingTest`, `ConstantGenerator` (`RuleIds`) and `TimelineReaderTest`'s drift guard all
   read `rulepacks/2026-27/`. Removing it (the row asks for that) means moving all three.

**Size:** the whole row is a compiler (~150 lines), a lock format (~60), a provider rewrite (~100),
the six test roots migrated, four test classes changed, three readers moved, and the new test
(~150). That is well over ~300 lines. **I propose a split (§7):**

### A. Proposed split

- **W-045g (this item):** the compiler, the canonical form, the lock file and `RulePackCompilerTest`.
  It proves the compiled 2026-27 pack **equals today's**, layer by layer, while today's still exists
  to compare against. The provider, the test roots and `rulepacks/2026-27/` are untouched.
- **W-045g2 (new):** `ClasspathRulePackProvider` serves compiled packs from the timeline and the lock;
  the six test roots are migrated to timeline form; `rulepacks/2026-27/` is removed; `RuleIdNamingTest`,
  `ConstantGenerator` and `TimelineReaderTest` read the timeline; T9-21 is re-proved.
- **Unowned, to record:** wiring a provider into the application at startup, and loading the timeline
  from the JAR. I propose they belong to whichever item first computes through the API, and ask you to
  name it (see B4).

### B. Choices inside this item

- **B1 — canonical form (what a checksum is taken over).** The compiled layer as JSON with keys
  sorted, no whitespace, and **fields starting with `_` removed**. Those are notes (`_note`,
  `_pendingRules`): editing a note is not a change in the law, so it must not move a checksum.
  **Recommended.**
- **B2 — which versions a year's pack holds.** Every `PUBLISHED` version whose `validity.window()`
  overlaps the tax year, **plus** every `PUBLISHED` `PendingNotification` version. Those have no
  window, and the pack needs them, because I16 checks that their interim rule is present. A rule
  left with no version is omitted, and any reference to it then fails I2 as today. Regimes: every
  regime whose `lifecycle.inForceWindow` overlaps the year. **Recommended.**
- **B3 — the lock file,** `rulepacks/2026-27.lock.json`: `taxYear`; per layer `{version, checksum}`
  (today's manifest block); **per rule `{ruleId: checksum}`**, so that a timeline edit without a lock
  update **names the rule** (the row's Verify); and `instruments`, moved verbatim from the manifest
  (no code reads them). The law layer's version becomes `2026-27.law.4`, because the canonical form
  changes the checksum even though the law does not change. **Recommended.**
- **B4 — owner for startup wiring and JAR loading:** your call. `W-103`, `W-109` or a new id.

## Amendment 1 (R13) — found before any code, needs re-approval

Checked against the actual types while writing the test; three things in the approved plan are wrong:

1. **`Timeline` keeps no source JSON.** It holds parsed `RuleRow`/`RegimeSpec` records, and nothing
   serialises them back. The compiler must emit each rule's JSON with only its selected versions, so
   `Timeline` gains `ruleSources` and `regimeSources` (id → verbatim file content), the same shape as
   its existing `pipelineNodes`. `TimelineReader` fills them. **Modifies two `W-045f` files.**
2. **The layer → files list is private to `ClasspathRulePackProvider`** (`LAYER_FILES`). The compiler
   must emit exactly those files, and a second copy would drift. I'll move it to
   `RulePackLayer.files()`, and the provider will read it from there: a pure move, with no behaviour
   change. **So the provider is touched after all** (plan A said untouched).
3. **B3 bumped only the law version,** but canonical form (B1) changes **every** layer's checksum,
   because every file has a `_note`. By the same rule, all four versions bump: `law.4`, `exec.2`,
   `forms.2`, `content.2`.

Nothing else changes. Size grows by ~30 lines.

**Re-approved:** "approved, go with your recommendations throughout" — 2026-09-24, owner. B4 still undecided (no recommendation was made): UNOWNED.
