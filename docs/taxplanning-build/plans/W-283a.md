## Plan for W-283a — rebuild `assets` from `transactions` (design first)

**What this item is for (one sentence, in my own words):** decide, in writing, how a user's lots can be recomputed
from what is stored. The two hard parts are lot shape and corporate actions, and the decision must come before any
code (D-576).

**Findings (read this session, 2026-11-12):**

1. **Lot shape depends on the flow, which a transaction does not record.**
   - V1 merges a buy into an existing lot with the same email, stock, broker, account holder and date, at a
     weighted-average price, and adds its charges and order time (`PortfolioService:372 – 420`).
   - V2 writes one lot per buy.
   - `trade_flow` is set only on temporaries (`TransactionEntity:162 – 167`, `TemporaryTransactionService:51`).
   - The only surviving record of a merge is a stored lot whose `buy_transaction_ids` lists two or more buys.
2. **Corporate actions are recorded in three different ways:**
   - **Bonus:** writes its own zero-price BUY transaction on the allotment date, plus a lot
     (`CorporateActionService:280 – 345`). It replays from `transactions`.
   - **Name or symbol change:** rewrites every user's transactions as well as their lots (`:227 – 251`). It replays
     from `transactions`.
   - **Stock split:** rewrites lots only — quantity and price by the ratio — and "transactions stay the record of what
     was traded" (`:384 – 414`, D-438). It must be replayed from `corporate_actions`.
   - **Demerger:** reprices and renames the parent lot and adds a new lot per demerged stock, with no transaction behind
     it (`:357 – 488`). It must be replayed from `corporate_actions`.
3. **What was applied is only partly recorded.** `LastlyPerformedCorporateAction` keeps the **latest** action date
   per user, stock, asset type, action type and broker (`:179 – 192`, `:346`), not a history. Each action is also
   copied onto every lot it touched (`corporate_actions`), but on the lots being rebuilt.
4. **Temporaries were never applied.** A trade held by a pending corporate action is stored with `status = TEMPORARY`.
   A rebuild must skip it until it is redriven; the redriven trade is its own transaction (`sourceTempTransactionId`).
5. **Prior art:** §2.2's `trade_outcomes` rebuild already replays transactions FIFO (D-284). W-283's P&L rebuild
   gives the report-then-replace shape (D-575).

**Choices for the owner:**

- **C1 — lot shape for a transaction with no recorded flow.**
  - **C1a (recommended):** from now on, record `trade_flow` on every transaction — a fact, as on temporaries.
    For older transactions, read the shape from the stored lots: buys listed together on one lot were merged, and
    any other buy is its own lot. The dry run lists every buy whose lot it could not find.
  - C1b: one lot per buy for everything. A V1 same-day merge splits apart, and a later partial sale then prices from
    the first buy rather than the average.
  - C1c: record `trade_flow` from now on, and refuse to rebuild any user with an older transaction.
- **C2 — corporate actions in the replay.**
  - **C2a (recommended):** bonus and name changes come in through `transactions`. Splits and demergers come from
    `corporate_actions`, each one applied whose record date is on or before that user's last-performed date for its
    stock, type and broker. They are interleaved with the trades in record-date order; anything later stays pending.
    The rebuild never performs an action.
  - C2b: refuse to rebuild a user who holds any stock that has had a split or demerger.
- **C3 — what this item delivers.**
  - **C3a (recommended):** the written design, `docs/trade-ledger/assets-rebuild.md`, and two placed rows:
    - **W-283a1:** record `trade_flow` on every transaction (if C1a or C1c).
    - **W-283a2:** the `SUPER_USER` rebuild with a dry run and runbook entry, built to the design.
    No code here.
  - C3b: the design and the build together in this item.

**Five roles:**
- **Architect:** recording the flow is a fact, not a rule. Corporate actions stay in `corporate`, and the replay only
  reads them.
- **Product manager:** the design states what a rebuilt holding can differ in (merged prices, pending actions) before
  anyone runs it.
- **Senior engineer:** design before code, since a wrong replay corrupts the very collection it repairs.
- **Automation tester:** the worked example becomes W-283a2's golden test.
- **Manual tester:** the design lists the dry-run checks the owner reads on staging.

**Risks or ambiguities:**
- The design does not settle which comes first on the same day, a corporate action or a trade. A trade on its
  record date is blocked or temporary, which suggests "corporate action first". I will verify it against
  `FILTERABLE_CORPORATE_ACTIONS` and the blocking check before writing it down.
