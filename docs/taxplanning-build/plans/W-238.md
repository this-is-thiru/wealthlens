**For:** given a salary whose components the user may move, the engine says which allocation costs the least tax
(regime included), measured by full computation, with what each change saves. It also gives PRD §5 N3 (p99 < 3 s)
something to time. Parent: W-143 (D-459). Product feature F14 (`01-PRD.md:268`).

- **(a) Recommended: split.** **W-238a**, the engine optimiser in `taxengine` behind `TaxCalculator.optimise`,

- (b) One item. One commit of about 1,500 lines, which is too large for a careful review.

**C1: where candidates come from** (A2.4 steps 2 – 3, the saturation points).
- **(a) Recommended: measured.** For each movable component, find by bisection the smallest allocation beyond
  which moving another rupee from the residual no longer lowers `totalIncome`, in each regime. Candidates are
  {0, current, saturation}. No legal formula in Java, so CLAUDE.md §4 holds and a law change is pack data.
  INFERENCE: in the shapes A2.3 lists (HRA's least-of-three, the 80C cap, the aggregate cap), `totalIncome` is
  convex piecewise-linear in one component, so the slope's sign is monotone and bisection is sound. The
  exhaustive step (C3) catches a case where it is not. Cost: about 23 computes per component per regime at
  ₹1 resolution up to ₹50 lakh.
- (b) A2.4's per-component formulas (HRA, NPS 14 / 10 %, CEA caps) in Java. This is law in code (§4), so not
  offered.
- (c) Saturation declared as new pack data per rule. This states the law a second time beside the rules that
  already apply it.

**C2: regime.** **(a) Recommended:** every evaluation is `compareRegimes`, and the objective is the least
eligible bill (A2.1: the regime is inside, because restructuring can flip it). This is G6.2's ×2. (b) A fixed
regime is wrong exactly where HRA-heavy structuring pays.

**C3: verification breadth.** **(a) Recommended:** a request parameter (default 6, A2.5), recorded in the

**C4: constraints in W-238a.**

- C8: basic is not movable in W-238a, so employer PF does not move. A movable basic is a proposal for later.

### Shape (names checked against the code at build)

`taxengine/optimise/`: `AllocationSpace(EngineInputs base, Set<ComponentCode> movable, ComponentCode residual,
Money cashFloor, int verificationBreadth)`, validated on the way in (residual present and not movable, movable
codes defined in the pack, breadth ≥ 1). `SalaryOptimiser` (steps 3 – 6) and `Optimisation`: the chosen regime,
the bill before and after, per component current / suggested / measured saving, the verified codes, the
evaluation count, and `Optional<Notice>`. Each type stays under the 60-line method and 7-parameter limits.

### Hand figures (the tests' expected values)

- **HRA saturation**, old regime. Pack `SAL-HOUSE-RENT-ALLOWANCE` limbs: (b) rent − 10 % of salary, (c) 50 %
  of salary for a metro. Salary 6,00,000 and rent 3,00,000: (b) = 3,00,000 − 60,000 = **2,40,000**; (c) =
  **3,00,000**. Saturation is the least, **2,40,000**. With HRA movable from 0 and enough residual, suggested HRA
  = 2,40,000; at 2,40,001 `totalIncome` is unchanged.
- **New regime:** the same move saves 0 (the HRA exemption is excluded there), so where the new regime wins, the
  suggestion is "no change".
- **Bills:** each case's before and after bill is worked by hand from the pack's slab rows, cited in the build
  report. Expected values are never copied from a run.
- **Properties:** the result is never worse than the input; exhaustive ≤ greedy; C3 holds on every result.
