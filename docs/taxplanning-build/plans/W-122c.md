## Plan for W-122c — the first figure

> **Approved as recommended — C1a – C4a** (owner, session 101, 2026-11-16). Every path below was read on 2026-11-16 at `dc942854`; grep each
> again before relying on it. Probe: code read; no code changed.

**What this item is for (one sentence, in my own words):** one call takes step 1's answer — the year's gross pay — and
returns the tax under each regime of the year, labelled coarse with its band. It creates the draft and marks step 1
answered, so a person sees a figure before filling in any form (PRD F34.1; `DR 20` F34; W-122 C1a, C2a, D-701).

**Probe (2026-11-16): what an otherwise empty draft needs to compute.**
- **A profile.** A draft lives under a profile's year workspace (`DraftController.java:51` →
  `DraftService.createDraft`, `DraftService.java:96`, which also needs a label, `:97`). The assessee's age and residence
  come from the profile (`EngineInputsAssembler.java:61`, `:88` – `:93`). The call therefore takes an existing
  profile, as draft creation does.
- **A due date.** A blank draft (`DraftInputs.blank()`, `DraftInputs.java:39`) cannot compute.
  `Filing.toFilingFacts` refuses it: *"A computation needs the draft's /filing/dueDate"* (`DraftInputs.java:104` –
  `:107`). No rule in the pack holds the return's due date: the person states it, and extensions are why
  (`DeadlineSpec.java:6` – `:7`). The only fallback in the code is a sentinel, the year's end, used for capital-gains
  reads (`EngineInputsAssembler.java:77`). That would be an assumption.
- **Nothing else.** A draft holding one employment and a due date computes today. `DraftIntegrationTest.renting`
  (`:513`) saves an employment, a tenancy and a due date, and every compute case there runs on that.
- **The pay component.** W-122 C2a says "one fully taxable pay component, nothing assumed". `BASIC` is in the salary
  bases, so it would move HRA's and PF's limits once step 2 splits pay. `SPECIAL_ALLOWANCE` is
  *"an allowance paid in money that no exemption covers. In no salary base"* (`exec/components/SPECIAL_ALLOWANCE.json`
  `_note`, D-094): taxable as salary, and it moves no base.
- **The regimes.** `DraftComputationService.compare` (`:98`) prices the year's default and each alternative through
  the election resolver (`TaxCalculator.compareRegimes`, `TaxCalculator.java:237`). Its codes name the regimes to
  compute.
- **The label.** `compute` (`DraftComputationService.java:68`) stores each computation with `coarse` and `band`
  (W-122b). After step 1 only step 1 is answered, so each figure is coarse.

**Hand figures:** TY 2026-27, a profile born 1985 (under 60), resident, no family. Gross pay ₹12,00,000; due date
31-07-2027, as the person states it.
- **New regime (the default):** 12,00,000 − 75,000 = 11,25,000. Tax is 5% × 4,00,000 + 10% × 3,25,000 = 20,000 +
  32,500 = 52,500. The rebate is the lesser of 52,500 and 60,000, so the bill is **₹0**. The band is ₹0 to ₹0, and
  the figure is still coarse.
- **Old regime:** 12,00,000 − 50,000 = 11,50,000. The bill is **₹1,63,800**. The band's lower end is **₹88,920**
  (the same rooms as W-122b's step 1: Schedule XV, health, own NPS, rent paid).
- **Refusals:**

  - A profile not this account's: 400, as `createDraft` gives today.
- **Red first:** the integration case asserting `coarse: true` on both figures is shown failing against a build that
