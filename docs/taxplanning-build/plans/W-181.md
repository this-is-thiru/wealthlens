**What is wrong today:** a caller posting `{"assetType":"GOLD_BOND", …}` with no `maturityDate` to
`/portfolio/user/{email}/transaction` or `…/transaction/v2` gets 200, and the trade is stored with null in
`transactions.maturity_date` and `assets.maturity_date` — while the same row through the Excel upload is refused
with a 400. The same instrument fact is required on one entry point and absent on the two that are actually used.

### Choices (recommended first)

**C1 — the message.**

- **(a) Recommended: `A GOLD_BOND needs its MATURITY DATE; it is not assumed`.** The parser's sentence with only
  its `Row N:` locator and the word "row" dropped. Both messages compose the field name from
  `ExcelHeaders.MATURITY_DATE`, so they cannot drift on it; the Excel text stays exactly as pinned.
- (b) The parser's sentence unchanged, "row" included. Literal sameness — but a JSON caller is told about a row it
  never sent.
- (c) A JSON-specific sentence naming the JSON field: `A GOLD_BOND needs its maturityDate (yyyy-MM-dd); it is not
  assumed`. Clearest for a client, but then the two entry points teach two messages, against the item's words.

Why not (b): byte-identical is impossible without inventing a row number for JSON, and the item asks for "the same
message", not "the same bytes". (a) keeps every word that carries meaning (the type, the field, "it is not
assumed") and drops only the Excel locator.

**C2 — buys only, or both sides?**

- **(a) Recommended: both sides, exactly as the Excel rule does.** `setMaturityDate` fires on any `GOLD_BOND` row,
  read or sell; the guard in `validateAssetRequest` runs before the side is known, so this costs no extra
  condition, and the two paths keep one rule.
- (b) Buys only. A sell of a bond bought before today stays submittable without the date — but the rule would then
  read differently from the Excel path's, and the sell's own transaction row would keep a null whatever the
  portfolio holds.

**C3 — the redrive and the upload's own path.**

- **(a) Recommended: leave `processTransaction` unguarded.** The upload is guarded by the parser (row-located);
  a redrive finishes a temporary transaction the user already submitted under the old rule, and refusing it would
  strand a stored row with no route but deletion. The JSON endpoints reach it only after the new guard.
- (b) Guard `processTransaction` too. Uniform, but a `GOLD_BOND` temporary transaction stored before today becomes
  unredrivable — a hole with no remedy short of a database edit.

### Risks or ambiguities

1. **A live endpoint starts refusing.** Any client that posts a `GOLD_BOND` without a date now gets a 400 where it
   got a 200. That is the item, but it is a behaviour change on a live API path; no request in `api-collection`
   does it (row 21), so nothing shipped breaks visibly.
2. **The two messages are not byte-identical** under C1a — JSON drops `Row N:` and "row". If the owner wants the
   arrays compared literally, take C1b.
3. **Sells are included** under C2a: a client selling a bond must now repeat the date, even though the sell does not
   consult it. The Excel path already behaves this way; if the owner prefers buys only, take C2b and the guard
   gains a transaction-type condition.
4. **Stored nulls stay.** The export column remains empty for bonds traded before this change; there is nothing to
   tell them from an omission, and inventing a date is what W-164 stopped.
