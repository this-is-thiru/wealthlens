**What this item is for (one sentence, in my own words):** the application stops running as root inside its container, without giving
W-131f's PDF reader a way back to the application's secrets.

### What the design, the code and the sources say

- **Today:** `Dockerfile` has no `USER`, so `java -jar /app.jar` runs as root (probe run 44338803065: `uid=0(root)`). `/app.jar` is
  `-rw-r--r-- root root` (same run). The deploy is `docker run -d -p 8080:8080 --name wealthlens-container tperamasani/wealthlens`
  (`aws/runbook-daily.sh:7`). Port 8080 needs no root.
- **The app writes nothing to disk:** `logback-spring.xml` has only the console appender (lines 10, 12). `rg` finds no file writes in
  `backend/src/main/java` except the child's stdout (`PdfReadChild.java:28`). Tomcat's multipart temp files go to `/tmp`, which any
  user can write.
- **The catch, from W-131f:** `IsolatedPdfRead` hands the reader to `nobody` only when the app runs as root (`launching(…, user)`).
  BusyBox `su` needs root to switch user without a password. A non-root app therefore starts the reader **as its own user**. A
  same-user process can normally read the app's `/proc/<pid>/environ` (the secrets), which is the hole W-131f closed. So "just add
  `USER`" would **reopen** it.
- **Linux's answer:** a process marked non-dumpable (`prctl(PR_SET_DUMPABLE, 0)`) has its `/proc/<pid>/environ`, `mem` and
  `maps` owned by root, and a same-user process cannot ptrace it. Java 25 can make that call without native code, through the Foreign
  Function API (`java.lang.foreign`). This is from the Linux and JDK documentation, **not yet observed here** (C4).

### Choices for the owner (recommended first)

- **C1 — the user:**
  - **(a)** `Dockerfile`: `RUN addgroup -S wealthlens && adduser -S -G wealthlens wealthlens` and `USER wealthlens`. `/app.jar` stays
    root-owned and read-only, so the app cannot rewrite its own code. No change to `docker run`.
  - (b) `docker run --user` in the deploy script instead. Not recommended: it depends on every deploy remembering it.
- **C2 — keeping the reader away from the secrets once the app is not root:**
  - **(a)** At start, on Linux, the app marks itself non-dumpable through the Foreign Function API. The reader, as the same user, is then
    denied the app's `environ`, `mem` and `maps`, and its environment is still cleared (W-131f). The start log says so. On macOS (dev)
    the call is skipped, with a log line. **Cost:** no core dumps of the app, and attach tools (`jcmd`, `jstack`) may not attach to it.
    C4 checks.
  - (b) A setuid-root helper (`su-exec` or `doas`) so the reader still becomes `nobody`. Not recommended: it puts a setuid-root
    binary into the image, which is more attack surface than it removes.
  - (c) Keep the app as root and close W-131j without code. The reader stays `nobody`, but a compromise of the app itself is root in
    the container.
- **C3 — what if the non-dumpable call fails at start on Linux:**
  - **(a)** The start fails, loudly. A deploy that cannot protect the secrets does not come up (fail fast, `CLAUDE.md` §4).
  - (b) Log a warning and carry on.
- **C4 — the probe:** may I run a one-off CI workflow on a throwaway branch? It would build the image with `USER wealthlens`, start a
  probe main as PID 1 with fake secrets that calls `prctl`, and check four things:
  - the reader reads PDFs;
  - the reader is denied `/proc/1/environ`, `/proc/1/mem` and `/proc/1/maps`;
  - a control run without the call **can** read them, so the check can fail;
  - whether `jcmd 1 Thread.print` still works.

### Five roles

- **Architect:** least privilege for the app, without trading away W-131f's separation. No setuid binary, no new dependency.
- **Product manager:** nothing visible changes. A broken deploy fails at start rather than running unprotected.
- **Senior engineer:** one small startup class, Linux-guarded, failing loudly. The image is the single place the user is set.
- **Automation tester:** the protection is proven by a child that reads the secret before and fails after. A control run in C4 shows the
  check can fail.
- **Manual tester:** on staging, `docker exec wealthlens-container id` shows `wealthlens`, the start log names the protection, and an
  upload reads as before.

### Risks or ambiguities

- **Diagnostics:** non-dumpable may stop `jcmd` and `jstack` attaching to the live app (C4 measures it). Thread dumps would then come
  from `kill -3` into the log.
- **The EC2 kernel** is not the CI runner's. The runbook's `id` check and the start log confirm it there.
