## Plan for W-162 — deductibility of a charge as tax-side rule data (split proposal)

**What this item is for (one sentence, in my own words):** which broker charges reduce a capital gain is decided today
by a yes/no flag on `brokercharges`' catalogue, summed by `portfolio` and baked into the one net gain the engine
receives; this item moves that decision into the engine's year-versioned rule data, so `portfolio` publishes the sale,
the cost and the charges as facts and the law of the year nets them (D-315; audit T4).

**This item is well over §7.** It touches three modules (`brokercharges`, `portfolio`, `taxengine`), the engine's
input shape, and two stored fields — each of which needs a one-time operation (R15). This plan builds nothing: it
asks C1 – C4 and proposes a split (C5). On approval I place the rows, record D-375, write the first sub-plan, then
stop.

### C1 — where the decision lives

- **(a) recommended: the engine nets the gain.**
  - Each `portfolio` bucket carries facts instead of a net gain:
    - the full value of the consideration;
    - the cost — the adjusted buy price × quantity;
    - the charges by side (acquisition / transfer) and code, summed over the bucket's rows.
  - `CapitalGainsInput.Bucket` carries the same.
  - A new rule set `RS-CG-CHARGE` has a row per code, both years. Each row says what that code is under s.72(1) /
    s.48: (a) transfer expenditure, (b) part of the cost, or disallowed (s.72(3)(b) / the sixth proviso). It tests
    item facts `charge.code` and `charge.side`.
  - `CapitalGainsNode` computes each bucket's gain from the facts, with a trace line per charge naming its row.
  - The figures do not change for any code the catalogue holds today.
- **(b) a gain computed in `taxplanning`'s adapter from year data there.** The law would then sit outside the
  pack, the trace and the lock. I do not recommend it.
- **(c) keep the flag in `brokercharges`, windowed by year.** That is still law in the charge module, against
  D-315's direction. I do not recommend it.

### C2 — the nine codes the Acts do not name (yours)

- **(a) recommended:** carry today's classification unchanged as rows.
  - Buy-side charges go to cost under (1)(b); sell-side charges to transfer expenditure under (1)(a).
  - Each row's `_note` gives the clause it rests on and the charge's nature, from the catalogue's own description.
  - The reading is recorded as your ruling in D-375. The `STT` row is the only one sourced READ.
  - `AMC` and `ACCOUNT_OPENING` are billed per account, not per trade, so they never reach a trade breakdown and

- **(b) source first:** I give you a ChatGPT prompt asking for a CBDT circular or judgments on brokerage, stamp
  duty, GST on brokerage, DP charges, exit load and the mutual-fund transaction fee as transfer expenditure or
  cost. The rows wait for the share.

### C3 — a code no row covers

- **(a) recommended: refuse the computation, naming the code and the year.** This is the engine's rule for an
  uncovered bucket, `CapitalGainsNode:149–158`. A unit test reads `charge-catalogue.json` and checks that every
  code is either covered in every shipped year or recorded as account-level. A new code without a row therefore
  fails the build first.
- **(b) exclude the code with a trace line.** That is today's behaviour, but it lets an unknown cost pass
  quietly, against CLAUDE.md §2 ("nothing silent").

### C4 — user-entered misc charges (uncoded)

- **(a) recommended:** pass them as facts too, per side under one code, `MISC`. One row per year says they are not
  deducted, as today, and its `_note` gives the reason: the record does not say what they were for. The choice is
  then visible in the data and the trace, not in `portfolio`.
- **(b) leave them out of the bucket,** as today. This would be recorded in the audit file as `portfolio`'s
  evidentiary choice.

### Risks or ambiguities

1. **Rounding.** Today each row's gain is scaled to the paisa before buckets sum it
   (`CapitalGainsSummaryService:103`). Netting in the engine must scale the same figures in the same order, or a
   bucket can move by a paisa. W-162a's plan pins this with a case whose per-row figures carry three decimals.
2. **The engine input changes shape.** Eleven construction sites in four files build a bucket, nearly all in
   `CapitalGainsNodeTest`. Golden cases that carry capital gains need the facts form. I will count them in W-162a's
   plan.
3. **The summary's reference digest** (`CapitalGainsSummaryService:157–163`) hashes each row's gain. It will hash
   the facts instead, so its value changes for the same rows. Nothing stores it (`grep`: only the adapter passes it
   on), so no pinned draft is affected.
4. **`AssetCharges.deductibleSellCharges` disappears from the holdings responses** (W-162b). `portfolio` cannot
   ask the engine, because that would close a module cycle (`plans/W-160.md`). A per-holding deductible figure, if
   wanted, would be a `taxplanning` read endpoint. Nothing is proposed here unless you want one placed.
