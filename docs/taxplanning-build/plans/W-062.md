## Plan for W-062 — the salary bases, and what grounds them

**What this item is for (one sentence):** `salary.base` becomes the narrow "salary" that HRA, gratuity, leave
encashment and both NPS limits measure against: basic, plus dearness allowance where the terms of employment
provide for it, and nothing else. It is computed once, by one function, and cited to each rule that defines it.

**This plan raises design decisions (C1–C6) before anything is built.**

### Findings

1. **The ordering question recurs (D-084, D-089).** Nothing consumes a base yet: HRA is `W-067`, gratuity and
   leave encashment are the retirement node, NPS is `W-076`. No component that would be in a base exists yet
   (`W-064`). The node can be built and evaluated now, but every shipped run computes ₹0 bases until `W-064`,
   and nothing reads them until `W-067`.
2. **A base definition has no row shape.** "Salary includes DA if the terms provide, but excludes all other
   allowances and perquisites" is a definition, like `SAL-DEF-001`, but it isn't a head total.
3. **The DA condition has no home.** The registry says which components a base includes. Nothing says which
   of them count *only where the terms of employment provide*.
4. **`DR 05`'s field is misplaced and misnamed.**
   - The terms of employment belong to an employment, not to a pay line: the flag means nothing on `BASIC`.
   - The statute's words are *"if the terms of employment so provide"* (s.19(2)(b), s.124(13)(b), para 1(y)) /
     *"if provided for under the terms of employment"* (r.279(2)(b)). "Forms part of retirement benefits" is a
     different test, which the rulebook's quotations do not contain.
   - The two wordings differ slightly. H-4 treats them as one test; I'd follow H-4 and record it.
5. **`DR 15`'s `Map<RuleId, Money>` loses the employer.** HRA and gratuity are per employer (and HRA is per
   period, `SAL-HRA-003`), so a base summed across employments would be wrong for two employers.
   - The value should be per rule **and** per employment.
   - Per-period apportionment stays `W-066`/`W-067`'s ("no caller divides").
6. **"Five rules"** matches H-4's five *uses* (HRA, gratuity, leave encashment, employer NPS, employee NPS),
   which are **four** rule ids. `SAL-DEF-RPF-001` is a fifth id, but its base is unread (R1: can't ship).
7. **TY 2025-26** (standing rule 3): every 1961 counterpart is unverified.
   - The rulebook's "s.17(1) Expl. / r.2BA" for gratuity looks doubtful: 1961 gratuity is s.10(10), and leave
     encashment is s.10(10AA), which uses "average salary".
   - These must be read, or authored `UNVERIFIED` with `whatToCheck`.
   - Reading r.2A also settles `SAL-DEF-COMM-001` for 2025-26.
8. **A base is none of the seven `StepKind`s.** It is a measure that other lines use.

### Choices (recommended first)

- **C1 — scope and order.**
  - **(a) recommended: build and ship the node and the rows now, with no components.** The four verified
    definition rows go in, both years. `SalaryBaseNode` evaluates them, so I3 holds with no exception. Each row
    is ₹0 for everyone until `W-064` gives `BASIC`/`DA` a `salaryBaseFor`. D-089's order is unchanged.
  - **(b)** Also pull `BASIC` and `DA` forward from `W-064`, so a shipped run computes a real base now. This
    changes D-089's assignment.
  - **(c)** Build the node on a fixture only (like `W-059`) and ship rows with their consumers. This isn't
    possible as it stands: a node's `rules()` names `RuleIds` constants, which exist only for shipped rows.
- **C2 — the row shape:** a second `RuleDefinition` member, `SalaryBase`: "the components the registry lists
  for this rule, plus those listed as included only where the terms of employment provide, when they do."
  It carries no amounts and names no components (so it does not need `DA` to exist).
- **C3 — where "only where the terms provide" lives.**
  - **(a) recommended: in the registry.** A `salaryBaseFor` entry becomes `{rule, onlyWhereTermsProvide}`.
    `RegistryJson` changes shape, which is free now because no component ships.
  - **(b)** On the row, as a set of component codes. The row would name `DA` before `DA` exists, so I2 fails
    until `W-064`, which forces C1b.
- **C4 — the entered fact.**
  - **(a) recommended:** `Employment` gains `termsIncludeDearnessAllowance` (a boolean, required), named after
    the statute's words. It departs from `DR 05`'s `SalaryComponent.daFormsPartOfRetirementBenefits`, for
    finding 4, and that departure is recorded as an erratum.
  - **(b)** Keep `DR 05` as written.
- **C5 — the value:** `SalaryBases` (a new `NodeValue`) holds, per rule id, per employment position, the
  `Money` base, plus the counted lines. `asMoney()` is used for the trace summary only, as for `ComponentSet`.
  `DR 15`'s `Map<RuleId, Money>` is superseded (finding 5), and that is recorded as an erratum.
- **C6 — the trace.**
  - **(a) recommended:** one line per rule, citing it, with the counted lines in `in`. This needs a new
    `StepKind`, `MEASURE` ("a figure other rules are computed on; neither income nor relief").
  - **(b)** No line. The consumers show the base in their own lines' `in`. That's smaller, but the ₹0-until-
    `W-067` base would then be unexplained.
