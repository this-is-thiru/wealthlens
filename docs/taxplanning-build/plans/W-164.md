## Plan for W-164 — a Gold Bond's maturity not defaulted

**What this item is for (one sentence, in my own words):** an uploaded Gold Bond row with no maturity date should
not get one made up as "eight years after the trade". The date is a fact about the bond, and the app should not
assume it.

**Source:** `03-WORK-ITEMS.md` W-164; `reviews/2026-10-21-law-in-code-audit.md` § W-088l3, row **T5** (*"L1 (law not
identified), and a default in place of a missing fact | require the date, or take it from instrument data"*); D-315.

### What I read (session 38, 2026-10-28)

- **The default:** `portfolio/service/parser/AssetRequestParser.java:175-181`, `getDefaultMaturity`:
  ```
  case EQUITY, BOND, MUTUAL_FUND, FD, INSURANCE -> null;
  case GOLD_BOND -> maturityDate != null ? maturityDate : transactionDate.plusYears(8);
  ```
  It is called once, from `setMaturityDate` (`:107-112`), for every uploaded row, whether it is a buy or a sell.
- **Where it is reached:** only the Excel upload. `PortfolioService.uploadTransactions` (`PortfolioService.java:208-228`)
  is the only caller of `new AssetRequestParser(quarter)` (`:214`). The JSON paths (`addTransaction`, V2) take
  `AssetRequest.maturityDate` (`AssetRequest.java:75`) as sent, with no default. A Gold Bond sent there without
  a date is stored with none.
- **What reads the date afterwards:** nothing calculates with it. It is copied to `TransactionEntity` /
  `AssetEntity` (`AssetRequest.java:107`, `:136`; `maturity_date`), returned in the response DTOs and exported
  (`PortfolioExportColumns.java:47`, `:74`, `:97`). No tax or P&L code reads it.
- **Instrument data:** none. `GOLD_BOND` appears only in `AssetType.java:7` and this `switch`. No tranche list,
  issue calendar or Gold Bond seed exists in `src/main/resources`.
- **A second defect in the same method:** a maturity date given on a `BOND`, `FD`, `MUTUAL_FUND`, `EQUITY` or
  `INSURANCE` row is **discarded**, because those cases return `null` whatever the cell holds. The JSON path keeps
  it.
- **How an upload refuses today:** a bad `BROKER NAME` or `ASSET TYPE` cell makes `valueOf` throw
  `IllegalArgumentException` (`:90-104`), which becomes a 400 before anything is written (`uploadTransactions` parses
  everything first). A column-count mismatch goes into `errors` as `"… in row: N …"`
  (`AssetRequestParserImpl.java:93`).
- **Tests:** there is no parser test. `backend/src/test/java/.../portfolio/service/parser/` does not exist, and no
  test reaches `AssetRequestParser`.

### Choices (recommended first)

- **C1 — what replaces the default (the audit offers two):**
  - **(a) recommended: require the date.** A `GOLD_BOND` row with an empty `MATURITY DATE` refuses the upload with
    `BadRequestException` (400, nothing written), naming the row in the same numbering as the existing column-count
    error: *"Row N: a GOLD_BOND row needs its MATURITY DATE; it is not assumed"*. This applies to buy and sell rows,
    which are the rows the default reaches today.
  - **(b) take it from instrument data.** No such data exists. It would need a new, sourced data set of RBI tranches
    and a lookup by `STOCK CODE`, which is a feature, not this fix.
  - **(c) leave it absent.** Store no date, as the JSON path does. This changes the least, but the upload then
    accepts an incomplete Gold Bond without saying so.
- **C2 — the discarded date on the other asset types:**
  - **(a) recommended: keep a given date for every type.** The rewrite reads the cell, refuses a missing one for
    `GOLD_BOND`, and otherwise stores what was given. The `switch` goes, and keeping the drop would need code of its
    own. This changes behaviour: a `BOND` row's date is stored instead of dropped. A test covers it.
  - **(b) keep dropping it.** Change only the Gold Bond branch, and you place a separate row for the drop.
- **C3 — the JSON paths** (V1 / V2 accept a Gold Bond with no date):
  - **(a) recommended: not in this item.** The finding is the parser's default. I report it under "Found, not
    changed" for you to place or dismiss.
  - **(b)** Require it there too, in V1 and V2. That is a validation change on two live API flows.

### What I will build (C1a, C2a, C3a)

1. `AssetRequestParser`:
   - `setMaturityDate` takes the record number.
   - A `GOLD_BOND` row with no date throws `BadRequestException` with the message in C1a. Otherwise the cell's value
     is stored.
   - `getDefaultMaturity` is deleted, along with the `AssetType` import if it becomes unused (`setAssetType` still
     uses it).
2. New `backend/src/test/java/com/thiru/wealthlens/portfolio/service/parser/AssetRequestParserTest.java`, a plain
   unit test that builds an `InputRecord` from `CellDetail.of(...)` and calls `toRequest`. It sits in the same
   package, so the protected method is reachable:
   - `toRequest_whenGoldBondHasNoMaturityDate_refusesNamingTheRow`
   - `toRequest_whenGoldBondHasMaturityDate_keepsIt`
   - `toRequest_whenBondHasMaturityDate_keepsIt` (C2a)
   - `toRequest_whenEquityHasNoMaturityDate_leavesItAbsent`

   The expected dates are the ones put into the cell (2032-02-15 and similar), not anything the code computes.
3. **Probe:** restore the `plusYears(8)` default, and the first test must fail. Then revert byte for byte.
4. WI row, STATE (D-386), CHECKPOINT.

### What I am NOT doing

- Gold Bond instrument data (C1b).
- The JSON paths (C3a).
- Correcting stored rows. A date that was defaulted in the past cannot be told apart from one that was given, so
  there is nothing to select safely.
- The upload template (`EntityExportService.templateRow`, an `EQUITY` row with today as its maturity). That is a
  sample row, not a default.

they have (see "NOT doing").

### Risks or ambiguities

1. **Your existing sheets.** A quarter's sheet that relied on the default (a Gold Bond row with no date, buy or
   sell) will now be refused until the date is filled in. That is the point of C1a, but it is a visible change for
   you.
2. **Row numbering.** "Row N" counts data rows from 1, below the header, as the existing column-count error does.
   In Excel that is sheet row N + 1. I keep the existing numbering rather than invent a second one.
