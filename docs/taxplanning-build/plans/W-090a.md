engine cannot compute (assets abroad, directorships and the like), so W-090c's forms can bar on them as data.

- F2 — `ConditionContext` throws for a fact it does not hold rather than answer false (`ConditionContext.java:11` – `14`,
  D-NOSILENT). A declaration therefore needs three states: yes, no, and not answered. Not answered is refused with the
  question named.
- F3 — Where a declaration can live:
  - `EnteredFacts` is built in 37 files (grep `new EnteredFacts(`).
  - `FilingFacts` ("what was filed, when, and what had already been paid", `FilingFacts.java:32` – `34`; `DR 23` A3) is
    built in 8; the draft carries it as `DraftInputs.Filing` (`DraftInputs.java:51`).
  - `ConditionContext` is built in 8 places, one in main code for a run (`NodeContext.java:344`).

**Choices for the owner:**
- **C1a (recommended) — one open vocabulary, not one type per bar.** A declaration is `{code, answer}`, where the
  answer is yes, no, or an amount. Each code is a row in the pack's exec layer (`exec/declarations/<CODE>.json`: the
  question, the answer kind, the r.164 clause it serves, provenance). Two conditions read them: `Declared(code)` and
  `DeclaredAmountAbove(code, limit)`. A new bar the law adds next year is a data row, not code. The pack refuses a form
  that names a code it lacks.
- C1b — the design's sketch: one input field and one `Condition` type per bar (nine fields, nine types now, more each
  time the Rules change).
- **C2a (recommended) — declarations live on `FilingFacts` / `DraftInputs.Filing`.** They are what the return asks the
  person, beside the due date and the payments, and that is 8 call sites, not 37. C2b — on `EnteredFacts`.
- **C3a — split W-090a in two:**
  - **W-090a1** — the engine: the declaration catalogue in the pack (reader, compiler, locks), `DeclarationCode`,
    `Declaration`, the field on `FilingFacts`, `ConditionContext`, the two conditions, refusal of an unanswered or
    unknown code. Proven on the synthetic pack.
  - **W-090a2** — the draft: `/filing/declarations` in a patch, validated against the year's catalogue; the nine
    shipped rows (a – d, f – j) with r.164 provenance; the api-collection request.
  - (l) – (n) are read at the start of W-090a2. Any that turn out to be declarations join as data rows (C1a); any that
    are computed move to W-090c. A finding that changes this plan stops me (R13).

**Post-deployment actions (R15):** none in this step.

**Five roles:**
- Architect: facts, not labels — "holds a directorship", never "ITR-1 eligible"; an open vocabulary as law-in-data.
- Product manager: the user will answer about nine questions, once per year's draft; an unanswered question blocks only
  the form recommendation, never the tax figure.
- Senior engineer: 8 call sites, not 37; no field without a caller (each code is read by a W-090c bar).
- Automation tester: three-state cases per condition; unknown and unanswered refused.
- Manual tester: in W-090a2, patch a declaration and read it back.

**Risks or ambiguities:**
- (l) – (n) unread, so the count of nine may change.
- Agricultural income enters the rates (partial integration) in law, which the engine does not compute today. A user
  with agricultural income gets a form bar, but the tax figure ignores it. That is an existing gap, not new here, and it has no row (grep
  `agricultural` in `03-WORK-ITEMS.md` and `PARKED-ROWS.md` finds only W-090a). **C4a** — on approval I place
  **W-258**, agricultural income in the rates (partial integration), Phase 14, before the one deploy. Its law is to be
  read when it is planned.
