## Plan for W-238g — an employee's own contribution is not pay to move

**For:** a user asking the optimiser to restructure pay. Today it accepts a component the employer does not pay,
such as `EMPLOYEE_NPS`, funds it from the residual, and reports a cash impact twice the move. That should be
refused on the way in. Row `03-WORK-ITEMS.md` W-238g (W-238b finding, D-490). Design: `03-advisory.md` A2.1 (the
variables are the allocation of a fixed cost to company), A2.2 C1 (budget), C3 (cash floor, `D-CASHFLAG`).

### What I located (session 70)

- `AllocationPricing.over` checks only that each movable code and the residual exist in the year's pack
  (`taxengine/optimise/AllocationPricing.java:81-87`). Nothing reads a row's `kind` before moving it.
- The pack's 51 component rows (`rulepacks/timeline/exec/components/*.json`), counted by script: 19 `SALARY`/`CASH`,
  4 `EMPLOYEE_CONTRIBUTION`/`CASH_OUTFLOW` (`EMPLOYEE_NPS`, `EMPLOYEE_PF`, `EMPLOYEE_SUPERANNUATION`,
  `GOVERNMENT_DEFERRED_ANNUITY`), 27 `QUALIFYING_PAYMENT`/`CASH_OUTFLOW`, 1 `STATUTORY_DEDUCTION`/`CASH_OUTFLOW`
  (`PROFESSIONAL_TAX`). No `PERQUISITE` or `EMPLOYER_CONTRIBUTION` row exists. Employer funds move as `EmployerFund`s
  (W-238c), not as components.
- The residual is unchecked too. `PROFESSIONAL_TAX` or a life-insurance premium could be named as the pay that
  funds every move.
- Two pieces become unreachable once only pay can move. (1) The refusal "EMPLOYEE_PF follows BASIC, so it cannot
  also move by itself" (`AllocationPricing.java:124-126`) is tested at `TaxCalculatorOptimiseTest.java:471-476`.
  (2) W-238f's `HrSupport.likelihood` is empty only for a non-`SALARY` name (`DraftOptimisation.java:38`;
  `DraftOptimisationTest.java:35-51` uses `EMPLOYEE_NPS`). The W-238f coverage test already requires a value for
  every `SALARY` row and every fund.

### Choices (recommended first)

**C1: which components the residual may fund.**
- (a) Only rows whose `kind` is `SALARY`, read from the pack row. Any other kind is refused in `over`, with a message
  naming the code and its kind. This is the only kind the employer pays out of the cost to company that has rows
  today. A `PERQUISITE` row, if one is ever added, would be refused until an item decides how it is priced. Nothing
  is written in Java about a particular code.
- (b) Refuse by cash nature: only `CASH_OUTFLOW` is refused. That would let a future `PERQUISITE` or
  `EMPLOYER_CONTRIBUTION` row through without pricing for it.

**C2: the residual.**
- (a) The same rule: the residual must be a `SALARY` row. Otherwise it is refused.
- (b) Leave it unchecked and place a row for it.

**C3: an employee contribution as a choice of its own.**
- (a) Do not offer it here. I place a row, **W-238k**: an employee contribution (`EMPLOYEE_NPS`, the voluntary part
  of `EMPLOYEE_PF`) priced as paid from take-home, never from the residual, under the cash floor. You choose where it
  goes.
- (b) Build it in this item. That means a new request field, a new result list and a new search dimension, which
  is roughly a W-238c-sized item.

**C4: what becomes unreachable.**
- (a) Delete the `EMPLOYEE_PF` refusal at `:124-126`. Re-point its test to the new refusal's message: still a
  refusal, same input. Make `HrSupport.likelihood` a plain value rather than an `Optional`, since every movable name
  now has a table entry. Update `DraftOptimisationTest` and the api-collection example to match.
- (b) Delete the `EMPLOYEE_PF` refusal only, and keep `Optional` in the response shape.

### Build steps (after approval)

1. Test first. Engine cases: `EMPLOYEE_NPS` movable → 400 naming it and `EMPLOYEE_CONTRIBUTION`; `PROFESSIONAL_TAX`
   movable → refused; `LIFE_INSURANCE_PREMIUM` as the residual → refused (C2a); `HRA` moved with `SPECIAL_ALLOWANCE`
   as the residual → priced as before. Integration: one draft request with `EMPLOYEE_NPS` → 400.
2. Add the check to `AllocationPricing.over`, beside the existence check. Apply C4. Update `AllocationSpace`'s
   javadoc (`movable`, `residual`).
3. Probe: remove the kind check, so the new tests fail. Then restore it by `cmp`.
4. Verify: targeted tests, `DraftComputationIntegrationTest`, then `./mvnw clean test verify` once.
5. Close-out: STATE board line 65, decision row D-496, CHECKPOINT, `02-TECH-SPEC.md` optimise row (the refusal),
   W-238k row (C3a). The runbook (WL-A-2) is unchanged, since there is no stored data, flag or seed.

**Numbers:** none. No rate, cap or amount is introduced. The cases reuse W-238a/b's hand figures.

**Not doing:** pricing an employee contribution (C3), W-238h's fund history, perquisites as movable.

**Risks:** an existing client that sends a non-`SALARY` code now gets a 400. That is intended. The only known
client is api-collection, and its example moves `HRA`.
