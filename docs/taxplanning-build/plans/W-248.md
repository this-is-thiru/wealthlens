## Plan for W-248 — personal data encrypted outside `taxplanning`

**For:** the personal data the other modules store is encrypted like the tax data, using one cipher in a shared
home. DPDP Rules r.6(1)(a) lists encryption or masking among the reasonable safeguards (`sources/2026-11-07-data-protection.md`
row 10; W-237b C4a, D-472).

### What I read (session 57)

- **The cipher today**, all in `taxplanning/protection` (CLOSED, so other modules cannot use it):
  - `FieldCipher` uses AES-256-GCM, writes a `k1:` prefix, and refuses a value without the prefix.
  - `EncryptedField` is the `@ValueConverter`. It takes only text, a date or an enum.

### Choices (recommended first)

**C1 — the cipher's home.**
- **(a) Recommended: move it to `shared/protection`.** The move covers `FieldCipher`, `EncryptedField`,
  `IdentifierDigest` and `KeyBytes`. `TaxDataKeys` is renamed `PersonalDataKeys`, with the prefix
  `app.personal-data`.
  - The properties keep reading `${TAX_DATA_KEY}` and `${TAX_DIGEST_KEY}`. That means the same key and no
    deploy change, so every stored `k1:` row still reads.
  - `taxplanning` already depends on `shared`, so no `allowedDependencies` change is needed.
  - The access log stays in `taxplanning`.
- (b) A second key pair for data outside tax. This limits what one leaked key exposes, but adds two environment
  variables and a runbook entry for every database.
- (c) Expose `taxplanning.protection` as a named interface. Not possible: `portfolio` and `insurance` may not
  depend on `taxplanning`.

**C2 — which fields.**
- **(a) Recommended: encrypt the free text and third-party contacts now** (the first row of the table).
  - Place **W-253** for identifiers: email, `account_holder` and `demat_account_id`, each stored encrypted beside a
    keyed digest, with every query rewritten to use the digest. That is a query-wide change across about 35 files,
    the login and the erasures, and needs its own plan.
  - Financial figures stay plain. They rest on storage encryption and access control, which W-237f fact 1 (Atlas
    tier and backup) is still waiting for you to confirm. W-253's plan says this again.
- (b) Everything, including email, in this item. Not recommended: it mixes a cryptographic change with a rewrite of
  every query.
- (c) Free text only, with nothing placed. Not allowed (`never-leave-items-unplaced`).

**C3 — rows already stored in plain text** (`EncryptedField` refuses them on read).
- **(a) Recommended: a one-time `SUPER_USER` endpoint, `POST /privacy/stored-fields/encrypt?dryRun=true`.**
  It follows the pattern of `ProfitAndLossV2Backfill` (D-280).
  - It reads raw `Document`s and encrypts each named field that lacks `k1:`.
  - Each update is conditioned on the plain value still being there, so a second run, or a run after one that
    failed part-way, changes only what is left.
  - It reports counts per collection.
  - Removal row **W-254**, with a tracker issue.
- (b) Clear the collections instead. Not possible: the processing log must be kept a year (r.6(1)(e), row 10),
  and W-237e keeps privacy records a year.
