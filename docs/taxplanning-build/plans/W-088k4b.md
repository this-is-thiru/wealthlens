## Plan for W-088k4b — correct the bonus lots processed before W-088k4a

**What this item is for (one sentence, in my own words):** a one-time, `SUPER_USER`, dry-run-first operation that
records each existing bonus action's allotment date (owner-supplied) and re-dates that action's bonus lots,
transactions and `trade_outcomes` rows from the ex-date to it, so their holding period starts where the law starts it
(D-306 C2a, D-307).

**This plan raises C1 – C3.**

- **Where a bonus left its mark** (`CorporateActionService:336–395`):
  - **the bonus lot:** an `AssetEntity` with `corporate_action_type` `BONUS` and `transaction_date` = the action's
    ex-date;
  - **the bonus transaction:** a `TransactionEntity` with the same type and date;
  - **every lot and transaction of the holding:** each gets a copy of the action in `corporate_actions` (`:362–366`,
    `:391–394`), copied by `TJsonMapper.copy`, so with the action's id.
  - **`trade_outcomes` rows from a sold bonus lot:**
    - `buy_date` is the lot's date;
    - `holding_period_days` is `DAYS.between(buy, sell)` (`TradeOutcomeRecorder:141`, `TradeMatchingService:207`);
    - `capital_gains_type` is `portfolio`'s classifier on those dates (`TradeOutcomeRecorder:120`);
    - `acquisition_corporate_action` is `BONUS`;
    - `source_buy_lot_id` is the asset id for V2 and V1, and a synthetic lot id for the rebuild
      (`RebuildBuyChargeCorrection:51`).
- **§2.2's rebuild** re-derives a user's rows from transactions, but its rows carry no charge breakdown (runbook §3.1).
  Using it to re-date V2 rows would lose their breakdowns, so it is **not** the remedy here.
- **No endpoint** sets a field on an existing action (only `/update/priority`).

### Choices (recommended first)

- **C1 — how an existing action gets its allotment date:**
  - **(a) recommended:** the operation's request carries `[{ "corporateActionId": "…", "allotmentDate": "yyyy-MM-dd"
    }]`. For each entry it:
    - refuses an id that is not a `BONUS` action, and an action that already holds a **different** allotment date;
    - sets `allotment_date` (an equal one is a no-op), then re-dates (C2).

    It is one audited call per database, with the caller recorded, and no hand-written mongosh write.
  - **(b)** the owner sets each `allotment_date` with a runbook `mongosh` command first, and the call takes no body. It
    is simpler code, but a hand write to stored data with no audit.
- **C2 — what is re-dated, for each action given** (only rows still at the action's **ex-date**, so a second run
  finds none):

  | Collection | Matched by | Set |
  |---|---|---|
  | `assets` | `corporate_action_type` `BONUS`, `transaction_date` = ex-date, `corporate_actions` holds the action's id | `transaction_date` = allotment |
  | `transactions` | the same | `transaction_date` = allotment |
  | `trade_outcomes` | `acquisition_corporate_action` `BONUS`, `stock_code` = the action's, `buy_date` = ex-date | `buy_date` = allotment; `holding_period_days` recomputed; `capital_gains_type` re-run through `TradeClassifier` (D-302 D2a: `portfolio`'s own report) |

  - Every write sets `audit_metadata.updatedBy` / `updatedAt` to the caller.
  - **(a) recommended:** as the table.
  - **(b)** `assets` and `transactions` only, with `trade_outcomes` left to §2.2. That loses V2 breakdowns, so no.
  - **(c)** `buy_date` only, leaving `holding_period_days` and `capital_gains_type` inconsistent with it.
  - **Risk:** `trade_outcomes` has no action id, so it is matched by stock code, type and ex-date. A bonus on the same
    stock with the same ex-date is the same action. A stock renamed since (a symbol change rewrites `stock_code`) would
    be missed. The dry run reports matches per action, so a zero shows up.
- **C3 — where the code lives:** `portfolio/migration/BonusAllotmentDateCorrection`, beside the other one-time
  operations. `portfolio` may read `corporate`'s entity (`allowedDependencies` includes `corporate`). It has a
  controller in `portfolio/controller`, at `POST /corporate-actions/bonus/allotment-dates/correct` (`SUPER_USER`,
  `dryRun=true` default), and a report record `BonusAllotmentCorrectionReport` (per action: `assets`, `transactions`,
  `tradeOutcomes` counts, plus the dry-run flag and the caller).

before 21-1-2025, so the term is short (D-303).
