### Step 1 — the read-only count (you run it; nothing is written)

In `mongosh`, connected to each database the apps write to (`it-staging`, and prod's `Cluster0`):

```js
db.trade_outcomes.aggregate([
  { $match: { source_buy_lot_id: /^lot-/ } },
  { $group: {
      _id: { e: "$email", b: "$broker_name", h: "$account_holder", l: "$source_buy_lot_id" },
      rows: { $sum: 1 },
      charged: { $sum: { $add: [ { $ifNull: ["$buy_broker_charges", 0] }, { $ifNull: ["$buy_misc_charges", 0] } ] } } } },
  { $group: {
      _id: null,
      rebuildRows: { $sum: "$rows" },
      lots: { $sum: 1 },
      lotsSoldMoreThanOnce: { $sum: { $cond: [ { $gt: ["$rows", 1] }, 1, 0 ] } },
      rowsOnThoseLots: { $sum: { $cond: [ { $gt: ["$rows", 1] }, "$rows", 0 ] } },
      chargedOnThoseLots: { $sum: { $cond: [ { $gt: ["$rows", 1] }, "$charged", 0 ] } } } }
])
```

### Step 2 — the correction (built only if step 1 finds rows, and only on a fresh approval)

1. **`portfolio/migration/RebuildBuyChargeCorrection`.** For each user with an affected lot, it:
   - re-runs the rebuild's matching **in memory, read-only**, from that user's transactions, through the fixed
     `TradeMatchingService`;
   - pairs each recomputed portion with its stored row by `(email, broker_name, account_holder,
     source_sell_transaction_id, source_buy_lot_id)`;
   - sets only `buy_broker_charges`, `buy_misc_charges`, `total_buy_value`, `net_profit` and
     `profit_percentage`, where they differ.

   Rows written by V1 or V2 are never touched. Neither are other fields (FY, acquisition, classification).
2. **It refuses rather than guesses.** A user is skipped and named in the report, with nothing written for them,
   when the recomputation and the stored rows do not pair one to one. That happens if transactions were edited or
   deleted since the rebuild, or a row is missing. The report lists every skipped user and why.
3. **Dry run first.** `POST /trade-outcomes/rebuild-charges/correct?dryRun=true` (`SUPER_USER`, as
   `@PreAuthorize("hasRole('SUPER_USER')")` elsewhere) returns, per database, the rows that would change, the
   total buy charge before and after, and the skipped users. Writes happen only with `dryRun=false`. Idempotent: a
   second run finds nothing to change.
4. **Backup before the write, by you:** `mongoexport` of the rebuild rows (`source_buy_lot_id` starting `lot-`) in
   each database, kept until the correction is checked. The exact command goes in the step-2 plan.
5. **Tests:**
   - unit: the pairing, the refusal, the dry run, idempotence;
   - integration (Testcontainers Mongo): stored rows seeded with today's inflated charges for a lot sold 5 + 5,
     corrected to ₹5 + ₹5, and a V1 row and a V2 row beside them left byte-identical.
6. **Docs:** WI, STATE D-277, CHECKPOINT.
