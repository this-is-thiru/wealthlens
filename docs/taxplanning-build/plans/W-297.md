## Plan for W-297 — correct the segment stored before W-292 / W-295 (rev 2)

**Rev 2 (2026-11-12): two rules in C2a are corrected before any code (R13). C1a and C3a are unchanged.**

- **R2-1, the buy side.** Rev 1 took `buy_segment` from the row's lot's buy transactions. But a lot is deleted
  once sold out (`PortfolioService:487 – 491`, `:510 – 514`), so an intraday round trip's lot is almost always
  gone, and rev 1 would correct almost no rows.
  - Rev 2 takes it from the row's **holding's buys on its buy date**: transactions of type BUY with the row's
    email, stock, broker, account holder and `transactionDate` = `buy_date`. These are the buys a V1 lot merges, or a
    V2 lot is one of.
  - Where all of them agree on a non-delivery segment, `buy_segment` takes it.
  - Where they disagree, `buy_segment` is left and the row listed. This is a same-day mix stored before W-296.
- **R2-2, the guard.** Rev 1 corrected a row's `segment` and `sell_segment` "only where step 1 changed that
  transaction". A second run after a failure past step 1 finds no step-1 change, so it would never complete the rows.
  - Rev 2 corrects them wherever the **stored sale transaction's segment is non-delivery** and differs from the row.
    After step 1 that is the same set, and it stays the same on every run.
  - The probe becomes: drop the non-delivery condition. A V1 row whose sale transaction says `DELIVERY` (no charge
    row) but whose `sell_segment` says `INTRADAY` must then be overwritten, and so fail.
- Every rule still only moves a stored value to a recorded non-delivery fact.


**What this item is for (one sentence, in my own words):** every transaction stored before W-292 says `DELIVERY`,
and so do the lots and outcome rows built from it. This item restores the segment wherever stored data records the
real one: a trade's `user_charges` row (D-594), or an outcome row's `sell_segment` (D-597). It then puts each
affected user's lots and P&L right.

**Findings (read this session, 2026-11-12):**

1. **W-297's row says "then per user §2.12 → §2.2 → §2.11". §2.2 would harm these users.**
   - §2.2 rebuilds `trade_outcomes` from transactions. Its rows carry no charge breakdown, so the capital-gains
     summary refuses any user whose rebuilt rows carry broker charges (runbook §2.2 "Know this", D-238 C2a, §3.1).
   - A user with an intraday trade has charges, so §2.2 would make their summary unusable.
   - The rows have to be corrected in place instead.
2. **What records the real segment.**
   - **The trade's `user_charges` row** (`transaction_id`, `segment`, `event` BUY/SELL; `UserChargeEntity:81`,
     `:90`). It is written under the request's segment:
     - V2 always;
     - a V1 buy since W-280 (D-566);
     - a V1 sale through its P&L context (`PortfolioService:643`).
   - **An outcome row's `sell_segment`.** It is the request's on a live row (V1 `:678`, V2 `TradeOutcomeRecorder:209`)
     and the transaction's on a §2.2 row.
   - **A trade with neither stays unknown**: a V1 buy before W-280, or one recorded while the engine was off. That
     is said in the report and the runbook, and never guessed.
3. **The established one-time pattern** is a class in `portfolio/migration/` with a `SUPER_USER` endpoint, a dry run
   by default and a report. Examples: `BonusAllotmentDateCorrection` with its controller, and
   `ProfitAndLossSplitReshape` at `POST /profit-and-loss/split/reshape?dryRun=`. A test can prove that kind of
   operation idempotent, which §6 requires. A `mongosh` script can't be proven that way here: the transaction fix
   needs a join (`$lookup`), which `updateMany` cannot do.

**Choices for the owner:**

- **C1 — mechanism.**
  - **C1a (recommended):** `SegmentCorrection` in `portfolio/migration/`, `SegmentCorrectionController`
    (`POST /transactions/segment/correct`, `SUPER_USER`, `dryRun` default true) and `SegmentCorrectionReport`. Each
    database runs it once. A removal row (**W-299**) and a YouTrack subtask of WL-28 are opened when it is built.
  - C1b: owner `mongosh` scripts (`aggregate` + `$merge`), as §2.13 was. Simpler, but no test runs the script itself.
- **C2 — what it corrects, in this order. Every rule only moves a stored value to a recorded non-delivery fact.**
  - **C2a (recommended):**
    1. **Transactions:** set `segment` from the trade's BUY/SELL charge row where they differ.
    2. **Outcome rows:**
       - `segment` and `sell_segment` take the sale transaction's segment, but only where step 1 changed that
         transaction.
       - Then `segment` takes `sell_segment` where `segment` is still absent. This is the §3.19 case.
       - `buy_segment` takes the lot's buy transactions' segment, where the lot is still stored and every one of
         those transactions agrees. Otherwise it is left as it is and listed.
    3. **Report:** for each user, the transactions and rows changed, and the rows left listed (no lot, or mixed
       buys). It also lists the users who then need §2.12 (lots) and §2.11 (P&L). There is no §2.2 step.
  - C2b: transactions only. The rows go through §2.2, as the row says. This is refused by finding 1 unless you
    accept that the summary will refuse these users.
- **C3 — the per-user follow-up.**
  - **C3a (recommended):** a runbook entry, §2.14, that runs the endpoint and then, for each user it lists, §2.12 and
    then §2.11. §2.11's warning (W-295) is lifted for a user once this has run.
  - C3b: the endpoint also runs §2.12 and §2.11 itself. That makes one call do three things, and §2.12 and §2.11
    are standing operations with their own dry runs.

**Tests (`SegmentCorrectionIntegrationTest`):** data is seeded in the shape it had before W-292. Expected values
are by hand.
- A V2 intraday buy of 10 @ 100 and its sale @ 110. The transactions say `DELIVERY`, the charge rows say `INTRADAY`,
  and the row says `DELIVERY` / no segment.
  - The dry run reports 2 transactions and 1 row, and writes nothing.
  - The write corrects both transactions and the row (`segment`, `sell_segment` and `buy_segment` all `INTRADAY`).
  - A second run reports 0 and writes nothing.
- A V1 row with `sell_segment` `INTRADAY`, no `segment`, and no charge row. Its `segment` becomes `INTRADAY`.
- A buy with no charge row stays `DELIVERY`. It is not counted, and it is not listed as changed.
- A part-way failure: stop after step 1, then run again. The rows are completed, and nothing is changed twice.
- `USER` gets 403.
