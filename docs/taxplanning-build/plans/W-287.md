## Plan for W-287 — mutation testing for the trade ledger

**What this item is for (one sentence, in my own words):** `TradeOutcomeRecorder` and `TransactionService` join the
`mutation` profile, so a test that runs their code without checking its result is caught, as B-1 asked and W-282's C2a
could not yet do (D-570, D-571).

**Findings (measured this session, 2026-11-12):**

1. **The score is 80 %, not 57 %.** PIT scoped to the two classes (`TradeOutcomeRecorder*`, `TransactionService*`) over
   the unit tests in `com.thiru.wealthlens.portfolio.*` and `com.thiru.wealthlens.service.*` (the pom edited for the
   run, then restored): 84 generated, 67 killed (80 %), 8 survived, 9 with no coverage, test strength 89 %. D-571's
   57 % was measured before W-282's seven tests and over fewer test classes. Still under the profile's 85.
2. **The 17 unkilled mutants** (`backend/target/pit-reports/mutations.xml`):

   | # | Class:line | Mutant | Why it lives | Killable |
   |---|---|---|---|---|
   | 1 | `TradeOutcomeRecorder:63` | `<= 0` → `< 0` | only an empty lot list is tested; a zero-quantity lot is not | yes |
   | 2 | `TradeOutcomeRecorder:84` | returns `List.of()` | no test checks the returned rows of a recording sale | yes |
   | 3 | `TradeOutcomeRecorder:228` | fallback price → 0 | no test has a lot with no source buy | yes |
   | 4 | `TradeOutcomeRecorder:108` | `i < size` → `i <= size` | builds one extra, unused map | **no — equivalent** |
   | 5 – 7 | `TransactionService:106, 107, 118` | `addTransaction`: date default; `setEmail` dropped | no test sends a null date or checks the stored email | yes |
   | 8 – 10 | `TransactionService:52, 88, 89` | `recordTransaction`: date default; `setEmail`, `setIdempotencyKey` dropped | same, for V2 | yes |
   | 11 – 17 | `TransactionService:127, 131, 136, 140, 144, 148, 179` | the reads, the corporate-action queries, the save, the delete | covered by integration tests only, which PIT excludes | yes |

   Killing 1 – 3 and 5 – 17 gives 83 / 84 = **98.8 %**; only #4 survives.
