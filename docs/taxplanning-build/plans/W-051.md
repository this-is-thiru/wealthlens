## Plan for W-051 — `CessNode`

**What this item is for (one sentence):** the Health and Education Cess, 4% of the income-tax after rebate
(and, once it exists, the surcharge), read from a pack row and traced in one line. The cess can then
never be charged before the rebate (`REBATE-ORDER-001`).

### Findings

1. **The surcharge doesn't exist yet.** There's no `tax.surcharge` node ID and no surcharge node until
   `W-056`, so the node can't require it now. Without it, the cess is correct only where the surcharge
   is nil. Every `DR 08` case below 50 lakh has a nil surcharge (T2-1 is at the threshold: *"TI does not
   EXCEED 50,00,000 → no surcharge"*).
2. **A rate row with no new shape.** The cess is `PercentOfBase(4%, base)`, a cap shape used as a rate,
   exactly as the slab rates are `SlabLadder` caps. So no `W-049a`/`W-050a`-style wiring is needed.
3. **"Income-tax" is the whole post-rebate tax.** That's slab-rate and special-rate tax together
   (`TaxByBasis.asMoney()`). s.3(15) charges the cess on "such income-tax", with no split by rate basis.
4. **The ID is numbered.** `RATE-CESS-001` carries no year or OLD/NEW, so the `W-045d2` map left it. A
   concept name follows the rounding precedent (D-076).
5. **Standing rules.** The cess lives in the **Finance Act**, not in either Income-tax Act, and the
   coverage register and catalogue cover the two Acts' sections only (`content/acts/`). **No section
   is newly modelled**, as with the First Schedule ladders (D-072). Both years: TY 2025-26 (FA 2026
   s.2(6)) comes with `W-052c`, as for every other row.

### Choices (recommended first)

- **C1 — the surcharge (finding 1).**
  - **(a) recommended:** `CessNode` requires **`tax.afterrebate`** only, and the base is the post-rebate
    tax. There will be an erratum on `W-056` and T6: `W-056` adds `tax.surcharge` to this node's
    requires and to the base (tax plus surcharge).
    - The node's javadoc and the row's `_note` say plainly that the base lacks surcharge until
      `W-056`.
    - `W-053` runs T1 only, and every T1 case is below the surcharge threshold, so no golden case can
      be wrong in between. The T2 goldens come with `W-056`'s phase.
  - **(b)** Build `W-051` after `W-056` (reorder). This is correct from the start, but it holds up
    `W-052`/`W-053`, the first milestone, behind the whole of Phase 6.
- **C2 — the row: `RATE-HEALTH-EDUCATION-CESS`**, the concept from the Act's own name, "Health and
  Education Cess on income-tax".
  - TY 2026-27; `AllRegimes`; no conditions.
  - `cap: PercentOfBase {percent "4", base "INCOME_TAX_AND_SURCHARGE"}`. The base is named for what the
    Act charges it on, so the name stays true once `W-056` adds the surcharge.
  - `provision2025`: Finance Act, 2026 s.3(15); `provision1961`: Finance Act, 2026 s.2(6) (the 1961-side
    charge for AY 2026-27). `SOURCE_CHECKED`.
- **C3 — the node:**
  - `produces tax.cess`, `requires tax.afterrebate`, rules `{RATE-HEALTH-EDUCATION-CESS}`;
  - the in-force version's `PercentOfBase` is applied to `CapContext.of(base, afterRebate.asMoney())`;
  - it returns `MoneyValue(cess)` with **one `StepKind.TAX` line** (in = the base, out = the cess);
  - a row that isn't a `PercentOfBase` is refused, as `TaxByBasisNode` refuses a non-ladder.

## Built — where the build departs from the plan (for review)

- **B1 — the order probe is structural, not by figure.** The plan had the T1-N2 test supply both the
  pre-rebate and the post-rebate tax, so that a node reading the wrong one would fail on 2,400.06. That
  premise was wrong: `NodeHarness` refuses a stub the node doesn't declare. So:
  - a new test, `requires_isTheTaxAfterRebateNeverTheTaxBeforeIt`, asserts that `requires()` is exactly
    `{tax.afterrebate}`. The node can read only what it declares, so that is what keeps the order;
  - T1-N2 supplies the post-rebate 10.00 → 0.40;
  - the probe (declare and read `tax.bybasis`) fails that assertion, and the value tests fail because
    the harness refuses the mismatch.
