## Plan for W-358d1 — logs: a request id on every line, no email in any

> Planned in session 114 (2026-11-21), the first part of W-358d's split (D-872, `plans/W-358d.md`). Probe run before this plan (below).
> **Stop point: nothing is built until the owner answers C1 – C3.**

**What this item is for (one sentence, in my own words):** every log line written while serving a request names that request by an id
the caller also receives, and no log line ever carries a person's email, from our code, an exception message or a library.

### What the code is today

| | Today | Where |
|---|---|---|
| Request id | none: no MDC, no header | `grep MDC` |
| Log pattern | Boot's console pattern with `${LOG_CORRELATION_PATTERN:-}` already in it, and a `%replace` that masks a PAN-shaped token in a message or a stack trace (D-447 C4a), tested by `PanLogMaskTest` against the shipped file | `logback-spring.xml` |
| Boot setting | `logging.pattern.correlation` fills `LOG_CORRELATION_PATTERN` (Boot 4.1.0's configuration metadata) | `spring-boot-4.1.0.jar` |
| Emails written | 17 log statements name an email; `ControllerAdviser.log` (`:201`) writes **every** handled refusal's message with its trace at ERROR, and 5 messages carry an email (`AuthService:47, :51, :80`, `AccountErasureService:56`, `TransactionBasedTradeOutcomeMigration:81`) | `grep` |
| Processing log | `ProcessingLogFilter` stores one `privacy_processing_log` row per request with a principal (principal, subject email, method, route, status, address, time); no request id | `ProcessingLogFilter`, `ProcessingRecord` |

### Probe (run this session, all reverted)

A `RequestIdFilter` at `Ordered.HIGHEST_PRECEDENCE` (ahead of the security chain) putting a UUID in the MDC as `requestId` and in an
`X-Request-Id` response header; `logging.pattern.correlation: "[%X{requestId:-}] "`; an email `%replace` around the PAN one, replacing
`[A-Za-z0-9._+-]+@[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)*\.[A-Za-z][A-Za-z]+` with `[email]`. **Measured:**
- the header on a 200, on the security chain's 401 and on a 400; the logged refusal's MDC id equal to its response's header;
- live lines read `… [o-auto-1-exec-1] [2d1b1323-…] c.t.w.s.exception.ControllerAdviser : …`;
- an email masked in a message (`email: [email], ABCXXXXX4F`: both masks in one line) and in a stack trace (written once); left alone:
  `cluster0.x6trgen.mongodb.net`, `v1.2@3`;
- over the whole run of six test classes: **719** application lines, **531** with a request id (the rest start-up and background), **0**
  emails, **27** masked (e.g. `Fetching portfolio stocks of [email]`, `No erasure was requested for [email]`);
- PanLog 3, RouteAccess 8, ProcessingLog 10, Actuator 3 green with the change in.

### Decisions (for approval with this plan)

- **C1 — how no email reaches a log.** **C1a (recommended):** the mask in `logback-spring.xml`, as for PANs: it covers our 17 statements,
  every logged exception message and any library's line, in one place, proven against the shipped file; the 17 statements stay as they
  are and print `[email]`. **C1b:** C1a, and also reword the 17 statements and 5 messages to name no person (22 edits; the mask still
  needed for libraries and future lines).
- **C2 — whose id.** **C2a (recommended):** the app makes one for every request (a random UUID) and returns it; a caller's own
  `X-Request-Id` is ignored, so a log line's id can never be chosen or forged from outside. **C2b:** keep a caller's id when it is a UUID.
- **C3 — the processing log.** With emails masked in the logs, a line's id is what ties it to whom it concerned. **C3a (recommended):**
  each `privacy_processing_log` row also stores `request_id` (new rows only; nothing rewritten), so a masked line can be traced to its stored
  record. **C3b:** no change to the processing log.

### Files (if C1a – C3a)

equals its header; a caller's `X-Request-Id` is not echoed).

`ProcessingLogIntegrationTest` (a row's `request_id` equals the response's header); CLAUDE.md (cross-cutting: the header, the masks);
the runbook's "Next deploy" list (a line for callers: the header; `privacy_processing_log` rows gain `request_id`, older rows keep none).

oddly shaped address could pass (a quoted local part with spaces, which no account here can register).
