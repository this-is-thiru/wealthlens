## Plan for W-078g — the new regime's s.202(2)(a) disallowance set

**What this item is for (one sentence):** make "the new regime does not allow this" a fact the engine reads from one
shared set, citing s.202(2)(a). A disallowed rule is then explained as *disallowed* instead of quietly absent, and
35 rows stop restating it as their own `ExceptIn`.

### What I read

- **The row:** WI W-078g *(D-159)*:
  - `DIS-S202-2A`;
  - its basis row `REG-NEW-DISALLOW-001`;
  - run-time application, so a disallowed rule is explained as disallowed;
  - `NEW_TAX_REGIME` referencing the set;
  - the `ExceptIn NEW_TAX_REGIME` rows that rest on s.202(2)(a) moved onto it (1961 s.115BAC(2) for TY 2025-26).
- **Origin:** Appendix F; D-093 C4a (W-063 used `ExceptIn` for professional tax "until the set exists");
  `NEW_TAX_REGIME.json` `_pendingDisallowanceSets`.
- **Rulebook R2** `REG-NEW-DISALLOW-001`, renamed **`REG-NEW-TAX-REGIME-NO-EXEMPTION`** by the W-045d2 erratum (D-069).
  It is VERIFIED for TY 2026-27 against S2 s.202(2)(a), with (a)(iii) omitted by FA 2026 s.56.
- **TY 2025-26:** 1961 s.115BAC(2)(i) as substituted by FA 2023 s.52 (Gazette 244830, pp.33–34). It is already read
  and cited by the rows (e.g. `SAL-TAX-ON-EMPLOYMENT`, `SAL-HOUSE-RENT-ALLOWANCE`) and by sources
  `2026-10-07-chapter-via.md` M14.
- **Design:**
  - `DR 10` E3.3: `ExceptIn` exists because the statute speaks in exceptions.
  - `DR 10` E3.5: `disallowances.json` is shared and referenced by id (the s.205(1) pattern).
  - `DR 17` l.267: reuse a set.
- **Code as it stands:**
  - `pack/DisallowanceSet` (id, displayName, disallowedRules, basis `RuleId`, provenance) refuses an empty set, and
    `disallows` has **no caller**.
  - `PackValidator` l.110–113 requires the basis and members to be pack rules; l.169–178 (I6) checks a regime's
    references.
  - `RulePackCompiler` l.88 always writes `"disallowanceSets": []`, so **the timeline cannot author a set today**.
  - Nodes decide regime applicability themselves: **~30 call sites in 20 nodes** read
    `version.regimes().appliesIn(ctx.regime().code())`, and about eight of them write their own nil-line text
    ("not in the NEW_TAX_REGIME regime", `notInRegime(ctx)`, …).
  - A version needs a cap, relief, rounding, definition or condition (`RuleJson` l.112–133).
  - **I3 is live on the shipped pack** (`T1SlabAndRebateTest` l.106): every pack rule must be in some node's
    `rules()`.

### Findings

1. **Moving a row onto the set without run-time application changes figures.** Every node that today skips an
   `ExceptIn` row would apply it once the row is `AllRegimes`. So the seam and the migration of all ~30 call sites come
   first, and are what make the move safe.
2. **The basis row cannot be bare.** It needs a shape (`RuleJson`) and an evaluator (I3). Nothing like it exists:
   there is no regime-aware `Condition` and no definition that says "disallows".
3. **The rows (a scan for `ExceptIn NEW_TAX_REGIME` plus the cites):** 57 rows cite s.202(2)(a) or s.115BAC(2).
   - **35 are `ExceptIn NEW_TAX_REGIME` resting on them:**
     - 24 Chapter VIII `DED-*` rows;
     - HRA, the LTA concession and journeys rows, CEA, hostel, uniform, professional tax;
     - `HP-OWN-RESIDENCE-INTEREST`, and `HP-OWN-RESIDENCE-PRE-CONSTRUCTION` (TY 2025-26 only);
     - `SAL-ENTMT-ALLOWANCE` (TY 2025-26 only), and `SAL-LEAVE-TRAVEL-DISTANCE-RATE` (TY 2026-27 only).
   - **Not disallowances, so they stay `ExceptIn`:**
     - `SAL-STANDARD-DEDUCTION-ANY-OTHER-CASE` — s.19 Table Sl. 2(b) keys the amount on the regime;
     - `DED-NPS-EMPLOYER-OTHER` — the 10%/14% split of s.124(1), which the regime *allows*;
     - `PERQ-MEAL-VOUCHER` TY 2025-26 — r.3(7)(iii) second proviso, a Rule, not s.115BAC(2).
   - Each of the 35 must be read against its own clause before it moves, which is research per row.
4. **`DIS-S202-2A` carries a section number,** against D-035 / D-069 (concept names, no section). The basis row's
   concept name is `REG-NEW-TAX-REGIME-NO-EXEMPTION`.

### Choices (recommended first)

- **C0 — size (§7):** the whole row is about four parts: the set on the timeline, the basis row, the seam with ~30
  call sites and their nil lines, and 35 rows read and moved. That is well over 300 lines plus the row research.
  - **(a) Recommended — split in two:**
    - **W-078g** (this item) = C1–C6 below, with the one member Appendix F names, `SAL-TAX-ON-EMPLOYMENT`, both
      years. Estimate ~250 lines of code and tests.
    - **W-078g2**, placed directly after = the other 34 rows, each read against its clause of s.202(2)(a) /
      s.115BAC(2)(i), moved and errata'd; the three not-a-disallowance rows recorded as staying `ExceptIn`.
  - **(b)** One item.
- **C1 — where a set is authored:**
  - **(a) Recommended.** `timeline/law/disallowances/<id>.json`, one file per set, with a version per tax year
    (validity, basis, members, provenance). `TimelineReader` reads it, and `RulePackCompiler` writes the year's
    version into `disallowanceSets`, in the law layer, so it is checksummed and locked.
  - **(b)** Inline in `NEW_TAX_REGIME.json`. This loses "shared, by id" (DR 10 E3.5).
- **C2 — the set's id:**
  - **(a) Recommended.** `DIS-NEW-TAX-REGIME-NO-EXEMPTION`, the concept name matching its basis row (D-035), with a
    WI erratum noting the rename.
  - **(b)** Keep `DIS-S202-2A`.
- **C3 — the basis row `REG-NEW-TAX-REGIME-NO-EXEMPTION`:**
  - **(a) Recommended.**
    - A new definition `DisallowanceBasis(set)`, both years: TY 2026-27 from S2 s.202(2)(a) (p.227) and TY 2025-26
      from 1961 s.115BAC(2)(i) (Gazette 244830 pp.33–34). The row says which set it is the reason for.
    - `PackValidator` checks the link both ways: a set's basis row must name that set.
    - I3 counts a set's basis as evaluated wherever a regime references the set, because the seam (C4) cites it in
      every explanation.
  - **(b)** No basis row: the set carries its own provision and provenance. This contradicts the row and
    `DisallowanceSet.basis`.
- **C4 — run-time application:**
  - **(a) Recommended.** One seam, `NodeContext.inRegime(RuleId, RuleVersion)`, returning a sealed `RegimeVerdict`:
    - `Applies`;
    - `ExcludedByRow` — today's `ExceptIn` / `OnlyIn`, with today's wording;
    - `Disallowed(set, basis)` — "disallowed in the NEW_TAX_REGIME regime by s.202(2)(a)", with the provision taken
      from the basis row of the year.
  - All ~30 call sites move to it.
  - A new `ArchitectureTest` rule stops `..taxengine.node..` calling `RegimeApplicability.appliesIn`, so a future node
    cannot skip the set.
- **C5 — what a disallowed rule leaves in the trace:**
  - **(a) Recommended.** Where the node has the amount, the same nil line it gives today, with the `Disallowed` reason
    as `limitedBy`. Professional tax gains one, because `SalaryDeductionNode` leaves none today for a rule not in the
    regime. For an `ExcludedByRow` rule nothing changes.
  - **(b)** Only professional tax's line changes.
- **C6 — records:**
  - D-165.
  - `NEW_TAX_REGIME.json` `disallowances: [the set]`, with `_pendingDisallowanceSets` removed.
  - Errata: under WI W-078g (C0, C2), `DR 10` E3.5 (sets live under `law/disallowances/`), and the W-063 erratum
    block (professional tax now on the set).
  - TECH-SPEC `pack/`, `timeline/` and `pipeline/` rows.
  - Appendix F row marked done.
  - Both locks relocked and the law layers bumped (`2025-26.law.43` → `.44`, and the 2026-27 equivalent).

   honest but uneven, which is why W-078g2 sits directly after.
3. **Size.** If the call-site migration runs over, I stop under R13 and split it out rather than cut the ArchUnit
   guard.
