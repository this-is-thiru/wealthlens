## Plan for W-049a — a relief on a rule row (D-074, split from `W-049`)

**What this item is for (one sentence):** a rule version can carry a relief, read from the pack like
a cap, so that `W-049`'s rebate rows are data and no node hard-codes a rebate.

### What I read

- **The `W-049a` row** (added by D-074 at `W-049`'s EXPLAIN) and D-073/D-074.
- **Code:**
  - `RuleVersion`: `cap` is already nullable, there's no relief, and `conditions` defaults to empty;
  - `RuleJson.version`, which builds a `RuleVersion`, and `RuleJson.capOrNull`, which refuses a rule
    with neither cap nor conditions;
  - `ShapeJson.cap`, the pattern for a tagged shape;
  - the relief family (`W-048`);
  - the 13 `new RuleVersion(` sites: `RuleJson` plus 6 test files.
- **Test home:** rule JSON is tested in `rules/json/PackJsonTest`.

### A. Choices (recommended first)

- **A1 — the type.** `rules/relief/RuleRelief(ReliefShape shape, boolean limitedToSlabRateTax)`. On
  `RuleVersion` it's `Optional<RuleRelief> relief`, placed after `cap`. It's `Optional` because the
  standards forbid a new null across a boundary, though `cap` is nullable from before.
- **A2 — JSON:** a `relief` block beside `cap`, tagged like a cap:
  - `FlatWithCeiling {maximum, incomeCeiling}`;
  - `ExcessOverThreshold {threshold}`;
  - `ThresholdLadderCeiling {thresholds: [...]}`;
  - `NoRelief {}`.

  Each has **`limitedToSlabRateTax` required**, with no default: absent is refused, naming the path.
  A rebate's limit then always has to be stated, never assumed.
- **A3 — what a rule must carry.** A cap, a relief, or conditions; a rule with none of them is still
  refused. A cap **and** a relief together is refused in the `RuleVersion` constructor (a domain
  invariant), so a hand-built version can't slip past the JSON check.
- **A4 — the 13 sites** pass `Optional.empty()`. That's mechanical; no test changes meaning.
