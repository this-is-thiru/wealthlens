**What this item is for (one sentence, in my own words):** the docs a developer reads first should say what each
trade flow does with the charge engine, as the code does it today (W-264b G-4, D-615).

**What the code does (read this session, 2026-11-13):**

| Flow | Priced and recorded (`user_charges`) | Charge summary in P&L | Computed total as cost basis |
|---|---|---|---|
| V2 buy | yes: `PortfolioService:437` | yes: handed on, `:441` → `ProfitAndLossService.mergeChargeSummary` | yes, when `authoritative`: `:438`, `:460` |
| V2 sell | yes: `:620` | yes: `:628` → `recordSale` | — |
| V1 buy | **yes**: `buyStock` (`:417`) → `updateBrokerChargesAndProfitAndLoss` (`:580 – 586`) → `updateProfitAndLoss` (`ProfitAndLossService:292`) → `recordCharge` (`:525 – 529`) | no: nothing is handed in, so `mergeChargeSummary` returns at once (`:549 – 553`) | no |
| V1 sell | **no**: `allocateSale` calls the deprecated `updateProfitAndLoss(ProfitAndLossContext)` (`PortfolioService:576`, `ProfitAndLossService:85 – 92`), which reaches no gateway | no | — |

`engine-enabled` and `shadow-recording` are on (`:62`). All three flags ship `true` in all three yamls
(`application.yaml:137, 141, 149`; `-staging` and `-prod` `:129, 133, 141`).
