### Choices (recommended first)

**C1 — how fields are encrypted.**
(a) **In the application:** AES-256-GCM (JDK `javax.crypto`, random 96-bit nonce) through a Spring Data property
converter on each sensitive field; the stored value is `k1:<base64 nonce+ciphertext>`, so a later key is new data. PAN
and TAN uniqueness move to an HMAC-SHA256 digest field (`pan_digest`, `tan_digest`) with its own key. Two keys,
`TAX_DATA_KEY` and `TAX_DIGEST_KEY`, from the environment like `JWT_SECURITY_KEY`; the app refuses to start without them.
No new dependency, no native library, works on any Atlas tier and on Testcontainers.
(b) **MongoDB explicit field encryption** (`@ExplicitEncrypted`, `mongodb-crypt`): the driver's reviewed mechanism,
deterministic mode keeps the unique index directly; costs a native library, a key-vault collection and a data key
created at each deploy (a runbook seed).

**C2 — which fields.** (a) Every O1.1 field listed above: identifiers, third-party name and address, special category
(disability, dates of birth), and the four JSON blobs that carry money and claims. Ids, tax year, status, kinds and audit
metadata stay plain — they are O1.1's *operational* class and are what queries filter on. The legacy salary module
(`salary_profiles`, `tax_computations`) is placed as **W-134a**, not done here. (b) Identifiers only.

**C3 — reads of special-category data (O1.1, O4).** (a) An append-only `tax_access_log`: one row per read of a profile,
family member or draft — profile id, principal, what was read, when; no values. (b) Place it as its own row.

**C4 — logs.** (a) Remove the money and the email from the three calls above, **and** a Log4j2 rewrite that masks any
PAN-shaped token (`[A-Z]{5}[0-9]{4}[A-Z]`) with `Pan.masked()`'s form (`ABCPE1234F` → `ABCXXXXX4F`, `Pan.java:19-21`) in every log line, which also
covers exception text. (b) The three calls only.

**C5 — W-135, third-party data out of exports.** (a) An `ArchitectureTest` rule: nothing in `taxplanning.document` (and
any future export package) may depend on `Landlord`, `Lender` or their responses — the guard is in place before Phase
10's first export. (b) Park W-135 until Phase 10.

**C6 — W-136, retention.** (a) **Merge into W-137:** a retention schedule has no caller until `RetentionPurge`
exists, so building it now is speculative code (CLAUDE.md §2); W-137 builds both, reading the period as the largest
`LossCarryForward` span in the draft's year's pack and refusing when there is none (`DR 19` E8). (b) Build now with a
read endpoint telling the user what is kept and until when (O5). Either way the erasure request O5 assumes has no row:
placed as **W-235**.

**C7 — rows already stored on staging and dev.** (a) No real PAN exists before the one deploy, so the runbook clears the
eight `tax_*` collections on each database (count first, backup, then drop; nothing to remove later). (b) An idempotent
startup encryptor for plaintext rows, with its Phase 15 removal row and WL-28 child.

### Build record (D-447)

**Departures from the plan, each found while building:**
1. **Logging is Logback, not Log4j2.** Lombok's `@Log4j2` writes through the Log4j2 API, but no Log4j2 starter is in
   either pom, so Spring Boot's Logback does the writing. The mask is `backend/src/main/resources/logback-spring.xml`:
   Boot's own console pattern with `%replace(%m%n%wEx)` and `%nopex`, so a stack trace is written once, masked.
2. **`shared/config/mongodb/MongoConfig` changed.** Spring Data made `@ValueConverter` classes by reflection, so the
   converter could not be handed its key ("No default constructor"). The conversions now use a bean-aware
   converter factory. Generic, with no tax import.
3. **A taken PAN answers 400, not 409.** That was the behaviour before this item (`TaxProfileService`, a
   `BadRequestException`); the plan's "409" was wrong. Kept as it was.
4. **§0.5 drops eleven collections, not eight.** Workspaces, bank accounts and election history point at profile ids,
   so they go with the profiles.
5. **The access record has no `profile_id`.** It names the read subject (profile, draft or receipt id). A receipt's
   profile would cost a second read. W-235 decides pseudonymisation from these fields.
6. **The unit vector's key.** The integration test's digest key is bytes 0x1F – 0x3E. My first expected value used
   0x00 – 0x1F. Recomputed with Python `hmac` (`fc7b5d1c…bca62`), it matched what the code stored.

**Probes, each reverted byte for byte (`cmp`):** Landlord address not encrypted, and `pan_digest` without its unique
index → `TaxProfileIntegrationTest` 2 failures; a `document` class reading `Landlord` →
`exports_carry_no_third_party_data` fails; the mask replaced by `$0` → `PanLogMaskTest` 2 failures.
