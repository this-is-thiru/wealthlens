This is by far the largest single sub-item in W-337: nearly 3× W-337d2's 13 moving tests (29 here), 24 services
against d2's 5+1, and no encryption converters to offset the embedded-structure work. Against **§7**, it is clearly

inventing a collection-by-collection split that would not actually build green at each step.

### Core findings from probing the code before planning (`probe-before-plan.md`)

1. **Why a collection-level split does not work.** `PortfolioService.addTransactionV2` (and `addTransaction`)
   writes `assets`, `transactions`, `trade_outcomes` and `profit_and_loss` together inside one local
   `@Transactional` method, itself wrapped by `TradeCollisionRetry` (`TradeCollisionRetry.java:53-67`) — there is no
   way to leave e.g. `transactions` on MongoDB while `assets`/`trade_outcomes`/`profit_and_loss` move to Postgres and
   still have that method compile, let alone run atomically. Separately, `PortfolioQueryService.searchAssets` /
   `EntityExportService` run ad-hoc queries against `AssetEntity` via `MongoTemplateService` (`MongoTemplateService.java:28-37`)
   — once `AssetEntity` drops its Mongo mapping annotations, `MongoTemplate.find(query, AssetEntity.class)` stops
   working at all, so the `QueryBuilder`/`Criteria` → JPA rewrite (C6) cannot be deferred to a later item either. 29
   of the repo's integration test classes reach at least one of the 4 entities (most through the shared
   `addTransaction`/`addTransactionV2` path), confirming the coupling rather than just the entity graph.
2. **`RealisedProfits` tree is opaque (`RealisedProfits.java`, `FinancialReport.java`, `MonthlyReport.java`,
   `FortnightReport.java`, `ReportModel.java`, plus `brokercharges.entity.model.YearlyChargeSummary` — none carry
   `@Document`, so they are pure nested POJOs).** Grepped every service for `realisedProfits.` / `outSourcedRealisedProfits.`
   / `gainsByAssetAndSegment` / `yearlyChargeSummary` (`ProfitAndLossService.java:131,420,431,434,576,579`): every
   touch loads the whole `ProfitAndLossEntity`, mutates deep inside the tree in memory, and saves the whole document
   back — no repository or `@Query` ever filters inside it. Same pattern, same conclusion, as W-337d2's `rules_json`
   (D-947 C1a).
3. **Corporate-action copies are opaque too.** `AssetEntity.corporateActions`, `TransactionEntity.corporateActions`,
   `TradeOutcomeEntity.appliedCorporateActions` are each `List<CorporateActionEntity>` — but these are **snapshot
   copies at the time of the action** (`TradeMatchingService.java:80,120` only read/merge them in memory), not
   references to the `corporate_action` table W-337d1 created. `CorporateActionEntity` is now itself a `@Entity`
   mapped to its own table (D-946), so it cannot also be the element type of a `@ElementCollection` on these 3
   entities without conflating "this asset's copy of a corporate action" with "a row in `corporate_action`" — grepped
   every portfolio file for a query filtering inside either list: none found.
4. **`TransactionEntity.assetRequest` (`AssetRequest` DTO) is opaque.** Kept only so a redrive can replay the original
   request (`TemporaryTransactionService.java:49-75`); grepped for any query on its nested fields: none.
5. **`TradeCollisionRetry.isCollision` (`TradeCollisionRetry.java:70-78`) checks only `MongoException` +
   `TRANSIENT_TRANSACTION_ERROR_LABEL`.** That label is MongoDB's multi-document-transaction write-conflict signal —
   it is *also* what currently stops `ProfitAndLossEntity.version` (`ProfitAndLossEntity.java:77-82`,
   `@Version`) from ever actually raising `OptimisticLockingFailureException` in practice: two concurrent trades for
   the same user+year collide at the Mongo transaction layer first, so the `@Version` check's own javadoc ("there is
   deliberately no automatic retry") describes a path that today is normally pre-empted. **Under Postgres there is no
   equivalent document-level write-conflict detection** — the `@Version` mismatch becomes the *only* place this
   collision is caught, surfacing as `ObjectOptimisticLockingFailureException`. If `TradeCollisionRetry` is not
   re-based to retry on it, the W-269/D-554 guarantee ("a trade is retried until it succeeds or every attempt
   collides, never silently lost") breaks silently the first time two trades race under Postgres.
6. **`PortfolioIndexInitializer` (`PortfolioIndexInitializer.java`) is the portfolio counterpart of
   `ChargeIndexInitializer`**, which W-337d2 already deleted in favour of Flyway-declared indexes (D-948) — same
   pattern, no decision needed, just build scope.
7. **`UserRecordsErasureService` (`UserRecordsErasureService.java:41`)** already calls two Postgres-backed deletes
   (`userChargeService.deleteByEmail`, `chargeAccountService.deleteByEmail`, both on `postgresTransactionManager`
   since W-337d2) alongside the 4 portfolio deletes it owns directly — once those 4 move too, its own
   `@Transactional` should move to `postgresTransactionManager` so the whole wipe (now entirely Postgres rows) shares
   one atomic transaction again, matching D-943 C1a's reasoning for `AccountErasureService`.
8. **Flyway version numbers are a single global sequence across all module folders** (`V1` auth/insurance … `V8`
   brokercharges, `backend/src/main/resources/db/migration/*/V*.sql`), so `portfolio`'s new file is `V9`.

### Decisions (for approval with this plan)

- **C1 — split or one item.** **C1a (recommended):** build W-337e as **one** item covering all 4 collections,
  `TradeCollisionRetry`, `PortfolioIndexInitializer`, the `QueryBuilder`/`Criteria` → JPA rewrite, and
  `TransactionBasedTradeOutcomeMigration`, in one commit — justified by finding #1 above (no split leaves the module
  compiling and correct at each step). **C1b:** split anyway along some other axis (e.g. core trade write-path vs.
  admin/reporting path); I found no axis that doesn't require the entity/repo conversion — the largest piece — to
  land in the first half regardless, so the second half would be small bookkeeping only; I don't recommend manufacturing
  a split that isn't real.
- **C2 — corporate-action copies (`AssetEntity.corporateActions`, `TransactionEntity.corporateActions`,
  `TradeOutcomeEntity.appliedCorporateActions`, all `List<CorporateActionEntity>`).** **C2a (recommended):** one
  `AttributeConverter<List<CorporateActionEntity>, String>` (`CorporateActionListConverter`, Jackson `JsonMapper`,
  same shape as `ChargeRuleListConverter` from D-947 C1a) storing each as a `TEXT` JSON column
  (`corporate_actions_json` / `applied_corporate_actions_json`) — preserves exact copy semantics (no FK, no shared
  identity with the `corporate_action` table), no query ever needs to filter inside. **C2b:** normalize into child
  tables referencing `corporate_action` by id — changes semantics from "this entity's copy at the time" to "a live
  reference", which the embedded-copy encryption work (W-341) and this session's grep both show is not what the
  field means today.
- **C3 — the `RealisedProfits` tree (`ProfitAndLossEntity.realisedProfits` / `.outSourcedRealisedProfits`).** **C3a
  (recommended):** one `AttributeConverter<RealisedProfits, String>` (`RealisedProfitsConverter`, Jackson) per field,
  storing each as a `TEXT` JSON column — same reasoning as C2a and as W-337d2's `rules_json`. **C3b:** flatten the
  5-level nesting (`AssetType × TradeSegment × Month × fortnight × 5 numeric fields`, plus `YearlyChargeSummary`'s own
  hierarchy) into child tables — many tables for data nothing ever queries into.
- **C4 — `TransactionEntity.assetRequest` (`AssetRequest` DTO).** **C4a (recommended):** `AttributeConverter<AssetRequest, String>`
  (`AssetRequestConverter`, Jackson), `TEXT` column — same reasoning. **C4b:** normalize `AssetRequest`'s own fields
  into columns on `transactions` — duplicates most of `TransactionEntity`'s own columns for a field only a redrive
  reads back whole.
- **C5 — `TradeCollisionRetry.isCollision`'s Postgres basis.** **C5a (recommended):** retry on
  `org.springframework.dao.OptimisticLockingFailureException` (covers `ObjectOptimisticLockingFailureException` from
  `ProfitAndLossEntity`'s `@Version`) **and** `org.springframework.dao.CannotAcquireLockException` (Postgres lock
  timeout/deadlock, SQLState `40P01`), replacing the `MongoException` check; update `ProfitAndLossEntity`'s javadoc
  (now stale under Postgres — the "no automatic retry" statement described Mongo's pre-emption, not a design choice).
  **C5b:** retry only `CannotAcquireLockException`, leave `OptimisticLockingFailureException` uncaught — matches the
  entity's current javadoc literally but reintroduces the exact user-facing "trade silently lost on a race" failure
  W-269/D-554 eliminated, since under Postgres nothing else catches that race.
- **C6 — the ad-hoc `QueryBuilder`/`QueryFilter` (Mongo `Criteria`) search path (`MongoTemplateService`, backing
  `PortfolioQueryService.searchAssets`/`getExportEntities`, `TransactionController`, `EntityExportService`).** **C6a
  (recommended):** add a JPA-Specification-based builder in `shared/entity/query` (same `QueryFilter` shape — field,
  operator, value — unchanged, so no caller's request/response contract changes) producing `Specification<T>`,
  consumed via `JpaSpecificationExecutor<T>` added to `PortfolioRepository`/`TransactionRepository`; replace
  `MongoTemplateService` with a thin JPA-backed equivalent. **C6b:** hand-write JPQL per known filter combination —
  loses genuine ad-hoc field+operator combinations the admin search allows today; not recommended, changes behaviour.
