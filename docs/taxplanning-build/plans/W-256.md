### Choices (recommended first)

**C1: the converter.**
- **(a) Recommended: `SearchableIdentifier`** on `createdBy`, `updatedBy`, `changedBy` and the cursor's
  `updatedBy`.
  - It keeps one stored form per value across the database. Runbook §2.0's and §2.2's look-ups still work using
    `<stored email>` from §0.7.
  - It leaks nothing new: on a user's own rows, the actor is the same email already stored in the `email` field.
- (b) `EncryptedField`, with a random nonce. Stronger, because two rows by the same person cannot be linked. But
  §2.0's and §2.2's "delete by `createdBy`" way back stops working, and no erasure can ever find an actor's rows.

**C2: actor values that are not emails** (`"unknown"`, the anonymous name, job names).
- **(a) Recommended: encrypt every actor value the same way.** Nothing has to tell them apart at write time. The
  stored-row pass tells plain from encrypted by the `k1:` prefix, as it already does.
- (b) Encrypt only values shaped like an email. That needs a shape rule, which a login name that isn't an email
  breaks silently.

**C3: rows already stored.**
- **(a) Recommended:** extend W-253's identifier pass in `StoredFieldEncryption`
  (`POST /privacy/stored-fields/encrypt`, runbook §1.r, which has not run on any database yet). It covers
  `audit_metadata.createdBy` and `audit_metadata.updatedBy` on every collection whose entity holds `AuditMetadata`.
  That list is **taken from the mapping context, not hand-listed**, so a new entity can't be missed (W-253's
  inventory missed two fields). It also covers `changed_by` and `updated_by`.
  - No unique index involves these fields, so a conflict is impossible.
  - W-254 already removes the whole class.
- (b) A separate endpoint, with its own Phase 15 row and YouTrack child.

**C4: the unused system auditor.**
- **(a) Recommended:** not in this item. I'd place it as **W-257**: remove `SYSTEM_AUDITOR` and its two static
  methods (dead weight), and decide whether jobs stamp their own name instead of `"unknown"`.
- (b) Fold it into W-256.

## Amendment A (R13): the first start, 2026-11-08

**Found while building, after the probe passed.** `FieldCipher.decrypt` refuses a value without `k1:`
(`FieldCipher.java:62-64`). With the converter on `AuditMetadata`, any row in the 36 collections whose actor is still
plain fails to load until §1.r runs. That includes reference data (charge cards, tax policies, corporate actions), not
just user rows. Risk 1 ("nothing is missed in that window") is **wrong**.

**Worse, the start can fail.** `TaxJobSchedule.stalenessSweep` runs on `ApplicationReadyEvent` (`:40-43`) and loads
every `READY` or `ACTED_ON` `FilingDraft` and its `DraftComputation`s (`StalenessSweep.java:54-62`). `TaxJobRunner.run`
does not catch (`:37-41`). Spring Boot 4.1.0 aborts the start when a ready listener throws (`SpringApplication.java:333-339`).
So on a database holding such a draft, the build carrying W-256 never comes up, and §1.r can never be called.

- **W-253 already carries this for `tax_draft_computations.email`.** It is unpushed and undeployed, so no database
  has hit it yet.
- **The §1.r call itself is safe.** `AuthFilter` asks `HeldAccounts` through an `exists` query
  (`HeldAccounts.java:18`), which decodes no row, and `ProcessingLogFilter` only inserts.

**Fix: runbook only, no code (recommended, A1a).** Jobs have a switch already, `app.tax.jobs.enabled`
(`TaxJobSchedule.java:19`). §1.r becomes:
1. First start with `APP_TAX_JOBS_ENABLED=false`.
2. Call §1.r (with its checks before and after).
3. Restart with the jobs on.

  This covers W-253's case too. §1.r's text also says reference data is unreadable until the call, not only user rows.
- (A1b) A plain stored value reads as itself until W-254 removes that tolerance. This needs code in `SearchableIdentifier`
  and `EncryptedField`, and goes against W-248's deliberate refusal. Not recommended.

**Build unchanged** (steps 2 – 5 as approved). The reverted code is kept at
