## Plan for W-304 — a trade no broker card covers is reported as priced

**What this item is for (one sentence, in my own words):** a card that has no rule for a trade's event must not
stand in for the missing card, so a trade with no broker card is reported `NO_SCHEDULE` (and listed by `/gaps`)
instead of `RESOLVED` with brokerage, exchange, IPFT and DP silently missing (W-264b G-1, D-613).

**Findings (read this session, 2026-11-13):**

1. **The cause.** A card's unset dimension matches anything (`ChargeScheduleResolver:152 – 162`), and nothing about
   a card's rules takes part in the choice (`agreeing`, `:111 – 113`). `ZERODHA_MAINTENANCE_2025_04` has no asset
   type, segment, exchange or plan, and one rule, `AMC`, for `AMC_CYCLE` only (`zerodha-maintenance-2025-04-01.json`).
   With the delivery card closed, it is the only agreeing card, so it is chosen; the engine then finds no rule for
   `BUY` (`ChargeEngine.declaresEvent:298 – 300`), the statutory card's lines are priced, and the result is
   `RESOLVED` (`ChargeEngine:98 – 109`). Report §6.2 reproduced it twice: `RESOLVED`, STT 10.0, SEBI_FEE 0.01,
   STAMP_DUTY 2.0, GST 0.0, `scheduleCode` `ZERODHA_MAINTENANCE_2025_04`.
2. **The statutory twin.** `STATUTORY_ACCOUNT_2025_04` is unscoped too, with one rule, `GST`, for `AMC_CYCLE` only
   (`statutory-account-2025-04-01.json`). If a statutory trade card closes without a successor, it stands in the same
   way: STT, stamp duty, SEBI fee and the GST on brokerage go missing and the result is `RESOLVED`, where
   `NO_STATUTORY_SCHEDULE` (`ChargeResolution:30 – 36`) is the fact. `resolveStatutory` uses the same `agreeing`
   (`:102 – 109`), so one change covers both.
3. **Shipped cards are safe under the fix.** Every shipped card's active rules declare exactly `BUY` and `SELL`,
   except the three maintenance cards and the statutory account card, which declare only `AMC_CYCLE` (counted by
   script over `data/charges/*.json`). The only events built in `src/main` are `BUY`, `SELL` and `AMC_CYCLE`
   (`AmcChargeService:146` for the last). The AMC context has no asset type or segment (`AmcChargeService:138 – 146`),
   so no trade card agrees with it today, and none will after.
4. **The cache.** `ScopeKey` is "everything the choice depends on, and nothing else" (`:181 – 200`); it holds no
   event. Once the event decides which card agrees, it must be in the key, or a cached `BUY` answer would serve an
   `AMC_CYCLE` request for the same scope and date.
5. **Why the suite misses it.** `ChargesIntegrationTest.gapsEndpoint_surfacesATradeWithNoRateCardForItsPeriod`
   (`:612`) runs with the shipped cards deleted, the maintenance card among them (report §3 G-1).
6. **Tests the fix reaches.** `ChargeScheduleResolverTest` builds its cards with no rules (`card(...)`, `:301 – 313`),
   so under the fix none of its 18 tests would find a card. Its fixture gains one rule from
   `ChargeFixtures.rule(...)` (`:40 – 53`: active, events `BUY`, `SELL`), and `trade()` is a `SELL`
   (`ChargeFixtures:79`). That is a fixture change, not an assertion change. `ChargeEngineTest`,
   `ChargeInvariantTest` and the two service tests mock the resolver; `ChargeGoldenFileTest:150` uses the real one
   over shipped-shape card files, which declare `BUY` and `SELL`.

**Choices for the owner:**

- **C1 — where the fix lives.**
  - **C1a (recommended):** in the resolver. A card agrees only if it has an active rule that declares the trade's
    event, beside the four scope dimensions. This applies to the broker card and the statutory card through the same
    `agrees`. `ScopeKey` gains the event. The choice then means what the Javadoc says: "a card that disagrees is
    removed from consideration rather than merely outranked" (`:32 – 34`).
  - C1b: in the engine. When the broker card yields no rule for the event, answer `NO_SCHEDULE`. That leaves the
    wrong card named in `scheduleCode`, and it does not cover the statutory twin, which still prices nothing for the
    trade and answers `RESOLVED`.
- **C2 — inactive rules.** **C2a (recommended):** only an active rule counts, as in the engine
  (`ChargeEngine:219 – 220`). A card whose only rule for the event is switched off prices nothing for it, which is the
  same hole. C2b: any declared rule counts.
- **C3 — what the old Javadoc says.** **C3a (recommended):** `ChargeResolution.UNRESOLVED`'s Javadoc (`:59 – 71`)
  names the maintenance card winning by default as the route to `NO_MATCHING_RULES`. After C1a that route is
  closed: an empty result now comes from a card that declares the event but whose rule's side does not match. The
  Javadoc is reworded to say that. The value stays in the list.
- **C4 — stored rows.** **C4a (recommended):** a read-only runbook row, §3.21. Per database it counts `user_charges`
  rows whose event is `BUY` or `SELL` and whose `schedule_code` names a card with no active rule for that event (a
  `$lookup` on `charge_schedules` by `schedule_code`, in one `db.aggregate` over every database, §0.7). The same
  count is made for `statutory_schedule_code`. With the shipped cards this should be 0, but a database may carry
  its own cards. If the count is non-zero, a correction row is placed with its own plan. No write now. C4b: no
  runbook entry.
