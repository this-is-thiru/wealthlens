## Plan for W-283a1 — record the flow on every transaction

**What this item is for (one sentence, in my own words):** every trade a flow stores says which flow received it.
That lets the `assets` rebuild (W-283a2) give it the lot shape it got live: V1 merges same-day buys, V2 gives each its
own lot (D-577 C1a, D-578).

**Findings (read this session, 2026-11-12):**

1. **One writer.** Both live flows store their trade through `TransactionService.recordTransaction`. V1 does so at
   `PortfolioService:100`, which the upload and a V1 redrive also reach. V2 does so at `:140`, which a V2 redrive
   reaches (`redriveThrough`, W-270). Neither passes its flow; only a temporary gets one
   (`TemporaryTransactionService:49 – 51`, from the flow's own call at `:92` / `:132`).
2. **A bonus copies a buy.** The bonus transaction is a JSON copy of the user's first buy (`CorporateActionService:327`).
   `trade_flow` is not `@JsonIgnore`, so once buys carry a flow, the bonus would inherit that buy's flow — a flow that
   never received it.
3. **The flow stays internal.** `TransactionResponse` has no `tradeFlow`, and `AssetRequest` cannot set it ("set by
   the server from the route", `TradeFlow` javadoc).
4. **An uncalled method.** The deprecated `TransactionService.addTransaction` (`:104`) has no caller in `src/main`.
   Its javadoc says it is "retained because the V1 flow is in live use", but V1 has used `recordTransaction` since
   TL-7. Only `TransactionServiceTest` calls it, including W-287's two new tests.

**Choices for the owner:**

- **C1 — the bonus transaction's flow.**
  - **C1a (recommended):** none. The copy clears it, since no flow received the bonus; its lot is its own whatever the
    flow (design §Lot shape).
  - C1b: keep what the copy carries.
- **C2 — the uncalled `addTransaction`.**
  - **C2a (recommended):** leave it, and place a row to delete it with its tests. That removal is a separate
    no-behaviour change.
  - C2b: delete it here.

**Files I will modify:**
- `TransactionService` — `recordTransaction(userMail, assetRequest, tradeFlow)` sets `trade_flow` on what it stores.
- `PortfolioService:100, :140` — pass `TradeFlow.V1` and `TradeFlow.V2`.
- `CorporateActionService:327 – 333` — clear it on the bonus copy (C1a).
- `TransactionEntity` and `TradeFlow` javadocs — the field is no longer "absent on every other transaction".
- `docs/trade-ledger/assets-rebuild.md` — the flow is recorded from W-283a1's deploy.
- Tests:
  - `TransactionServiceIdempotencyTest`: the flow is stored; a replay stores nothing.
  - `PortfolioServiceTest`: V1 passes V1 and V2 passes V2; the 15 existing `recordTransaction` stubs take the new
    argument.
  - A new `TradeFlowRecordingIntegrationTest`: a V1 POST stores `V1`, a V2 POST stores `V2`, the upload stores `V1`,
    and a V2 temporary's redrive stores `V2` on the new transaction.
  - `CorporateActionIntegrationTest`: a bonus copied from a `V1` buy stores no flow.

**Numbers I will use:** none.

**Design sections I read:** D-555 (W-270, `trade_flow`), D-577 C1a, `assets-rebuild.md` §Lot shape.

**What I am NOT doing:**
- Backfilling older transactions. C1a reads their shape from the stored lots instead.
- Exposing the flow in any response.
- C2's deletion.

**How I will verify:**
- The targeted tests first; each new one red before the change.
- Probe: pass `V1` from V2's call site, so the V2 integration case fails; then restore byte-for-byte.
- The unit tier, then the integration tier, once each.

**Post-deployment actions (R15):** none. Older transactions keep no flow by design; the runbook needs no step.

**Five roles:**
- **Architect:** a fact recorded at the one place a trade is stored; no new seam.
- **Product manager:** nothing visible to the user. The owner's future `assets` rebuild gets the exact lot shape for
  every trade from this deploy on.
- **Senior engineer:** one parameter on one method, two call sites, one cleared copy.
- **Automation tester:** a red-before test per flow and route, the bonus case, and the probe.
- **Manual tester:** after deploy, a V2 trade on staging then
  `db.transactions.find({ _id: <id> }, { trade_flow: 1 })` → `"V2"`; the same for V1 and an upload → `"V1"`.

**Risks or ambiguities:** none found. `recordTransaction`'s idempotent replays write nothing, so a replay cannot
change a stored flow.
