## Plan for W-358d4 — request validation, sized by what an empty body does today

> Planned in session 114 (2026-11-21), the last part of W-358d (D-872). Measured first (a temporary probe over the generated spec,
> removed). **Stop point: nothing is built until the owner answers C1 – C3.**

**What this item is for (one sentence, in my own words):** a body missing what a route needs is refused before it reaches a service,
the same way on every route, and no failure tells a caller about the code's insides.

### What the code does today

| | Today | Where |
|---|---|---|
| Bodies | **49** `@RequestBody` parameters: 32 named request types (records and classes) plus three `Map<String, String>` and one `JsonNode` | `git grep` |
| Bean Validation | `spring-boot-starter-validation` on the classpath; **no** `@Valid`, no constraint annotation; `ControllerAdviser` has no `MethodArgumentNotValidException` handler | |
| Checks | almost none in the types (0 in 22 of them; 1 – 2 in the tax-planning requests' `applyTo`, `RefreshRequest`, `AssetRequest`); the services check | survey |
| **An empty body** (`{}`, or `[]` for a list) on each of the 50 body-taking operations in the spec, with an admin's or user's token | **44** answer 400 (a service's check, or the placeholder id not found), 1 answers 401, **2** searches and **xirr** answer 200 legitimately (an empty filter; "Insufficient cash flows"), **`POST /api/v1/me/charges/charge-accounts` answers 200 and stores an account with every field null**, and **`PUT /api/v1/admin/corporate-actions/perform` answers 500** | probe |
| A 500's answer | the exception's own message as `detail` — the perform route says `Cannot invoke "com.thiru.wealthlens.corporate.dto.enums.CorporateActionType.ordinal()" because "action" is null` | `ControllerAdviser` `@ExceptionHandler(Exception.class)` |

### Decisions (for approval with this plan)

- **C1 — how much validation.** **C1a (recommended):** `@Valid` on all 49 bodies with a guard that fails on a body without it; a
  `MethodArgumentNotValidException` answered as a 400 `ProblemDetail` naming each field ("Field 'brokerName' is required"); constraints
  where a missing or empty field gets past today's checks — the two measured (the demat account's broker, demat id and AMC frequency;
  the admin perform body's required fields) and any found by a **build-time probe** that takes each api-collection request body and
  sends it with each top-level field removed in turn, recording every 500 and every 2xx that stores a null. Checks that live in
  services stay there (they are the domain's, and `applyTo` messages are already worded for people). **C1b:** constraints on all 32
  types, every service check restated as annotations — about 300 fields, most already refused; much duplication.
- **C2 — a 500's answer.** **C2a (recommended):** placed as its own small item, **W-364**, built with this one but its own commit: a
  500 answers "Something went wrong; quote the X-Request-Id …" (W-358d1's id), the exception's message only in the log, where emails are
  masked. **C2b:** leave 500 answers as they are.
- **C3 — split.** **C3a (recommended):** no further split: one item (W-358d4) of three steps — the guard and `@Valid` with the 400
  handler; the measured constraints; the probe's findings — plus W-364. If the probe finds more than a handful, the extra ones become a
  row rather than growing this item. **C3b:** one item per module.

### Files (if C1a – C3a)

**Modify:** the 49 handler parameters (`@Valid`); `ChargeAccountRequest` (`@NotNull` broker and AMC frequency, `@NotBlank` demat id —
which fields exactly, and on the perform body, read from the services at the build); `ControllerAdviser` (the 400 handler; W-364: the
500 detail); the api-collection's docs only if a request it sends is refused; CLAUDE.md (validation); the runbook's "Next deploy".
**Create:** `architecture/RequestValidationTest` (every `@RequestBody` carries `@Valid`, red first: 49 offenders today); cases in
`CallerMistakeIntegrationTest` for the two measured gaps (red first: 200 storing nulls, and 500); a W-364 case (an unexpected failure
answers no class name).
**Numbers I will use:** 49, 32, 50, 44 / 1 / 4 / 1 (the probe).
**What I am NOT doing:** moving service checks into annotations (C1a); validating `Map` / `JsonNode` bodies (their routes read named
keys and refuse others already); W-363.
**How I will verify:** red first as above; the guard proven by removing one `@Valid`; the build-time probe re-run after (no 500, no
null stored); CallerMistake, ApiCollectionContract, RouteAccess, ArchitectureTest, WealthLensModulith, `validate`; the pipeline.
**Post-deployment actions (R15):** nothing in a database. A "Next deploy" line: a missing field answers 400 naming it; a 500 names no
class. **An account registered with nulls before this** (if any) is only counted: a read-only console query for `charge_accounts`
with no `broker_name` or `demat_account_id`, reported to you, corrected by nobody in this item.
**Five roles:** Architect: one refusal path for a bad body, one guard. PM: no crash or empty record from a half-filled form. Senior
engineer: annotations where a gap was measured, not everywhere. Automation tester: the probe as evidence, red first per gap. Manual
tester: an empty body in the api-collection gets a 400 naming its field.
**Risks or ambiguities:** a constraint stricter than a client's real request would refuse it — the ApiCollectionContract check and the
api-collection's own bodies show that at the build.
