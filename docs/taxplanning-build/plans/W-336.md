## Plan for W-336 — the tax jobs run on request while the app is local

> **Approved — C1a – C5a** (owner, session 108, 2026-11-19: "yes to all your recommendations, go ahead with W-336"); built, awaiting review. Placed by the owner, 2026-11-19 ("place W-336 and plan it before W-334a"), from
> the question "with just 10 persons and just local only app, why not apis?". Built before W-334a, so `m1` carries it.

**What this item is for (one sentence, in my own words):** while the app runs only on the owner's machine, nothing runs on a
clock — the jobs are off by default, and the owner runs each one through a `SUPER_USER` endpoint, on a written cadence, so
erasure and retention happen when the owner decides and are logged, instead of silently never firing at 03:00 – 05:00.

**Why now (facts read this session):**
- All three profiles ship `app.tax.jobs.enabled: true` (`application.yaml:93`; `application-staging.yaml:82`,
  `application-prod.yaml:82`); the crons fire at 03:00 Sunday, 04:00 on the 1st, 04:30, 04:45, 05:00 daily and every
  minute (`application.yaml:94 – 102`), so on a laptop they fire only when it happens to be up then.
- Nothing but the scheduler calls `TaxJobRunner` (grep: only `TaxJobSchedule`); no endpoint runs a job.
- No test reads the three shipped yamls (grep of `backend/src/test/java`); the integration profile already ships
  `jobs.enabled: false` (`application-integration-test.yaml:80 – 81`) and `TaxJobsIntegrationTest` runs jobs through
  `TaxJobRunner` directly. **Flipping the default moves no existing test.**
- The documents endpoints ship off (`application.yaml:133`, staging/prod `:122`), so `ParseRequests`' after-upload parse
  (`ParseRequests.java:18 – 20`, only when the schedule bean exists) is not reachable today.

### Choices for the owner

- **C1a — the default.** `app.tax.jobs.enabled: false` in all three yamls; the cron values stay, for the day the app is
  hosted (Milestone 2 B, D-781), when turning it on is its own decision. *(C1b: keep true and rely on D-782's
  env var — the crons then fire whenever the app is up at those hours.)*
- **C2a — the endpoint.** `POST /tax-planning/admin/jobs/{name}/run`, `SUPER_USER` only, beside the Gazette watch's
  (`GazetteWatchController.java:20`). Runs the named job synchronously through `TaxJobRunner` (same lease, same failure
  records, writes as the job's name, W-257). Answers `200 {"job": name, "ran": true}`, or `"ran": false` when another run
  holds the lease (`TaxJobRunner.java:34 – 38`). An unknown name is `400`, naming the seven known ones. `gazette-watch`
  while `app.tax.gazette-watch.enabled` is false is `400` naming that switch — the schedule refuses it the same way
  (`TaxJobSchedule.java:68 – 73`). A failure inside a job is not caught: `500` with its message, the lease lapses (as now).
- **C3a — the cadence**, a §5.2 recurring operation (the owner's choice, not a figure from law; the DPDP duties commence about
  May 2027, D-470): `account-erasure` and `log-retention` weekly; `auto-archive` weekly; `retention-purge` monthly;
  `staleness-sweep` after every start of a new build; `gazette-watch` only once §1.w turns it on; `parse-documents` not
  while documents are off. Each run is a run-log line.
- **C4a — the start-time sweep.** It stays under the same switch, so with C1a it no longer runs on start; §1.r step 7 and
  §5.2 run it through the endpoint instead. *(C4b: a second switch only for the sweep — a new flag with no other caller.)*
- **C5a — documents later.** `ParseRequests` is unchanged; the runbook's documents switch-on (§1.n) gains the line "with
  the jobs off, run `parse-documents` after an upload, or decide then whether an upload starts its own run".
