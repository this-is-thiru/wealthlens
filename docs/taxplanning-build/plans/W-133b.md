## Plan for W-133b — apply a reviewed salary preview to the draft

> **Approved — C1a – C6a** (owner, session 106, 2026-11-18: "yes, go with all (a)"). Every path:line below was read this session at `fc0ee34b`.

**What this item is for (one sentence, in my own words):** after the user reviews W-133a's preview, one call adds an employment with
those pay lines to the draft. Every returned row must be decided, the four employment facts no CTC sheet carries must be given, and
the draft's history must say the change came from that workbook.

### What the design, the code and the sources say

- **The write path:** `DraftService.patch(email, draftId, expectedRevision, patch)` (`DraftService.java:149`) checks the draft is the
  caller's and editable and that the revision is current. It applies the JSON Patch, requires the result to bind, checks the year's
  declarations, then inserts a `DraftRevision` whose `change_set_json` is **the patch itself** (`:169`), because a state is replayed
  from the patches (`inputsAt`, `:197`). `DraftSaveRetry.patch` (`DraftSaveRetry.java:50`) wraps it, retrying a collision on the
  revision's unique key. `DraftController` takes the revision from `If-Match` (`"rev-N"`).
- **The employment's shape:** `Employment(components, termsIncludeDearnessAllowance, employerKind, dearnessAllowanceCountsForRetirement,
  companyEmployer)` (`taxengine/input/Employment.java`), each required. A client already sends that object for a manual entry
  (`add /entered/employments/-`, `DraftFirstFigureService.java:78`).
- **The history:** `DraftRevision` has `revision_number`, encrypted `full_state_json` and `change_set_json`, `changed_by`, `reopened`.
  `RevisionResponse(revisionNumber, changedBy, reopened)` is what a client lists. There is no field for where a change came from.
- **W-133a's preview** returns matched lines, returned rows (with `row`, `label`, amount, `why`) and the year's components.

### Choices for the owner (recommended first)

- **C1 — what the apply call trusts:**
  - **(a)** The workbook is uploaded again with the decisions (multipart: `file` plus a JSON `decisions` part). The server reads it again
    in the child and matches it again, so the lines written and the SHA-256 recorded are the server's own reading. That costs a second
    read (about 0.7 s).
  - (b) The client sends the preview's lines back. One read only, but the lines and the "imported from" record are whatever the client
    says.
- **C2 — the returned rows:**
  - **(a)** Every returned row needs a decision, named by its row number: `map` to a code of the year's pay-line components, or
    `leaveOut` (recorded). A row left undecided, a code not in the year, or a mapping for a row that was not returned → 400 naming the
    rows. Matched rows go in as matched; the user can edit the draft afterwards.
  - (b) Also let the user override matched rows in the same call.
- **C3 — the same component twice** (two rows that resolve to one code, e.g. two "Bonus" rows):
  - **(a)** Refused, naming both rows. The user merges them in the sheet: the import does not add figures up on its own.
  - (b) Added together into one pay line.
- **C4 — the employment's facts:**
  - **(a)** The decisions carry `employment`: the same object a manual entry sends, without `components`. The server adds the pay lines,
    and the draft's own binding check (`requireBinds`) refuses anything missing or wrong. Nothing is defaulted.
  - (b) Defaults (`OTHER`, `false`, not a company). Not recommended: it guesses facts that move the tax (entertainment allowance,
    specified employee).
- **C5 — recording the import (C6a of D-775):**
  - **(a)** `DraftRevision` gains `imported_from`: the workbook's SHA-256, the rows applied, the rows mapped and the rows left out.
    `change_set_json` stays a pure patch, so replay is unchanged. `RevisionResponse` gains it as an optional field (additive JSON).
    Revisions stored before have none.
  - (b) A separate collection of imports keyed by draft and revision.
- **C6 — the same workbook twice:**
  - **(a)** Refused: the draft already has a revision importing that SHA-256, and the message names the revision. A second employment
    from one sheet is almost always a double click.
  - (b) Allowed; it adds a second employment.

### Files I will create / modify (names checked at build)

- `workspace/importing/SalaryImportDecisions` (the JSON part: `decisions` by row and `employment`), `SalaryImportService.apply`.
- `SalaryImportController`: `POST /drafts/{draftId}/salary-import/apply` (multipart, `If-Match` as a draft save takes it).
- `DraftService` / `DraftSaveRetry`: the patch path takes an optional import record for the revision (one path, not a copy).
- `DraftRevision.importedFrom` and `RevisionResponse` (C5a).
- Tests, worked by hand: apply with one mapped and one left out (the draft gains one employment of the expected lines, and the
  revision records rows and SHA-256); an undecided row, a wrong code, two rows for one code, a missing employment fact, a stale
  `If-Match`, the same SHA-256 twice. Replay (`inputsAt`) still gives the state.
- api-collection request; STATE, 03-WORK-ITEMS, CHECKPOINT. **No runbook entry:** the field is additive, and old revisions read without it.

### Numbers I will use

None new: the preview's (W-133a) and the draft's own checks.

### What I am NOT doing

- Editing or merging into an existing employment (an import always adds one); a template download; aliases.

### How I will verify

- **Red first:** the apply integration test before the endpoint exists (404).
- **Deliberate breaks:** an undecided row allowed; the SHA-256 not recorded; the duplicate check dropped. Each must fail its test, then
  be restored by `cmp`.
- **Targeted:** the new tests, `SalaryImportServiceTest`, `SalaryImportIntegrationTest`, `DraftIntegrationTest` (replay and `If-Match`
  unchanged), `WealthLensModulithTest`, `ArchitectureTest`; `validate`.

### Five roles

- **Architect:** one write path; the import is a patch plus a record of where it came from. Replay is untouched.
- **Product manager:** upload, review, decide the few unknown rows, answer four questions, and the employment is there, with its origin
  shown in history.
- **Senior engineer:** the server trusts its own reading (C1a). There are no defaults (C4a), and a second import of the same file is
  refused (C6a).
- **Automation tester:** each refusal has its own case, and the happy path checks the draft's state and the revision record.
- **Manual tester:** on staging, a real CTC sheet goes through preview, apply and history, and a double click is refused.

### Risks or ambiguities

- The `decisions` JSON part beside a file needs a multipart part with JSON content. Spring binds it with `@RequestPart`. The
  api-collection request shows both parts.
