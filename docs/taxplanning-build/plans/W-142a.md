## Plan for W-142a — trace presentation: step order and the backwards interval

**For:** a reader of the published trace (the JSON view now, the PDF at W-123) sees steps in the order the law reads —
salary before credits — and never an interval that runs backwards (W-142, D-457).

### What I read (session 48)

- **Why credits come first:** `TopologicalSort` (`taxengine/pipeline/TopologicalSort.java`) orders by the edges and
  breaks every tie on `NodeId` — alphabetically — so independent nodes `capitalgains.income` and `credits` sort before
  `salary.*`. Its Javadoc: the order must be *canonical, not merely valid*, because `TraceLine.sequence` comes from it and
  computations are cached, compared and replayed. Its only caller is `PipelineRunner.java:106`, with
  `regime.pipeline().nodeRefs()` — the regime's declared list (in its `law/regimes/*.json`, e.g. `inputs.components`, `salary.base`, …
  `credits`, `advance.tax`, …).
- **The interval text:** `InterestAndFeeNode.java:141` (late return) and `:177` (advance-tax shortfall) write
  `months + " months from " + from + " to " + end` even when `end` precedes `from` (a computation before the due date),
  giving *"0 months from 2027-08-01 to 2026-11-06"*.
- **No law is involved.** No amount changes: the graph's edges, hence every value, are untouched.

### Choices (recommended first)

**C1 — the step order.** (a) **Break ties by position in the regime's declared pipeline** instead of by `NodeId`: the
edges still decide; among nodes ready together, the one the regime lists first runs first. Still canonical — the list is
pack data, checksummed with its layer — so the same inputs give the same trace. (b) Keep execution order and sort
steps by the declared pipeline only when projecting `ComputedTax.trace`: two orders for one trace, and a `sequence` that
no longer matches the engine's. (c) Leave it, and document that the trace runs in evaluation order.

**C2 — the interval text.** (a) When the end precedes the start: *"not yet due: runs from 2027-08-01"*; otherwise as
now. (b) Omit the dates when the months are 0.

### Build record

**Result:** the three snapshots now follow each regime's declared pipeline exactly (checked against
`law/regimes/*.json` `pipeline.nodeRefs`); their line counts are unchanged (37, 26, 37); ignoring sequence numbers, the
only changed lines are `INT-LATE-RETURN` and `INT-ADVANCE-SHORTFALL`, now *"not yet due: runs from 2027-08-01"* /

**Departures from the plan:**
1. The ready set is a priority queue on the declared position, not a FIFO with sorted ties: with a FIFO, a node freed
   late but listed early would wait behind later-listed ones, and the declared order would not come out where the
   edges allow it.
2. `TopologicalSortTest`'s `theSameGraphGivesTheSameOrderWhateverTheInputOrder` stated the contract C1a replaces; it is
   now `of_whenTheSameListIsOrderedAgain_givesTheSameOrder` (determinism for one declared list), beside three cases of
   the new tie-break. An approved change of contract, not a weakened assertion.

**Tests:** `TopologicalSortTest` (4 replacing 3), `AdvanceTaxAndInterestTest` +1; snapshots rewritten.

**Probes, reverted byte for byte (`cmp`):** tie-break on `NodeId` again → the two list-order cases fail; the old
interval text → the new interest test fails.
