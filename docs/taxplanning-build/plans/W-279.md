## Plan for W-279 — a V1 same-day merge loses an order time

**What this item is for (one sentence, in my own words):** when V1 merges a buy into the day's lot, the buy's order
time is kept on the lot, so the lot's order times account for its whole quantity (G-4, PS-3).

**Findings (each read this session, 2026-11-11):**

1. **The line.** In `buyStock`'s merge branch the order time is added to the request (`PortfolioService.java:418`,
   `assetRequest.getOrderTimeQuantities().add(...)`), which is discarded; the new-lot branch adds it to the lot
   (`:426`). Proven: W-264a scenario 9 — two V1 buys of 10 on one day, one lot of 20 whose order times sum to 10.
2. **Lots already merged this way** are the V1 lots with more than one buy transaction (`buy_transaction_ids`; V2
   writes a lot per buy, so never more than one). Among them, an incomplete one has order times
   (`order_time_quantities.quantity`) summing to less than what was bought. Sales reduce `quantity` but not the order
   times, so the sum is compared with nothing that changes — a lot sold down can still read complete; the check
   counts only lots never sold from.

**Choices for the owner:**

- **C1a (recommended):** add the order time to the lot in the merge branch.
- **C2 — lots already stored.**
  - **C2a (recommended):** runbook 3.14, read-only: count lots with two or more buy transactions, no sales, and order
    times summing to less than their quantity; a correction would be its own row (the times lost are not recoverable
    from the lot — only from each buy's transaction row).
  - C2b: no check.

**Files I will modify:** `PortfolioService` (one line); tests — W-264a scenario 9 as the first test (two V1 buys of 10
at ₹100 and ₹120 on 5 Jan: one lot of 20 @ ₹110 whose order times sum to 20); `post-deployment-runbook.md` 3.14 (C2a),
so WL-A-2 is republished.

**Numbers I will use:** none beyond the scenario's.

**What I am NOT doing:** recovering lost order times; V2 (a lot per buy).

**How I will verify:** scenario 9 red then green; probe: the request line back → fails; the affected classes;
`./mvnw validate`.

**Post-deployment actions (R15):** runbook 3.14, read-only, owner, any time, safe to repeat, nothing to undo:
`db.assets.countDocuments({ "buy_transaction_ids.1": { $exists: true }, sell_transaction_ids: { $size: 0 }, $expr: { $lt: [ { $sum: "$order_time_quantities.quantity" }, "$quantity" ] } })`.

**Five roles:**
- **Architect:** the lot is the record; what describes it is written to it.
- **Product manager:** intraday order times are complete for every V1 lot from now on.
- **Senior engineer:** a one-line fix; the count tells whether old lots matter.
- **Automation tester:** scenario 9 with its weighted price; a probe.
- **Manual tester:** two V1 buys of one stock on one day: the lot lists two order times.

**Risks or ambiguities:** none known.
