## Plan for W-277 — upload and redrive skip trade validation

**What this item is for (one sentence, in my own words):** every trade is checked by the same rules before it changes
a holding, whichever way it arrives — the JSON routes, the upload or a redrive (PS-1).

**Findings (each read this session, 2026-11-11):**

1. **One check, two of four entries.** `validateAssetRequest` (`PortfolioService.java:190`) — quantity above zero,
   price not negative, no future date, a Gold Bond's maturity date, land refused — is called only by `addTransaction`
   (`:88`) and `addTransactionV2` (`:130`). The upload and redrive enter at `processTransaction` /
   `processTransactionV2`, which do not call it; the parser casts cell values without range checks.
2. **So a sheet row with quantity 0, a negative price or a date next year writes a holding**, and a stored
   temporary is redriven unchecked. The method's own Javadoc says a negative quantity "is not recoverable from the
   stored document alone".
3. **The email check is inert on the upload:** the parser reads no EMAIL column (`AssetRequestParser`), so the request
   carries none and the check is skipped, as for a JSON request that omits it.
4. **An upload is one transaction** (`@Transactional`), so one refused row refuses the file and nothing is stored;
   the parser's own refusals already name the row ("Row N: …").
5. **A redrive item that throws is reported failed with its message** and stays `TEMPORARY`
   (`redriveTemporaryTransactions`).
6. **An empty PRICE cell** reaches the check as `null` and fails with an NPE (500) — that is G-1, W-278 next; not here.

**Choices for the owner:**

- **C1 — where the check runs.**
  - **C1a (recommended):** at the top of `processTransaction` and `processTransactionV2`, the two points every trade
    passes; the routes stop calling it themselves, so it runs once per trade.
- **C2 — how the upload reports a refused row.**
  - **C2a (recommended):** the file is refused (400) and the answer names the row — "Row 2: Quantity must be greater
    than zero, but was: 0.0" — numbered as the parser numbers rows.
  - C2b: the bare message.

**Files I will modify:** `PortfolioService` (the check moves into both processing methods; the upload prefixes the row);
tests — upload rows with quantity 0, a negative price and a date next year each refused naming the row with nothing
stored; a stored temporary with quantity 0 redriven reports failed with the reason and changes nothing; the JSON
routes' existing refusals unchanged (`PortfolioIntegrationTest`, `LandTradeRefusalIntegrationTest`).

**Numbers I will use:** none.

**What I am NOT doing:** the null price (W-278); reading the EMAIL column (out of scope; W-285 reads the holder).

**How I will verify:** first tests red then green; probe: the check removed from `processTransaction` → the upload and
V1 redrive cases fail; the affected classes; `./mvnw validate`.

**Post-deployment actions (R15):** none — stored rows are not re-checked. (Rows already written by an unchecked upload
are not counted: no single condition finds them — a zero quantity is also a sold-out lot.)

**Five roles:**
- **Architect:** one rule set at the one point all four entries share.
- **Product manager:** a spreadsheet cannot record what the form would refuse, and says which row.
- **Senior engineer:** move the call, do not duplicate it.
- **Automation tester:** each rule on the upload, one on redrive; a probe.
- **Manual tester:** upload a sheet with quantity 0 in row 2: refused, "Row 2: …".

**Risks or ambiguities:** a temporary stored by an earlier unchecked upload that breaks a rule now fails at redrive
instead of being applied — the intended outcome; it stays `TEMPORARY` for the owner to see.
