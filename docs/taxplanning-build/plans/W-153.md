deducts against, today Java maps, sets, `==` tests and a `switch` in four classes, becomes conditions on the rows. A
new kind, or a law that changes which kinds a deduction reaches, then becomes new data instead of new code (audit P3,
D-313).

### Risks or ambiguities

1. **Person and item conditions on one row (W-153a).** `DepositInterestDeduction.isSenior` (`:82–86`) and
   `NodeContext.appliesHere` test all of a row's conditions together. W-153a's plan has to choose between testing the
   row per item (the senior row then applies item by item) and keeping the item conditions apart. The choice is
   stated there, with the trace consequences.
2. **Nil lines name the row an item misses.** Today they cite the row whose set the node reads unconditionally. With
   item conditions, an `AT_MOST_ONE` set returns no row for the item. The nil line then cites the row by its generated
   `RuleIds` constant (an id, G7 plumbing). The row id is unchanged; only how the code reaches it changes.
3. **W-153c may be mis-sized on its own.** The path definition is the one new concept. If its plan finds it over
   §7, it proposes c1 / c2.
