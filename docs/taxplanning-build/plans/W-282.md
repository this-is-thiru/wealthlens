## Plan for W-282 — a coverage floor on the trade-ledger code

**What this item is for (one sentence, in my own words):** the portfolio classes that record trades and their
outcomes get the same build-enforced coverage floor the charge engine has, so a branch added without a test fails the
build (B-1).

**Findings (each read or measured this session, 2026-11-11):**

1. **B-1's list has shrunk.** Of the classes it named (2026-09), `TradeClassifier` and the `HoldingPeriod*` classes are
   gone — holding-period logic moved to `taxengine` (W-160f), which has its own gates (`check-taxengine`,
   `check-taxengine-rules`). `TradeOutcomeRecorder` and `TransactionService` remain.
2. **Measured** (full suite, all tiers, `./mvnw clean test jacoco:report`, 5,767 tests, 0 failures):

   | Class | Line | Branch |
   |---|---|---|
   | `PortfolioService` | 345/350 = 98.6% | 101/110 = 91.8% |
   | `PortfolioQueryService` | 72/74 = 97.3% | 12/14 = 85.7% |
   | `TransactionService` | 65/66 = 98.5% | 17/18 = 94.4% |
   | `TradeOutcomeRecorder` | 107/109 = 98.2% | 18/24 = **75.0%** |
   | `TradeCollisionRetry` | 25/28 = 89.3% | 9/12 = **75.0%** |

3. **The missed branches** (JaCoCo XML): `TradeOutcomeRecorder` — a sale that matched no quantity (`:63`), a charge
   amount of `null` (`:112`, `:253`), a lot whose original quantity is 0 (`:129`), a zero buy value (`:176`), an
   empty or absent buy breakdown (`:249`); `TradeCollisionRetry` — an `Error` from the trade (`:91-92`) and a checked
   exception (`:94`).
4. **The existing gate's shape:** `check-charges-engine` is a JaCoCo `CLASS` rule at 90% line / 85% branch, run at
   `verify` (`pom.xml`); CI's `verify` runs it.
5. **PIT:** the `mutation` profile targets `brokercharges.engine.*`, `brokercharges.service.*` and
   `taxplanning.engine.*` at a profile-wide threshold of 85.

**Choices for the owner:**

- **C1 — which classes the floor covers.**
  - **C1a (recommended):** the five above — the trade path as it stands after W-264a's fixes — in a new
    `check-trade-ledger` `CLASS` rule at 90 / 85, with tests for the eight missed branches so all five clear it.
  - C1b: B-1's two only.
- **C2 — mutation testing.**
  - **C2a (recommended):** add `TradeOutcomeRecorder` and `TransactionService` to the `mutation` profile's targets and
    run it scoped to them; if their score is under the profile's 85, I stop on this part and report the score rather
    than lower anything.
  - C2b: leave PIT out; place it as a row.

**Files I will modify:** `pom.xml` (the rule; C2a the targets); tests — `TradeOutcomeRecorderTest` (six cases, values
by hand) and `TradeCollisionRetryTest` (two).

**Numbers I will use:** 90 / 85 — the charge engine's floor (`check-charges-engine`), as B-1 proposed.

**What I am NOT doing:** lowering any gate; covering classes outside the trade path.

**How I will verify:** the gate run at `verify` on the full suite passes; probe: one new test disabled → the gate fails
on its class (proves the rule bites); C2a's PIT score reported.

**Post-deployment actions (R15):** none.

**Five roles:**
- **Architect:** the trade ledger joins the charge engine and tax engine as gated code.
- **Product manager:** the code that writes what a tax return is filed from cannot quietly lose its tests.
- **Senior engineer:** the same rule shape as the existing gate.
- **Automation tester:** each missed branch gets a test with a hand-derived value; the gate is shown to fail.
- **Manual tester:** nothing visible.

**Risks or ambiguities:** the full suite takes over ten minutes; I run it detached at low priority, once for the
measurement (done) and once to prove the gate.
