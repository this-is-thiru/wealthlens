## Plan for W-238i — a provident fund that does not follow basic

**For:** a user whose employer pays provident fund on a capped wage, so the contribution does not change when basic
does. W-238d moves it with basic at the entered ratio. For this user, every basic move is then priced against a
contribution that will not happen. Row `03-WORK-ITEMS.md` W-238i (W-238d finding, C1a). Design: `03-advisory.md`
A2.2 C8.

### What I read (session 72)

- **Followers are built in one place.** `AllocationPricing.following` puts `EMPLOYEE_PF` and the employer's
  `RECOGNISED_PROVIDENT_FUND` contribution into `followers` whenever `BASIC` is movable
  (`taxengine/optimise/AllocationPricing.java:125-148`). No entered fact can keep either one out.
- **A follower that is left out is held automatically.** `entered` only puts movable items and followers into the
  allocation (`AllocationPricing.java:151-167`). The RPF cannot be named in `movableFunds` (`api/AllocationSpace.java:37-40`).
  `EMPLOYEE_PF` cannot be movable either, because it is not `SALARY` (W-238g, `AllocationPricing.java:89-96`). So a
  follower kept out of `followers` stays at its entered amount in the base inputs, and `Allocation`, `Saturation`
  and `Following` need no changes.
- **The dearness allowance refusal covers more than it needs to.** It fires whenever DA counts for retirement and DA
  is entered (`AllocationPricing.java:131-134`), even when nothing follows basic. Its stated reason is "whether the
  provident fund follows it too", which only matters when something does follow.
- **The draft stores `EnteredFacts` whole** (`taxplanning/workspace/DraftInputs.java:18`, per `plans/W-238h.md`).
  Jackson 3 turns `FAIL_ON_NULL_FOR_PRIMITIVES` on by default (`brokercharges/service/ChargeSeederService.java:96-99`).
  So a new boolean on `Employment` would make stored drafts that lack it fail to read.
- **Constructor limits.** `AllocationSpace` has 6 components, so it can take one more within Checkstyle's 7.
  `DraftOptimisationRequest` has 5.

### Choices (recommended first)

**C1: where the fact lives.**
- **(a) Recommended: on the optimisation request.** Add an `AllocationSpace` component,
  `ProvidentFundTerms(boolean employerShareFollowsBasic, boolean employeeShareFollowsBasic)`, about the residual's
  employment, which is the only employment the optimiser moves. The request gains two optional booleans, and each
  one defaults to `true` (W-238d's behaviour). Nothing is stored, so no runbook entry is needed and old requests
  answer the same. The cost: a user states this on each optimisation rather than once on the employment.
- (b) On `Employment`, stored with the draft. This matches the row's wording ("per employment"), but `Employment` is
  documented to hold only what a built rule reads (`input/Employment.java:9-11`), and no rule reads this. It is also
  a stored-shape change: old drafts fail to read (see above) unless they get a default and a runbook check, and
  there are 30 test constructors to update.

**C2: what "does not follow" means.**
- **(a) Recommended: held at the amount entered, whatever basic becomes.** This is the user's own statement, and no
  wage ceiling or rate goes into Java or the pack (CLAUDE.md §4). The limitation: if basic falls below a capped
  wage, the real contribution would fall too. The answer states that the contribution is held as entered.
- (b) Model the capped wage as versioned rule data. That needs the EPF scheme sourced from the Gazette first. It is
  W-238d's C1b, its own item.

**C3: refusals.**
- **(a) Recommended:**
  - The DA refusal fires only when a follower moves with basic. With both shares held (or none entered), nothing
    depends on whether PF follows DA. This is a narrowing: a request refused today for a DA employment with no PF
    entered would now be answered, and it is tested.
  - A term set to `false` when that share is not entered, or when `BASIC` is not movable, is refused (400): it holds
    nothing, and accepting it silently would hide a typo.
- (b) Keep the DA refusal as it is, and only add the refusal for an unused term.

### Shape (names checked at build)

- `api/ProvidentFundTerms` (public record), with `FOLLOW_BASIC` = both `true`, the default the 15 test constructors pass.
- `AllocationPricing.following` adds a follower only where its term says it follows, and applies the C3a refusals.
- `DraftOptimisationRequest` gains `Optional<Boolean> employerShareFollowsBasic` and
  `Optional<Boolean> employeeShareFollowsBasic`. `DraftComputationService.optimise` passes the terms through.

### Hand figures (TY 2026-27, new regime; slabs and starting point from `plans/W-238d.md` cases 1 – 2)

1. **The employer's share is held.** Basic 10,00,000, special 14,00,000, employer RPF 1,20,000, `BASIC` movable,
   `employerShareFollowsBasic: false`. Any basic move leaves basic + special at 24,00,000 and the RPF at 1,20,000,
   so salary does not change. Result: no change and no saving. The bill stays **2,92,500** (W-238d case 1 "before").
   With the term `true`, the same input gives W-238d's 39,000 saving, so this case fails if the term is ignored.
2. **The employer's share follows, the employee's is held.** Case 1, plus `EMPLOYEE_PF` 1,20,000, with
   `employerShareFollowsBasic: true` and `employeeShareFollowsBasic: false`.
   - The employer side is as in W-238d case 1: basic **22,50,000**, RPF **2,70,000**, bill **2,53,500**, saving
     **39,000**.
   - `EMPLOYEE_PF` stays at **1,20,000** and is not in `followingChanges`.
   - Basic's cash impact is +12,50,000 − 14,00,000 = **−1,50,000**, not W-238d case 2's −3,00,000.
3. **DA counts for retirement and nothing follows (C3a).** Basic 10,00,000, DA 2,00,000 counting for retirement,
   special 12,00,000, employer RPF 1,20,000 held. Salary is unchanged by any move, so the result is no change. Today
   this input is refused.
4. **Refusals:** DA counts for retirement with a share that follows (unchanged); a `false` term for a share not
   entered; a `false` term when `BASIC` is not movable.

4. **Probes, each restored by `cmp`:** the term ignored (cases 1 – 2 fail); the DA refusal left wide (case 3 fails);

### Five roles

- **Architect:** `taxengine` stays pure, with no new `allowedDependencies`, no rate or ceiling in Java (C2a), and no
  stored shape (C1a).
- **PM:** a capped-wage employee no longer gets a basic move priced on a contribution their employer will not pay.
  Old requests work as before.
- **Engineer:** `Allocation`, `Saturation` and `Following` are unchanged. W-238a's, W-238c's and W-238d's cases stay
  green, with their expectations unchanged.
- **Automation tester:** hand figures 1 – 3, the refusals in 4, three probes, each tier run once.
- **Manual tester:** curl a local run with case 2's draft, which should give a saving of 39,000 and `EMPLOYEE_PF`
  absent from `followingChanges`. Then a `false` term with no PF entered, which should give 400. Then a body
  without the terms, which should give W-238d's answer.
- **Runbook:** unchanged. No stored data, flag or seed.
