### What I found (session 43, 2026-10-31)

**What the build checks today.** `CoverageRegister.verify` (`coverage/CoverageRegister.java:119-138`) does three
things: it requires every section a rule or regime *cites* to be registered (`:122-127`, via
`requireRegistered` `:190-194`), it requires every rule a MODELLED row names to exist and have a PUBLISHED version
(`:129-133`, via `requirePublished` `:196-203`), and it requires the register to list exactly each Act's sections
(`:145-159`). It never asks whether a row's named rule cites that row. `SectionRef.citedBy` (`SectionRef.java:55-67`)
is the reader: PRESENT only, the instrument must equal one of the two Acts' citations, and `CITATION` is **anchored at
the start** of the reference (`:20`) — `^s\.([0-9]+[A-Z]*(?:-[A-Z]+)?)` — returning one section and nothing else.

**What is wrong today:** the register is the build's answer to "which sections do we model" (`CoverageRegisterTest:28`),
and 30 of its 89 MODELLED rows name a rule with no demonstrable connection to the section, while 11 rules that carry a
MODELLED section out are named by no row at all. Nothing is computed from a wrong listing today — but the register is
what the next reader (and the coverage MODELLED ⇒ catalogue SC-1 rule) trusts about what is modelled, and `verify` is
green on all of it.

### Choices (recommended first)

**C1 — how the check reads a citation.**

- **(a) Recommended: one new scanner in `SectionRef` — `namedBy(Provision)` returning every section the reference
  names, in citation order.** It reads `s.N` anywhere in the string, expands a plural `ss.` list, strips another
  instrument's citation (`Finance Act, 2026 s.127(a)(iii)`, `Finance (No. 2) Act, 2004 s.98`), and keeps
  `citedBy`'s instrument filter. Measured effect: 18 of the 109 `citedBy` cases are artifacts and disappear
  (109 → 91, 38 rows → 30). `citedBy` itself is untouched.
- (b) Keep `citedBy`: the 18 artifacts become baseline entries whose reason reads "the reference names the section
  later, which the reader cannot see" — a baseline that records a blind spot as if it were a register defect.
- (c) Change `citedBy` to the new reading: `requireRegistered` (`:190-194`) would then demand registration for every
  section named anywhere — unmeasured against the pack — and `SectionCatalogue.catalogued()` (`:108-114`) publishes a
  set derived from it, so a coverage item would change what the catalogue claims. Not here.

`namedBy` and `citedBy` are two questions, not two names for one: `citedBy` = *the section this provision is under*
(anchored, one); `namedBy` = *the sections this provision mentions* (anywhere, ordered). Both are documented as such.

**C2 — where the check lives.**

- **(a) Recommended: a test, `taxengine/rules/coverage/CoverageCitationTest.java`, beside `CoverageRegisterTest`,
  reading `TimelineReader.read` + `CoverageRegister.of` and a baseline from `backend/src/test/resources/`.** The same
  shape as W-183's guard: it runs in `-Punit` and therefore in `.claude/hooks/pre-commit-gate.sh`, it adds no
  production surface, and `verify` keeps its stated scope ("unregistered or falsely modelled", `:114-118`).
- (b) A `CoverageRegister.verifyCitations(timeline, baseline)` production method, build-time only like `PackValidator`
  — reads better as "a `CoverageRegister` check", but adds a production method whose only caller is a test.
- (c) Inside `verify` with the baseline under `content/` — puts a build artefact into the shipped pack. It would cost
  no relock (the content layer hashes only `content/explanations.json`, `RulePackCompiler:85`), but every future reason
  edit would then change what loads at startup.

**C3 — what the two halves of the check claim.**

- **(a) Recommended: two claims, one baseline.**
  - **A — a row's listing is backed or explained.** For every MODELLED row and every rule it names, the rule names
    that row's section, or the pair is in the baseline with a reason. *91 cases today.*
  - **B — no rule is orphaned.** Every rule that names a section of either Act whose row is MODELLED is named by at
    least one MODELLED row; a rule whose provisions name no Act section, or name only non-MODELLED rows, is exempt by
    shape (16 rules name no Act section; 1 names only PLANNED rows). *11 violations today, all closable by adding the
    rule to that row — this half ships with an empty baseline.*
- (b) Only the forward half (the item read literally): leaves the 11 real gaps unplaced and the 25 orphans invisible.
- (c) Add "the row that names a rule is the row of the first section it names" as a third claim: 31 cases, mostly the
  D-208 C2a head rows, so it would baseline the register's own precedent. It is judgement material, not a check.

**C4 — the exceptions.**

- **(a) Recommended: `backend/src/test/resources/coverage/citation-baseline.json`, one entry per (row, rule) with a
  reason.** The check fails both ways — a live mismatch absent from the file, and an entry that no longer mismatches
  (stale) — so the file can only shrink, and a stale entry cannot outlive its fix.
- (b) No baseline: impossible, because half of the exceptions *are* the register's design (D-208 C2a).
- (c) Reasons inside `coverage.json` per row: a pack change for a build-time concern, and the reason would sit in the
  locked layer's neighbourhood rather than beside the guard.

**C5 — how far the row surgery goes.**

- **(a) Recommended: judge every unit and act on it.** 91 forward cases in 30 rows and 11 orphan placements: a listing
  stays only if the row's claim can be stated in one sentence (the section computes it, or the rule's provision is a
  Schedule that section opens), otherwise the listing is removed and the rule is placed under the row of the section
  it names. The report publishes the table (row, rule, verdict, reason).
- (b) Baseline all 91 with one generic reason and place the 11: cheapest, and it turns today's open questions into
  permanent exceptions, which is what the item exists to stop.

### Risks or ambiguities

1. **The judgement is the work and the plan cannot promise its size in advance.** 91 cases is the ceiling, not the
   target: a listing either earns a one-sentence reason or is removed. If a row's claim cannot be stated, the listing
   goes and the rule is placed under the section it names — that is the item working, not failing.
2. **`namedBy` is a second reader beside `citedBy`.** The difference (anchored vs anywhere, one vs ordered) is the
   whole point, but it must be in the Javadoc of both, or the next session will pick the wrong one.
3. **A section named only in an exclusion counts as named.** `SAL-ALW-UNIFORM`'s 2025 provision ends
   "excluded by s.202(2)(a)(ii)", so the row for s.202 *could* list it under half A and be green. No row does today;
   if the owner reads "exclusion is not a citation", that is C1(b), and the plan is rewritten.
4. **11 rules gain a row, which changes what the register claims.** No computation reads the register (it is
   build-time only), but SC-1 (`SectionCatalogue.verify`) reads the register's MODELLED set, which these edits do not
   change — the integration tier plus `SectionCatalogueTest` are the proof.
5. **Two rows' judgements may disagree with D-208 C2a's precedent as recorded.** If a case cannot be decided against
   the precedent as written, it is reported and left baselined with the question stated, rather than decided silently.
