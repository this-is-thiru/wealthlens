## Plan for W-358c3b — pagination

> Planned in session 113 (2026-11-21), placed by D-859 (C1a split of W-358c3). **Stop point: nothing is built until the owner answers
> C1 – C4.**

**What this item is for (one sentence, in my own words):** a list that keeps growing is read a page at a time, so no answer grows
without bound and a caller can walk it.

### What the code is today (read this session)

| | Today | Where |
|---|---|---|
| Lists | 38 routes answer a bare JSON array; none takes a page | the zoned controllers' return types |
| Paging in the code | none: no `Pageable`, `PageRequest` or `PagedModel` in `backend/src/main` | `git grep` |
| Spring Data | 4.1.0 (Boot 4.1.0's `spring-data-bom` 2026.0.0) ships `PagedModel`; its default page serialisation is `DIRECT` (the internal `PageImpl`, an unstable shape Spring warns about); Boot sets it with `spring.data.web.pageable.serialization-mode`, and the size with `…default-page-size` / `…max-page-size` | `EnableSpringDataWebSupport` (javap), Boot's configuration metadata |
| Fetching | repository `findBy…` / `findAll` lists, and `MongoTemplateService.getDocuments` for filtered searches | `TransactionService`, `UserChargeService.findHistory`, `CorporateActionService.getAllCorporateActions`, `GazetteWatchService.leads`, `DraftComputationService.computations`, `DraftController.revisions` |

### Decisions (for approval with this plan)

- **C1 — what a page looks like.** **C1a (recommended):** Spring Data's own `PagedModel` (`serialization-mode: via-dto` in the three
  profile yamls): `{"content": [ … ], "page": {"size": 50, "number": 0, "totalElements": 123, "totalPages": 3}}` — Spring's documented,
  stable shape, nothing of ours to maintain. **C1b:** keep the body a bare array and put the total in a header
  (`X-Total-Count`, `Link` per RFC 8288) — clients keep reading an array, but every list's total needs a header reader.
- **C2 — the size.** **C2a (recommended):** `?page=0&size=50` (0-based, Spring's default), 50 when not given, at most 200 (a larger
  `size` is cut to 200, Spring's behaviour) — set once in the yamls. **C2b:** other numbers (name them).
- **C3 — the order.** A page needs a fixed, total order. **C3a (recommended):** each paged list keeps the order it has today, newest
  first where it has none (by its date), with the id as the tie-break; no `sort` parameter (no caller needs one today). **C3b:** a
  `sort` parameter as well.
- **C4 — which lists.** **C4a (recommended):** the seven that grow without bound:
  | Route | Grows with |
  |---|---|
  | `GET /api/v1/me/portfolio/transactions` | every trade |
  | `POST /api/v1/me/portfolio/transactions/search` | every trade matching |
  | `GET /api/v1/me/charges/user-charges` | every priced trade |
  | `GET /api/v1/me/corporate-actions` | every action ever recorded (all users) |
  | `GET /api/v1/admin/tax/gazette-leads` | every Gazette notification flagged |
  | `GET /api/v1/me/tax/profiles/{profileId}/computations` | every computation stored |
  | `GET /api/v1/me/tax/drafts/{draftId}/revisions` | every edit of a draft |
  The rest stay whole lists: they are bounded by what is open or held now (holdings, temporary trades, charge gaps, the grievance
  queue, AMC dues), by a profile's own references, or are reference data of a known size (rate cards, the catalogue, declarations).
  **C4b:** page every list.

### Files (if C1a – C4a)

**Modify:** the three profile yamls (`spring.data.web.pageable`: `serialization-mode`, `default-page-size`, `max-page-size`); the seven
handlers (a `Pageable` in, `PagedModel<…>` out); their services and repositories (`Page<…> findBy…(…, Pageable)`, and
`MongoTemplateService.getDocuments` with `query.with(pageable)` plus a count); the tests reading these seven as arrays; the api-collection
requests and docs for them; the runbook's "Next deploy" list.
**Create:** `PaginationIntegrationTest` — for each of the seven, three rows read with `size=2` answer 2 items, `totalElements` 3, and
page 1 holds the third (red first: today each answers an array of 3); `size=1000` is cut to 200 (read from the page metadata).
**Numbers I will use:** 50 and 200 (C2a — design values, not legal); the counts above.
**Design sections I read:** `plans/W-358c3.md`, D-859, D-860; the six services and two controllers named; Spring Data's
`EnableSpringDataWebSupport`.
**What I am NOT doing:** a `sort` parameter (C3a); paging the bounded lists (C4a); OpenAPI (W-359b).
**How I will verify:** red first as above; the moved tests; `ArchitectureTest`, `WealthLensModulithTest`, `validate`; the pipeline.
**Post-deployment actions (R15):** nothing in a database; callers of the seven read `content` and `page` — a "Next deploy" line.
**Five roles:** Architect — Spring's own page type and settings, nothing hand-rolled. PM — long histories stay fast to read. Senior
engineer — seven routes, one pattern. Automation tester — a red test per route on real rows. Manual tester — the api-collection's
seven requests, page 0 and page 1.
**Risks or ambiguities:** a caller that read the whole list now reads page 0 only (50 rows) unless it walks the pages — the api-collection
and any saved command change; an index may be wanted for a sorted page on a large collection (none of today's data is large — measured
at the build by the query plan, not assumed).
