## Plan for W-428 — personal data stored plain (encryption off, for now)

> Planned in session 127 (2026-11-28; owner, priority: "I don't want to keep as encrypted, as of now, keep them as plain as
> usual, we can think about the encryption later", "all the data apart from password"). Stop point: this plan; nothing built.

**What this item is for (one sentence):** every value the app now stores as `k1:…` ciphertext — emails, account holders, demat
ids, actors, PANs, names, dates of birth, addresses, the encrypted JSON columns and uploaded documents' bytes — is stored and
read as plain text, on all three databases; passwords stay Argon2id / BCrypt hashes and refresh tokens SHA-256 hashes (those
are hashes, not encryption, and are not touched).

**Facts (read this session):**
| Fact | Source |
|---|---|
| Columns encrypted by converter: 37 `EncryptedColumn`, 32 `SearchableColumn` (deterministic, so an email can be looked up), 3 `EncryptedDateColumn`, 3 `EncryptedDisabilitySeverityColumn`; JSON copies encrypted inside `CorporateActionListConverter`, `AssetRequestConverter`; document bytes in `DocumentBytes:46, :60` | grep of `@Convert`, `FieldCipher` users |
| `pan_digest` / `tan_digest` are HMACs (`IdentifierDigest`, digest key) used to find a PAN / TAN without reading it | `IdentifierDigest.java`; the columns on `TaxpayerProfile` (`panDigest`) and `Employer` (`tanDigest`) |
| Sign-in finds the account by the stored (encrypted) email: a plain query against encrypted rows finds nobody | `SearchableColumn`; D-485 |

**The hard part — order:** the app can only decrypt with the keys, and nobody can sign in once the code expects plain emails
while the rows are still encrypted. So the stored data must be turned plain **by the app itself, before it serves anyone**, on
each database, and the keys stay until every database is done.

### Split (§7: too large for one item)
- **W-428a — read both, write plain, and a one-time rewrite (code).** Every converter writes plain and reads plain **or**
  `k1:` (decrypting it); a query parameter goes in plain. A one-time **rewrite run**: the jar started with a profile
  (`plain-text-rewrite`, no web server, as the copier ran) reads every row of every affected table and saves it plain, one
  transaction per table, logs the counts, exits; a second run finds nothing to change (proven by a test). Tests: every
  converter's round trip, the rewrite on a seeded Testcontainers database (encrypted rows in, plain rows out, a second run 0),
  sign-in after the rewrite. Runbook entry (backup first: a `pg_dump` per database; the way back is the restore) and a removal
  ticket.
- **W-428b — the runs (you):** dev, then staging, then prod — backup, the rewrite run, a read-only SQL check that no column
  starts `k1:`, a start and sign-in; logged.
- **W-428c — remove the encryption (code), after W-428b on all three:** `FieldCipher`, the converters, `IdentifierDigest` and
  the digest columns (C2), `TAX_DATA_KEY` / `TAX_DIGEST_KEY` from config, CLAUDE.md, the runbook and your env files; §0.7 retired.
- **W-429 — encryption again, with rotation (placed, not planned):** "we can think about the encryption later" — due before
  the duties commence (about May 2027), so it is not lost.

### Choices
- **C1 — the rewrite run.** **C1a (recommended):** the jar with a one-time profile, before the first normal start (it needs no
  sign-in). **C1b:** a `SUPER_USER` endpoint — impossible here: the owner's own email is encrypted, so the sign-in it needs fails
  until the rewrite has run.
- **C2 — `pan_digest` / `tan_digest`.** **C2a (recommended):** dropped in W-428c — with PAN and TAN plain, a lookup is by the
  value itself (Flyway: a unique index on the plain column where the digest had one). **C2b:** kept as HMACs (the digest key stays).
- **C3 — log masking** (`[email]`, masked PAN in logs, W-358d1). **C3a (recommended):** kept — logs are not the store. **C3b:** off too.

**What I am NOT doing:** passwords, refresh-token hashes; the api-collection; anything beyond the split above.

**Five roles:** architect — one storage form, plain, with a clean path back to encryption (W-429); PM — no user-facing
change; senior engineer — the order (rewrite before serving) and the keys kept until the last database; automation tester — the
rewrite's idempotence and sign-in after it; manual tester — your three runs and the `k1:` check.

**Risks:** (1) a value missed by the rewrite stays `k1:` and is read wrongly after W-428c removes the decrypt path — the
read-only `k1:` check over every text column of every table (W-428b) must answer 0 before W-428c. (2) Backups taken before the
rewrite hold ciphertext; they need the keys to be read, so the keys are kept (with your backups) until those backups expire.
(3) Law: r.6(1)(a) names encryption as one safeguard; with it off, W-429 is the commitment to revisit it before the duties
commence.
