## Plan for W-326a — "what would change it", the engine

**What this item is for (one sentence, in my own words):** where a least-of limit binds and one input drives the
binding limb, the engine works out how much more of that input would bring it to the next limit, and carries that on
the line. Nothing shows it yet (W-326b).

**Probe (a read of the cap shapes, `TemporallyApportionedCap`, `TraceLine` and `PipelineRunner`; 2026-11-14):**
- `LeastOf.apply` (`rules/cap/LeastOf.java`) evaluates every limb, keeping the least and the winner's name.
- `CapShape.amountsRead()` already lists the amounts a shape reads, nested shapes included. That is the check for "no
  other limb reads this input".
- **What raises each shape**, read from each `apply`:
  - `PercentOfBase`: its base, at its rate.
  - `PercentOfBaseByLocation`: its base, at its band's rate for the place (`percentFor`, private today).
  - `AmountInExcess`: its amount, one for one. Its threshold's amounts lower it, so they are not the input that
    raises it.
  - `Fixed`: nothing. `PerUnitPerPeriod`: counts, not rupees.
  - `SlabLadder`, `PercentOfBaseByPopulation`, `LeastOf` and `AggregateWithCeiling` are in no `LeastOf` limb today;
    they publish nothing.
- **A rule apportioned across two versions** gets a new `CapResult` from `TemporallyApportionedCap.prorated`, so any
  headroom drops out. A rule governed by one version keeps it.
- `TraceLine` is built by `new TraceLine(` only inside itself and at `PipelineRunner:242` (the renumbering copy), plus
  one refusal test (`TraceLineTest:107`).
- `Rate.baseYielding(earned)` turns a rupee rise back into the input that gives it; the result is exact (`Money.CALC`).

**The design:**
- `CapShape` gains `Optional<BaseId> raisedBy()`, the input that raises the shape, and
  `Money moreToRaiseBy(Money rise, CapContext ctx)`, the extra of that input a rise needs. `AmountInExcess` adds the
  amount still below its threshold first.
- `LeastOf.apply` publishes a `Headroom(BaseId input, Money more, Money next)` only when every one of these holds:
  - the winner has a `raisedBy` input;
  - no other limb reads it (`amountsRead`), and neither does the winner's own threshold;
  - another limb is strictly higher; `next` is the least of those.
  Otherwise (a `Fixed` or count-driven winner, a shared input as in C3a, a tie, or a single limb) it publishes none.
- `CapResult` gains `Optional<Headroom> headroom` (the existing constructors pass none). `TraceLine` gains the same, set
  by `withCapResult` and carried by the `PipelineRunner` copy.
- **Exact, not rounded:** the engine keeps the exact figure. How the sentence rounds it is W-326b's.
- **Every input, not only levers:** the engine publishes headroom wherever it can be computed. Which inputs are
  levers is content (`terms.input`), so the renderer (W-326b) shows only those. The engine does not read content.

**Choices for the owner:** none beyond D-695. The one design call is above: the engine publishes for every input, and
the lever filter sits in the renderer. That follows "the engine does not read content" (W-327). Say if you want it the
other way.

    - a winner whose input another limb reads: none;

  - One test per shape for `moreToRaiseBy`.
  - `TraceLineTest`: `withCapResult` carries it, and the `PipelineRunner` copy keeps it.
  - A trace through a real node (HRA in `ExemptionNodeTest` or `HraExemptionTest`, found at build): the line carries
