**What is wrong today, in one sentence:** the D-252 check states a rule ("a row is reached only through its set") that
is not the whole rule — a basis row is reached through the set that rests on it — so two rows are filed in rule sets no
node can read, and the generated constants promise a caller that does not exist.

### Choices (recommended first)

- **C1 — the two sets:**
  - **(a) recommended: fold.** Teach the validator the second way a row is reached, drop the two sets, the two
    `"ruleSet"` lines and the two generated constants, and relock. Effect: 153 sets → 151, 153 constants → 151, the
    shipped pack unchanged in what it computes (nothing evaluated these sets), and the two rows keep every property
    that matters — their per-year provisions, their provenance, their `DisallowanceBasis`, and the explanation that
    cites them.
  - **(b) keep them, with a reason.** The reason would have to be "the row must live in a set", which is the rule
    this item finds overstated; and the kept set is `EXACTLY_ONE` / `REGIME`, i.e. it advertises itself as the kind of
    set a node evaluates, while its row defines no amount. `RuleSetIds`' header says a constant names "the set it
    evaluates" — two constants that no node may ever name contradict the file they sit in. I would be writing a
    comment where a caller should be.
  - **(c) keep the rows, delete the sets without touching the validator.** Not possible: the parser refuses a
    `ruleSet` naming an undeclared set (`RuleSetJson.java:46-52`), so the `ruleSet` lines must go, and then
    `checkEveryRuleIsInARuleSet` refuses both rows on every shipped-pack load.
- **C2 (only if C1a) — which bases the exemption counts:**
  - **(a) recommended: every set's basis** — a disallowance set's or a condition set's. One sentence — "a row is
    reached through its set, or through a set resting on it" — and one predicate, because `DisallowanceSet` and
    `ConditionSet` both require a `basis` and both print it (`RegimeVerdict.java:62`, `RegimeOffers.java:80`). The
    condition-set half has no shipped instance, so it gets its own test on a fixture; that test fails on HEAD, which
    is what makes it a guard rather than decoration.
  - **(b) disallowance sets only.** The narrower change, and enough for today. I recommend against it only because
    the two record types are the same mechanism and the second half costs three lines and one test; if you prefer the
    smallest possible diff, take this.
