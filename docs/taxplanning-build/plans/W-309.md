**What this item is for (one sentence, in my own words):** decide whether the P&L charge summary's "reprocessing one
trade counts it twice" limit (`docs/charges-engine/implementation-checklist.md:457 – 460`) can still happen. Then
either derive the summary from `user_charges` or close the limit with its reason (D-618).

**Findings (read this session, 2026-11-13):**

1. **The trigger has passed.** The limit was to be revisited "when Chunk 11 deletes the old hierarchy" (`:459 – 460`).
   The checklist's status says Chunk 11 is done and "the superseded implementation is deleted" (`:7`). Its own open
   list says "worth revisiting now that the old hierarchy it was matching is deleted" (`:21 – 24`).
2. **Writers of the summary:**
   - The live path: `ProfitAndLossService.mergeChargeSummary` → `foldCharges` (`:549 – 588`), from a V2 buy (`:349`)
     and a V2 sale (`:383`). It folds only a computation handed in; a V1 buy hands none (W-306).
   - The rebuild: `ProfitAndLossRebuild` (`:90 – 98`, runbook §2.2, W-283 / D-575) folds every BUY and SELL row of
     `user_charges` (`TRADE_EVENTS`, `:61`) into fresh documents and replaces the stored ones. It is "idempotent by
     construction" (`:52 – 53`). **So a summary derived from `user_charges` already exists, as a repair.** Its folding
     of V1 buys, which the live path never folds, is deliberate and pinned
     (`ProfitAndLossRebuildIntegrationTest:165`).
3. **Can the live path process one trade twice?**
   - A collision re-run (`TradeCollisionRetry`) runs each attempt in its own transaction, and "an aborted attempt left
     nothing behind" (`:19 – 28`). Transactions ship on: `app.mongodb.transactions-enabled: true`
     (`application.yaml:118`). **Not reachable.**
   - Redrive of a `TEMPORARY` trade processes it once.
   - **The one replay:** `POST /test/user/{email}/transact/sell` (`helper/controller/TestController:18 – 31`,
     `SUPER_USER`) calls `allocateSaleV2` with any transaction id and lots. Replaying a sale through it folds its
     charges again. It also writes the gains, the trade-outcome rows and the lots again, so a derived charge summary
     would not make a replay correct. That endpoint is the defect, not the summary.
   - **Drift has a repair:** §2.2's rebuild puts the summary back to what `user_charges` holds.
4. **What deriving would cost.** Summaries would be computed on read from `user_charges` instead of stored. That
   touches the readers (`RealisedProfitsResponse.yearlyChargeSummary`, the P&L reports), the rebuild, and the stored
   field in every `profit_and_loss` document, which needs a runbook clear. That is about two sessions, and it overlaps
   W-264d (the P&L audit). With no live path producing the double count (finding 3), it buys idempotence nothing
   currently needs.
