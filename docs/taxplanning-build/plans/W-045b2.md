## Plan for W-045b2 — two tax modules instead of four

**What this item is for (one sentence):** fold `taxrules` into `taxengine` (as `taxengine.rules`) and
remove the empty `taxdocs`, keeping the one boundary that pays for itself — the pure engine versus
the I/O application — and exposing to `taxplanning` only what it may use.

**No behaviour change.** Package moves, module declarations, and the rules that name packages.

### Facts this plan rests on (read in this session)

| Fact | Source |
|---|---|
| A closed module's sub-packages are internal; only its base package is visible to other modules | Spring Modulith reference, *Fundamentals* — "`order.internal`, just as any other sub-package of the application module base package, is considered an *internal* one" |
| A sub-package is exposed with `@NamedInterface` on its `package-info.java`; the default name is the package's local name | same page; `NamedInterface.java` javadoc in `spring-modulith-api-2.1.0-sources.jar` |
| A consumer allows it as `"module :: name"`; `"module :: *"` allows **all declared** named interfaces, **not** the base package | Fundamentals, *Named interfaces* |
| `propagate` (default `true`, since 2.0) adds types that appear in the **public signatures** of the annotated types "and are located in the same package space" — it is **not** "include sub-packages" | `NamedInterface.java` javadoc, 2.1.0 |
| Installed version: **Spring Modulith 2.1.0** | `~/.m2/…/spring-modulith-api/2.1.0` |
| `OPEN` would expose every internal package, including `pipeline` — the internals the boundary exists to hide | Fundamentals, *Open application modules* ("usually hints at sub-optimal modularization") |

### The exposure decision (the one design choice in this item)

**Named interfaces, declared only for what a consumer uses — growing with the items that need them.**
Today no new `taxplanning` code exists, so this item declares the two the plan's first consumers need,
proves the mechanism with a probe, and leaves the rest to the items that first import them:

| Package | Named interface | Why now |
|---|---|---|
| `taxengine.input` | `input` | `W-103` (`EngineInputsAssembler`) builds `EngineInputs` |
| `taxengine.result` | `result` | `W-104` (`TaxComputationService`) returns `TaxComputation` |

`taxplanning` declares `allowedDependencies = {…, "taxengine :: *"}` (drops `taxrules`, `taxdocs`).
Vocabulary types in those packages' public signatures (`Money`, `TaxYearId`, …) are expected to join
through `propagate`; **the probe proves or disproves that** — if it does not hold, `rules.money` and
`rules.id` get their own `@NamedInterface` (one line each), and I report which was needed.

Rejected: `OPEN` (exposes `pipeline` and every node); `@NamedInterface` on all ~12 `rules.*` packages
up front (the B-002 cost, for consumers that do not exist yet).

## Deviations from the plan, found while doing it
1. **`propagate` did not carry `Money`/`TaxYearId`** (probe B failed) — so `rules.money` and `rules.id` got their own `@NamedInterface` (`money`, `id`), as the plan provided for.
2. **`taxengine_does_not_swallow_failures` failed on the moved code** — 10 hits, all legitimate (four exception classes *extending* `RuntimeException`; `PackJson.construct` reading `getMessage()` to rethrow with a path). The rule's pattern `..taxengine..` now covered the former `taxrules`. Kept its **previous scope** by excluding `..taxengine.rules..` (no behaviour change, as planned). The rule is miswritten — it forbids *defining* an exception — raised as **OQ-5**, due before `W-105`.
3. `EngineInputsTest`: a now-redundant `startsWith("…taxengine.rules")` alternative removed (the `…taxengine` prefix already covers it); assertion unchanged in meaning.
