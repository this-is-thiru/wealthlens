## Plan for W-088j2b — venue facts on the capital-gains read-model

**What this item is for (one sentence):** `portfolio` publishes, for the buy and for the sale of each disposal
separately, the exchange and the segment it recorded. With those, W-088j2c can judge STT chargeability under Chapter
VII (sources row 8) where no breakdown exists.

**Split of W-088j2 (D-293). It raises C1–C4.** C3 asks you to revisit D2(a): as written, it cannot be built.

### What I read (session 26, 2026-10-20)

- **The row** (`03-WORK-ITEMS.md`, W-088j2b); D-293 (D1a, D2a); D-294 and sources row 8. Chargeability turns on:
  - whether the transaction was *"entered into in a recognised stock exchange"*;
  - whether it was *"settled by the actual delivery or transfer"*, which is serial 1 or 2 against serial 3;
  - s.113A's exclusions (the NPS Trust; an IFSC exchange with foreign-currency consideration).

  **Not the broker:** row 8 found no provision turning on it, so it is not published.
- **`trade_outcomes` today has one exchange and one segment per row, and which side they describe depends on the
  writer:**

  | Writer | `exchange_name` from | `segment` from |
  |---|---|---|
  | V2, `TradeOutcomeRecorder:128`, `:133` | the **sale** | the **sale** |
  | V1, `PortfolioService:705` | the **buy lot** (`assetEntity`) | **not set** (null) |
  | rebuild, `TradeMatchingService:182` | the **sale** | not set |

  So a row's `exchange_name` cannot be read as either side's fact without knowing which writer made it.
- **Where the facts come from:**
  - **The buy:** the lot `AssetEntity` holds `exchangeName` and `segment` (`:50`, `:68`).
  - **The sale:** the request `AssetRequest` holds them.
  - **The rebuild's inputs:** `BuyLot` and `SellRequest` (`TradeMatchingService:350–397`) carry the exchange, not the
    segment.
- **The segment's default:**
  - `AssetRequest:61` (*"Delivery unless the client says otherwise"*), `AssetEntity:66–70` and
    `TransactionEntity:63–65` all initialise `segment = DELIVERY`.
  - A stored document without the field loads with that default.
  - **No stored marker tells a recorded `DELIVERY` from a defaulted one**, for old rows or new.
- **The read-model:** `CapitalGainsBucket` and `BucketKey` (W-088j), and `CapitalGainsSummary`'s one-per-key check
  (which reads the fields generically).
- **Runbook:** §2.2 (W-088u8b's per-user rebuild, `SUPER_USER`, dry run first) and §3 (standing conditions).

### Choices (recommended first)

- **C1 — storage:**
  - **(a) recommended:** four explicit fields on `trade_outcomes`: `buy_exchange_name`, `buy_segment`,
    `sell_exchange_name` and `sell_segment`.
    - Each is written from that side's own record by all three writers: V2 takes them from the lot and the sale, V1
      likewise, and the rebuild's `BuyLot` / `SellRequest` gain the segment from their transactions.
    - The existing `exchange_name` / `segment` stay as they are, for the other readers (charges, P&L), and are not
      read for tax.
  - **(b)** reinterpret the existing pair. Rejected: they mean different sides by writer (table above).
- **C2 — rows written before this item:**
  - **(a) recommended:** no backfill, as with D-249 C4a.
    - Missing fields read as `UNRECORDED`.
    - The remedy for a user is §2.2's per-user rebuild, which writes the new fields. It is the same path that leaves
      rows with no breakdown, which is exactly where these facts are needed.
    - New runbook **§3.4:** a read-only count of rows without `sell_exchange_name`.
  - **(b)** a one-time backfill from the lots and transactions. That is a new write operation with its own runbook
    §2 entry, test and Phase 15 removal row (R15), for facts the rebuild already restores.
- **C3 — the segment (revisits D2(a)):** D2(a) said a row from before segments existed publishes its segment as
  `UNRECORDED`, not the `DELIVERY` default. That cannot be done faithfully: every entry point defaults to `DELIVERY`,
  so nothing stored distinguishes "said delivery" from "said nothing".
  - **(a) recommended:** publish the segment as recorded.
    - Where a side's record holds a segment, the read-model publishes it. The bucket's documentation states that
      `DELIVERY` is also the entry default *"unless the client says otherwise"*.
    - Where the `trade_outcomes` row lacks the new field, the segment is `UNRECORDED` (C2).
    - D2(a) is superseded by D-295.
  - **(b)** publish no segment. j2c then cannot tell serial 1/2 from serial 3, and every no-breakdown side stays
    `UNKNOWN`.
  - **(c)** keep D2(a) by changing every default to "unrecorded" in `AssetRequest` and the entities. That touches the
    charge engine's pricing path, which prices by segment; out of this item and against D-293's "facts only".
- **C4 — read-model shape:**
  - **(a) recommended:** a new record `portfolio/dto/TradeVenue(Optional<String> exchange, Optional<TradeSegment>
    segment)`. `CapitalGainsBucket` gains `acquisitionVenue` and `transferVenue`, both in `BucketKey`.
    - The exchange is the recorded string, passed as is. Mapping `NSE` / `BSE` / … to "a recognised stock exchange"
      is j2c's rule data (an open category).
    - "Venue" is a new word; nothing in the repo uses it.
  - **(b)** four flat fields on the bucket. Rejected: a twelve-component record.
