### Choices (recommended first)

**C1 — the tool.**

- **(a) Recommended: no new build plugin — an ArchUnit rule plus a source scan, in a new test class.** The ArchUnit
  rule works on bytecode, so Lombok-generated getters and setters count as reads (PMD's blind spot is gone); the source
  scan covers the `private static final` constants that are inlined out of the bytecode (SpotBugs' blind spot). Both
  are already on the classpath, both run in the unit tier and therefore in `.claude/hooks/pre-commit-gate.sh`, and the
  probe proves they find all nine.
- (b) PMD `UnusedPrivateField` — measured: zero findings on this codebase, because every class is annotated. It would
  ship green and guard nothing.
- (c) SpotBugs — catches the injected-never-read field but not one of the five constants; adds a plugin whose 125
  findings would need another baseline, and a baseline is the thing the repository says may only shrink.
- (d) Error Prone `UnusedVariable` — not measured here; it needs a javac plugin, `-XDcompilePolicy=simple` and a
  `disables` file for Lombok's generated code, and the interaction with Lombok on Java 25 is a toolchain risk this item
  should not carry.

**C2 — the findings.**

- **(a) Recommended: remove all eight; exempt the constant variable by shape.** Nothing is baselined, so the first run
  of the new guard is green.
- (b) Baseline the eight behind a counted list — the guard would start life unable to fail, and W-182 removed a
  baseline's worth of code precisely so the tree could stop carrying it.

### What I will build

1. **New test** `architecture/UnusedPrivateFieldTest.java`, two tests:
   - `privateFields_whenImported_areReadAtLeastOnce` — imports main classes (`ClassFileImporter`,
     `DoNotIncludeTests`); every `private` field that is neither `static final` nor a constant variable must have at
     least one `GET` access in `getAccessesToSelf()`; the failure names each `className.field`.
   - `privateStaticFinalConstants_whenScanned_occurMoreThanOnceInTheirFile` — walks `src/main/java`, reads each
     `private static final` declaration's name, counts `\bNAME\b` in that file; one occurrence (the declaration) is a
     failure. The same walk collects the constant-variable declarations (`private final <primitive|String> NAME =
     <literal>`) that the first test exempts.
   - A shared, small source-scan helper inside the class — no new production type, no new dependency.
2. **Delete** the eight fields (rows 1, 2, 3, 5-9), with the three imports the removals orphan.
3. **Nothing else** — no behaviour change, no API change, no pack, card, seed or runbook change.

The guard's own contract, stated in its Javadoc: it sees what bytecode and source can see. A field read only by
reflection (with no Lombok-generated accessor) is reported as unread; a name that appears only in a comment counts as
used. Both are stated rather than hidden.

### Risks or ambiguities

1. **The bytecode rule's first run is the judge.** Today's probe found exactly four fields and one of them is the
   constant-variable case; if the rule flags a fifth on the real tree I will report it and stop rather than add an
   exception. A field read only by a framework without a Lombok accessor would be a false positive — the exemption for
   that must be a shape rule, not a list of class names.
2. **The constant-variable exemption is a shape, not a name.** `private final` plus a primitive or `String` type plus
   a literal initialiser. A constant variable written as a computed constant (`1 + 2`) would be flagged, and the fix is
   to widen the shape, not to name the field.
3. **The source scan counts text.** A constant named only inside a comment or a string would be counted as used — a
   miss, never a false build failure.
4. **Lombok-generated fields are invisible to both guards** (`log` from `@Log4j2` is `static final`, so the bytecode
   rule skips it, and it is not in the source, so the scan does not see it). An unused `@Log4j2` stays possible; it is
   not this item's defect class.
5. **Three beans lose a constructor parameter.** Spring wires by type and the integration tier loads the context, but
   this is a bean-shape change and worth the owner's eye.
