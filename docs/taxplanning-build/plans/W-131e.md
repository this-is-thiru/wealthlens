**What this item is for (one sentence, in my own words):** O6's "Scan before storage". Every uploaded file is scanned by a malware
scanner before any byte is written, and before PDFBox opens it. A file that fails, or that could not be scanned, is never stored.

### What the design, the code and the sources say

- **O6** (`14-operational-design.md:161` –): "**Scan before storage**, not before parse. A file that fails the scan is never written
  to durable storage".
- **The upload path:** `DocumentService.upload` checks the switch, the owner, a parser for the form and the year's layout. It then looks for the
  same bytes already stored, and calls `DocumentBytes.store` (`documents/DocumentService.java`, read this session).
  `DocumentBytes.store` (`documents/store/DocumentBytes.java:39`) checks the size, then `%PDF-`, then **opens the PDF with PDFBox**
  to count pages (`pagesOf`), then writes to GridFS. So today an unscanned file is already parsed by PDFBox in-process.
- **Settings:** `DocumentSettings` (`documents/store/DocumentSettings.java`) has 5 components. Adding host, port and timeout would make 8,
  past Checkstyle's 7 (`ParameterNumber`), so the scan's settings become one nested record.
- **Deploy:** one container on one EC2 host (`Dockerfile`; `aws/ec2-setup.sh` installs Docker). The pipeline's deploy job is
  commented out (`.github/workflows/cicd.yaml:176` –), so the owner deploys by hand. There is no scanner today: `rg -i "clam|antivirus|malware"`
  outside docs finds nothing.
- **ClamAV** (docs.clamav.net, fetched 2026-11-18):
  - **Protocol** (`manual/Usage/ClamdProtocol.html`): "`INSTREAM` … must use `n` or `z` framing". "Each chunk starts with a
    4-byte unsigned length in network byte order". "End the stream with a zero-length chunk". The replies are "stream: OK" and
    "stream: Eicar-Signature FOUND". "If the stream exceeds that limit, `clamd` replies with an `INSTREAM size limit exceeded`
    error". "`PING` … replies with `PONG`".
  - **Image** (`manual/Installing/Docker.html`): `clamav/clamav:<feature>` is "preloaded with signature databases", and
    the docs advise "the tag for a feature release". Docker Hub's newest feature tag today is `1.5` (1.5.4). The container "runs both
    `freshclam` and `clamd`", and freshclam updates "once per day" by default. clamd listens on 3310.
  - **Memory:** "Minimum: 3 GiB", "Preferred: 4 GiB".
  - **Not found in the docs read:** the image's default `StreamMaxLength`. Our uploads reach 20 MiB (`max-bytes` 20,971,520), and
    the multipart limit is 21 MB.

### Choices for the owner (recommended first)

- **C1 — the scanner:**
  - **(a)** ClamAV's `clamd` in its own container beside the app, pinned to `clamav/clamav:1.5`. The app reaches it over TCP with
    `INSTREAM`. The client is a small class of our own (socket, chunks, one reply), with no new library. The bytes never leave the
    host.
    - **Your fact needed:** the EC2 host's memory. ClamAV needs 3 – 4 GiB on top of the app. I can't read the instance size from
      the repo.
  - (b) A cloud scanning API. **Not recommended:** it sends tax documents to a third party, against O1 and the notice.
  - (c) AWS GuardDuty Malware Protection. It scans **S3** objects, and our bytes are in GridFS (D-761 C2a), so it doesn't fit.
- **C2 — the outcomes:**
  - **(a)** `stream: OK` → the upload goes on.
  - **(a)** `… FOUND` → 400 "This file failed the malware scan and was not stored". Nothing is written, and the log carries the
    signature name only (no identifiers, O1.1).
  - **(a)** Anything else — unreachable, a timeout, an `ERROR` reply or the size-limit error → 503 "The malware scan could not be
    completed; nothing was stored". This fails closed: an unscanned file is never stored.
- **C3 — where:**
  - **(a)** First in `DocumentBytes.store`, after the size check and before `%PDF-` and PDFBox. Every write of bytes passes it, and PDFBox
    never opens an unscanned file.
  - (b) In `DocumentService.upload`, before `store`. This leaves a write path that doesn't scan.
- **C4 — tests:**
  - **(a)** An in-process fake `clamd` (a `ServerSocket` speaking INSTREAM: OK, FOUND on a marker, ERROR, or a closed port), started
    once in `AbstractIntegrationTest` with its port as a `@DynamicPropertySource`, as Mongo's is. Every upload test then passes
    through the scan.
  - **(a)** Unit tests of the client's framing (chunk lengths in network order, the zero chunk) against that fake.
  - **(a)** A real ClamAV is checked by the owner on staging with the EICAR string (runbook).
  - (b) Testcontainers ClamAV on CI. This needs a ≥ 3 GiB container and a signature load on every run, so it is not recommended.
- **C5 — the probe:** may I run the ClamAV container locally at build (OrbStack, no real data), to see the replies and the 20 MiB limit
  before I write the client? If the answer is no, the size limit is confirmed on staging by the runbook step, and a refusal there is a 503 (C2a)
  until `StreamMaxLength` is raised.

### Post-deployment actions (R15)

A new **§1.q**, for the owner, before §1.n's switch is turned on:

1. **Before:** `free -g` on the host is at least 3 GiB above the app.
2. `docker volume create clam_db`, then `docker run -d --name clamd --restart unless-stopped -v clam_db:/var/lib/clamav -p 127.0.0.1:3310:3310 clamav/clamav:1.5`.
3. **Check:** `docker exec clamd clamdscan --ping 1` answers PONG.
4. Set `CLAMD_HOST` for the app.
5. **After:** with the switch on in staging, upload the EICAR test file → 400 and nothing stored; then a real Form No. 130 → stored.

Running it a second time is safe (the name is taken: `docker start clamd`). The way back is `docker rm -f clamd`, which stores nothing. The exact commands will be
checked against the docs at build.

### Five roles

- **Architect:**
  - The scan sits at the one place bytes are written, so PDFBox never sees an unscanned file. It fails closed.
  - The bytes stay on the host. There is no new module dependency, and no law in code.
- **Product manager:** nothing changes while the switch is off. Once it is on, an infected file is refused in plain words, and a scanner outage
  is a 503, never a silent store.
- **Senior engineer:**
  - A small client of our own, with no new dependency.
  - Settings nested to stay within 7 components.
  - No catch-all: only `IOException` and `SocketTimeoutException` are mapped.
- **Automation tester:** the fake covers OK, FOUND, ERROR, closed port and slow reply. The infected case is red first. Every existing upload test now
  passes through the scan.
- **Manual tester:** on staging, EICAR → 400 and `tax_documents` unchanged; `docker stop clamd` → 503 and nothing stored;
  a real Form No. 130 → stored.

### Risks or ambiguities

- **Host memory** (C1a) is unknown to me. If the host can't carry ClamAV, the switch stays off.
- **`StreamMaxLength`** for 20 MiB is unverified (C5).
- **Signature freshness** is freshclam's daily update. There is no alert if it stops; that would be a proposal.
