## Revision 1 (R13, session 35, 2026-10-25) — what step 1 found, before any code

**What was missing from the plan.** `AssetRequest.assetType` is not validated (`AssetRequest:48`, no constraint),
and a sale without one is accepted today on both paths:
- V1's P&L never reads it;
- V2 classifies it: `HoldingPeriodResolver.classify` (`:50–62`) finds no policy for a `null` asset and returns
  `UNCLASSIFIED`, which `HoldingPeriodService.isShortTerm` (`:52–58`) counts as short-term, with a warning.

The split is keyed by `AssetType` in an `EnumMap`, which refuses a `null` key. As planned, such a sale would throw
inside the P&L write and fail the whole sell. That is a behaviour change the plan did not name. No code was written.

I cannot tell from here whether any client sends a sale without an asset type.

### Choices (recommended first)

- **R1-C1 — a sale with no asset type:**
  - **(a) recommended: the lot's asset type** (`AssetEntity.assetType`, recorded at the buy), when the sale's
    request has none. It is a fact of the same holding, and both paths have the lot in hand: V1 in
    `ProfitAndLossContext.from`'s `assetEntity`, V2 in the `AssetEntity` that each `BuyContext` is made from (so
    `BuyContext` gains the lot's asset type, one more file). If the
    lot has none either, the sale is refused with a message naming the stock. That refusal is new, but it applies only
    where no record anywhere says what was sold.
  - **(b) refuse any sale whose request has no asset type,** at the sell boundary (`IllegalArgumentException` → 400).
    Fail fast, but it changes the sell API for every client that omits the field today.
  - **(c) leave the sale out of the split,** logged. The split would then not reconcile with the pair, silently. I do
    not recommend it.
- **R1-C2 — the rest of the plan:** unchanged (C1a, C2a). Under R1-C1a, one more test each for V1 and V2: no asset
  type on the request, so the lot's is used; and one test where neither has one, so the sale is refused.
