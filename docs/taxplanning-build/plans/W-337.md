## Plan for W-337 — move the data store from MongoDB to MySQL (split proposal)

> Planned in session 118 (2026-11-22), next by D-899. The engine is decided (D-827: MySQL on Oracle Cloud's Always Free MySQL
> HeatWave); everything else is open (D-786 C4a). W-337 is far too large for one item (00-START-HERE §7), so this is a split
> proposal with its decisions. **Stop point: nothing is built until the owner answers C1 – C6.**

**What this item is for (one sentence, in my own words):** every byte the app stores moves from three MongoDB Atlas clusters to
one MySQL database system, with the code, the tests and the runbook changed to match, and nothing lost, unencrypted or erased
data brought back.

### Decisions (for approval with this plan)

- **C1 — the mapping layer.** **C1a (recommended): Spring Data JPA (Hibernate) with Flyway migrations.** Each collection becomes
  an entity and table; embedded lists become child tables, and opaque blobs (the `*_json` fields, already text) stay one
  column; `EncryptedField` / `SearchableIdentifier` become JPA `AttributeConverter`s. Repositories keep their derived-query
  names, so services change least. **C1b:** Spring Data JDBC (aggregates map closest to documents; whether it takes
  Spring's property-level `@ValueConverter` is **unverified**, so C1b needs a probe first). **C1c:** jOOQ (most control, most
  rewriting). The choice is proven, not assumed: **W-337a** builds one small module both ways before anything else.
- **C2 — the order of the port.** **C2a (recommended):** a branch `w-337` carries the whole port, one sub-item per commit,
  merged to master once every module and the data copier pass; master stays on MongoDB until then. A module-by-module merge
  would split one transaction across two stores (a V2 trade writes `portfolio`, `brokercharges` and `corporate` rows
  together). **C2b:** both stores side by side on master during the port.
- **C3 — how the data moves.** **C3a (recommended):** a one-time copier inside the app (both drivers, for the move only):
  reads each Mongo collection and writes MySQL, the ciphertext and keyed digests copied as they are (same keys, no
  decryption), idempotent by primary key, counts and fingerprints compared after; then removed (removal ticket, CLAUDE.md §6).
  **C3b:** `mongoexport` archives (W-334's) converted by a script outside the app — every encrypted field and type mapping
  reimplemented twice.
- **C4 — databases and access.** D-827 allows **one** Always Free DB system per tenancy, in a private subnet. **C4a
  (recommended):** one DB system with three schemas (`wealthlens_dev`, `_staging`, `_prod`), each with its own user; the
  owner reaches it through OCI Bastion (an SSH tunnel) from their machine, as the app runs locally (D-820, local only); the VM
  question waits for W-374 (host). **C4b:** an Always Free VM now, running the app beside the database.
- **C5 — backups and erasure in them (W-237f's re-plan, D-786 C5a).** **C5a (recommended):** the 1-day automatic backups are
  the only automatic copies, so an erased row leaves every backup within a day; the owner's own dump before each runbook run is
  deleted once the run is signed off, at most after `app.privacy.erasure-hold`; runbook §1.s rewritten to that. **C5b:**
  longer-kept dumps with an erasure re-apply step on restore (W-237f's `reapply` already exists).
- **C6 — the split.** **C6a (recommended):**
  1. **W-337a** — probe: `insurance` (1 collection) and `auth` (2, `refresh_tokens` with its family revocation) ported on
     C1a and C1b against Testcontainers MySQL pinned to HeatWave's version (the owner reads it in the console — not stated on
     the pages D-827 read); encryption converters, a transaction, pagination; an ADR closing C1.
  2. **W-337b** — the schema: Flyway baseline for all 40 collections (tables, keys, indexes, unique keys, TTL as a column a
     job sweeps), `docs/modules/*.md` §4 updated per table.
  3. **W-337c – f** — the port, by module: `shared` + `auth` + `insurance`; `brokercharges` + `corporate`; `portfolio`
     (P&L hierarchy, `TradeCollisionRetry` re-based on lock/deadlock errors); `taxplanning` (20 tables; GridFS → a
     `LONGBLOB` table of sealed bytes). Each moves its integration tests to the MySQL container; `AbstractIntegrationTest`
     changes once in c.
  4. **W-337g** — the copier (C3a), with its idempotence test; runbook entries (precheck, run, counts, way back).
  5. **W-337h** — the Oracle setup (owner): DB system, schemas, users, Bastion; runbook entries; C5's §1.s.
  6. **W-337i** — the moves: dev fresh, then a rehearsal on a copy of prod, staging, prod, each signed off; the
     `~/wealthlens-runs/archives` kept from W-334 deleted (D-848: at most to 2027-11-21); merge `w-337` to master.
  7. **W-337j** — removal: the Mongo starter, Testcontainers Mongo, the copier, Mongo-only runbook sections; `ArchitectureTest`
     `mongo_fields_are_snake_case` (`architecture/ArchitectureTest.java:176`) re-pointed to `@Column`.

  **C6b:** fewer, larger items (schema and port together per module).

**Five roles:**
- **Architect:** one store, the module boundaries unchanged; a single merge so no transaction spans two stores.
- **PM:** the app keeps every behaviour; the owner's tooling moves from the IntelliJ Mongo console to a MySQL one over Bastion.
- **Senior engineer:** ciphertext copied, never decrypted in transit; the copier is idempotent and removed after use.
- **Automation tester:** every integration test runs on MySQL before the merge; counts and fingerprints prove the copy.
- **Manual tester:** each api-collection request run against dev on MySQL before staging.

**Risks or ambiguities:**
1. **Size.** 40 collections, 79 integration classes and 59 test files on `MongoTemplate`: the port is the largest change since
   the tax build; C6's sub-items may split again as each is planned.
2. **HeatWave's limits are unknown** (version, connections, CPU); W-337a stops if they rule MySQL out.
3. **Idle reclamation** applies to Always Free VMs, not the DB system, per D-827's reading; Bastion sessions expire, so long
   runbook runs need a session renewed mid-way.
4. **Money and dates:** MySQL `DECIMAL` and `DATETIME(6)` in UTC must hold what Mongo held exactly; W-337a proves both.
