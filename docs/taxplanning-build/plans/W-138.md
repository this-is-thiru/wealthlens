## Plan for W-138 — the staleness sweep

**For:** a user whose filed or ready figures were computed under law that has since changed is told so, and told which
rules changed, never by quietly recomputing (`DR 13` R-8; `DR 18` V9).

### What I read (session 47)

- `DR 13` R-8: pinning the pack makes an old answer *reproducible*, not *right*. On a pack upgrade, every `ACTED_ON`
  and `READY` draft whose pinned pack is superseded is flagged, with a diff; never a silent recompute. `DR 18` V9 and
  V10 widen this: it fires on **any** new rule version for a computed year, not only on a declared supersession.
- **What a stored computation pins today:** `ComputedTax.lawAndExec`, the law and exec layer versions (e.g.
  `2026-27.law.129`, `2026-27.exec.31`; `TaxCalculator.java:62`). Every law or exec change bumps one of them
  (`rulepacks/2026-27.lock.json` `layers`). Its trace names each rule read (`ComputedTax.Step.rule`). All of this sits
  inside `result_json`, which is encrypted (D-447).
- **What the current pack knows:** its layer versions (`RulePack.layers`), and a checksum per rule in the lock
  (`RulePackLock.ruleChecksums`, verified at startup, D-210). A stored computation does **not** record the per-rule
  checksums it ran under, so today no rule-level diff is possible.
- `RulePack` has no `supersedes` / `retrospectiveFrom` (R-8's sketch). V10 makes them unnecessary for detection: a
  changed layer version already says the law moved.
- **No law is involved:** no figure or rate to source.

### Choices (recommended first)

**C1 — when it runs.** (a) At every startup, through W-137's `TaxJobRunner` (lease, failures, the
`app.tax.jobs.enabled` switch). Idempotent, so the first start after an upgrade flags and later starts change nothing.
(b) Only when the layer versions differ from a stored "last swept" record: one more collection to keep right.

**C2 — what "changed" means, and the diff.** (a) A draft is stale when its latest computation's pinned law/exec
versions differ from the current pack's for that year. The diff lists the rules **its own trace read** whose checksum
changed. For that, each new computation also stores `law_and_exec` and `rule_checksums` (for the rules its trace
read) as plain fields: pack structure, which `DR 14` O1.1 / O7 class as operational. A rule the old trace never read
can't have changed this result, so it isn't listed. (b) Versions only, no rule list. (c) Re-run and compare figures:
refused, since R-8 forbids it, and interest runs to the day, so figures move without any law change.

**C3 — where the flag lives and shows.** (a) On the draft: `staleness` holds since when, the computation's receipt,
the pinned and current versions, and the changed rule ids. `DraftView` carries it, and omits it when there is none.
Computing again under the current pack clears it. Only `ACTED_ON` and `READY` drafts are flagged (R-8): a `DRAFT` is
recomputed as the user works. (b) A separate collection read beside the draft.

### Build (C1a – C3a)
1. `taxengine`: `TaxCalculator.packVersions(TaxYearId)` (the current law/exec versions) and

2. `DraftComputation`: `law_and_exec`, `rule_checksums` (plain), set by `DraftComputationService.compute`.
3. `FilingDraft.staleness` (`DraftStaleness` record); `DraftView.staleness`; cleared on a compute under the current
   versions.
4. `taxplanning/jobs/StalenessSweep implements TaxJob`, run at `ApplicationReadyEvent` when the switch is on.
5. Runbook §1.y: the sweep's log line after each deploy that changes a pack. WL-A-2.

### Tests, by hand
- Computation pinned `2026-27.law.128` / `exec.31`, current `law.129` / `exec.31`, `READY` → flagged. The changed
  rules are the trace rules whose pinned checksum differs: a fixture pins `ADV-INSTALMENTS` as `sha256:0`, the rest as
  the lock has them → `[ADV-INSTALMENTS]` only.
- Same pins, `DRAFT` → not flagged. Pinned to the current versions → not flagged. A second sweep → no change.
- A flagged draft computed again now → `staleness` cleared.
- `ACTED_ON` (frozen) → flagged; its inputs and revision untouched.
- **Probes:** compare only `law` (drop `exec`) → an exec-only change goes unflagged and its test fails; list every
  trace rule → the rule-list test fails.

### Post-deployment (R15)
No data operation. After a deploy that changes a pack, §1.y gains: grep the log for `Job staleness-sweep flagged`
and its count. Way back: the switch.

### Roles
- **Architect:** two read methods on the engine's `api` interface; `taxplanning` imports no lock type. Facts stored
  (versions, checksums), no derived flag kept past its evidence.
- **Product:** `GET` draft gains `staleness` when the law moved: the versions and the rule ids. A friendly
  description per rule is later work (`content` layer). api-collection: add the field to the draft example.
- **Senior engineer:** plain fields hold no value; reading pins needs no decryption.
- **Automation tester:** fixtures with pinned versions and checksums set by hand; the two probes.
- **Manual tester:** on staging, change `law_and_exec` on a `READY` draft's computation in the console, restart,
  then `GET` the draft → `staleness` shown; compute again → gone.

**Risk:** computations stored before this item hold no `rule_checksums`. Their flag names no rules and says so
(`changedRules` empty, `ruleDiffAvailable: false`). §0.5 clears them before the first deploy anyway.

### Build record (D-450)

**Departures from the plan, each found while building:**
1. **The per-rule checksums come from the provider.** The compiled `RulePack` keeps none, so `RulePackProvider`
   gains `ruleChecksums(year)`, read from the verified lock (`ShippedRulePacks` keeps each year's at startup). No test
   fakes implement the interface.
2. **A legacy computation's versions are read from `result_json`'s `/tax/lawAndExec` alone,** not by mapping the
   whole view: an older result need not bind to today's `DraftComputationView`.
3. **The engine tests read the expected versions and checksum from `rulepacks/2026-27.lock.json` itself,** so they
   survive a relock without editing.
4. **A year with no shipped pack is refused,** with a `tax_job_failures` row naming the draft, and the draft left
   unflagged: whether the law moved cannot be told.
5. **api-collection:** it holds no draft read, so there is no example to update.

**Probes, reverted byte for byte (`cmp`):** law compared without exec → the exec-only case fails; every trace rule
listed → the changed-rule case fails. Two failures, those two tests.
