## Plan for W-142 — trace snapshot tests

**For:** the trace a client reads is a contract (`D-VIEWFROMTRACE`: the JSON, the PDF, ITR figures and diffs all read it);
an unreviewed change to its shape fails the build as a diff, not as a silently broken PDF later (`DR 19` E4.3).

### What I read (session 48)

- **`DR 19` E4.3** (`taxplanning-design/19-engineering-foundations.md`): `approvals.verify(compute(CANONICAL_CASE)
  .trace().toStableString())`. No approvals library is in the repo; `PackReviewTest` (W-139) already does
  generate-compare-commit with `-Dpack.review.write=true`.
- **The published trace** is `ComputedTax.trace`: `Step(sequence, node, rule, kind, limitedBy)`
  (`taxengine/api/ComputedTax.java:74`), projected from the engine's `TraceLine`s at `TaxCalculator.java:184` — no
  amounts. It reaches clients as `/tax/trace` in the compute response (`DraftComputationView`) and in each stored receipt.
- **A canonical case exists:** `DraftComputationIntegrationTest.compute_whenT13IsEntered_chargesTheGoldenBill` posts the
  end-to-end T13 draft (D-427) with a listed-equity sale in the portfolio (`listedEquitySale()`) and asserts only that
  `/tax/trace` is non-empty. The regime is chosen in the compute request body (`{"regime": …}`, as
  `compute_whenTheRegimeIsUnknown_expected400` sends).
- **No law is involved.**

### Choices (recommended first)

**C1 — what is snapshotted.** (a) **The published trace**, `/tax/trace` of the compute response: one line per step,
`sequence | node | rule | kind | limitedBy`, in committed files; amounts are not in it (the goldens and the W-141 oracle
guard them). (b) The engine's internal `TraceLine`s with values: every amount change would churn the snapshot, and it is
not what a client reads.

**C2 — the canonical cases.** (a) Three computes through the real HTTP path in `DraftComputationIntegrationTest`: T13 as
that test enters it (the listed-equity sale included, so the capital-gains steps appear); the same draft with no sale in
the portfolio; and T13 computed under the other regime (`{"regime": …}` in the body), so its steps appear. (b) Wait for W-145's persona fixtures: nothing
guards the trace meanwhile.

**C3 — what counts as a change.** (a) Any difference in a line fails — node, rule, kind and the `limitedBy` text,
which a user reads as the explanation. (b) Ignore `limitedBy`: a reworded explanation would reach users unreviewed.

### Build record

**Snapshots** (`src/test/resources/taxplanning/trace-snapshots/`): `t13-new-regime-with-sale` 37 lines,
`t13-new-regime-no-sale` 26, `t13-old-regime-with-sale` 37; stable over two further runs. Read line by line:
- every node is in its regime's pipeline, and sequences run 1 … n;
- **finding 1:** the order is execution order, derived by the engine from dependencies, not the regime's declared
  pipeline — `capitalgains.income` and `credits` precede `salary.base`. A valid order (neither depends on salary), but a
  view reading the trace in order shows credits before salary;
- **finding 2:** `INT-LATE-RETURN` and `INT-ADVANCE-SHORTFALL` read *"0 months from 2027-08-01 to 2026-11-06"* — the
  interest is rightly nil, but the interval runs backwards;
- the old regime's lines differ only where its law does (professional tax and its standard deduction, its slab, its
  rebate, its surcharge rows).
Both findings are placed as **W-142a**, before the PDF (W-123); nothing changed here.

**Departure from the plan:** rule-set membership was not checked from data: a node's rule sets are declared in its Java
class (`exec/pipelines/*.json` hold only `nodeId`, `produces`), so only node presence and order were checked.
