## Plan for W-139 — pack linter and cross-year review

**For:** a year's new law reads as a legal change in review, not a copy-paste: every rule that changed, vanished or was
copied between two shipped years is listed in a committed file a reviewer signs off, and the build fails when the packs
change without that file changing with them (`DR 15` C4, `DR 18` V7; W-045h erratum, D-057).

### Choices (recommended first)

**C1 — how the review is signed off.** (a) A test compiles each consecutive pair of shipped years, renders a
`PackReview` (lint findings in full, then the plain diff one line per rule) and compares it with the committed
`docs/taxplanning-build/reviews/pack-review-2025-26-to-2026-27.md`. Different → the build fails, naming the command
that rewrites it (`-Dpack.review.write=true`). So a pack change cannot land without its review file changing in the
same commit, where the reviewer reads it. (b) Log the findings only: nothing forces a read. (c) Fail on any lint
finding unless an allow-list names it with a reason: a second list to keep, beside the file.

**C2 — the lints.** (a) Five, each a fact the reviewer judges, none failing the build by itself:
  1. `TenfoldChange` — a numeric leaf whose new value is ≥ 10× or ≤ 1/10 of the old (a decimal slip). From or to 0:
     no ratio, not flagged.
  2. `UnexplainedDrop` — a rule in year N and not N+1 where no version's provision says `ABSENT_IN_THIS_ACT` (today:
     the 2 club rows).
  3. `CopiedVersion` — consecutive versions with the same `introducedBy` and `provenance.sourceUrl` (today: 3 STT rows).
  4. `ShapeChanged` — a definition's `type` changed, or a list in it gained or lost an entry (bands, contributors,
     limbs, read generically from the JSON) — V7's four shape lints in one.
  5. **Regimes and disallowance sets diffed** — the same walk over compiled `law/regimes.json`, closing the erratum gap.
  
  And **one build guard** in `PackValidator`: a verified version whose `accessedOn` predates its instrument's
  `notifiedOn` cannot have been read (0 today) — no judgement, so it fails. (b) Lints only, no guard.

**Not taken from C4/V7, with why:** `ProvisionRenumbered` (a provision's change is already a `ValueChanged` on its
path); `CarriedForwardUnverified` (`Provenance` I1 already forces `whatToCheck` on an unverified row); the I3, I6, I7,
gap, overlap and `UNDETERMINED` lints (already in `PackValidator`).

### Build (C1a, C2a)
1. `PackDiff`: `law/regimes.json` walked like rates (findings name the regime or set); finding `TenfoldChange`.
2. `timeline/PackLint` (cross-year): `UnexplainedDrop`, `CopiedVersion`, `ShapeChanged`, read from the timeline JSON.
3. `timeline/PackReview`: diff + lint for one pair → Markdown text; deterministic order.
4. `PackValidator`: the verification-date guard.
5. `PackReviewTest`: each consecutive shipped pair against its committed file; writes it under the property.
6. The first review file, generated and **read by me line by line** before the report; the W-139 row; the
   `shipped-years.json` `_note` says shipping a year also means regenerating and reviewing its file.

### Tests, by hand
- `TenfoldChange`: 250000 → 2500000 flagged; 250000 → 300000 not; 0.04 → 0.4 flagged; 0 → 5 not; "NEW" → "OLD" not.
- `UnexplainedDrop` on the shipped pair → exactly `PERQ-CLUB-BUSINESS`, `PERQ-CLUB-UNIFORM`; the 5 `ABSENT_IN_THIS_ACT`
  rows not listed.
- `CopiedVersion` on the shipped timeline → exactly the 3 STT rows.
- `ShapeChanged`: a copy with one band added to a 2026 slab version → one finding; the shipped timeline → none.
- Regimes: a copy with `NEW_TAX_REGIME`'s first band rate edited → one `ValueChanged` naming the regime.
- Guard: a copy with `accessedOn` set to the day before `notifiedOn` → refused; shipped packs → pass.
- **Probes:** drop the ≤ 1/10 side → the 0.04 case fails; ignore `ABSENT_IN_THIS_ACT` → 7 drops, test fails; edit one
  shipped rule's value without regenerating → `PackReviewTest` fails.

### Roles
- **Architect:** all inside `taxengine.rules.timeline` and `validate`; no new module dependency; `rules` stays free of
  the runner (`ArchitectureTest.rules_do_not_depend_on_the_runner`). Lints read facts already stored; no threshold is
  law (10× is a typo heuristic).
- **Product:** nothing a user sees. The owner, as reviewer, gets a file per year pair; the 5 findings above are the
  first sign-off.
- **Senior engineer:** `PackDiff` stays the one walk; lints are records in its `Finding` family; no catch-all; sizes
  within Checkstyle (the walk is split if it grows past 60 lines).
- **Automation tester:** the shipped-data assertions above are exact lists, derived by the survey and checked against
  the JSON by hand; edited-copy fixtures as `PackDiffTest` does; three probes reverted by `cmp`.
- **Manual tester:** edit a rate in a timeline JSON copy, run `./mvnw test -pl backend -Dtest=PackReviewTest` → fails
  naming the file; rerun with `-Dpack.review.write=true` → `git diff` shows the change in the review file.

**Risk:** the plain diff between two compiled years may be long (every rule split at 2026-04-01 shows a version removed
and one added). If the generated file passes ~600 lines I stop and ask whether the diff part stays one line per rule or
goes to `target/` only (R13).

**Size:** about 350 lines of main code, 350 of test.
