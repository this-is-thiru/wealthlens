read ciphertext — four converters, the cipher, the digests and their columns, the two keys, the one-time rewrite, and a

### Choices
- **C1 — a PAN's uniqueness without its digest.** **C1a (recommended):** a partial unique index on `pan` for profiles not held for
  erasure — a held profile frees its PAN as today, and its PAN stays readable for the reapply. **C1b:** unique on `pan`, and the PAN
  nulled when held — loses the PAN of a profile the owner may reapply.
- **C2 — the date columns.** **C2a (recommended):** back to `DATE` (`USING date_of_birth::date`; every stored value is
  `LocalDate.toString()`, ISO). **C2b:** stay `TEXT` with a plain converter — keeps a column type that exists only because of ciphertext.
- **C3 — the JSON converters.** **C3a (recommended):** `CorporateActionListConverter` onto `JsonColumnConverter`; `AssetRequestConverter`
  stays standalone (its mix-in mapper). **C3b:** give `JsonColumnConverter` a mapper hook for `AssetRequestConverter` — a seam for one caller.

**What I am NOT doing:** the log masking (D-1036 C3a); W-429 (encryption again, deferred); `ChargeRuleListConverter`, which duplicates
`JsonColumnConverter` but is not encryption — **proposed** as its own small item; the api-collection (no route or body changes).

**How I will verify:** `./mvnw validate`; the unit tier's moved classes; the integration classes listed above plus `AuthIntegrationTest`,
`ConsentNoticeIntegrationTest`, `DocumentStoreIntegrationTest`, `RefreshTokenIntegrationTest`, `StockSplitIntegrationTest`,
`DraftIntegrationTest`, `DraftComputationIntegrationTest`, `ArchitectureTest`, `UnusedPrivateFieldTest`, `WealthLensModulithTest`;
a red test for each new rule first (a taken PAN refused by the partial index; a held profile's PAN registers again; a prefix
filter on `account_holder` accepted) — each proven by a deliberate violation; the full tiers on the pipeline. `grep -rn "FieldCipher\|k1:\|TAX_DATA_KEY\|TAX_DIGEST_KEY\|personal-data.data-key" backend` → none.

**Post-deployment actions (R15):** one new runbook step, per database, before the release carrying W-428c first starts:
read-only precheck — `SELECT count(*) FROM wealthlens.tax_profiles WHERE date_of_birth !~ '^\d{4}-\d{2}-\d{2}$'` (same for
`tax_family_members`) → 0, and the duplicate-PAN count among active profiles → 0; Flyway V14 then runs at start; after: sign-in,
a profile read. Then `TAX_DATA_KEY` / `TAX_DIGEST_KEY` leave the env files (backup first) — **the values stay in your password
manager while `dev-pre-w428a.dump` and `prod-pre-w428a.dump` are kept**, since those hold ciphertext. Way back: the previous
release reads plain values too (W-428a), but its Flyway history lacks V14 — so a way back is a restore of the pre-start dump.

**Five roles:** architect — one storage form, nothing left that only serves a removed design; PM — no user-visible change (search on
account holder gains prefix and ordering); senior engineer — the order (precheck, then the start that migrates) and the unique
semantics kept; automation tester — red tests for the two indexes and the filter; manual tester — the precheck, a sign-in, a
profile with a PAN on each database.

**Risks:** (1) a duplicate active PAN or a non-ISO date would stop V14 at start — the read-only precheck answers it first.
(2) Size: ~30 entity files, 10 deleted classes, ~17 tests — mostly deletion; one commit, since a half-removed cipher does not
compile. (3) Old dumps hold ciphertext; restoring one onto this build would need the keys and W-428a's read path — the way back
for such a restore is the W-428a release (`m1.9`), named in the runbook step.
