## Plan for W-134a — the legacy salary module's stored data

**For:** no salary structure or tax figure sits readable in `salary_profiles` or `tax_computations` once the app holds
real users (`DR 14` O1.1, sensitive financial; placed by D-447 C2a).

### What I read (session 47)

- **Stored in plain text** (`taxplanning/salary/entity/`): `salary_profiles` holds the components and their amounts, the
  80C / 80D / NPS / home-loan / rent figures, `is_physically_disabled` (special category), `number_of_children`, the
  employer and city, and `source_text` (a pasted CTC letter, which can hold anything). `tax_computations` holds two
  `TaxResult`s (gross salary to take-home, `Long`s) and four `Object`-typed fields (`applied_exemptions`,
  `applied_deductions`, `warnings`, and `capital_gains_result`).
- **Queries:** `findByEmailOrderByAuditMetadata_CreatedAtDesc`, `findBySalaryProfileId`. Neither filters on a
  sensitive field.
- **Served by** `TaxPlanningController` under `/tax-planning/user/{email}/…`: profile CRUD, compute, restructure and
  the PDF. Tested by `TaxPlanningControllerIntegrationTest` and the engine and document tests.
- **The module is already scheduled for deletion.** W-159 (D-314, D-361) removes all of Appendix E group L2:
  `salary/**`, `service/TaxComputationService`, the engines, `recommendation/**`, `document/**`, the controllers and
  the legacy collections. It runs after W-123 (Phase 12), so **before the one deploy** that follows Phase 14.
- **What W-134 can't do here:** `EncryptedField` takes text, dates and enums only. These are `Long`, `Integer` and
  `Boolean` values, plus nested objects. Their `Object` fields would come back from a JSON round trip as maps, not
  their stored types, which changes what the compute and PDF paths read.

### The choice (recommended first)

**C1 — how this data is protected.**
(a) **Merge into W-159, and hold the deploy on it.** The data and its code go together before the one deploy, so
nothing new is ever stored in the clear. Code that is deleted a phase later isn't built now (CLAUDE.md §2). A
read-only runbook check (§0.6) counts `salary_profiles` and `tax_computations` on each database and stops the deploy
while W-159 is not D. W-159's own plan then decides the fate of any rows the count finds (export for the user, then
drop). **Cost:** docs only; no code.
(b) **Encrypt now.** Extend `EncryptedField` to `Long` / `Integer` / `Boolean`, and store `components` and each
`TaxResult` as one encrypted JSON value. The `Object` fields' read-back types change, so the compute, restructure and
PDF paths need re-testing. **Cost:** about 250 lines of main code and 150 of test, all deleted by W-159.

### Roles
- **Architect:** no new seam. A second encryption path for a module that is being removed would be speculative
  code. W-159 stays one import group (D-361).
- **Product:** nothing changes for a user now. The legacy endpoints keep working until W-159 replaces them.
- **Senior engineer:** no code, so nothing to clean up after.
- **Automation tester:** no behaviour change, so no test. The guard is the §0.6 check and the board.
- **Manual tester:** run §0.6 on staging and prod, and log the counts. A non-zero `source_text` count means pasted
  CTC letters exist; W-159's plan must cover them.

**Risk:** if W-159 slips past the deploy, the §0.6 stop holds the deploy rather than letting plain data in. The only
way past it is an owner waiver D-row (as §0.4 does).
