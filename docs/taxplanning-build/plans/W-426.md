## Plan for W-426 — the store by Spring Boot's auto-configuration: the dual-store wiring removed

> Planned in session 127 (2026-11-28; owner: "postgresTransactionManager, any explicit declaration like this and package
> configs … not needed anymore, can we remove those, all scenarios of redundancy"). **Probe applied (probe-before-plan):**
> every change below is in the working tree and proven; reverted if not approved.

**What this item is for (one sentence, in my own words):** with PostgreSQL the only store, nothing about it is hand-wired any
more — no named data source, entity manager, transaction manager or package lists — so Spring Boot's own auto-configuration
builds the store from `spring.datasource` / `spring.jpa`, and every `@Transactional` is plain.

**Kept on purpose:** the env names `APP_POSTGRES_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD` — `application.yaml` maps them
(`spring.datasource.url: ${app.postgres.datasource.url}` …), so your env files, the runbook's `PSQL()`, the Dockerfile and
`AbstractIntegrationTest`'s `registry.add("app.postgres.datasource.*")` need no change (see C1).

**Facts (read this session):** every `@Entity` (41) and every repository (41) sits in the 7 listed packages, so Boot's scan from
`com.thiru.wealthlens` finds the same set; no `@Converter(autoApply = true)` exists (a global scan would otherwise apply it
everywhere); nothing else declares a `DataSource`, `EntityManagerFactory` or transaction manager.

### Choices
- **C1 — the env names.** **C1a (recommended):** kept as `APP_POSTGRES_DATASOURCE_*`, mapped in `application.yaml` (no change for
  you, the runbook or the image). **C1b:** renamed to Spring's own `SPRING_DATASOURCE_*` (your three env files, §2.19's `PSQL()`,
  CLAUDE.md and the test's `registry.add` change; one fewer mapping).

**What I am NOT doing:** the Flyway layout (per module, W-399); `spring.jpa.open-in-view`; any query or entity.

**Post-deployment actions (R15):** none under C1a (the same env names, the same schema; one start of the new build on each
database at its next deploy, as every release has).

**Five roles:** architect — one way the store is built, Boot's; PM — nothing user-facing; senior engineer — 89 qualifiers and a
hand-built factory gone, so a new module's repository needs no list edit; automation tester — the must-fail schema check;
manual tester — the next deploy's start.

**Risks:** (1) Boot's defaults differ from the hand-built factory in ways no test reached (e.g. open-in-view on, a different
naming strategy) — the schema check would catch a naming change at start, and the integration tier covers the rest on the
pipeline. (2) A big diff (≈ 65 files), mechanical.
