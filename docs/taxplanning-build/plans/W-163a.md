## Plan for W-163a — the engine reads a statutory card

**What this item is for (one sentence, in my own words):** the charge engine learns to find a second rate card for
a trade, the law's card, which belongs to no broker, and to price its rules together with the broker's card. No
data moves yet; that is W-163b.

**Source:** `plans/W-163.md`, D-380 (C1a, C2a, C3a).

### What I read (session 37, 2026-10-28)

- **`ChargeEngine.compute`** (`brokercharges/engine/ChargeEngine.java:71–106`):
  - It resolves one schedule; none means `NO_SCHEDULE`.
  - It resolves the instrument profile only when the card says so, and enriches the context with the profile's
    facts.
  - `applicableRules` (`:194–210`) merges the card's and the profile's rules into one list sorted by `order`.
  - `resolveOverrides` (`:223–238`) lets the instrument win when both declare a code.
  - It builds `ChargeComputation(scheduleId, scheduleCode, instrumentId, resolution, lines, total)`.
  - Each line records its `source` (`ChargeRuleSource`: `SCHEDULE`, `INSTRUMENT`).
- **`ChargeScheduleResolver`** (`:63–120`):
  - It is cached by `ScopeKey.of(context)` and evicted by `evictAll()`.
  - `findCandidates(brokerName, date)` (`ChargeScheduleRepository:29`) matches `broker_name` exactly. So a card with
    no broker is never a candidate today: it can be published and would price nothing, silently.
  - The ranking: a card that disagrees is dropped, the most specific of the rest wins, and a tie on start date is
    refused by name.
- **`ChargeScheduleEntity`:** "Scope dimensions left null match anything"; `brokerName` is the only dimension the
  resolver does not treat that way.
- **`DerivedChargeCalculator` / `ChargeAccumulator.sumOf`** (`:41–49`): a base code with no line adds 0. One GST row
  naming `DP` therefore also serves intraday, which has no `DP` line. That answers W-163's risk 2.
- **`ChargeScheduleValidator.validateDerivedBase`** (`:262–282`): a derived rule's base code must be declared **on
  the same card** and ordered before it. A statutory GST card fails this, because its base (`BROKERAGE`, `DP`, …) is
  on the broker's card.
- **The recording.** `UserChargeService:156` copies `computation.scheduleCode()` onto `UserChargeEntity` (`:109`,
  `:112`, one card), and `ChargeBreakdownResponse:46` shows it. `ChargeComputation` is built in two places: the engine
  (`:101`) and `empty(…)` (`ChargeComputation:25`).

### Choices (recommended first)

- **D1 — what makes a card statutory:**
  - **(a) recommended: no broker.** That is the entity's own rule that a dimension left null matches anything, and
    here it means the card applies to every broker. The validator makes the rule explicit: a card with no broker may
    not name a plan or require an instrument profile, since both are the broker's terms. No new field, and the 11
    broker cards are unchanged.
  - **(b)** a new field, `ChargeScheduleKind { BROKER, STATUTORY }`, with the broker required if and only if the kind
    is `BROKER`. It is more explicit, but the field goes on every card file and every card stored.
- **D2 — a code on both the broker's card and the statutory card:**
  - **(a) recommended: refused** (`BadRequestException` naming the code and both cards). Applying both charges the
    tax twice. Letting either win hides a card defect, and the engine already refuses an ambiguous rule
    (`rejectAmbiguousRule`).
  - **(b)** the broker's card wins, as the more specific one, the way the instrument wins over the card.
- **D3 — no statutory card for the trade's scope:**
  - **(a) recommended: in W-163a it adds nothing, as today.** No statutory card exists until W-163b, so a recorded gap
    would mark every trade. W-163b adds `NO_STATUTORY_SCHEDULE` to the gaps report together with the data, so no
    window ever exists in which a missing card goes unnoticed.
  - **(b)** add the gap now and update every test whose resolution changes.

### What I will build (D1a, D2a, D3a)

- **`ChargeScheduleRepository`:** `findStatutoryCandidates(date)`, the same window and status as `findCandidates`,
  with `broker_name` absent.
- **`ChargeScheduleResolver`:** `resolveStatutory(context)`. It uses the same agreement, specificity and tie refusal
  as the broker's card, cached under a key without the broker, and cleared by the same `evictAll()`. The ranking is
  shared, not copied.
- **`ChargeEngine`:**
  - The statutory card's rules join the merged list as a third source, `ChargeRuleSource.STATUTORY` (a new value).
  - A code applicable on both the broker's card and the statutory card is refused (D2a).
  - A derived rule whose base code is priced **after** it is refused. The validator cannot see across cards, and that
    line would otherwise drop out of the base silently.
- **`ChargeComputation`:** `statutoryScheduleId` and `statutoryScheduleCode`. `UserChargeEntity` gains
  `statutory_schedule_id` and `statutory_schedule_code`; `UserChargeService` sets them; `ChargeBreakdownResponse`
  shows the code.
- **`ChargeScheduleValidator`:**
  - A card with no broker may not have a `planCode`, or `requiresInstrumentProfile` true (D1a).
  - Its derived base codes are checked against the catalogue, not against its own card. They are still ordered before
    the rule when they are declared on the same card.
- **Tests** (`ChargeEngineTest`, `ChargeScheduleResolverTest`, `ChargeScheduleValidatorTest`, one in
  `ChargesIntegrationTest`):
  - A statutory STT line and a broker brokerage line priced together.
  - Statutory GST taxing the broker's lines; its base adds 0 for a code with no line.
  - The same code on both cards refused.
  - A late base code refused.
  - No statutory card: the figures are unchanged.
  - Two equally specific statutory cards refused.
  - The validator's two refusals, and a no-broker card with a cross-card base accepted.
  - The recorded statutory code.

  Expected amounts are worked by hand in each test from the rule's rate and base.
- **The probe:** run the engine with the statutory card ignored. The "priced together" case must then fail.

### Figures

There is no new rate. The tests use made-up round rates (for example 1 % of ₹10,000 = ₹100), worked out by hand. No
shipped card or figure changes, so every existing test and the `staging-runbook.md` §4 figures stay as they are.

### What I am NOT doing

- Moving a rule or adding a statutory card file. That is W-163b.
- The `NO_STATUTORY_SCHEDULE` gap (D3a, W-163b), and sourcing the rates (W-163c).
- A listing endpoint for statutory cards. `GET /charge-schedules/{code}`, drift and unverified already reach any card.

### Post-deployment actions (R15)

**None.** `statutory_schedule_id` and `statutory_schedule_code` are additive. They are absent on stored rows, and
nothing reads them except the breakdown response, which shows none. No data ships.

### Risks or ambiguities

1. **A card with no broker could already be published today** and priced nothing. After W-163a it prices every
   broker's trade in its scope. None ships, because every seed file names a broker. A card published by hand without a
   broker is possible, but none is known on either database, and §1A clears every card at the deploy.
2. **The resolver's cache key.** A broker-free key must not collide with the broker's key. It gets its own map.
