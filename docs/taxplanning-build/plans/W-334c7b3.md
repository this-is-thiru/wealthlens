**What this item is for (one sentence, in my own words):** find out what each of the 18 trades held `TEMPORARY` without a recorded flow
(runbook §3.11, W-334c5 row 2) is — whose, which stock, which action held it, and whether it was already recorded — so the owner can
decide, per trade, whether to redrive it, remove it or leave it, before prod.

**Read in code this session:**
- A trade is held when a bonus, split or demerger on its stock is not yet performed for that user and broker: one in the trade's quarter
  up to its date, or an earlier one that reaches a lot held (`TemporaryTransactionService.anyCorporateActionToPerform`; the types are
  `CorporateActionType.FILTERABLE_CORPORATE_ACTIONS` — BONUS, STOCK_SPLIT, DEMERGER). "Performed" is a
  `lastly_performed_corporate_action` row for that user, stock, type and broker dated on or after the record date
  (`isCorporateActionToPerform`).
- Redrive (`POST /temporary-transactions/user/{email}/redrive`, `PortfolioService.redriveTemporaryTransactions`) has **no dry run**. It
  skips a trade still held ("still filtered"), sends one with no flow through V1 (`redriveThrough`, D-555 C2a), marks each one done
  `PROCESSED`, and lists a refused trade as failed. A V1 replay of a V2 trade merges into a same-day lot and is not priced by the
  charge engine (W-264a G-8).
- A user who has any temporary is refused new trades ("There are pending temporary transactions …", `PortfolioService.java:82`), so
  leaving them blocks those users on prod.
- The V2 route first appears in `52000e1e` (2026-06-21), which is in the build prod runs (`ec85b188`). So a temporary stored before
  2026-06-21 came through V1, and that is a fact; one stored later is unknown.
