## Plan for W-253 — identifiers stored encrypted, looked up by digest

**For:** the identifiers that point at a person (email, account holder, demat account id) stop being stored as plain
text and can still be queried, indexed and kept unique. DPDP Rules r.6(1)(a) (`sources/2026-11-07-data-protection.md`
row 10; W-248 C2a, D-479).

### What I read (session 61)

- **The row** (`03-WORK-ITEMS.md:1531`) and D-479. The cipher is `shared/protection/FieldCipher`: AES-256-GCM with a
  random 12-byte nonce stored in front of the ciphertext (`FieldCipher.java:33-37`). `decrypt` reads the nonce back from
  the stored value (`:47-58`). `IdentifierDigest` is an HMAC-SHA256 under the digest key; its only user is the PAN
  (`TaxpayerProfile.pan_digest`).
- **Where the identifiers are stored.** I checked all 43 `@Document` classes. None of these fields is encrypted today.

| Field | Collections |

| `email` | `transactions`, `assets`, `profit_and_loss`, `trade_outcomes`, `user_charges`, `charge_accounts`, `lastly_performed_corporate_action`, `insurances`, `salary_profiles`, `tax_computations`, `tax_profiles`, `tax_profile_erasures`, `tax_draft_computations`, `privacy_consents`, `privacy_erasure_requests`, `privacy_breach_intimations`, `privacy_grievances`; `user_details` (as `_id`) |

- **How they are queried.** 103 call sites in 42 main files: derived `…ByEmail…` methods, three `@Query` strings
  (`UserChargeRepository:24/30/35`, `PortfolioRepository:24`, `LastlyPerformedCorporateActionRepo:11`), `Criteria` in
  the four erasures, and the user's own filters (`QueryFilter`, which runs typed through `MongoTemplateService:33`).
  Tests reference these 184 times in 27 files. Every query is an exact match. I found no range, regex, sort or
  `distinct` on any of these fields. Emails are not normalised anywhere (`AuthService:50` looks up the value as sent).
- **Spring Data MongoDB 5.1.0** puts a query value through the field's `@ValueConverter`
  (`QueryMapper.getMappedValue`, source lines 467-478, `convertValueWithConversionContext` covers `$in` too). It
  writes the `@Id` without one (`MappingMongoConverter` 919-939 skips the id property).
- **Raw-`Document` paths** that would read or match the stored form: `TransactionBasedTradeOutcomeMigration:121-137`,
  `ProfitAndLossV2Backfill:90`, `ProfitAndLossSplitReshape:92/126`, `RegisteredUserDirectory:37` (`_id`).

### Choices (recommended first)

**C1: the mechanism.**
- **(a) Recommended: one field holding a deterministic ciphertext; queries unchanged.** A new converter,
  `SearchableIdentifier`, encrypts with the same key and the same `k1:` format. The nonce is not random: it is the
  first 12 bytes of HMAC-SHA256(digest key, `"identifier-nonce:" + value`).
  - Equal values store equally, so equality queries, unique indexes and `$in` keep working through `QueryMapper`.
    No repository, `@Query` or caller changes.
  - `EncryptedField`'s existing `decrypt` reads it back unchanged.
  - The nonce is the keyed digest the row asks for, carried inside the value instead of beside it. It leaks the same
    thing a digest does: that two rows hold the same value.
  - This is a synthetic-IV construction. The standard form, AES-GCM-SIV (RFC 8452), is not in the JDK. A nonce
    collision between two different values breaks GCM. With 96 bits, the odds stay negligible below about 2^40
    distinct values.
- (b) The row's literal form: encrypted value plus a `*_digest` sibling, with every query rewritten to the digest.
  That is 103 main call sites and 184 test references across every module, well over §7's size. It would need a split
  per module, with the modules switched over one at a time.

**C2: the login** (`user_details` uses the email as `_id`, which gets no converter).
- **(a) Recommended:** `_id` becomes a generated id. `email` becomes a converted field with a unique index.
  `findById(email)` at `AuthService:50/113` and `UserDetailsServiceImpl:23` becomes the existing
  `UserDetailsRepository.findByEmail` (`:9`). `RegisteredUserDirectory:37` matches on `email`.
- (b) Leave the login's email plain, as a documented exception. Not recommended: it is the one collection holding
  every user's email.

**C3: rows already stored.**
- **(a) Recommended: extend `POST /privacy/stored-fields/encrypt`** (W-248) with an identifier pass:
  - Each field in the table, conditioned on the plain value read, like W-248's pass.
  - `user_details` re-keyed: insert the new document, then delete the old one. On a second run it finds the new one
    and only deletes.
  - A row whose encrypted value would collide with a unique index entry (written between deploy and the run) is
    counted as `conflicts` and left unchanged.
  - W-254 already removes the endpoint. Runbook §1.r gains the step.
- (b) A separate endpoint, with its own Phase 15 row and YouTrack child.

### Five roles

- **Architect:** everything stays in `shared/protection`, so no `allowedDependencies` change. One key pair is kept.
  The nonce is domain-separated from the PAN digest by its label. Financial figures stay plain: they rest on storage
  encryption, which W-237f fact 1 is still waiting for you to confirm.
- **Product:** no response changes, because values are decrypted on read. Emails stay case-sensitive, as today. V1
  and V2 trades, uploads and every broker go through the same entities. No api-collection change.
- **Engineer:** no new seam. The converter is one class. The three migrations are corrected, not left to fail
  silently.
- **Automation tester:**
  - **Golden:** for a fixed test key and `a@b.in`, the stored value comes from Ruby OpenSSL (HMAC, then
    AES-256-GCM), computed outside the code and pasted in. `A@b.in` gives a different value, and the same value
    twice gives the same output.
  - **Integration:** a raw `k1:` value on every collection in the table. Login and register still work after
    re-keying. The endpoint's dry run counts and changes nothing; a real run works; a second run finds 0. A conflict
    row is left unchanged.
  - **Probes**, run and reverted with `cmp`: a random nonce → the equality tests fail; the converter removed from
    `TransactionEntity.email` → the raw-`k1:` test fails.
  - **Runs:** the targeted test, then the unit and integration tiers once each.
- **Manual tester:** after the §1.r call on staging:
  - Sign in, then `GET /portfolio/user/{email}`: same holdings as before.
  - In the console, `db.transactions.findOne({}, {email: 1, account_holder: 1})` shows both starting `k1:`.
  - Run the endpoint again: every count is 0.
  - **Edge cases:** an email with different case is a different user, as before; an empty `account_holder` stays
    `null`.

   choice.

## Amendment A (R13): the probe, 2026-11-08

**Probe result** (`SearchableIdentifierIntegrationTest`, Testcontainers Mongo):
- **Converted:** derived methods (2/2 pass), and `Criteria` or `@Query` where the stored name equals the Java name (`email`,
  `principal`).
- **Not converted:** a stored name that differs from the Java name. `findEligibleHoldingsForSell` (`'account_holder': ?3`)
  and `where("account_holder")` both found **0** rows, silently. `QueryMapper.forName` (source lines 1384-1407) resolves
  Java property names only.
- `where("accountHolder")` against the entity converts and finds the row (1 / 0 / 0; probe reverted, `cmp` clean).

**So C1a's "no query changes" is wrong at five sites:**
- `PortfolioRepository:24`, `UserChargeRepository:24/30/35`: `'account_holder'` becomes `'accountHolder'` in the `@Query`
  strings. The indexes keep the stored names; they are not queries.
- The user's dynamic filter key `account_holder` (`AssetEntity.ALLOWED_FIELDS`): the API keeps the key, and `QueryBuilder`
  maps it to `accountHolder`.

**Two more found while building:**
- **Missed by the plan's inventory:** a TEMPORARY transaction embeds its `AssetRequest` (`asset_request.email`,
  `asset_request.accountHolder`). Both are now annotated, and the encrypt pass covers them by dotted path.
- **A new refusal:** a user filter on `account_holder` with `STARTS_WITH` or a range cannot work on ciphertext. It now
  answers 400 ("stored encrypted and can only be matched exactly") instead of silently matching nothing.
  - `EQUALS`, `NOT_EQUALS`, `CONTAINS`, `IS_NULL` and `IS_NOT_NULL` still work.

**Guard, so a later query cannot repeat this:** a unit test reads every `@Query` string in `src/main`. It fails if one
names the stored name of a `SearchableIdentifier` field that differs from its Java name. Its probe: put
`'account_holder'` back, and the test fails.

**Asks:** approve A (the five sites, the embedded request, the 400 refusal and the guard).
