## Plan for W-283a3 — write the rebuilt `assets`

**What this item is for (one sentence, in my own words):** after a dry run, a `SUPER_USER` can replace one user's
lots with the replay W-283a2 built, keeping each surviving lot's id so the `trade_outcomes` that name it still do
(D-582 C3a, D-583).

**Findings (read this session, 2026-11-12):**

1. **Saving under a kept id replaces the document.** `AssetEntity` has `@MongoId` and no `@Version`
   (`AssetEntity:40 – 43`), so a lot saved under a stored lot's id is a full replace. But auditing treats it as
   not new: the stored `audit_metadata.created_*` is lost unless carried.
2. **The replay leaves out what it cannot rebuild.** A V2 lot's order times come from the request, which a
   transaction does not keep. A lot's list of corporate actions is not compared either (`assets-rebuild.md`, "Copied
   as live, not compared"). Writing the replay's versions would drop both.
3. **Matching already exists.** `LotComparisons` pairs a rebuilt lot with a stored one by stock, broker, holder, date
   and buy transactions, in order within a key. That covers demerged lots, which list no buy, as long as their key is
   unique.
4. **A delete exists.** `PortfolioRepository.deleteByEmail` is the user's lots (`UserRecordsErasureService:65`).

**Choices for the owner:**

- **C1 — writing when the replay read something it could not confirm** (`shapeNotFound`, `saleFlowUnknown`
  non-empty).
  - **C1a (recommended):** write. The dry run listed each one, and the runbook makes the owner read it first.
  - C1b: refuse unless the call adds `acceptReadings=true`.
- **C2 — what a kept lot carries over from the stored one.**
  - **C2a (recommended):** its id (C3a), its order times, its list of corporate actions and its
    `audit_metadata` (creation). The figures are always the replay's. A new lot has the replay's everything, and is
    listed.
  - C2b: the id only.

**Files I will modify:**
- `AssetsRebuild` — `rebuild(userMail, dryRun)`. A real run, in one transaction, deletes the user's lots and saves
  the rebuilt ones with C2's carry-over. The class's `readOnly` moves to the dry-run path.
- `LotComparisons` — expose the pairing it already makes, rebuilt lot to stored lot.
- `AssetsRebuildReport` — add `dryRun`, `lotsWritten`, `lotsKeptById`, and `newLots` (each new lot's stock, date and
  buys).
- `AssetsRebuildController` — `dryRun` defaulting to `true`, as D-284 and D-575.
- The runbook gets a new standing entry, §2.12.
- api-collection: the request gets `dryRun`.
- `assets-rebuild.md`: the write.
- Tests:
  - `AssetsRebuildIntegrationTest`:
    - A stored lot's quantity is corrupted (8 instead of 5). The dry run reports 1 differing and writes nothing.
      The real run restores 5 under the same id, and the sale's `trade_outcomes` row still names it. A second run
      reports nothing differing.
    - A stored lot is deleted. The real run restores it under a new id, listed.
  - `AssetsRebuildTest` gets the carry-over.

**Numbers I will use:** none from law. The integration figures are the W-283a2 scenario's, by hand (5 and 6 held).

**Design sections I read:** `assets-rebuild.md`; D-582 C3a, D-583; D-575 (shape of the write).

**What I am NOT doing:** touching `trade_outcomes` or P&L; fixing W-291 / W-292; running any operation.

**How I will verify:**
- The tests above, each red before.
- Probe: skip the id carry; the link test must fail.
- The unit and integration tiers, run from cleared report directories.

**Post-deployment actions (R15):** runbook §2.12, a standing operation, not removed after use. It gives:
- **When:** after a correction to a user's `transactions`.
- **Who:** the owner.
- **Steps:** back up the user's `assets` with `mongoexport`; dry run; read `lotsDiffering` and the lists; write;
  verify with a second dry run showing 0 differing and a `countDocuments` before and after.
- **Second run:** safe.
- **The way back:** delete the user's lots and `mongoimport` the backup.

**Five roles:**
- **Architect:** the write is the dry run plus one replace in one transaction. Links into `assets` are kept by id;
  nothing outside `portfolio` is written.
- **Product manager:** the owner can correct a user's holdings without hand-editing lots. The holdings view shows
  the rebuilt lots.
- **Senior engineer:** the carry-over is explicit and listed. The id policy is the comparison's pairing, not a second
  matcher.
- **Automation tester:**
  - a correction case and a lost-lot case;
  - a second-run case;
  - the link check;
  - a probe.
- **Manual tester:** on staging, a dry run, a write, a second dry run (0 differing), then the user's holdings
  endpoint unchanged in shape.

**Risks or ambiguities:**
- Two stored lots with one key (two demerged lots of one date and stock) are paired in order. If the order differs,
  ids swap between equal-looking lots. Their figures are then the replay's either way.
