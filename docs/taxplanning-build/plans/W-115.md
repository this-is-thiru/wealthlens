## Plan for W-115 — completeness, weighted by measured worth (F33)

**What this item is for (one sentence, in my own words):** answer "is this number trustworthy yet?" by listing what
the draft leaves out. Each item carries the change in tax it could make, measured by computing the draft twice
(`D-MARGINAL`). Items are ranked and the top five are surfaced. It is served at
`GET /tax/user/{email}/drafts/{draftId}/completeness`.

**Design sections I read:** `01-PRD.md:211` (F33.1 – F33.3); `20-product-gaps.md:178` F33 (the pseudo-code: the
upper bound is the rule's cap at the user's own facts, and the worth is `tax(current) − tax(current + upperBound)`);
`23-architecture-consolidation.md:428` (`CompletenessProjection`, N recomputes); `02-TECH-SPEC.md:368` (the route).

**Probe (run before this plan, then removed):** `TaxCalculator.compute` on TY 2026-27, old regime (`FIRST_SCHEDULE_RATES`):

| Scenario | Bill |
|---|---|
| Basic 10,00,000 + HRA 4,00,000, no tenancy | 2,26,200 |
| The same, with a year's tenancy (rent 1 crore) at ANY_OTHER_PLACE, MUMBAI or BENGALURU | 1,06,600 each |
| Basic 10,00,000 alone, no rent | 1,06,600 |
| The same, with a year's tenancy and `RentDeclaration(12, false, false)` | 94,120 |

**The probe figures, checked by hand:**
- **2,26,200:** 14,00,000 less 50,000 standard deduction is 13,50,000. Tax is 12,500 + 1,00,000 + 30 % × 3,50,000, which is 2,17,500; with 4 % cess, 2,26,200.
- **1,06,600:** 4,00,000 of HRA is exempt, because the HRA received binds below 40 % and 50 % of salary, so income is 9,50,000. Tax is 12,500 + 90,000, which is 1,02,500; with cess, 1,06,600.
- **94,120:** s.134 takes 60,000 (₹5,000 × 12, below 25 % of income and below the rent's excess), so income is 8,90,000. Tax is 12,500 + 78,000, which is 90,500; with cess, 94,120.

So rent is worth ₹1,19,600 to the HRA payee and ₹12,480 without HRA. The location did not matter here; it matters
only where 40 % of salary is below the HRA received.

**Choices for the owner:**
- **C1: which items.**
  - **C1a (recommended):** six kinds. The four from `priceDeductionRoom` (Schedule XV, own health cover, parents' health cover, own NPS), plus HRA rent and s.134 rent. Each has a cap that can be evaluated at the draft's own facts. Anything else goes into `notIncluded` by name: home-loan interest (s.22), which needs an owned house; LTA, whose bound is a fare; and education-loan interest, which has no ceiling.
  - C1b: only the four rooms that are already priced. This leaves out rent, the design's lead example.
- **C2: F33.2, items that raise tax.**
  - **C2a (recommended):** the repo holds no figure for an omitted income, and a guessed one would break F33.1. Place **W-324** (*omitted income that raises tax, measured from department data*), after an AIS / 26AS import exists, and name the gap in `notIncluded`. The response still carries a `direction` (`REDUCES` / `RAISES`) so the shape does not change later.
  - C2b: list unentered income heads with no rupee figure. This is unmeasured, so it does not meet F33.1.
- **C3: HRA's location, which is unknown when no tenancy is entered.**
  - **C3a (recommended):** run once per location band the row holds, plus one at ANY_OTHER_PLACE. Each band is read from the pack, so no city name appears in Java. Report the largest saving as "up to", naming the location that gives it. Where a tenancy is entered, run at its location only.
  - C3b: run at ANY_OTHER_PLACE only, and report "at least".
- **C4: the rent used in a filling run.**
  - **C4a (recommended):** a rent equal to the base run's gross total income for the whole year (12 months on the declaration). That rent is always large enough that the rent limb does not bind. The response states the rent needed: for HRA, the exemption plus one-tenth of salary; for s.134, the deduction plus 10 % of total income, both read off the filled run's trace. It also states the assumption of a full year's stay.
  - C4b: a fixed large sentinel. That is an unexplained constant.
- **C5: partly used room.** Schedule XV with ₹50,000 paid still has ₹1,00,000 of room.
  - **C5a (recommended):** include it, with `counted` showing what is already entered. The question F33 answers is what the number does not yet reflect.
  - C5b: unentered items only.
- **C6: ranking.**
  - **C6a (recommended):** rank by measured worth, largest first, and drop items worth nil (a regime that allows them nothing). Return `top` (five) plus `others`, and the total of `top` for the "worth up to ₹X" line. The items overlap (for example HRA and s.134 exclude each other), so the total is labelled "not additive" in `notIncluded`, as the calendar does.
- **C7: storage and regime.** As W-113 and W-114 (D-664 C2a, D-665 C5a): compute on request and store nothing. Use the elected regime, else the default (`DraftForecastService.regimeOf`). That is about nine runs per view.

**Risks or ambiguities:**
- **OQ-6** (`SAL-HOUSE-RENT-ALLOWANCE` `_note`): the row uses the accommodation's location, and C3a inherits that.
- **A full year's stay.** Assuming the stay lasts the whole year overstates the worth for someone who moved mid-year. It is stated in the response.
- **Overlap.** HRA and s.134 exclude each other, and a draft with HRA never gets the s.134 item. The total is labelled not additive.
