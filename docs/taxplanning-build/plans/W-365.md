## Plan for W-365 — required fields on the trade, finance and simulation bodies

> Planned in session 115 (2026-11-22), from D-886's build-time probe. Probed first (below), reverted byte-identical.
> **Stop point: nothing is built until the owner answers C1 – C3.**

**What this item is for (one sentence, in my own words):** a trade, a finance calculation or a charge preview that leaves out
something it cannot do without is refused with a 400 naming it, instead of being stored half-empty, priced at nothing, or crashing.

### What the code does today

| Body | Gap (D-886 probe) | Why, read this session |
|---|---|---|
| Trade, V1 and V2 (`AssetRequest`) | stored with no `stockCode` or `brokerName` | `PortfolioService.validateAssetRequest` (`PortfolioService.java:191`) checks email, quantity, price, a spaced code, a future date, GOLD_BOND, land, exchange — never that a stock or broker is named |
| Trade | stored with no `transactionDate` | `sanitizeAssetRequest` (`:252`, called at `:92`, `:132`) **sets it to today** |
| Trade | 500 with no `transactionType` | nothing checks it; the `switch` on it in `processTransaction` / `processTransactionV2` |
| `POST /api/v1/public/finances/calculate` (`FinanceRequest`) | 500 with no `calculationType` | `FinancesService.java:15` switches on it |
| `POST /api/v1/public/finances/interest-rate` (`StepUpSIPRequest`) | 500 with no `stepUpFrequency` | `StepUpSIPCalculator.java:52`, `:97` call `getValue()` on it |
| `POST /api/v1/me/charges/simulate` (`ChargeSimulationRequest`) | priced with no `price` | `price` is a primitive `double` (`ChargeSimulationRequest.java:67`): absent reads as 0, so turnover is 0 |
| Simulate | priced with no `stockCode` | `ChargeInstrumentResolver.java:40` returns no instrument for a blank code, so a fund's exit load is silently absent |

`validateAssetRequest` is the one point that V1, V2, every upload row and both redrives pass through (its javadoc; W-277). The upload already refuses a
blank broker or transaction type per row (`AssetRequestParser` `requiredConstantOf`), but not a blank stock code or date.

### Decisions (for approval with this plan)

- **C1 — where the trade checks go.** **C1a (recommended):** in `validateAssetRequest`, in the style of its asset-type check ("A trade must name
  its …"), so the JSON routes, the upload and redrive refuse alike. **C1b:** `@NotNull` on `AssetRequest`. That reaches the two JSON routes only, and
  upload rows and redrives would still pass unchecked.
- **C2 — a trade without a date.** **C2a (recommended):** refused; `sanitizeAssetRequest` and its two calls removed. The date picks the rate card,
  the financial year of a gain and the holding term, so filling in today silently gives a confident wrong number (`ChargeSimulationService`'s javadoc
  refuses it for the same reason). A client that relied on the default gets a 400. **C2b:** keep the default to today. Then only the stock code,
  broker and transaction type are new checks.
- **C3 — the preview.** **C3a (recommended):** `price` becomes a `Double`, required, and may be 0 (worded as the trade route's
  "Price is required; it may be 0 for a free allotment"). `stockCode` is required on a `BUY` or `SELL` event and stays optional on the events that
  name no scrip (`AMC_CYCLE`, `ACCOUNT_OPENING`; the comment at `ChargeInstrumentResolver.java:41`). **C3b:** `price` only; `stockCode` stays
  optional everywhere.
- **Finance (no choice offered):** `@NotNull` on `calculationType` and `stepUpFrequency`, as W-358d4 did: no service check exists, and
  `ControllerAdviser.handleInvalidBody` (`:106`) already answers "Field 'x' must not be null".
