## Plan for W-045l — the assessee family (D-039)

**What this item is for (one sentence):** replace the one `TaxpayerFacts` record, which gives every
assessee an individual's facts and a *set* of types, with a closed family of one record per assessee
type, each carrying only the facts that type has.

### What I read

- **Brief §8.** The family: `Assessee` (sealed) with `type()` and `residence()`, `Individual`
  (`dateOfBirth`, `residence`, `disability`, `dateOfDeath`) and `Huf(residence)`. Rules select
  assessee types through `HasPersonType` and `RegimeSpec.appliesTo`. Anything that differs by type is
  data, sourced before code reads it (R1).
- **`DR 23` A5** (the extension taxonomy the row cites for keeping `PersonType`).
- **Code:**
  - `TaxpayerFacts`, `EngineInputs`, `InputsFingerprint`;
  - `PackValidator.checkExactlyOneDefaultPerPersonType`;
  - `NodeHarness.plainTaxpayer()`;
  - the fixtures in `NodeRegistryTest`, `InputsFingerprintTest` and `EngineInputsTest`;
  - `TaxpayerFactsTest`;
  - every `git grep` hit for `TaxpayerFacts`, `ResidentialStatus`, `.taxpayer()` and `PersonType.`.

### A. The blocker: adding `HUF` fails I5 on every rule pack

`PackValidator.java:138-160` (I5, which is also I11) loops over **`PersonType.values()`** and refuses a
pack in which any person type has no default regime. No regime applies to an HUF: `NEW_TAX_REGIME`
and `FIRST_SCHEDULE_RATES` say `appliesTo: ["INDIVIDUAL"]`, as do the test packs and
`RegimeFixtures`. So the moment `HUF` exists, **every pack is refused**: the shipped 2026-27 pack and
every test pack.

Two ways out:

- **A1 (recommended): I5 counts only the person types the year's regimes serve.** The new wording:
  "exactly one default among the applicable regimes, for every person type that **any** applicable
  regime applies to".
  - A pack that serves no HUF passes.
  - A pack with a regime open to HUFs but no HUF default is still refused, which is the defect I5
    exists for.
  - This is a `PackValidator` change (not in the row's Produces) and an in-place edit to
    `02-TECH-SPEC.md` I5/I11, with a Changes entry.
  - It moves one duty to the future regime-selection code: handed a `Huf` for a year whose pack serves
    none, it must refuse, not pick a regime. Nothing selects a regime by person type yet, so I'll
    record that as a note on the item that builds selection. I won't build it here.
- **A2: make the packs serve HUFs.** Add `HUF` to `NEW_TAX_REGIME.appliesTo`, relocking the pack, and
  to every test pack and fixture.
  - The rulebook sources only s.202's **heading** ("individuals, Hindu undivided family and others",
    `01-rulebook.md:128`). Whether the s.202(1) rate table applies to an HUF, and for which year, is
    unverified.
  - Declaring it would let the engine compute an HUF on unsourced law. That breaks R1 and brief §8's
    "each row must be sourced before any code reads it".

### B. Choices (recommended first)

- **B1 — where `ResidentialStatus` lives.** It is nested in `TaxpayerFacts`, which is deleted.
  - **Recommended:** nest it in `Assessee` (`Assessee.ResidentialStatus`), since every assessee
    declares a residence. That also keeps the Produces list.
  - The alternative is its own `input/ResidentialStatus.java`.
- **B2 — the `EngineInputs` component name.**
  - **Recommended:** rename `taxpayer` to **`assessee`** (typed `Assessee`), because the standards
    say one word per concept.
  - `NodeHarness.plainTaxpayer()` keeps its name, which the row states.
  - The alternative is to keep `taxpayer`.
- **B3 — `type()` is derived, not stored.** `Individual.type()` returns `INDIVIDUAL` and `Huf.type()`
  returns `HUF`. A set of types is gone (brief §8's second defect). Nothing to choose here unless
  you object.
- **B4 — the checks move with the fields.** `Individual` keeps `TaxpayerFacts`' checks: a date of
  birth is required, residence is required, optional fields are non-null, and death is not before
  birth. `Huf` requires residence. `TaxpayerFacts`' javadoc (why it's a projection, D-024; why a date
  of birth rather than an age, D-025; why no PAN) moves to `Assessee`/`Individual`.
- **B5 — folding the fixtures.** `NodeRegistryTest.inputs()` becomes `NodeHarness.plainTaxpayer()`.
  `InputsFingerprintTest.baseline()` becomes `plainTaxpayer()` with its one family member added
  (its `family.members[0]` perturbations need it). `EngineInputsTest` builds from the harness where
  it only needs a valid assessee.

`./mvnw test -pl backend -Dtest=AssesseeTest,EngineInputsTest,InputsFingerprintTest,NodeHarnessTest,WealthLensModulithTest,PackValidatorTest`,
