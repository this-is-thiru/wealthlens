## Plan for W-255 — registration lets the caller choose its own role

**For:** a person registering always becomes a plain `USER`, so nobody can make themselves a `SUPER_USER` through the
public `POST /auth/register`. Today `AuthService.addUser` stores whatever role the body sends
(`auth/service/AuthService.java:66`, `userEntity.setRoles(request.getRole().name())`).

### Choices (recommended first)

**C1 — what registration does with a role.**
- **(a) Recommended: remove `role` from `RegistrationRequest`. Every registration stores `USER`.**
  - A body that still sends `role` is refused with 400 by the existing unknown-field rule (#7), so the refusal is loud.
  - The missing-role 500 (#5) goes away too.
- (b) Keep the field: accept a missing role or `USER`, and refuse anything else with 400. Not recommended: the request
  would keep a field whose only allowed value is the default.

**C2 — who may grant a role above `USER`.**
- **(a) Recommended: nobody through the API. The owner grants `SUPER_USER` with a `mongosh` update written in the runbook
  (§0.1.3, and the new §1.o).** There is one super user (you), and no client exists to call a grant endpoint.
- (b) A `SUPER_USER`-only `PUT /auth/user/{email}/role`. Not recommended now: it would be an endpoint with no caller. It can
  be placed as a backlog row if you want it.

**C3 — the unused role-upgrade code (#6).**
- **(a) Recommended: delete `upgradeRole`, `canUpgradeRole` with its hierarchy map, `RoleUpgradeRequest`, `POST /auth/test`
  and *Register Test.yml*.** The row asks this item to decide on `upgradeRole`. With C2a none of this code has a use, and
  `upgradeRole` would reopen the hole if anyone wired it up.
- (b) Delete only `upgradeRole`, and place a row for the rest.

**C4 — accounts that already chose a role (R15).**
- **(a) Recommended: runbook §1.o.**
  - **Before deploy:** a read-only count of `user_details` grouped by `roles`, one `db.aggregate` over all databases, and
    a list of any account whose role is not `USER`.
  - **Correction, only if an account other than yours holds a higher role:** back up `user_details` first, then
    `updateMany` those emails to `USER`. The update can be run again safely.
  - **After:** the same count again.
  - Its existing token keeps the old role until it expires (30 minutes at most); the next sign-in carries `USER`.
- (b) A startup runner that resets the roles. Not recommended: it would write to real data with no owner check.
