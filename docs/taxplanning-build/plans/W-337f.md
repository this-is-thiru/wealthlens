## Plan for W-337f — port `taxplanning` to JPA (size check + decisions)

> Planned in session 120 (2026-11-24), next after W-337e (D-950, merged to `master` as `55b06df0`). **Stop point
> (Stage 2 EXPLAIN):** nothing is built until the owner answers C1 – C7.

**What this item is for (one sentence, in my own words):** cut the `taxplanning` module's 20 MongoDB collections over
to PostgreSQL via Spring Data JPA on branch `w-337` — the largest single sub-item in the W-337 port — replacing its
one GridFS bucket with a plain bytes table, re-basing its one raw `MongoTemplate` lease-acquire and one raw
`MongoTemplate` bulk-delete onto JPA/JPQL, and (per this session's discussion with the owner) bringing all 20
entities to the same audit-column shape.

This is **the largest single sub-item in W-337** — 20 collections against `portfolio`'s 4 (W-337e) and
`corporate`+`brokercharges`'s combined 7 (split into W-337d1/d2). Against **§7** it is clearly mis-sized on a
collection-count basis. I looked for a split axis along the module's own sub-packages (`profile` / `workspace` +
`compute` / `documents` / `gazette` + `jobs` + `protection` — a natural grouping, since nothing in the module joins
across collections at the database level, D-929 (2)) and found the same blocker W-337e found for `portfolio`, only
wider: see finding #1. **This EXPLAIN proposes building it as one item (C1a)**, the same conclusion as W-337e and for
the same class of reason, now confirmed across a bigger surface.

### Core findings from probing the code before planning (`probe-before-plan.md`)

1. **Why a sub-package split does not work — the decisive finding.** `jobs/ProfileRemoval.remove()`
   (`ProfileRemoval.java:38` class-level `@Transactional`, method `:54-68`) writes/deletes across **all seven**
   sub-package groups in one local transaction: `profile` (`profiles.delete`, plus the raw `mongoTemplate.remove(...)`
   loop over `FamilyMember`/`Employer`/`Landlord`/`Lender`/`BankAccount`, `:65-66`), `workspace`
   (`TaxYearWorkspace`/`RegimeElectionHistory`, `:42-43`, plus everything `draftRemoval.remove(draft)` touches),
   `compute` (`computations.findByDraftId`, `:61`), `documents` (`documents.findByProfileId`,
   `documentRemoval.removeUnder`, `:63-64`), `protection` (`accessRecords.deleteBySubjectIdIn`, `:62`). This is the
   exact shape that blocked `portfolio`'s split (`addTransactionV2` writing 4 collections in one transaction,
   W-337e finding #1) — here it spans every group there is, not just some of them. `jobs/DraftRemoval.remove()`
   (`DraftRemoval.java:24-30`, independently `@Transactional`) separately crosses `workspace`+`compute` on its own
   (`computations.deleteByDraftId`, `revisions.deleteByDraftId`, `workspaces.save`, `drafts.delete`). Confirmed from
   the test side too: of the 25 moving integration tests, only 7 stay within one sub-package
   (`DocumentStoreIntegrationTest`, `DocumentSwitchOffIntegrationTest`, `GazetteWatchEndpointIntegrationTest`,
   `HeldAssetsIntegrationTest`, `PurposeLapseIntegrationTest`, `TaxJobEndpointIntegrationTest`,
   `PrivacyNoticeIntegrationTest`); the rest, including `TaxErasureIntegrationTest`/`TaxJobsIntegrationTest`, each
   span 5 – 7 groups.
2. **`ProfileRemoval`'s raw `MongoTemplate.remove(...)` loop (`ProfileRemoval.java:65-66`) is in a service, not a
   repository** — the earlier repository-only grep (`*Repository.java`) missed it. It removes rows from 7 entity
   classes by `profile_id`; under JPA this becomes 7 individual `deleteByProfileId` calls (or equivalent) inside the
   same transaction, not a repository-level change.
3. **`jobs/TaxJobRunner`'s lease pattern** (`TaxJobRunner.java:46-54`) does
   `mongoTemplate.findAndModify(query(where("job").is(name).and("expires_at").lt(now)), update,
   upsert(true).returnNew(true), JobLease.class)`, catching `DuplicateKeyException` as "another run holds it" — i.e.
   "acquire if no lease exists for this job, or the existing one's `expires_at` has passed." `run()`'s `finally`
   (`:38-41`) unconditionally deletes the lease on completion, success or thrown exception. `holds()` (`:56-58`) is a
   liveness poll: the lease still exists for this `job`+`holder` with `expires_at > now`. No TTL index backs it in
   Mongo either — an abandoned lease (crash mid-run) is reclaimed lazily by the next acquire's `expires_at < now`
   check, never swept. Same shape, same precedent, as `auth`/`refresh_tokens`'s TTL-free expiry (D-937 C3a).
4. **Both nullable nested-object fields are the exact `RealisedProfitsConverter`-null-vs-empty bug class (W-337e,
   D-949/D-950) — flagging up front so it is not found again the same way.**
   - `DraftRevision.importedFrom: WorkbookImport` (`DraftRevision.java:55`) — `RevisionResponse.java:12`:
     `Optional.ofNullable(stored.getImportedFrom())`, documented at `:6` as "if one." A converter defaulting
     null→empty would make every revision look like it came from a workbook import.
   - `FilingDraft.staleness: DraftStaleness` (`FilingDraft.java:67`) — three call sites treat `null` as meaningful:
     `DraftService.java:94-95` (`.filter(draft -> draft.getStaleness() != null)` then explicitly `setStaleness(null)`
     to *clear* it) and `StalenessSweep.java:85` (`draft.getStaleness() != null && draft.getStaleness().current()...`).
   Both converters' `empty()` must return `null`, per the fix already in `RealisedProfitsConverter.java:25-31`.
5. **GridFS specifics for the `tax_document_bytes` replacement.** Bucket `tax_document_bytes`
   (`DocumentBytesConfig.java:14`), one file per document keyed by `filename = documentId`
   (`DocumentBytes.java:47,54,67`), content already `FieldCipher`-encrypted bytes (no further column-level
   encryption needed). Only `filename` (equality/`in`) and `uploadDate` (range, for the retention sweep's
   `storedBefore`) are ever queried on it — nothing else GridFS-native is used. **Bonus finding:**
   `DocumentRemoval.removeAll()` (`DocumentRemoval.java:33-41`) defers the bytes delete to
   `TransactionSynchronization.afterCommit()` specifically *because* "GridFS takes no part in [the transaction]"
   (D-762 C4a) — once bytes are an ordinary table row, this after-commit split is no longer needed and can be
   dropped, a genuine simplification this port gets for free.
6. **The generic JSON-converter machinery (`JsonColumnConverter`, `StringListConverter`, …) currently lives in
   `portfolio.entity`** (W-337e, D-949), not `shared`, even though it is generic and has no portfolio-specific logic.
   `taxplanning`'s `allowedDependencies` already include `portfolio` (CLAUDE.md's module table), so reusing it
   directly is not a build-breaking issue — see C8.
7. **Flyway version numbers are a single global sequence** (`V1` auth/insurance … `V9` portfolio,
   `backend/src/main/resources/db/migration/*/V*.sql`), so `taxplanning`'s new file is `V10`.
8. **`compute/HeldAssetsViewService` imports `portfolio.entity.AssetEntity`/`portfolio.repository.PortfolioRepository`
   directly** (the one cross-module read W-337e's own sizing flagged) — now a non-issue, since `portfolio` is
   already on Postgres/JPA (merged to `master`, D-950); an ordinary Spring Data call, no join-across-two-stores
   problem.

### Decisions (for approval with this plan)

- **C1 — split or one item.** **C1a (recommended):** build W-337f as **one** item covering all 20 collections, the
  GridFS replacement, both raw-`MongoTemplate` usages, and all 20 `@Transactional` classes, in one commit — justified
  by finding #1 (no split leaves the module compiling and correct at each step; `ProfileRemoval` alone touches every
  group). **C1b:** split anyway along some sub-package axis; I found none that `ProfileRemoval`/`DraftRemoval` don't
  cross, so the erasure path — unavoidably the largest, most cross-cutting piece — would land in every half
  regardless. Not recommended.
- **C2 — the 5 plain `List<String>`/`Map<String,String>` fields** (`DraftComputation.lawAndExec`,
  `DraftComputation.ruleChecksums`, `StoredConfirmation.rejectedFields`, `GazetteLead.matchedTerms`,
  `GazetteLead.possiblyAffected`). **C2a (recommended):** reuse the existing `StringListConverter`
  (`portfolio.entity.StringListConverter`, proven in W-337e) for the four `List<String>` fields; add one new
  `StringMapConverter` (same `JsonColumnConverter` base, `Map<String,String>` — `StringDoubleMapConverter` is typed to
  `Double` values, so `ruleChecksums` needs its own) for `ruleChecksums`. **C2b:** write `taxplanning`-local
  duplicates of these converters instead of reusing — no reason found to duplicate proven code.
- **C3 — `RegimeElectionHistory.events: List<ElectionEvent>`** (a list of nested records, not a list of entities or
  scalars). **C3a (recommended):** one new `AttributeConverter<List<ElectionEvent>, String>`
  (`ElectionEventListConverter`, `JsonColumnConverter` base, Jackson), `TEXT` column — same pattern as
  `CorporateActionListConverter` (W-337e, D-949 C2a). **C3b:** normalize into a child table — nothing ever queries
  inside the list (same reasoning W-337e used for corporate-action copies); not recommended.
- **C4 — the 2 nullable nested-object fields** (`DraftRevision.importedFrom: WorkbookImport`,
  `FilingDraft.staleness: DraftStaleness`). **C4a (recommended):** two new converters
  (`WorkbookImportConverter`, `DraftStalenessConverter`), `JsonColumnConverter` base, **each overriding `empty()` to
  return `null`**, not a default instance — per finding #4, this is the exact bug class `RealisedProfitsConverter`
  hit and fixed in W-337e (D-949/D-950); getting it right the first time here avoids rediscovering it the same way.
  **C4b:** default to an empty instance like the list/map converters — would reintroduce the exact bug just fixed.
  Not recommended.
- **C5 — `ProfileRemoval`'s raw `mongoTemplate.remove(...)` loop over 7 entity classes by `profile_id`**
  (`ProfileRemoval.java:65-66`). **C5a (recommended):** 7 individual `deleteByProfileId` derived-query calls (one per
  repository: `FamilyMemberRepository`, `EmployerRepository`, `LandlordRepository`, `LenderRepository`,
  `BankAccountRepository`, plus whichever two more the loop's entity list names at read time), called in sequence
  inside the same `@Transactional("postgresTransactionManager")` method — same shape, same transaction boundary,
  just no more raw template calls. **C5b:** one bulk JPQL/native statement per table — more code for no behaviour
  difference; not recommended.
- **C6 — `jobs/TaxJobRunner`'s lease-acquire** (`TaxJobRunner.java:46-54`). **C6a (recommended):** one atomic
  statement — an `INSERT ... ON CONFLICT (<job's key>) DO UPDATE ... WHERE <existing>.expires_at < EXCLUDED.expires_at`
  (native query via the repository), reclaiming an expired lease lazily on the next acquire attempt exactly as today,
  still no TTL index or scheduler (matches the `refresh_tokens` precedent, D-937 C3a). **C6b:**
  `SELECT ... FOR UPDATE SKIP LOCKED` — changes the semantics from "reclaim an expired lease" to "skip a held one",
  which is a different guarantee than today's; not recommended.
- **C7 — audit metadata on the 5 entities that currently have none** (`GazetteCursor`, `GazetteLead`, `AccessRecord`,
  `JobLease`, `JobFailure`). **C7a (recommended, per this session's discussion):** add `AuditableEntity`/`AuditColumns`
  to all 5, so every one of the 20 `taxplanning` entities carries `created_by`/`updated_by`/`created_at`/`updated_at`
  consistently — the fields stay nullable for a system-triggered write with no caller context (a cron job, a lease
  acquire), exactly like every other entity's audit columns already behave. **C7b:** leave the 5 as they are — not
  recommended; the owner's stated preference this session was consistency across all 20.
- **C8 — where the generic JSON-converter base lives** (finding #6: `JsonColumnConverter`/`StringListConverter`
  currently sit in `portfolio.entity`, W-337e). **C8a (recommended):** reuse them directly from `taxplanning`
  (`allowedDependencies` already permits `taxplanning → portfolio`) — no code moves, no touch to already-merged
  `portfolio` files. **C8b:** relocate the generic ones (`JsonColumnConverter`, `StringListConverter`,
  `StringDoubleMapConverter`) into `shared/util` first, then point both `portfolio` and `taxplanning` at the
  relocated classes — cleaner long-term (a `shared`-level utility, not a one-module-reaches-into-another dependency),
  but it is a drive-by refactor of already-closed, already-merged W-337e code that this item does not need in order
  to build; **not recommended** for this item specifically — raised as a named proposal instead, not done
  unilaterally (CLAUDE.md §2).

**Not a decision in this item — explicitly parked:** primary-key type. Every already-ported module (`auth`,
`insurance`, `shared`/privacy, `corporate`, `brokercharges`, `portfolio`) uses caller-assigned `VARCHAR(255)` string
ids (W-337a's convention). The owner raised, then explicitly deferred, whether this should become a numeric `Long` —
discussed this session, not decided; `taxplanning` keeps the established string-id convention for now, matching
every other module, with the question left open for the owner to revisit separately later.

4. **C5a's exact list of 7 entity classes `ProfileRemoval`'s loop names** is read from the probe's summary, not
