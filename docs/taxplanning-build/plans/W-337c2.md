### Core findings from probing the code before planning (`probe-before-plan.md`)

1. **`PrivacyConsents.java:62-68` catches `DuplicateKeyException`**, which is Spring Data Mongo's subclass; PostgreSQL + Hibernate throws `DataIntegrityViolationException` on `privacy_consents_email_idx` violation. Widening the catch to `DataIntegrityViolationException` preserves the concurrent-first-sign-in idempotence.
2. **`BreachNotice.affected` (`BreachNotice.java:49-51`)** maps to `@ElementCollection(fetch = FetchType.EAGER)` on `privacy_breach_notice_affected` (`V3__privacy.sql:94-98`) with `@Convert(converter = SearchableColumn.class)`. In `PrivacyRecordErasure.erase(String email)`, pulling an erased person's email from every notice loads notices containing that email (`BreachNoticeRepository`) and removes the email via `removeIf` + save, letting `SearchableColumn` handle the encryption automatically.
3. **Transaction managers (`GrievanceService.java:21`, `BreachNoticeService.java:25`, `AccountErasureService.java:22`, `LogRetention.java:33`, `PrivacyRecordErasure.java:28`):**
   - `GrievanceService`, `BreachNoticeService`, `PrivacyRecordErasure`, and `LogRetention` are 100% PostgreSQL once ported and switch to `@Transactional("postgresTransactionManager")`.
   - `AccountErasureService` writes `AccountErasureRequest` (Postgres) and invokes `PersonalDataHolder`s across both Postgres (`LoginErasure`, `InsuranceRecordErasure`, `PrivacyRecordErasure`) and Mongo (remaining modules until W-337f). Switching `AccountErasureService` to `@Transactional("postgresTransactionManager")` keeps all Postgres erasure writes atomic in one transaction while Mongo holders run independently until W-337f (D-937 C2a).
4. **`AccountErasureIntegrationTest.java:190-245`:** once the 6 `privacy_*` entities move to `@Entity`, `personTables()` automatically discovers `privacy_consents`, `privacy_breach_intimations`, `privacy_processing_log`, `privacy_grievances` (and excludes `KEPT = "privacy_erasure_requests"`). `aRowInEveryCollectionFor` seeds them via repositories or `JdbcTemplate` (note `privacy_consents.email` is unique, handled by unique per-person email).
5. **No Flyway changes needed:** `V3__privacy.sql` already matches all 6 entities column-for-column (`created_by`/`updated_by`/`created_at`/`updated_at` on the 5 auditable tables, omitted on `privacy_processing_log`).

### Decisions (for approval with this plan)

- **C1 — `AccountErasureService` transaction manager during W-337c2 – W-337e.** **C1a (recommended, carries D-937 C2a):** switch `AccountErasureService` to `@Transactional("postgresTransactionManager")` so `AccountErasureRequest` and all Postgres holders share one transaction, while unported Mongo holders run their own writes until W-337f ends the split. **C1b:** keep `AccountErasureService` on Mongo's `@Primary` transaction manager until W-337f — would leave `AccountErasureRequest` outside any Postgres transaction.
- **C2 — `BreachNotice.affected` erasure in `PrivacyRecordErasure`.** **C2a (recommended):** query affected `BreachNotice` rows via `BreachNoticeRepository` (`@Query("SELECT n FROM BreachNotice n WHERE :email MEMBER OF n.affected")`) and remove the email from `affected` in JPA — zero direct `FieldCipher` / native SQL, persistence context stays consistent. **C2b:** native `DELETE FROM privacy_breach_notice_affected WHERE affected = :encryptedEmail` using `FieldCipher.encryptSearchable(email)`.
