## Plan for W-358d3 — password hashes upgraded at sign-in

> Planned in session 114 (2026-11-21), the third part of W-358d (D-872). Probe run before this plan (a temporary unit test, removed).
> **Stop point: nothing is built until the owner answers C1 – C3.** This item **writes stored data** (`user_details.password`, one row at
> each sign-in), so it adds a runbook entry.

**What this item is for (one sentence, in my own words):** every stored password moves to a stronger, labelled hash the next time its
owner signs in, with nobody asked to reset anything, and a later change of algorithm is a setting rather than a migration.

### What the code does today

| | Today | Where |
|---|---|---|
| Encoder | one `new BCryptPasswordEncoder()` bean (cost 10) | `shared/config/InvestmentTrackerConfig:13-15` |
| Stored | `$2a$10$…` in `user_details.password`, no `{id}` label | `UserDetail:33`; probe |
| Sign-in | `DaoAuthenticationProvider` with that encoder; no `UserDetailsPasswordService`, so nothing is ever rehashed | `AuthConfig:79-83`, `UserDetailsServiceImpl` |
| Who encodes | registration and a password change (`AuthService`); the owner's own resets were `htpasswd -B` (`$2y$`, W-334) | |

### Probe (this machine, five encodes each, warm)

| Encoder | Per sign-in | Stored as |
|---|---|---|
| BCrypt cost 10 (today) | 73 ms | `$2a$10$…` |
| BCrypt cost 12 | 294 ms | `$2a$12$…` |
| Argon2id, Spring's `defaultsForSpringSecurity_v5_8` | 20 ms (and 16 MiB) | `$argon2id$v=19$m=16384,t=2,p=1$…` |

- Spring's `PasswordEncoderFactories.createDelegatingPasswordEncoder()` encodes `{bcrypt}` at cost 10 — "upgrading" to it only adds the
  label — and its map also accepts `{noop}`, `{MD5}`, `{SHA-1}` …; an unlabelled hash makes it throw until a default for matching is set.
- With BCrypt as the default for matching: an unlabelled hash matches, `upgradeEncoding` says **true** (so a sign-in rehashes it); a
  `{bcrypt}` cost-10 hash says false. A `$2y$` (`htpasswd`) hash matches.
- **A plain `BCryptPasswordEncoder` cannot read a labelled hash** (`{bcrypt}$2a$…` → false): after this deploy, going back to `m1.5`
  refuses every account that has signed in since, until its password is reset.

### Decisions (for approval with this plan)

- **C1 — the algorithm.** **C1a (recommended):** Argon2id with Spring's own defaults (memory-hard; 20 ms here; BouncyCastle, which it
  needs, is on the classpath since W-360). **C1b:** BCrypt cost 12 (294 ms a sign-in, so slower for people and no harder for a guesser's
  memory). The parameters are Spring's published defaults, not a standard I read.
- **C2 — which labels a stored hash may carry.** **C2a (recommended):** only `{argon2}` (written) and BCrypt (matched: labelled or not,
  for every hash stored today), built by hand rather than from the factory, so a `{noop}` (plain text) or `{MD5}` value written into the
  database by any means can never sign anyone in. **C2b:** Spring's full factory map.
- **C3 — the way back.** Going back to `m1.5` breaks upgraded accounts' sign-in. **C3a (recommended):** no backup of hashes (a copy of
  every password hash is itself a risk); the runbook's way back is: deploy `m1.5`, then reset each upgraded account's password with a
  BCrypt hash (`htpasswd -bnBC 10 "" <password>`, as W-334 did) — staging holds 14 accounts, prod 12. **C3b:** before the first start,
  export `_id` and `password` of `user_details` (IntelliJ, or the MongoDB tools reinstalled), and restore the upgraded rows from it.

sign-in limit (W-358d2).
