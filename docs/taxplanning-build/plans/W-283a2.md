## Plan for W-283a2 — rebuild `assets` from `transactions`

**What this item is for (one sentence, in my own words):** a `SUPER_USER` can recompute a user's lots as the
design lays it out (`docs/trade-ledger/assets-rebuild.md`, D-577), seeing the difference from what is stored before
anything is written.

**Findings (read this session, 2026-11-12):**

1. **The design missed one thing: a sale's flow changes the lot too.**
   - A V1 sale records its share of the lot's buy charges on the lot: `allocated_buy_charges` and
     `allocated_buy_misc_charges`, through `LotChargeAllocator` (`PortfolioService:549 – 550`).
   - A V2 sale does not; its share is computed from the original quantity when the outcome row is built
     (`allocateSaleV2`, `:587 – 628`).
   - So the replay needs each **sale's** flow as well as each buy's. Since W-283a1 a sale records it (D-580). For an
     older sale, its `trade_outcomes` rows tell: a V2 recorder row carries `sell_charge_breakup` and a V1 row does not
     (`ProfitAndLossV2Backfill:31`).
2. **Rebuilt lots need ids.** `trade_outcomes.source_buy_lot_id` names the lot a sale drew from. A rebuilt lot given a
   fresh id would cut that link for every lot still held.
3. **Size.** The replay touches every input the design lists, the corporate module's repositories, three flows' lot
   rules, and an id policy. The write and its runbook entry are a second, riskier half.
4. **Reusable parts:**
   - V1's same-day merge, as a computation (`buyStock`, `:372 – 420`).
   - The demerger's per-lot step, `CorporateActionService.processDemergerForEachAssetEntry` (`:449`), which
     `portfolio` may call (`allowedDependencies` includes `corporate`).
   - `SplitRatio`.
   - `LotChargeAllocator` for a V1 sale.
   - The report-then-replace shape of W-283.

**Choices for the owner:**

- **C1 — split the item.**
  - **C1a (recommended):** **W-283a2** is the replay and a **read-only** dry run,
    `POST /portfolio/user/{email}/assets/rebuild` (`SUPER_USER`). It reports stored against rebuilt lots and writes
    nothing, so it cannot harm data. **W-283a3** (placed) adds the write: the id policy (C3), the replace, and the
    runbook entry.
  - C1b: both in this item.
- **C2 — an older sale's flow.**
  - **C2a (recommended):** its `trade_outcomes` rows. A row with `sell_charge_breakup` means V2; rows without it
    mean V1. With no rows the sale is listed, and taken as V2, which leaves the lot's charges whole.
  - C2b: always V1.
- **C3 — lot ids** (decided now, built in W-283a3).
  - **C3a (recommended):** a rebuilt lot whose `buy_transaction_ids` equal a stored lot's keeps that lot's id, so
    `trade_outcomes` links hold. Any other lot gets a new id and is listed.
  - C3b: every lot gets a new id.

**Files I will create (C1a):**
- `portfolio/service/AssetsRebuild.java` — reads the inputs and runs the replay.
- `portfolio/service/LotLedger.java` — the in-memory replay of buys, sales, splits and demergers, by date with
  corporate actions first on a date.
- `portfolio/dto/AssetsRebuildReport.java`.
- `portfolio/controller/AssetsRebuildController.java`.
- Tests:
  - `LotLedgerTest` — the design's worked example and its tie-break variant as the golden test, by hand (14 held,
    then 20 held); a V1 merge (10 @ 100 + 10 @ 120 = 20 @ 110); a V1 sale's allocated charge (₹30 lot, 1 of 3
    sold → ₹10); a V2 sale leaving charges whole; a pending split not applied; an oversale refused.
  - `AssetsRebuildIntegrationTest` — trades made live through V1, V2, a bonus and a performed split. The dry run
    reports rebuilt lots equal to stored, field for field, and nothing is written. A USER gets 403.

**Files I will modify:**
- `docs/trade-ledger/assets-rebuild.md` — the sale flow (finding 1), C2 and C3.
- `03-WORK-ITEMS.md` — W-283a3.
- `api-collection` — the request.

**Numbers I will use:** none from law. Every expected figure is by hand, shown in the tests and in the design's
example.

**Design sections I read:** `assets-rebuild.md`; D-577, D-580; D-575 (shape).

**What I am NOT doing:**
- Writing `assets` (W-283a3).
- Fixing W-289 (the rebuild already orders correctly).
- Rebuilding `trade_outcomes` or P&L.

**How I will verify:**
- `LotLedgerTest` first, each case red before its rule exists.
- The integration "rebuilt equals stored" case.
- Probe: swap the same-date order to trade first; the tie-break test must fail.
- The unit and integration tiers, run from cleared report directories.

**Post-deployment actions (R15):** none. The dry run writes nothing; W-283a3 brings the runbook entry.

**Five roles:**
- **Architect:** `portfolio` reads `corporate`'s actions and calls its demerger step, both allowed. The replay lives
  in one pure class, so live and rebuild can be compared.
- **Product manager:** nothing changes for users. The owner can now see, per user, whether stored lots have drifted
  (and W-289's users) before any correction exists.
- **Senior engineer:** one ledger class with one job, no writes, failures named.
- **Automation tester:** golden values by hand, rebuilt equal to live-built, the probe, and both tiers.
- **Manual tester:** on staging, a dry run for one user with a split history. Expect `differs: false` per stock, or
  each difference explained by the report's lists.

**Risks or ambiguities:**
- Lots stored before fields existed (allocated charges, segment) may report differences that are only history. The
  report names each field, so they can be read.
- The live V1 sale path has a whole-lot tolerance (`takesWholeLot`, W-274), which the ledger reuses.
