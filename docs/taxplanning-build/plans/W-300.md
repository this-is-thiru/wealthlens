## Plan for W-300 — ten simultaneous same-day V1 buys sometimes answer one 500 (rev 2)

**Rev 2 (2026-11-12): the cause is found, so the item is unblocked. Rev 1 is kept below as the record of how it was
found.**

**The cause** comes from the failed job's log, read with `gh run view 43249161713 --job 131289915842 --log` once you
had logged in.
- The 500 was `org.springframework.dao.IncorrectResultSizeDataAccessException: Query { email: audit-owner@example.com,
  financialYear: 2025-2026 } returned non unique result`, thrown at `ProfitAndLossService.handleNormalBuyCase:338`
  (`findByEmailAndFinancialYear`) from `PortfolioService.buyStock:416`. Two `profit_and_loss` documents existed for
  one user and year.
- The unique index `pnl_user_year_idx` (`ProfitAndLossEntity:53`) forbids that. It was missing because
  **`AnalyticsIntegrationTest.setUp` drops `transactions`, `assets`, `trade_outcomes` and `profit_and_loss` before
  every test** (`:58 – 68`). A drop removes a collection's indexes, and they are created only at startup
  (`PortfolioIndexInitializer`, `@PostConstruct`), because auto index creation is not configured.
- All integration classes share one container, and in every CI run Analytics runs just before
  `PortfolioGapAuditIntegrationTest`. It did so in 43249161713 (failed) and in 43255624955 and 43259440268 (passed),
  so the class runs with no unique indexes on those four collections. The ten first-of-year buys then create two P&L
  documents only when they interleave the wrong way. That is the intermittent part.
- **This failure is test-only.** Nothing in `src/main` drops a collection: I searched for `drop`, `dropCollection`
  and `dropIndex`, and the only hits are these four test lines. So production keeps `pnl_user_year_idx`, and two
  documents for one year cannot be stored there.
- **Not verified:** whether, with the index in place, two simultaneous first-of-year buys collide as a write conflict
  (labelled `TransientTransactionError`, so `TradeCollisionRetry` re-runs it) or as a duplicate key (E11000, not
  labelled, so a 500). After C1a the ten-buy test runs with the index. If it ever fails again, that log names which.
  I am not adding to this item for a case nobody has seen.
- `AbstractIntegrationTest.cleanDatabase` (`:120 – 136`) already uses `deleteMany` on purpose, "rather than drop".
  Its note says a drop forces "a rebuild on the next write", which is not true here: nothing rebuilds the index.

**Choices for the owner (rev 2):**

  - **C1a (recommended):** Analytics clears its four collections with `deleteMany`, as the base class does. Its data
    stays cleared before each of its tests.
  - C1b: delete Analytics' `setUp` and rely on the base class's `@AfterEach` clean. That depends on every class
    before it having cleaned up.
- **C2 — a guard, so no test or code drops a collection again.**
  - **C2a (recommended):** a test in `ArchitectureTest` that imports main **and** test classes, in the way
    `simple_class_names_are_unique` (`:472`) imports its own. It fails on any call to `MongoCollection.drop` or

    today on `AnalyticsIntegrationTest.clearCollections`.
  - C2b: no guard.
- **C3 — the base class's note.**
  - **C3a (recommended):** correct "forcing a rebuild on the next write" to say that a drop removes the indexes and

## Plan for W-300 — ten simultaneous same-day V1 buys sometimes answer one 500 — rev 1 (blocked)

**What this item is for (one sentence, in my own words):** a V1 buy that collides with others at the same moment
should be recorded after a retry, or else answered 409. One of ten answered 500 once in CI, so some failure escapes
the collision retry (D-602).

**Findings (read and run this session, 2026-11-12):**

1. **The failure.** GitHub Actions run 43249161713 (`e934550c`, job 131289915842) failed
   `PortfolioGapAuditIntegrationTest.addTransaction_whenTenSameDayBuysArriveTogether_holdsEveryUnit` (`:435`) with
   `[200 × 9, 500]`. The same test passed in runs on `3f131843`, `c168e600`, `b20fdf90` and `664529ca`.
2. **Not reproduced locally.** I ran that method alone 10 times with `nice -n 19`: 10 passes, about 8 s each. The
   passing runs log no exception, because a retry that succeeds leaves no trace.
3. **What a 500 can be here.**
   - `TradeCollisionRetry` re-runs a trade only when Mongo labels the failure `TransientTransactionError`
     (`isCollision`). A collision that exhausts the retries answers 409 (`TradeCollisionException`).
   - Every other failure reaches `ControllerAdviser.handleGenericException` (`:100 – 104`), which answers 500 and
     **logs the exception with its stack trace** (`:102`, `:137`). So the cause is in that job's log.
   - Candidates, none confirmed:
     - `OptimisticLockingFailureException` on the year's P&L document (`ProfitAndLossEntity:81`, `@Version`). This
       is not a labelled Mongo error.
     - A duplicate key on `pnl_user_year_idx` (`:53`), when two trades each create the year's first document.
     - A commit that fails with `UnknownTransactionCommitResult`, a label the retry does not test for.
4. **I cannot read the job log.** The log needs a login: `GET /actions/jobs/131289915842/logs` returned 403
   without one, and `gh` is not logged in.

**This is BLOCKED on the cause (§1, "Unknown is an answer").** I will not write a fix for a guessed exception.

**Choices for the owner:**

- **C1 — getting the cause.**
  - **C1a (recommended):** you open run 43249161713, job "build", step "Verify formatting, run tests, generate
    consolidated report". Search it for `ERROR` near `PortfolioGapAudit` and paste the exception and its first
    `Caused by` lines. Alternatively, run `! gh auth login` and I fetch the log myself.
  - C1b: I make the test report what it got, then wait for the next failure in CI. On failure, the assertion would
    print each response body (the 500's message is the exception's). That changes only the test's failure message,
    and the fix waits for a CI failure that may take many runs.
- **C2 — after the cause is known.** A rev 2 of this plan: a red test that forces that exception (a fault injected
  at the failing call, since a timing race cannot be relied on), the fix, and a probe. It comes back to you for
  approval.

**Files I will modify:** none until C1 is answered. Under C1b: `PortfolioGapAuditIntegrationTest`, the assertion
message only.
