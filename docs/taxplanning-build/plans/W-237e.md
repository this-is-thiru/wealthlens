## Plan for W-237e — logs of processing, kept a year, for every user

**For:** WealthLens can see who reached whose personal data, when, by what route and with what result, for every user and
every module; it keeps those logs and the privacy records a year from the processing, then erases them (Rules r.6(1)(c),
(e), r.8(3); D-470 C2a).

### Choices (recommended first)

**C1 — what the log records.** (a) **One record per request that reaches a person's data, app-wide:** `principal` (from
the token; the tried email for a login), `subject_email` (the path's `{email}`, else the principal), `method`, `route`
(the matched pattern, `/portfolio/user/{email}/transaction` — never the raw path, a query value or a body), `status`,
`remote_address` (r.8(3)'s "traffic data"), `recorded_at` (UTC, `Clock`). Collection `privacy_processing_log`, class
`ProcessingRecord` in `shared/privacy`, written by a filter after `AuthFilter`. Login attempts, failed ones included,
are recorded — they are what detection of unauthorised access (r.6(1)(c)) looks for. Public paths with no person
(`/helper/**`, `/template/**`, the notice) are not. `tax_access_log` stays: it records record-level reads, finer than a
request. (b) As (a) without `remote_address` — less personal data held, but an access from an unknown place cannot be seen.
(c) Record-level reads in every module, as `tax_access_log` does — every service touched; large.

**C2 — how the year ends a log.** (a) **A daily job `log-retention`** (`app.tax.jobs.log-retention-cron`) erases
`privacy_processing_log` and `tax_access_log` rows older than **`app.privacy.log-retention: P1Y`** (its own key, citing
r.6(1)(e) and r.8(3), because the erasure hold counts from a request and this from each processing). Calendar year, `Clock`,
a delete by date — a second run changes nothing. (b) A MongoDB TTL index: no job, but a fixed second count (365 or 366
days?), a changed period needs the index dropped and rebuilt, and the boundary cannot be tested with a clock.

**C3 — account erasure and the log.** (a) **As W-237d does for `tax_access_log`: the person's own rows (`principal`) go
with the account; rows others wrote about them (`subject_email`, e.g. the owner reading a receipt during the hold) stay
until their own year** — r.8(3) Case 1. The person cannot log in while held, so every row of theirs is a year old when the
account goes. The guard keeps working unchanged (it keys on `principal`). (b) Erase by both fields at account erasure:
simpler, but a row younger than a year goes early.

**C4 — the privacy records (the row's "`privacy_grievances` among the data").** (a) **Each is erased a year after its
last processing, by the same job and key:** a grievance a year after `answered_at` (an unanswered one is kept);
an intimation a year after the latest of `posted_at`, `read_at`, `emailed_at`; an erasure request a year after
`erased_at`. The breach notice itself stays (the owner's record to the Board, as W-237d C7a). (b) Keep them until the
account is erased, as today — an erased account's request is then kept forever.

**C5 — console logs.** (a) **No change; the runbook says the processing log is the record, and console logs live only
for the container** — they are diagnostics, not the log r.6 asks for. Your word needed: if you read r.8(3)'s "other logs of
the processing" to take in console logs too, choose (b). (b) Ship console logs to CloudWatch (Docker `awslogs` driver, a
365-day group) — your AWS action and cost, placed as its own row.

### Out of scope
Reviewing the logs (r.6(1)(c)'s "monitoring and review" is the owner's duty: a runbook step, recurring, with a read-only
query for failed logins and access by one principal to many subjects); backups holding erased logs (W-237f);
purpose-lapse erasure (W-249).

### Post-deployment (R15)
Nothing stored changes on deploy; the job runs on its own. Runbook: a recurring monthly review (§1.v's weekly grievance
queue is the pattern) with the read-only queries; the first `log-retention` run after a year confirmed by a count;
WL-A-2 republished.

### Build record

**Main:** `shared/privacy/` — `ProcessingRecord` (`privacy_processing_log`: `principal`, `subject_email`, `method`, `route`,
`status`, `remote_address`, `recorded_at`), `ProcessingLogFilter` (in the security chain ahead of `AuthFilter`; writes after
the response; `nameLoginAttempt` for the login, which no token names yet), `LogRetention` (C2a, C4a: processing records by
`recorded_at`, grievances by `answered_at`, intimations by the latest of their three times, erasure requests by
`erased_at`, each `≤` the cutoff), `PrivacyIndexInitializer` (`recorded_at`, `principal`); `PrivacySettings` gains
`log-retention` (refused when absent or not positive; the two period checks share one method to stay within Checkstyle's
complexity 12). `PrivacyRecordErasure` erases the person's own rows by `principal` (C3a). `AuthConfig` registers the
filter; `AuthController.login` names the attempt. `taxplanning/jobs/LogErasure` (`log-retention`, daily 04:45) runs
`LogRetention` and erases `tax_access_log` by `read_at`. Four yamls: the key; three: the cron.

**Tests:** `ProcessingLogIntegrationTest` 10 (times by hand: processed 2027-06-10T08:00Z → kept by a run at
2028-06-10T07:59:59Z, erased at 08:00:00Z; Anu's own read: one row with the route pattern, 200, 127.0.0.1, the time; a
PAN-shaped query value never stored; the owner reading Bala's: principal owner, subject Bala; wrong password: a row, 401
(`ControllerAdviser` maps `BadCredentialsException` to 401); right password: a row, 200; no token: 401 and no row; every
kind kept a second before the year, erased at it except the unanswered grievance and the intimation emailed a day later;
a second run changes nothing; Anu's account erasure takes her rows and keeps the owner's about her). `PrivacySettingsTest`
11 → 13. `AccountErasureIntegrationTest`'s "hold not passed" test compared each collection to exactly one row; the request
itself now adds a log row, so it compares the counts before and after the run (stronger: any erasure fails it).

**Probes, each run alone and restored by `cmp`:** (1) the insert removed → 6 tests fail; (2) `lte` → `lt` on
`recorded_at` → the boundary test fails; (3) erasing by `subject_email` too → the C3a test fails; (4) the login naming
removed → both login tests fail; (5) unanswered grievances erased too → three retention tests fail.

**Departures:** (1) Probe 1 removes the insert, not the filter's registration: the filter is also a `@Component`, so
Spring Boot registers it as a servlet filter too (as `AuthFilter` is) and dropping the chain registration would still
record most requests. (2) The `-Pbenchmark` budgets were not run: `EngineBenchmarkTest` times the tax engine in-process,
with no HTTP, so it cannot see the filter. The filter's cost is one Mongo insert per named request, unmeasured.
(3) `cleanDatabase()` needed no change: it clears every collection it finds. (4) A signed-in request to a public path
(`/helper/**`) is recorded too: it has a named person, and the plan's line excluded only requests with nobody named.
(5) A held account's token is refused by `AuthFilter` without naming anyone, so its attempts are not recorded; a request
that fails with an uncaught exception escaping the dispatcher is not recorded (no status yet; `ControllerAdviser`'s
catch-all makes this rare).

**Not changed, noted:** `Grievance`'s and the other privacy entities' `@Indexed` fields create no index (no
`auto-index-creation`, no initializer lists them); `GET /privacy/grievances/user/{email}` checks no ownership in the
controller — whether a user can read another's grievances was not tested here. Both are proposals, not done.
