## Plan for W-296 — V1 merges a same-day buy only into a lot of the same segment

**What this item is for (one sentence, in my own words):** V1 folds a buy into an existing lot of the same stock,
broker, holder and day. The match ignores segment, so an intraday buy and a delivery buy become one lot that carries
the first buy's segment (D-593).

**Findings (read this session, 2026-11-12):**

1. **Three places merge V1 same-day buys, and none of them keys on segment.**
   - **Live V1:** `PortfolioService.buyStock` (`:381`) uses
     `PortfolioRepository.findFirstByEmailAndStockCodeAndBrokerNameAndAccountHolderAndTransactionDateOrderByIdAsc`
     (`:18`). That is its only caller.
   - **The lot replay (§2.12):** `LotLedger.buy` (`:51 – 52`) matches with `sameHolding` (stock, broker, holder) and
     the date.
   - **The trade-outcome rebuild (§2.2):** `TradeMatchingService.buildCompositeKey` (`:126 – 131`) keys on email,
     stock, broker, holder and date. A merged mixed lot gets an empty buy venue (`TradeVenue.only`, as with mixed
     exchanges).
2. **Sales match lots by holding and date, not by segment.**
   - Live: `findEligibleHoldingsForSell` (`PortfolioService:482`, `:503`).
   - The replay: `LotLedger.sell`, through `sameHolding` (`:106`).
   - Whether an intraday sale may draw a delivery lot is a separate question, and this item does not change it.
     That is why `sameHolding` itself stays as it is. Only the merge filter gains the segment.
3. **No stored data shows the problem yet.** Before W-292 every transaction and lot said `DELIVERY`, so a merged
   mixed lot cannot be told apart from stored data. W-297 corrects the transactions' segment from their charge rows,
   then runs §2.12 for each user. Under this item's key, that rebuild splits such lots.

**Choices for the owner:**

- **C1 — the merge key.**
  - **C1a (recommended):** segment joins the key in all three places. Live gets the repository method
    `...AndSegmentAndTransactionDate...`, which replaces the old one (no caller is left). The replay filter adds
    `Objects.equals(lot.getSegment(), buy.getSegment())`. The rebuild key adds `getSegment()`. Sales are unchanged.
  - C1b: live and the replay only. The §2.2 key stays, and a mixed lot keeps its empty venue.
- **C2 — stored data.**
  - **C2a (recommended):** no runbook entry. Nothing stored can show the problem before W-297, and W-297's §2.12 step
    splits the lots. W-297's row gains a note saying so.
  - C2b: a read-only count (§3.20) of lots whose `buy_transaction_ids` name transactions of more than one segment.
    It finds only merges made between this deploy and W-297.

- **Product manager:** an intraday buy no longer averages into a delivery holding's price.

**Risks or ambiguities:**

  is the right reading of the key.
- The repository method's name grows to seven parts. That is still a derived query, not `@Query`.
