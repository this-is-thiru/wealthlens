## Plan for W-090b — The ITR form model, synthetic pack

**What this item is for (one sentence, in my own words):** a year's return forms become rows the pack reads, each
with its person types, return kinds, cascade order, positive conditions, bars, exclusions and manners of furnishing,
versioned per tax year and checked at build time, so that W-090c can write TY 2026-27's forms as data and W-091 can
select one; this item proves it on the synthetic pack only.

**Findings (each read this session):**
- F1: the pack already has a `forms` layer. `RulePackLayer.java:45` is `FORMS(false, "forms/itr-forms.json")`, which
  "changes no number" and is "versioned apart from `law` because form notifications follow their own cadence"
  (`:40` – `44`). The compiler writes it empty today (`RulePackCompiler.java:94`), and nothing reads it:
  `JsonPackAssembler.java:54` – `58` parses no forms file. Every lock carries its own `forms` version and checksum
  (`2026-27.lock.json:12` – `15`). `TimelineReader.java:42` says "`forms/` has none yet". The approved row (D-516 C2a)
  says `law/itr-forms/`, which would put forms into the `law` checksum and the compute cache key. See C1.
- F2: condition sets (W-244) are the pattern to follow. Each is one file under `law/condition-sets/` holding an `id`
  and its `versions`. `SetVersions` reads it (`SetVersions.java`: `forTaxYear` refuses two versions in one year,
  `everyVersion` refuses overlap). `RulePackCompiler.java:122` – `128` projects it, and
  `RegistryJson.java:196` – `208` parses it with `ConditionJson.conditions`. `SetVersions.projected` writes the
  identity under the key `id`.
- F3: `ItrFormCode` exists (`rules/id/ItrFormCode.java`, `^[A-Z0-9-]{3,16}$`). Its Javadoc still says "nine … plus
  ITR-V", which D-516 C4a's erratum overturned. `PersonType` and `HasPersonType` exist. There is no `ReturnKind`,
  `FurnishingOption` or `ItrFormSpec` anywhere (grep).
- F4: the design's sketch (`DR 21` I3, `21-itr-forms.md:49` – `95`) gives a per-bar `ruleRef`, `reason` and
  `status`, so that the user is told *which* bar is uncertain. It gives a `validity` for each form so that the
  selector can filter by filing date. It also names return kinds (`ORIGINAL | BELATED | REVISED | UPDATED | LOSS`)
  and manners of furnishing (`ELECTRONIC_DSC`, …) as fixed values. r.164(1) scopes the form set by "the tax year",
  not by the filing date, and covers returns under s.263(1), s.268(1)(a) or s.280 (`01-rulebook.md:1583`,
  `ITR-SCOPE-001`). I have not read r.164(12)'s Table or r.165. W-090c and W-090e read them.
- F5: call sites: `new RulePack(` in 22 files (1 main), and `new Timeline(` in 1 (`TimelineReader.java:229`).
  `DeclarationReferences.check` walks rules and condition sets (`DeclarationReferences.java:35` – `45`). A form's
  conditions must join that walk.
- F6: `ContentPerturbationTest` (I27) says the shipped timeline "holds no `forms/`". The shipped timeline still holds
  none after this item, so the test is unchanged, and W-090c brings the first shipped forms. The synthetic locks
  carry `forms.1` (`rulepacks-synthetic/*.lock.json:12` – `13`). Only those three locks move, by hand (session 80's
  trap; `run_relock.sh` relocks only the shipped locks).

**Choices for the owner:**
- **C1a (recommended): forms live on the timeline at `forms/itr-forms/<CODE>.json` and compile into the existing
  `forms` layer.** That layer is separate because form notifications follow their own dates, and it is outside the
  cache key (F1). An erratum on the W-090b row and on D-516 C2a's path. C1b: keep `law/itr-forms/` as approved. Then
  the `forms` layer stays empty for good, and every form edit bumps `law` and invalidates the cached computations.
- **C2a (recommended): a return kind and a manner of furnishing are open codes in `rules/id`, `ReturnKind` and
  `FurnishingManner`** (pattern `^[A-Z][A-Z0-9_]{1,63}$`, as `DeclarationCode`). They are not enums. Their values are
  the law's (s.263 sub-sections, r.164(12)'s Table and r.165), so they belong to W-090c's data (CLAUDE.md §4, facts not
  rules). W-091's input can name them because `rules.id` is a named interface. C2b: enums with the design's values,
  which I cannot source today.
- **C3a (recommended): one version per tax year, through `SetVersions`, and no `validity` on the compiled
  `ItrFormSpec`.** r.164(1) chooses the form set by tax year (F4), and a year's pack holds one version, as condition
  sets do. C3b: keep a filing-date `validity` and allow several versions in a year. Nothing today says a bar changes
  by filing date.
- **C4a (recommended): a bar is `ItrFormBar(reason, condition, provenance)`.** The clause and its verification level
  sit on the bar's own provenance, so that W-091 can name the bar that refused a form and whether it is verified
  (F4, `DR 21` I3's inference). C4b: plain `List<Condition>` bars, which lose which clause refused.

**Files I will create** (under `backend/src/main/java/com/thiru/wealthlens/taxengine/rules/` unless stated):
- `id/ReturnKind.java`, `id/FurnishingManner.java`: the two open codes (C2a).
- `filing/ItrFormSpec.java`, a record:
  - Fields: `code`, `displayName`, `cascadeOrder`, `appliesTo` (`Set<PersonType>`), `returnKinds`,
    `positiveConditions`, `bars`, `excludes` (`Set<ItrFormCode>`), `furnishing` and `provenance`.
  - It refuses an empty `appliesTo`, `returnKinds` or `furnishing`, a `cascadeOrder` below 1, and a form that
    excludes itself.
  - No `schedules` (W-092) and no `validity` (C3a).
- `filing/ItrFormBar.java`: `reason`, `condition` and `provenance` (C4a).
- `filing/FurnishingOption.java`: `manner`, the `conditions` under which it is open (for example r.164(12)'s age
  condition), and `provenance`.
- `json/ItrFormJson.java`: parses a form, as `RegistryJson.conditionSet` does. The identity key is `id` (F2).
- `validate/ItrFormReferences.java`, run at build time from `PackValidator`. In the year's pack:
  - Every `excludes` names a form in that pack.
  - That form has a lower `cascadeOrder`, because r.164(4) excludes only an earlier sub-rule.
  - No two forms that share a person type and a return kind share a `cascadeOrder`, so the cascade is deterministic.
- `backend/src/test/resources/rulepacks-synthetic/timeline/forms/itr-forms/`: two synthetic forms, labelled "not
  law":
  - `SYN-1`: cascade 1, `INDIVIDUAL`, kind `SYN_ORIGINAL`, a positive `IsResident` and a bar on `SYNTHETIC_YES_NO`.
    It has a second version from 2101-04-01 whose bar is `DeclaredAmountAbove SYNTHETIC_AMOUNT ₹1,000`.
  - `SYN-2`: cascade 2, `INDIVIDUAL` and `HUF`, which excludes `SYN-1`.
- Tests:
  - `ItrFormSpecTest`: the refusals.
  - `ItrFormJsonTest`
  - `ItrFormReferencesTest`: an unknown exclude, an exclude of a later form, a shared cascade order, and a bar naming
    an unknown declaration.
  - `ItrFormProjectionTest`: the synthetic pack read, compiled and assembled per year.
