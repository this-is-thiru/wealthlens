## Plan for W-272 — a V1 buy answers 500 after two V2 buys that day

**What this item is for (one sentence, in my own words):** a V1 buy is recorded however many lots of the stock were
bought that day, instead of failing because V1 expected at most one (G-6).

**Findings (each read this session, 2026-11-11):**

1. **V1's merge expects one same-day lot.** `buyStock` (`PortfolioService.java:356`) calls
   `findByEmailAndStockCodeAndBrokerNameAndAccountHolderAndTransactionDate` (`PortfolioRepository.java:17`), which
   returns `Optional`. V2 writes a lot per buy, so after two V2 buys of a stock on one day the query is non-unique and
   Spring throws → 500. Proven: W-264a scenario 11 (two V2 buys on 5 Jan, then a V1 buy on 5 Jan: 500 "returned non
   unique result").
2. **With one same-day lot, V1 merges into it today** — including a V2 lot (W-270's no-flow test, scenario 13): the
   weighted price and summed charges.
3. **The same finder's only other caller is dead.** `PortfolioQueryService.findAssetsForCorporateAction` (its only
   method) has no caller in `main` or `test`; `SearchableIdentifierIntegrationTest.java:57` calls the finder directly
   to prove an encrypted lookup.

**Choices for the owner:**

- **C1 — which lot a V1 buy merges into when several were bought that day.**
  - **C1a (recommended):** the oldest of them (first stored), through a new
    `findFirstByEmailAndStockCodeAndBrokerNameAndAccountHolderAndTransactionDateOrderByIdAsc`. Unchanged when there is
    one or none; defined when there are more.
  - C1b: none — when more than one exists, the V1 buy writes its own lot, as V2 would.
- **C2 — the dead `PortfolioQueryService` and the `Optional` finder.**
  - **C2a (recommended):** remove both (no caller once V1 uses the new finder); `SearchableIdentifierIntegrationTest`
    proves the encrypted lookup through the new finder instead.
  - C2b: leave them for W-281 (hygiene).

**Files I will modify:** `PortfolioRepository`, `PortfolioService.buyStock`; `PortfolioQueryService` (deleted, C2a);
tests — W-264a scenario 11 as the first test (V2 10 @ 100 and 10 @ 140 on 5 Jan, then V1 10 @ 120 on 5 Jan: 200, the
first lot 20 @ (1000 + 1200) / 20 = ₹110, the second still 10 @ ₹140), `SearchableIdentifierIntegrationTest`, any
mock of the old finder in `PortfolioServiceTest`.

**Numbers I will use:** none beyond the scenario's own arithmetic.

**What I am NOT doing:** V1's lost order time on a merge (W-279); fractional comparisons (W-274); corporate-action
processing (W-264c).

**How I will verify:** scenario 11 red then green; probe: the old `Optional` finder back → 500; the affected classes;
`./mvnw validate`.

**Post-deployment actions (R15):** none — no stored data changes meaning.

**Five roles:**
- **Architect:** V1's merge rule is stated for the case V2 creates, rather than assumed away.
- **Product manager:** a V1 buy never fails because of how earlier buys were entered.
- **Senior engineer:** a derived `findFirst…OrderByIdAsc` — deterministic, no new query string.
- **Automation tester:** scenario 11 with distinct prices so the merged lot is identifiable; a probe.
- **Manual tester:** two V2 buys and one V1 buy of one stock on one day all answer 200.

**Risks or ambiguities:** C1a merges a V1 buy into a lot V2 created, changing that lot's price — the same thing that
already happens when only one V2 lot exists.
