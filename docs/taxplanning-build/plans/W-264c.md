## Plan for W-264c — gap audit: corporate actions

**What this item is for (one sentence, in my own words):** drive bonus, split, demerger, quarterly processing,
blocking into `TEMPORARY` and redrive end to end through the HTTP API. I write each expected answer by hand first.
Every gap I find is reported and placed as a row (W-264, D-530).

**What the module is (read this session, 2026-11-13):**
- Two controllers: the admin routes under `/corporate-action/`, and `PUT /corporate-action/user/{email}/perform`.
- One service, `CorporateActionService` (591 lines).
- `CorporateActionIntegrationTest` (47 tests) covers entry validation and one happy path per action. This audit goes
  after the edges it does not cover.

**Hypotheses read from the code** (each is a scenario below; none is claimed as a gap until a run shows it):
- **H1. A bonus pools account holders.** `processBonusShares` (`CorporateActionService:280 – 320`) sums every lot of
  the broker into one count. It writes **one** bonus lot copied from the first lot, so a second account holder's
  entitlement goes to the first holder.
- **H2. A demerger reads its share ratio backwards.** The Indian convention is **new:held**. ITC's demerger was "1:10",
  one ITC Hotels share for every 10 ITC shares held, with the record date 6 Jan 2025 (ITC's investor page; broker and
  press reports agree). The repo writes ratios the same way: the api-collection's Motherson Sumi Wiring bonus is
  `1:2`, one new for every two held, and the bonus code reads it so (`total × 1 ÷ 2`, `:283 – 287`). `demergeLots`
  instead multiplies the held quantity by the **second** number (`:466`, `asNewEntity` `:525`) and never uses the
  first (`:465`). The cost split is given main-first (ITC 86.49 : ITC Hotels 13.51), which is the order the code reads
  it. `DemergerDetail:12` documents neither.
- **H3. Two actions block trades but can never be performed.** `FILTERABLE_CORPORATE_ACTIONS` lists `BONUS`,
  `STOCK_SPLIT`, `RIGHTS_ISSUANCE`, `BUYBACK` and `DEMERGER` (`CorporateActionType:20`), and the perform loop
  fetches all five (`:163 – 165`). Its switch handles only three and throws "Invalid action type" for the rest
  (`:198 – 202`). So a trade blocked by a rights issue or buyback stays `TEMPORARY`, and the quarter's run stops at
  that action. `CLAUDE.md` names only three blocking types.
- **H4. Same-quarter order is not defined.** `findByTypeInAndRecordDateBetween` (`:164`) sorts nothing, so a split
  and a bonus in one quarter may be applied in either order.
- **H5. A wrong month answers in Java's words.** `Month.valueOf(actionPerformDto.month())` (`:138`): "april" answers
  "No enum constant java.time.Month.april" (W-302's kind of gap).
- **H6. Partial runs.** The per-user perform is not `@Transactional` (`:119 – 161`), so a run that fails at its
  second action keeps the first.
