## Plan for W-302 — the upload's existing type columns name the row and the words when refused

**What this item is for (one sentence, in my own words):** a wrong word under `BROKER NAME`, `ASSET TYPE` or
`TRANSACTION TYPE` should be refused the way W-301 refuses one under `SEGMENT`, naming the row, the column and the
words accepted, not with Java's `No enum constant …` (D-608).

**Findings (read this session, 2026-11-13):**

1. **The three are read with `valueOf`:** `setBrokerName` (`AssetRequestParser:106 – 111`), `setAssetType`
   (`:142 – 150`), `setTransactionType` (`:184 – 189`). A wrong word answers 400 because `valueOf` throws
   `IllegalArgumentException` (`ControllerAdviser:29`), but the message names neither the row nor the words.
2. **A blank cell or an absent column answers 500 today.** A blank cell is stored as `CellDetail.def()`, so its
   value is `null` (`AssetRequestParserImpl:104`, `CellDetail:14 – 15`), and `valueOf(null)` throws
   `NullPointerException`. A column the sheet does not have is not in the record at all, so `record.get(...)` is
   `null` and `.getCellValue()` throws. Neither is mapped to 400.
3. **`constantOf` alone would make it worse.** It answers `Optional.empty()` for a blank or absent cell
   (`:127 – 132`), because `SEGMENT` and `ACCOUNT TYPE` have a JSON default. These three have none
   (`AssetRequest:50`, `:51`, `:54`). Reading them through `constantOf` and `ifPresent` would store a trade with no
   broker, asset type or side, where today it fails.
4. **The words:** `BrokerName` is `UPSTOX`, `FYERS`, `ZERODHA`. `TransactionType` is `BUY`, `SELL`. `AssetType` is
   `EQUITY`, `MUTUAL_FUND`, `BOND`, `GOLD_BOND`, `FD`, `INSURANCE`, `LAND_OR_BUILDING`. The last one is refused
   straight after it is read (`:146 – 148`, W-088g5).

**Choices for the owner:**

- **C1 — a blank or absent cell in these three columns.**
  - **C1a (recommended):** refuse it, naming the row and the column, for example
    `Row 3, BROKER NAME: blank; one of [UPSTOX, FYERS, ZERODHA] is needed`. Today's 500 becomes a 400 that says what
    is missing. This is one method, `requiredConstantOf`, which is `constantOf` plus `orElseThrow`.
  - C1b: leave it as it is (500). That would mean keeping `record.get`, which `constantOf` does not do.
- **C2 — the words listed for `ASSET TYPE`.**
  - **C2a (recommended):** every constant, `LAND_OR_BUILDING` included, so one `constantOf` serves all five columns.
    A `LAND_OR_BUILDING` row still gets its own refusal, as today.
  - C2b: list the words without `LAND_OR_BUILDING`. That needs a word list that differs per column.

**Files I will modify (all recommended):**
- `AssetRequestParser`: `requiredConstantOf`. The three setters read through it, the land refusal stays, and the
  unused `BrokerName` / `TransactionType` imports go if nothing else uses them.
- Tests:
  - `AssetRequestParserTest`: a wrong word in each of the three refused with the message (red before: `No enum
    constant …`); a blank `BROKER NAME` refused (red before: `NullPointerException`); a workbook without a
    `TRANSACTION TYPE` column refused (red before: `NullPointerException`).
  - `PortfolioGapAuditIntegrationTest`: an uploaded row with a blank `BROKER NAME` answers 400 with the message (red
    before: 500).
- `STATE.md`, `03-WORK-ITEMS.md` (row closed), WL-A-2 unchanged (no operation).

**Numbers I will use:** none.

**Design sections I read:** D-607 (W-301, C3a, `constantOf`), D-608 (the row), W-088g5 (the land refusal).

**What I am NOT doing:**
- The other required columns (`STOCK CODE`, `PRICE`, `QUANTITY`, `TRANSACTION DATE`) also throw
  `NullPointerException` when absent. They are not type columns, and a placed row could take them if wanted (a
  proposal, not done).
- The template, because the columns already exist.
- Case-folding, so `buy` stays refused, as JSON refuses it.

**How I will verify:**
- The red tests run first.
- Probe: put back `BrokerName.valueOf` in `setBrokerName`. The wrong-word case must fail, then I restore the line
  byte-identical.
- Locally: `AssetRequestParserTest`, `PortfolioGapAuditIntegrationTest` and `validate`. The tiers run on the PR's
  pipeline.

**Post-deployment actions (R15):** none.

**Five roles:**
- **Architect:** one reader for every enum column; a required column has no default to fall back on.
- **Product manager:** a mistyped broker or side tells the user which row, which column and what to type.
- **Senior engineer:** one method, three setters shortened; no new type.
- **Automation tester:** a wrong word ×3, blank and absent column, all red first; one upload round trip; a probe.
- **Manual tester:** upload the template with `BROKER NAME` `Zerodha` (wrong case) and with it blank. Each answers 400
  naming the row.

**Risks or ambiguities:** none beyond C1. `recordNumber` is the same number the existing refusals use (`:147`,
`:161`).
