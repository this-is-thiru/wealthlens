### Findings

1. **Today every individual has a free choice every year.** The only binding that could tie someone to a regime
   (`FIRST_SCHEDULE_RATES`, s.202(4)(a); 1961 s.115BAC(6)(i)) applies only with business income, which no input can
   carry. So L3's history branches (continuing, withdrawn, permanently ineligible with revival, lapsed) decide nothing
   for any person the engine can compute. Code for them could only be reached from contexts built in tests.
2. **Some of the offer logic is reachable through the data:** person type (a HUF: both shipped regimes are
   `INDIVIDUAL` only), the lifecycle windows (including a grandfathered regime kept by an IN_EFFECT person) and
   eligibility condition sets. A new year's pack can declare any of these.
3. **Each regime runs its own pipeline** (`D-REGIMESTEP`), so the resolver must take the `RegimeSpec` from the choice
   rather than the one it is handed.
4. **The trace line needs a rule.** `TraceLine` refuses an empty rule, and no row stands for the option. A new row
   would also mean teaching I3 about elections, because no node evaluates it. What the choice actually changes is
   the regime's rate table, and each regime names one (`rateTable`).
5. **Size:** `RegimeOffer` + offers (~110 lines), `RegimeElection` (~70), the resolver and `Election` changes (~25), plus
   tests (~250). That is within §7 if L3's history branches wait (C1).
