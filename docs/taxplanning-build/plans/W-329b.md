## Plan for W-329b — the creation fields of the tax-planning entities saved with their id set

> **Approved as recommended — C1a** (owner, session 101, 2026-11-16); the ArchitectureTest guard not placed. Every path below was read on 2026-11-16 at `3022ebd1`; grep each
> again before relying on it. Probe: the core change applied to four entities, the draft integration classes run,
> then reverted byte for byte (`git status` clean).

**What this item is for (one sentence, in my own words):** the 11 tax-planning entities whose id is set before their
first save should record when and by whom they were created. Spring Data's auditing does this for new entities only,
and today it treats them as updates (W-329 C2a, D-724).

**Probe (2026-11-16):**
- **The mechanism**, applied to `TaxYearWorkspace`, `FilingDraft`, `DraftRevision` and `RegimeElectionHistory`:
  - Each implements `Persistable<String>`. `isNew()` returns a `@Transient` (and `@JsonIgnore`) flag.
  - The creation paths in `DraftService` set the flag beside `setId(UUID.randomUUID()…)` (`:55` – `:56`,
    `:101` – `:102`, `:229` – `:230`, `:289` – `:290`).
  - One `AfterSaveCallback` clears the flag after a save, so a second save of the same instance is an update.
- **Result:**
  - A first figure plus a second draft stored `createdBy`, `updatedBy`, `createdAt` and `updatedAt` on the workspace,
    both drafts and all three revisions. `createdBy` was encrypted, `k1:…`, by its existing converter.
  - `tax_profiles`, not probed, still had only `updatedBy` and `updatedAt`.
  - The workspace is saved twice in `createDraft`, the second time to set its primary draft, and was updated, not
    inserted again.
- **Nothing moved:** `DraftIntegrationTest` 40/0, `DraftComputationIntegrationTest` 63/0, `TaxJobsIntegrationTest` 18/0.
- **No entity is serialized to JSON.** No controller returns one of the 11 (all return views), and no
  `writeValueAsString` or `valueToTree` takes one. The `@JsonIgnore` is a guard only.
- **Creation paths:** the 4 classes D-724 names. `TaxProfileReferenceService.create` (`:138` – `:144`) serves all five
  reference kinds. The build greps `setId(` for each entity again before relying on this list.

**Choices for the owner:** none beyond D-724's C2a. One naming question, with a recommendation:
- **C1: names.**
  - **C1a (recommended):** the interface `CreatedWithId` (`shared/entity/model`), with `setNewlyCreated(boolean)`, and
    the callback `CreatedWithIdSaved`.
  - C1b: name them yourself.

**Files I will create:**
- `shared/entity/model/CreatedWithId.java`: the interface. Its Javadoc states why: an id is set before the first
  save, so Spring Data cannot tell a new record.
- `shared/entity/model/CreatedWithIdSaved.java`: the callback.
- `integration/CreationAuditIntegrationTest.java`: the tests below, a new class because `DraftComputationIntegrationTest`
  is at its size cap.

**Files I will modify:**
- The 11 entities (`implements CreatedWithId`, the flag, `isNew`).
- The 4 creating classes (set the flag beside each `setId`).
- `AuditMetadata.java` Javadoc: records created before W-329b have no creation fields.
- STATE, CHECKPOINT.

**Numbers I will use:** none.

**Tests:**
- Create each kind through its endpoint: a profile, each of the five references, a first figure (giving a workspace,
  a draft, revisions and computations), and a regime election.
  - Each stored document has `createdAt` and `createdBy`.
  - Then save each again through its ordinary update. `createdAt` is unchanged and `updatedAt` has moved.
- A document stored without the creation fields, as every one stored before W-329b is, loads and saves as an update
  and stays without them. Nothing is invented.
- **Red first:** the "has `createdAt`" assertion fails on today's code (D-724's measurement).

**Design sections I read:** D-724; session 62's finding on `createdBy`; W-257's row.

**What I am NOT doing:** any backfill (C2a); the other modules' entities; `AccessRecord`, `JobFailure` and
`ProcessingRecord`, which carry no audit block; changing `ThirdPartyRetention`'s read (it already prefers
`updatedAt`).

**How I will verify:**
- The targeted classes: `CreationAuditIntegrationTest`, `DraftIntegrationTest`, `DraftComputationIntegrationTest`,
  `TaxJobsIntegrationTest`, `StoredActorEncryptionIntegrationTest`, the profile and reference integration classes,
  `WealthLensModulithTest`, `ArchitectureTest`.
- `./mvnw validate`.
- The full tiers run on the pipeline only.

**Post-deployment actions (R15):** none. New records gain the fields as they are created, stored ones are untouched,
and nothing is run against a database.

**Five roles:**
- **Architect:** the shared interface lives in `shared/entity/model` beside `AuditableEntity`. No new module
  dependency, since `taxplanning` already uses `shared`.
- **Product manager:** nothing visible changes. The data now says when a record was made and by whom, which retention
  and any audit read can use.
- **Senior engineer:**
  - One flag, set only where a record is made and cleared after its save. The rules are stated in the interface's
    Javadoc.
  - Lombok's `@Data` generates the setter, so no hand-written accessor is added except `isNew`.
- **Automation tester:** the creation and update cases for all 11 entities, the old-record case, and the red-first
  check.
- **Manual tester:** on staging, create a draft and read its document in the console. Expect
  `audit_metadata.createdAt` to be present (§0.7's console form).

**Risks or ambiguities I noticed:**
- A future creation path that forgets the flag silently records no creation fields, as today. The new test covers
  today's paths only.
- A guard that every `setId(UUID.randomUUID()` sits beside a `setNewlyCreated(true)` could be an `ArchitectureTest`
  rule, placed only if you want it.
