## Plan for W-295 — an outcome row records the segment its sale was traded in

**What this item is for (one sentence, in my own words):** P&L files a sale under its outcome row's `segment`, and
two of the three places that write a row leave it unset. A V1 intraday sale, or any sale whose rows were rebuilt,
is therefore filed under delivery when the P&L is rebuilt (D-592).

**Findings (read this session, 2026-11-12):**

1. **Three places write an outcome row.**
   - V2 sets the row's `segment` from the sale: `TradeOutcomeRecorder:143`.
   - V1 does not: `PortfolioService.toTradeOutcomeContext`, builder at `:654`. It sets `sellSegment` from the request
     (`:678`), but not `segment`.
   - The §2.2 rebuild does not: `TradeMatchingService.toTradeOutcomeEntity` (`:276`), called by
     `TransactionBasedTradeOutcomeMigration:117`. It sets `sellSegment` from the sale's venue (`:313`), but not
     `segment`.
2. **What reads it.**
   - `ProfitAndLossService.foldSale` (`:397`) files each row under `row.getSegment()`, and null is read as delivery
     (`:431`). That is the §2.11 rebuild.
   - Live V1 P&L is not affected: it files under the request's segment (`PortfolioService:643`).
   - So the defect shows only after a §2.11 rebuild, which is the step W-297 depends on.
3. **`TradeMatchingService.toTradeOutcomeContext(MatchedTrade)` (`:233`) has no caller** in `src/main` or
   `src/test` (searched for `.toTradeOutcomeContext(` and `::toTradeOutcomeContext`). It leaves `segment` unset as
   well.
4. **`PropertySaleService:98`** writes a land or building row with no segment. A property sale is not traded in a
   market segment, so its row is left as it is.
5. **Stored rows.** A V1 row and a rebuilt row hold `sell_segment` (W-088j2b), but no `segment`. For every row,
   `segment` means the sale's segment, which is what `sell_segment` records. Only a row whose `sell_segment` is not
   `DELIVERY` is filed wrongly today.

**Choices for the owner:**

- **C1 — the row's segment.**
  - **C1a (recommended):** set it from the sale. V1 takes it from the request, as V2 does
    (`.segment(assetRequest.getSegment())`). The rebuild takes it from the sale's venue
    (`trade.getSellVenue().segment().orElse(null)`), the same value it already writes to `sell_segment`.
- **C2 — the uncalled converter (finding 3).**
  - **C2a (recommended):** leave it alone and place **W-298** to remove it. Removing it here would go beyond the row.
  - C2b: set `segment` in it too.
- **C3 — stored rows.**
  - **C3a (recommended):**
    - **§3.19 (read-only):** a count, per user, of rows with `sell_segment` other than `DELIVERY` and no `segment`.
      These are the rows a §2.11 rebuild files under delivery.
    - The correction goes into **W-297**, whose row is widened. It sets `segment` from `sell_segment` where
      `segment` is absent, then runs §2.11 for each user listed. W-297 is already the one stored-segment correction.
  - C3b: write that correction here as §2.14 (one-time, `mongosh`, backup, removal ticket).
