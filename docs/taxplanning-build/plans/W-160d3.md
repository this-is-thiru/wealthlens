## Plan for W-160d3 — the stored P&L documents

**What this item is for (one sentence, in my own words):** P&L documents written before W-160d1 hold their realised
figures only in the short/long pair (and V2's duplicate map), which nothing reads since W-160d2; a one-time,
idempotent `SUPER_USER` operation moves those figures into `gains_by_asset_and_segment` and unsets the old fields, so
earlier years show their figures again (D-366 C2a; T1 P6; R15).

**Medium: one operation (service, controller, report), an integration test, R15 entry, Phase 15 row, YouTrack child.**

### What I read (session 35, 2026-10-25)

- `plans/W-160d.md` (C2a, "its sub-plan settles which figures it can rebuild, and stops if a year cannot be");
  `ProfitAndLossEntity` (`profit_and_loss`, unique `{email, financial_year}`, `realised_profits` and
  `out_sourced_realised_profits`); `ReportModel` (`purchase_amount`, `sell_amount`, `profit`, `misc_charges`,
  `brokerage`), `FinancialReport` (months under `capital_gains`), `MonthlyReport` (`first_half_report`,
  `second_half_report`); `TradeOutcomeEntity` (`asset_type`, `account_type`, `sell_date`, `segment`,
  `sell_segment`); the W-160c operation as the template.
- **What the stored pair holds:**
  - **V1** wrote five figures per sale into one half of the pair: purchase, sell, profit, brokerage, misc.
  - **V2** wrote purchase and sell only, into one half of the pair **and** into `gains_by_classification`. So the map
    duplicates amounts the pair already has.
  - So **the pair alone holds every pre-W-160d1 sale, once**. Short plus long is the year's total, at every level
    (year, month, fortnight).
- **What `trade_outcomes` can add:** the facts the pair summed away. Rows are written by the same two sell paths
  that write the P&L (`PortfolioService:623` V1, `:674` V2 via `TradeOutcomeRecorder`). Corporate-action events write
  neither. A user can also have rows from the rebuild (runbook §2.2).
- **Why not rebuild the figures from `trade_outcomes`:** a row carries net profit and charges, but V1 and V2 stored
  different figures. Recomputing would add profit, brokerage and misc to every V2 year, which is W-169's change. It
  would also redraw V1's figures from a different formula. Either way users would see numbers change. Keeping the
  pair's own figures changes none.

### The operation (C1a)

For each P&L document carrying `short_term_capital_gains`, `long_term_capital_gains` or `gains_by_classification`,
handle each side (`realised_profits` ↔ `account_type` `SELF`; `out_sourced_realised_profits` ↔ any other) on its own:

1. **Facts:** the side's `trade_outcomes` rows, by email, account side, and sell date within the document's financial
   year (the year parsed as `TLocalDate.financialYear` writes it, such as `2024-2025`). Each row gives
   `(asset_type, sell_segment, else segment, else DELIVERY)` — `DELIVERY` as the P&L defaults (D-295).
2. **Placeable** when the pair is empty, or when every row gives one and the same `(asset type, segment)`. Then the
   pair's short and long reports are **added** into `gains_by_asset_and_segment[asset][segment]`: each of the five
   figures, at the year, at each month, at each half. Added, not replaced, because sales since the deploy may already
   be there. In the same update, the pair and the map are unset.
3. **Not placeable** when there are no rows, or rows give more than one `(asset type, segment)`, or an asset type is
   missing, or the year cannot be parsed. That side is left unchanged and listed in the report with its reason.

The dry run reports, per side, what it would place where, and every side it cannot place. A document is written in
one `updateFirst`. After it, no old field is left on a placed side. So a second run, including after a part-way run,
finds only what is still to do (idempotent).

### Choices (recommended first)

- **C1 — where the figures come from:**
  - **(a) recommended:** from the stored pair, with `trade_outcomes` used only for the facts (the operation above). No
    figure a user saw changes; it only moves.
  - **(b)** rebuilt from `trade_outcomes`' figures. It can place mixed years too, but changes V1 and V2 figures (above).
- **C2 — sides that cannot be placed:**
  - **(a) recommended:** left unchanged and listed. You run the dry run before the deploy's write, and the runbook
    says to bring the list back. A session then places a row for them with the list, and decides each by its facts,
    for example by building that side from `trade_outcomes` (C1b) for those sides alone.
  - **(b)** build those sides from `trade_outcomes` (C1b) in this operation now.
  - **(c)** unset their old fields anyway. Those years would lose their figures.
