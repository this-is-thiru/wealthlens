## Plan for W-269 — trades posted at the same time answer 500

**What this item is for (one sentence, in my own words):** a trade that collides with another being recorded at the
same moment is recorded anyway, by trying it again, instead of failing with a 500 and leaving the caller to guess
whether it was recorded (G-13).

**Findings (each read this session, 2026-11-11):**

1. **The conflicting write.** Every V2 buy reads and rewrites the user's one `profit_and_loss` document for the
   financial year (`ProfitAndLossService.java:332-350`, `findByEmailAndFinancialYear` then `save`); W-264a's run log
   shows the `WriteConflict` raised at `ProfitAndLossService.handleNormalBuyCase:350` (an insert of that document)
   under `PortfolioService.buyStockV2:400`. V1's buy also merges into one lot (`PortfolioService.java:341`).
2. **Transactions are on in every profile** (`application.yaml:118`, `transactions-enabled: true`; the profile
   yamls do not override it), so two trades touching that document abort one with Mongo error 112, labelled
   `TransientTransactionError` — the driver's signal that the whole transaction may be run again
   (`com.mongodb.MongoException.hasErrorLabel`, `TRANSIENT_TRANSACTION_ERROR_LABEL`, driver 5.8.0). Spring wraps it
   in `DataIntegrityViolationException`; `ControllerAdviser` answers 500.
3. **An aborted trade leaves nothing.** The four write paths are `@Transactional` (`PortfolioService.java:83, 125,
   226, 254`: V1, V2, upload, redrive), so a retry starts from a clean database; the fingerprint row of the first
   attempt was rolled back too, so the retry is not mistaken for a replay.
4. **The request object is changed while it is processed** (`setEmail`, the default date, `setTempTransactionId`, and
   V1's merge adds to `orderTimeQuantities` — G-4), so a second attempt must start from a copy of the original.
5. **Retry support is already on the classpath:** Spring Framework 7's `org.springframework.core.retry.RetryTemplate`
   with `RetryPolicy.builder()` (`maxRetries`, `delay`, `jitter`, `multiplier`, `maxDelay`, `predicate`) —
   checked with `javap` on spring-core 7.0.x. No new dependency.
6. **Proof of the gap:** W-264a scenarios 36 (ten V1 buys on one day) and 37 (ten V2 buys on ten days), posted at
   once — nine of ten answered 500, both runs.

**Choices for the owner:**

- **C1 — what does a collision do?**
  - **C1a (recommended):** try the whole trade again, from a copy of the request, while the failure carries
    `TransientTransactionError`: up to 5 more attempts, 20 ms then doubling, jittered, at most 500 ms apart. One
    component, `TradeCollisionRetry` (`portfolio/service`), wraps the four write paths; the controllers call it.
  - C1b: no retry; answer the collision as 409 so the client retries.
- **C2 — when every attempt collides.**
  - **C2a (recommended):** answer **409** "Another trade was being recorded at the same moment; this one was not
    recorded — send it again", through a new `TradeCollisionException` mapped in `ControllerAdviser`.
  - C2b: let the last failure through (500, as today).

**Files I will create:** `portfolio/service/TradeCollisionRetry.java`; `shared/exception/TradeCollisionException.java`
(C2a), beside `BadRequestException` and `ServiceUnavailableException` — `portfolio` has no exception package.

**Files I will modify:** `PortfolioController` (V1, V2, upload), `TemporaryTransactionsController` (redrive),
`ControllerAdviser` (409), the controllers' unit tests if they mock `PortfolioService` directly, CLAUDE.md's
`ControllerAdviser` line (a collision → 409). Tests: scenarios 36 and 37 into `PortfolioGapAuditIntegrationTest` as
the first tests; a unit test for the retry predicate (a labelled failure is retried, an unlabelled one and a
`BadRequestException` are not, the request is copied per attempt) and for the exhausted 409.

**Numbers I will use:** 5 retries, 20 ms first delay, ×2, 500 ms ceiling, jitter 10 ms — a choice, not a figure from
a source: ten concurrent trades need at most nine re-runs between them, and the longest wait (20 + 40 + 80 + 160 +
320 ms ≈ 0.6 s) stays well inside a client's 30 s timeout (`application.yaml`'s idempotency comment).

**What I am NOT doing:** making the P&L update atomic (`$inc`) so trades stop colliding at all — a redesign of
`ProfitAndLossService`, worth its own row if the retry proves too slow; the other portfolio rows.

**How I will verify:** scenarios 36 and 37 red before, green after (all ten 200, 55 units held), run twice; probe:
the predicate made to refuse the label → 36 and 37 fail again; the affected integration classes and
`./mvnw validate`.

**Post-deployment actions (R15):** none.

**Five roles:**
- **Architect:** the retry sits outside the transaction, at the one boundary the four paths share, and retries only
  what the database says is safe to retry.
- **Product manager:** a trade sent while another is saving is recorded; if it truly cannot be, the person is told
  it was not recorded and to send it again — never a bare 500.
- **Senior engineer:** a copy of the request per attempt, because processing changes it.
- **Automation tester:** the concurrency scenarios are the proof; a probe shows they depend on the retry.
- **Manual tester:** two browser tabs submitting trades together both succeed.

**Risks or ambiguities:** concurrency tests can be timing-dependent; each is run twice and a pass that depends on
luck shows as a flake, which I will report rather than retry quietly.
