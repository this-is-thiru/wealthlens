## Plan for W-066b — applying a rule that changed inside the year

**What this item is for (one sentence):** when a rule's value changes part-way through a tax year, apply its
versions the way the rule declares — per segment, the latest, the earliest — or fail loudly, instead of
silently using the year-end version as every node does today.

**This plan raises design decisions (C1–C5) before anything is built.**

### What I read

- **The `W-066b` row:** *"`rules/temporal/TemporallyApportionedCap.java` + `RuleRow.prorationBasis` + `…Test` —
  `DR 18` V5 (`:205-245`) — ⚠ nothing currently applies a mid-year change … without this a rule that changed
  inside the year is evaluated as though it never did. Test each `MidYearCombination` branch, and that
  `UNDETERMINED` throws"* (path corrected by D-097).
- **Appendix E (`:1250`):** *"`UndeterminedApportionmentException` is what `W-066b`'s `TemporallyApportionedCap`
  must throw on `UNDETERMINED` … `W-066b` is reached first"* (before `W-105`'s exception hierarchy).
- **`DR 18` V5:**
  - `apply(rule, t, ctx)`: an unchanged year → `versionAt(t).cap().apply(ctx)`;
  - otherwise split the year at every version boundary and switch on `midYearCombination`:
    - PRORATE_PER_SEGMENT: *"each segment gets its own cap, prorated to the segment"*;
    - LATEST: the last segment's version;
    - EARLIEST: the first segment's version;
    - STATUTORY: *"`ctx.pack().rule(rule.midYearCombinationRule()).evaluate(segments, ctx)`"*;
    - UNDETERMINED: throw.
- **Code:**
  - `MidYearCombination` has the five values.
  - `RuleRow` has `midYearCombination`, `midYearCombinationRule` (required iff STATUTORY) and
    `changesWithin(t)`.
  - `versionAt(t)` resolves the `TAX_YEAR` axis at **`taxYearEnd`** (`TemporalContext.on`), so every node today
    behaves as LATEST.
  - I14 (`PackValidator.checkMidYearChangesAreDeclared`) already refuses a pack in which a rule changes inside
    the year with UNDETERMINED.
  - Four nodes apply caps, each as `versionAt(t).cap().apply(...)`: `TaxByBasisNode` (slab ladder),
    `SurchargeNode` (ladder, with marginal-relief logic on the ladder's bands), `CessNode` (`PercentOfBase`)
    and `SalaryDeductionNode` (`LeastOf`).
  - No shipped row changes inside a year, and none declares PRORATE, EARLIEST or STATUTORY. Nothing
    evaluates a "combination rule".

### Findings

1. **Building the class alone changes nothing.** The row's warning, "nothing applies a mid-year change", stays
   true until the four nodes route through it, and they are not in the row's Produces.
2. **Not every node can take a combined result.**
   - `SurchargeNode` and `TaxByBasisNode` need the ladder itself (its bands, for marginal relief and basis
     partition), not a single `CapResult`.
   - For those, a mid-year change can only be LATEST or EARLIEST, with one version governing. Anything else
     must be refused, not approximated.
3. **PRORATE_PER_SEGMENT has one honest meaning with a `CapContext`: the cap over the whole year's figures,
   apportioned by the segment's share of the year on the rule's basis.** `CapContext` carries amounts and
   counts, not dates, so a cap whose input is itself for part of the year cannot be split correctly here.
   HRA's occupied periods are the node's concern (`W-067`).
4. **STATUTORY has nothing to evaluate.** No rule uses it, the rulebook names none, and "a rule that evaluates
   segments" has no shape.
5. **Package.** `rules.pack` already depends on `rules.temporal` (`RuleVersion`, `DateRange`). A
   `TemporallyApportionedCap` in `rules.temporal` that reads `RuleRow` would make the two depend on each
   other. No ArchUnit rule forbids that, but "dependencies point one way" (CLAUDE.md §4) does.

### Choices (recommended first)

- **C1 — scope.**
  - **(a) recommended: build it and route the four nodes through it.**
    - `CessNode` and `SalaryDeductionNode` call `apply(row, t, ctx)`.
    - `TaxByBasisNode` and `SurchargeNode` call `governingVersion(row, t)`. This returns the one governing
      version under LATEST or EARLIEST (or an unchanged year), and throws for PRORATE/STATUTORY, naming the
      rule and the node, because a ladder cannot be apportioned.
    - Every figure stays the same, since no shipped row changes mid-year.
  - **(b)** Build the class and tests only. The warning stays true, and the wiring is owed.
- **C2 — PRORATE_PER_SEGMENT:** each segment's version's cap applied to the context; the result apportioned by
  `row.prorationBasis().apportion(value, year, segment)`; the segments summed. `limitedBy` joins the segments'
  names in order. The Javadoc states finding 3's limit.
- **C3 — STATUTORY:** throws an `IllegalStateException` naming the rule and its combination rule ("not built;
  build it with the first rule that needs it"). A test proves it.
- **C4 — `RuleRow.prorationBasis`:**
  - `Optional<ProrationBasis>`, required iff PRORATE_PER_SEGMENT (the constructor refuses either mismatch, as
    `midYearCombinationRule` does).
  - JSON: `"prorationBasis": "DAYS" | "CALENDAR_MONTHS" | "COMPLETED_MONTHS"`.
  - No shipped row carries it, so no lock moves.
- **C5 — home and exception.**
  - **(a) recommended:** `rules/pack/TemporallyApportionedCap.java` (beside `RuleRow` and
    `MidYearCombination`), so dependencies still point one way. That corrects D-097's path again.
  - `rules/pack/UndeterminedApportionmentException.java` extends `RuntimeException` (like
    `NoRuleVersionException`), to be re-parented by `W-105`.
  - **(b)** `rules/temporal/`, accepting the package cycle.
