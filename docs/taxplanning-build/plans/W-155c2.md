## Plan for W-155c2 — which facts a retirement payment may carry, from its rows

**What this item is for (one sentence, in my own words):** `RetirementPayment`'s constructor decides, by
`RetirementEntry`, which facts each entry needs and refuses (`:50–65`). This item makes the node decide it from the
entry row instead: the bases its cap reads, its definition, and the bar rows. A row that starts or stops reading a
fact then changes what is required, with no Java edit (D-336 R6, D-339 C1a; audit P5).

**This plan raises C1 – C3. It changes no value and no pack file.**

### What I read (session 31, 2026-10-23)

- The WI row (W-155c2), D-339, `plans/W-155c.md` (the R6 reading), and `RetirementPayment` (115 lines):
  - `requireExactlyFor` four times, each with a `Set.of(RetirementEntry…)`: commuted value for
    `OTHER_EMPLOYER_COMMUTATION`; separation for `OTHER_GRATUITY`; leave figures for `OTHER_LEAVE_ENCASHMENT`; the
    statutory amount for `STATUTORY_GRATUITY` and `RETRENCHMENT`.
  - `:62`: arrears relief refused outside `VOLUNTARY_RETIREMENT`.
  - The commuted value must be positive. That is the fact's own consistency, not law, so it stays.
- **What each fact feeds, today:**
  - the separation → `AVERAGE_SALARY_BY_COMPLETED_YEARS`, and the leave figures → `LEAVE_SALARY_AT_CREDIT` and
    `AVERAGE_MONTHLY_SALARY` (`NotifiedRetirementLimits.context`, W-155c1);
  - the statutory amount → `AMOUNT_UNDER_STATUTE` (`RetirementNode.limited`);
  - the commuted value → the entry row's `CommutedPensionShare` (`RetirementNode.commutation`);
  - arrears relief → `retirement.arrears.relief.allowed`, read by `RET-BAR-ARREARS-RELIEF` (W-155b).
- **The rows:**
  - the bases are named inside the entry rows' caps (`RET-GRATUITY-OTHER`, `RET-LEAVE-ENCASHMENT-OTHER`,
    `RET-GRATUITY-STATUTORY`, `RET-RETRENCHMENT`), each a `LeastOf` of `PercentOfBase` / `Fixed` limbs;
  - `RET-COMMUTED-PENSION-OTHER` defines a `CommutedPensionShare`.
- **What a cap reads:** nothing lists it today. The nine shapes read `CapContext` as follows (`grep` of `ctx.`):
  - `PercentOfBase`, `SlabLadder`, `PercentOfBaseByLocation`, `PercentOfBaseByPopulation`: `base(base)`;
  - `AmountInExcess`: `base(amount)`, plus its threshold's;
  - `LeastOf`: its limbs';
  - `AggregateWithCeiling`: contributions, plus its sub-caps';
  - `PerUnitPerPeriod`: counts only;
  - `Fixed`: nothing.

  `Condition.isAboutItem` (`Condition.java:64`) is the precedent: a default method switching over a sealed family, so
  a new member does not compile until it says what it is.
- **Tests:** `RetirementPaymentTest` holds 8 refusals that move: `:42`, `:50`, `:58`, `:94`, `:102`, `:110`, `:133`,
  `:142`. `:75` (positive value) stays. `CapShapeTest` exists for the family. Only `taxengine` builds a
  `RetirementPayment` (`grep` of `taxplanning`: none), so no stored or API input changes.

### Choices (recommended first)

- **C1 — knowing which bases a cap reads:**
  - **(a) recommended:** `CapShape.amountsRead(): Set<BaseId>`, a default method with an exhaustive switch over the
    nine shapes (as `Condition.isAboutItem`). It names the ids looked up in `CapContext.bases` only; counts,
    locations and contributions are not amounts entered with a payment. No shape class is edited.
  - **(b)** the same switch inside the node. A tenth shape still fails to compile there, but the cap family's own
    question would then live outside it.
- **C2 — when arrears relief may be given:**
  - **(a) recommended:** where an `RS-RET-BAR` row would reach the payment if relief were allowed. This asks the same
    question the bar does, so the bar rows alone decide where the fact matters.
  - **(b)** where some bar row's conditions mention the fact (a walk over conditions). That holds even for a row
    that could never reach the entry.
- **C3 — where the check lives:**
  - **(a) recommended:** a new package-private `EntryFacts` in `node/`, which owns the mapping from fact to what it
    feeds (the three base ids, the definition, the bar fact) and `requireWhatTheRowReads(ctx, payment, row,
    version)`. `RetirementNode.payment` calls it after `requireFeeds` and before the regime test, so a payment is
    refused whatever the regime, as the constructor did. `NotifiedRetirementLimits` takes its base ids from it.
  - **(b)** inside `RetirementNode` (298 lines today), which would grow by ~50.

### The build (C1a, C2a, C3a)

1. **`CapShape.amountsRead()`**, plus a `CapShapeTest` case per shape (nine). The expected sets are read off each
   shape's `apply` by hand.
2. **`EntryFacts`:**
   - a separation is needed iff the row's cap reads `AVERAGE_SALARY_BY_COMPLETED_YEARS`;
   - leave figures iff it reads either leave base;
   - a statutory amount iff it reads `AMOUNT_UNDER_STATUTE`;
   - a commuted value iff the governing version's definition is a `CommutedPensionShare`;
   - arrears relief only where C2a holds.

   Each fact missing where needed, or given where not read, is refused, naming the row: "…; enter it" / "… it would
   be ignored, so it is refused", as today's words.
3. **`RetirementPayment`:** the four `requireExactlyFor` and `:62` go, with `requireExactlyFor` itself and the
   class note's sentence. The positive-value check stays.
4. **`RetirementNode`** calls it. **`NotifiedRetirementLimits`'s** three base constants move to `EntryFacts`, and
   `RetirementNode`'s `AMOUNT_UNDER_STATUTE` too, so each base id is named once.
5. **Tests:** the 8 refusals move from `RetirementPaymentTest` to `RetirementNodeTest`, as node runs with the same
   inputs. Each asserts the same fact word it does today ("commuted value", "separation", "leave", "statute",
   `GOVERNMENT_COMMUTATION`, `GOVERNMENT_LEAVE_ENCASHMENT`, `GOVERNMENT_GRATUITY`, "voluntary retirement" → the bar
   row's id), plus the entry row's id.
