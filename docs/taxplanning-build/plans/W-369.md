## Plan for W-369 — store a password by a targeted update, not a save

> Found by W-366b row 4 (session 115, 2026-11-22), planned and built in the same session. W-366 is paused (R13) until this ships as
> `m1.6.1`. Owner: "sure" to C1a (no data write) over C1b (rewrite every login's `_id`).

**What this item is for (one sentence, in my own words):** a re-keyed login can sign in on `m1.6` and change its password, because the
password is written by email and not by an `_id` whose stored type the entity does not match.

### What was found (evidence)

| | | Where |
|---|---|---|
| The failure | sign-in 500: `DuplicateKeyException` E11000 on `it-staging.user_details` index `user_email_idx`, from `SimpleMongoRepository.save` | staging `w366b/m16.log`, request 13d60643 |
| Staging's logins | 14 of 14 `_id` type `objectId`; fields `_class, _id, email, password, roles` (one with `last_signed_in_at`) | the owner's console, 2026-11-22 |
| Why | the m1.4 re-key inserted each login with `rekeyed.put("_id", new ObjectId())` | `git show m1.4:…/StoredFieldEncryption.java` |
| The mapping | `@MongoId private String id` — a login the app writes holds a **string** `_id`, and a save filters on the string | `UserDetail.java:24`; probe: an app-registered login's `_id` read back as `String` |
| Reproduced | throwaway integration test: an app-registered login signs in 200; one shaped as the re-key left it 500 with the same E11000 (test deleted) | session 115 |
| Also broken | `AuthService.changePassword`'s `userDetailsRepo.save` — the same miss, for every re-keyed login since m1.4 (staging and prod) | `AuthService.java:86` at HEAD before the fix |
| Not affected | registration (an insert of a new row), erasure (`deleteByEmail`), the sign-in record (`RegisteredUserDirectory.recordSignIn`, already a targeted update) | grep of `userDetailsRepo.save` / `UserDetailsRepository` |

### Decision (owner: "sure", C1a)

**C1a:** `RegisteredUserDirectory.storePassword(email, hash)`, a targeted `updateFirst` by email that refuses when no login matched. It is
used by `UserDetailsServiceImpl.updatePassword` (the sign-in rehash) and `AuthService.changePassword`. No data write. **C1b** (not
taken): rewrite every login's `_id` as a string, which would be a console write to every prod login.

**Five roles:**
- **Architect:** one write path for a stored password, by the key the data actually shares (the email).
- **PM:** sign-in on `m1.6.1` and change-password work for every login.
- **Senior engineer:** no save on a read-modify-write of a login; the miss is refused, not silent.

**Risks:** the `_id` type mismatch stays in the data. Any future code that saves a `UserDetail` read from such a row meets it again, and this
plan's evidence table is where to look.
