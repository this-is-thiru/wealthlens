**What is wrong today** (the review's probe, TY 2026-27): two `EQUITY` lots sold together on 2026-09-01, each for
₹60,00,000 on a cost of ₹20,00,000, and one ₹60,00,000 house. The engine charges **₹0.00**; measured as one sale, s.86(1)(i)
gives **₹40,00,000**. Had both lots been bought on one day, `portfolio` would have made one bucket and the engine
would already charge ₹40,00,000 — the figure turns on a bucketing detail the user cannot see.

### Choices (recommended first)

**C1 — how a claim that reaches several buckets is measured.**

- **(a) Recommended: together.** Every bucket of the claim's transfer date that the row reaches is one measure: their
  gains summed, their net considerations summed, the cap and the proportion applied once, and the exempt amount
  shared back to the buckets. Why: it gives the same figure however `portfolio` splits the sale — the figure it
  already gives when the lots share a key (row 3) — and it never counts the house's cost twice. Sharing the house's
  cost out to the buckets by net consideration first, then measuring each, gives the same figures (each bucket's
  ratio is then cost ÷ total net consideration), so that reading is not a separate option.
- (b) Refuse a claim that reaches more than one bucket. Honest and the smallest change, but it refuses the common
  case — one holding bought in instalments and sold at once — and the user has no way to make the claim fit.
- (c) Make the claim name its buckets (an acquisition date, or the lots). Rejected: the bucket is `portfolio`'s
  internal grouping, not something a user sees or enters, and the key has no stock code to name (row 3).

**C2 — which buckets join the measure.**

- **(a) Recommended: every bucket of that date the row reaches, gain or loss.** A lot sold at a loss in the same sale
  lowers the sale's gain and adds to its net consideration, exactly as it does when `portfolio` puts it in the same
  bucket — so the result again does not depend on the split. Where the buckets together show no gain, nothing is
  exempt.
- (b) Only the buckets with a gain — today's per-bucket guard (row 2, `:67`) carried over. It lets a loss lot stay
  outside the measure and then set off against what is left, which gives a larger exemption than the same sale as
  one bucket would (case 4 below: ₹0 charged under (b), ₹15,00,000 under (a) and as one bucket).

Short-term buckets, and anything else the row does not reach, never join: s.86(1) / s.54F(1) speak of a long-term
capital asset, and the row's term and asset conditions already say so.

### What I will build

1. **`ReinvestmentExemption`** — the one-bucket entry point becomes a list one:
   `static List<Money> chargeableGainsOf(NodeContext ctx, List<BucketGain> buckets, List<TraceLine> lines)`, the
   chargeable gain per bucket in the order given. For each distinct transfer date among `buckets`: the claim for it
   (still refusing two claims on one date — the existing test stays); where there is one, the row asked per bucket
   as today (`factsOf(bucket, term, claim)`); the buckets it reaches are the measure. One nested record,
   `BucketGain(CapitalGainsInput.Bucket bucket, CapitalGainsCharges.Gain gain, Term term)` — the facts the measure
   needs, already computed by the node.
   - Summed gain ≤ 0 → nothing exempt; an `EXEMPTION` line on each bucket with a gain, in = out, its reason saying
     the sale's buckets show no gain.
   - Otherwise the window as today (claim-level: outside it, nothing exempt, the same reason text), the cap as
     today, `exemptGain` on the summed gain and summed net consideration, then shared to the buckets with a gain in
     proportion to their gain, the last of them taking the remainder (case 6). A loss bucket is never written down.
   - One line per bucket with a gain: in = its gain, out = its chargeable gain. The reason is today's text; where the
     measure holds more than one bucket it adds "measured with the N buckets transferred on D: gain G against the
     net consideration NC", so the trace says why one bucket's figure depends on another's.
   - The governing row version is read per bucket as today; the measure uses the first bucket's definition. One row
     exists in `RS-CG-EXEMPTION` and it is `AT_MOST_ONE`; see "not doing".
2. **`CapitalGainsNode.evaluate`** — two passes: first charges → scope → term for every bucket into a
   `List<BucketGain>`; then `chargeableGainsOf` once; then STT → part → indexation per bucket with its chargeable

3. **Javadoc** — `ReinvestmentExemption`'s class comment (`:32-33`) and `HouseReinvestment`'s `@param transferDate`

### Risks or ambiguities

1. **The Act's unit is "the original asset"; the engine's is the bucket.** C1a measures every reached bucket of one
   date together, which is right for one holding sold in lots. Two different companies' shares sold on one day and
   one house claimed for both are also measured together — `portfolio` already merges them when their keys match,
   so this does not create the ambiguity, but it does not resolve it either. A taxpayer who wants the house against
   one sale only cannot say so; that needs the claim to name an asset, which needs a stock code in the bucket — its
   own item if wanted.
2. **C2a lowers some exemptions.** A sale with a losing lot is measured on the net; the per-lot answer it replaces
   was larger. This is the figure a one-bucket sale already gets, and it is the reading the plan recommends, but it
   is a reading — C2b keeps today's per-bucket guard.
3. **The node's trace order changes.** Exemption lines now follow every bucket's term line instead of sitting
   between each bucket's term and STT lines. No test pins the order (rows 6, 7); a reader of a trace sees the
   exemption after the terms.
4. **Rounding.** The remainder goes to the last bucket with a gain in input order, so which bucket carries the paisa
   depends on the order `portfolio` lists them — stable, but arbitrary. The total is exact.
