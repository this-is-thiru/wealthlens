## Plan for W-267 — the commit gate stops running the unit tier

**What this item is for (one sentence, in my own words):** a commit from a Claude Code session no longer runs the unit
tests on the owner's laptop, because the pipeline runs them; the gate keeps only the fast checks.

**Where this comes from:** owner, 2026-11-11, twice during commits: "no need to run unit tire here, we can check on
pipeline"; then, on my note that the gate has no skip option, a message cut off at "keep ski". I read that as "add the
skip". **If you meant something else, say so — nothing is built.**

**Findings (each read this session, 2026-11-11):**

1. `.claude/hooks/pre-commit-gate.sh` runs before every Bash command containing `git commit` (`.claude/settings.json:9`,
   timeout 600 s). It skips when the working tree matches the last green record, else runs `unit-tier.sh -q` and blocks
   the commit on failure (`pre-commit-gate.sh:22-36`).
2. `unit-tier.sh` runs `./mvnw test -pl backend -Punit` at low priority and records the tree it passed on (W-260, D-522).
   That one call is also what runs Checkstyle and `spotless:check`, in Maven's `validate` phase
   (`pre-commit-gate.sh:2-4`; D-045).
3. The gate's behaviour is tested by `.claude/hooks/unit-tier-stamp-test.sh` (10 cases, D-522) and described at
   `CLAUDE.md:123`.
4. CI runs `./mvnw clean spotless:check test verify` (`.github/workflows/cicd.yaml:45`), so tests, Checkstyle, Spotless
   and the coverage gates are all checked there.
5. A doc-only close-out edit changes the tree, so today the unit tier runs again at the item commit even when it was
   green minutes before (it did for W-263 and W-262).

**Choices for the owner:**

- **C1 — what the gate does at a commit.**
  - **C1a (recommended):** run Maven's `validate` only — Checkstyle and `spotless:check`, no compile, no tests. A
    formatting or standards violation still blocks the commit locally; a failing test is found by the pipeline.
    *Unverified:* how long `validate` takes here; I will time it before building and report it.
  - C1b: run nothing; the gate is removed. Fastest, but an unformatted commit goes red on the pipeline for a reason a
    few seconds locally would have caught.
  - C1c: keep the unit tier, but skip it when the commit command carries a marker (for example
    `SKIP_UNIT_TIER=1 git commit …`). Keeps the default strict; every skip is visible in the command.
- **C2 — the green-tree record (W-260).**
  - **C2a (recommended, with C1a or C1b):** remove `unit-tier.sh`'s record, `working-tree.sh`'s stamp and
    `unit-tier-stamp-test.sh`, since nothing reads the record any more; `unit-tier.sh` stays as the low-priority way to
    run the tier by hand.
  - C2b: keep them unused. Rejected by CLAUDE.md §2 "No dead weight" unless you want them.
- **C3 — order.** Before W-264a (recommended: it removes a wait from every commit after it), or after.

**Files I will modify (C1a, C2a):**

- `.claude/hooks/unit-tier.sh` — the record removed; the low-priority run stays.

**Files I will create:** `.claude/hooks/pre-commit-gate-test.sh` — the gate against a stand-in `mvnw`: a non-commit

**How I will verify:** the new gate test (each case by its exit code and the stand-in's recorded goals); a probe —

**Post-deployment actions (R15):** none. A developer tool; nothing reaches a database.

**Five roles:**
- **Architect:** the pipeline becomes the only place tests gate a commit; the local gate keeps the checks that cost
  seconds. One mechanism (the record) is removed with its reason.
- **Product manager:** nothing changes for a user of the application. For you: commits stop taking a minute or more
  and stop spiking the CPU; a red test shows on the pipeline instead of blocking the commit.
- **Senior engineer:** no dead scripts left; the gate script gets shorter.
- **Automation tester:** the gate is tested against a stand-in, as W-260's was; one probe.
- **Manual tester:** edit a Java file to break formatting, commit → blocked with Spotless's message; fix, commit →
  goes through without a test run.
