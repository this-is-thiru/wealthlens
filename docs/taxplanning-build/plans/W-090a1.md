## Plan for W-090a1 — Declarations, the engine

**What this item is for (one sentence, in my own words):** the engine can hold a person's answers to questions it
cannot compute (yes, no, or an amount), and a rule can test them through two new conditions, with every question
defined as a row in the pack and an unanswered or unknown question refused by name, never read as "no".

  in `rules.id`, a named interface (`rules/id/package-info.java:6`), so W-090a2 can use it. The rules side reads the
  answers as plain values, as `ItemFacts` does (`rules/condition/ItemFacts.java:19` – `20`).

**Choices for the owner:**

  approved. The two existing uses are private, nested, and about the pack, never the person. C1b: rename to

- **C2a (recommended): no `clause` field on a row.** The r.164 clause goes in `provenance.sourceDescription`, as every

**Files I will create** (under `backend/src/main/java/com/thiru/wealthlens/taxengine/` unless stated):
- `rules/id/DeclarationCode.java`: one question, such as `DIRECTOR_IN_COMPANY`. Same pattern as `ComponentCode`
  (`^[A-Z][A-Z0-9_]{1,63}$`).
- `rules/declaration/AnswerKind.java`: `YES_NO` or `AMOUNT`.
- `rules/declaration/DeclarationDefinition.java`: one catalogue row: code, question, answer kind, validity and
  provenance.
- `rules/condition/Declarations.java`: the answers as a condition reads them: yes/no by code and amount by code.
  `isYes(code)` and `amount(code)` throw with the code named when it has no answer. `NONE` means no answers.
- `rules/condition/Declared.java`: holds when the answer is yes.
- `rules/condition/DeclaredAmountAbove.java`: holds when the declared amount is greater than the limit, so an amount
  equal to the limit does not hold. This matches the law's "exceeding". The law's "does not exceed" is
  `Not(DeclaredAmountAbove)`.
- `input/Declaration.java`: a sealed answer, either `YesNo(boolean yes)` or `Amount(Money amount)`. A negative amount
  is refused. A question that is not answered is absent from the map, which is the third state.
- `rules/validate/DeclarationReferences.java`, run at build time:
  - Every `Declared` or `DeclaredAmountAbove` condition is checked, inside compositions too, in every rule version
    and every condition set.
  - Each must name a code in `pack.declarations()` with the matching kind (`Declared` with `YES_NO`,
    `DeclaredAmountAbove` with `AMOUNT`).
- `src/test/resources/rulepacks-synthetic/timeline/exec/declarations/`: three synthetic rows:
  - `SYNTHETIC_YES_NO`, valid from 2099.
  - `SYNTHETIC_AMOUNT`, valid from 2099.
  - `SYNTHETIC_LATER`, valid only from 2101-04-01, to prove a row is projected into a year only while it is valid.
- Tests: `DeclaredTest`, `DeclaredAmountAboveTest`, `DeclarationsTest`, `DeclarationTest`, `DeclarationReferencesTest`,
  and `DeclarationProjectionTest` (synthetic: read, compile and assemble, by year).

**Five roles:**
- Architect:
  - No module boundary changes. `rules` stays free of `input` (F1).
  - Facts, not rules: a declaration is the person's answer, never "ITR-1 eligible", and a question is a row of
    data.
  - Unscoped effects: the rules side holds answers only for codes in the year's catalogue, so a stray code cannot
    match anything quietly.
- Product manager: nothing changes for users yet. No shipped row exists and the draft has no field, so every figure is
  unchanged. Old clients and stored drafts are unaffected, because the declarations map is empty for both.
- Senior engineer:
  - Every new type has a caller in this item: the conditions read `Declarations`, `NodeContext` builds it, and
    `PackValidator` reads the definitions.
  - `FilingFacts.declarations` is filled only by tests until W-090a2. That is the split D-517 approved.
  - Methods stay within 60 lines and 7 parameters.
- Automation tester, with expected values worked out by hand:
  - `Declared`: yes holds, no fails, and an unanswered code throws naming it.
  - `DeclaredAmountAbove` with a limit of ₹1,000: ₹1,000 does not hold (equal is not above), ₹1,100 holds,
    unanswered throws, and a yes/no answer to an amount code is refused.
  - `NodeContext`: an entered code the pack lacks is refused, naming it.
  - Pack: a reference to an unknown code, or a kind mismatch, is a validator problem.
  - The 2101 row is absent from 2099-00 and present in 2101-02.
  - Probe: delete the kind check in `DeclarationReferences`, see the mismatch test fail, then revert byte for byte.
- Manual tester: there is nothing for a user to call in this item, because no endpoint changes. The owner's check
  is to run the unit tier and confirm that the shipped figures are unchanged (no golden test moves). W-090a2 brings
  the curl.
