**Corrected after a full read of all 31** (the owner asked for this before any DDL was written): three moved from the
first bucket to the second — `corporate_action`, `tax_draft_revisions`, `tax_filing_drafts` — each because a single
embedded field (`DemergerDetail`, `WorkbookImport`, `DraftStaleness`) turned out to hold a list of its own, which a
grep for top-level `List`/`Map` fields on the `@Document` class cannot see. The 25/12 split below is what was actually
read, not what the survey implied. This split is still narrower than counting embedded-`List`/`Map` fields naively
would suggest: a `List` of plain text or of one flat embeddable is a shape already proved; only a `Map` (dynamic
keys) or more than one level of nesting is genuinely new, and every one of those twelve collections sits inside a
module whose own port item (W-337d, e or f) was always going to read its model classes in full to port the code
around it — designing their tables today, before that reading happens, would be the same mistake the owner's own
scope call on W-337a avoided (a paper design that a real test later proves wrong).

### Decisions (for approval with this plan)

- **C1 — scope. C1a (recommended):** this item lays out the Flyway folder structure (one per module, D-929 (3)) and
  writes baseline DDL for the 31-collection bucket only; the other 9 (plus GridFS) are designed inside W-337d/e/f,
  each adding its own migration file to its own folder when it is built. **C1b:** design and write DDL for all 40 now,
  including the three genuinely new shapes — risks a repeat of W-337a's own lesson (the lazy-fetch, null-handling and
  transaction-boundary mistakes that only running a real test caught) on a map structure nobody has mapped to Postgres
  here yet.
- **C2 — primary keys.** **C2a (recommended, carries W-337a):** every table's `id` stays a caller-assigned `VARCHAR`,
  matching Mongo's opaque string id and the already-proven `UserDetailJpa`/`RefreshTokenJpa`/`InsuranceJpa` shape — no
  database-generated id, no revisit of the `GenerationType.UUID` question W-337a avoided by not needing it. **C2b:** a
  database-generated id (`GenerationType.UUID` or a sequence) for the 25 new tables — untested here, and inconsistent
  with the three tables already built.
- **C3 — one Flyway version sequence or one per module.** **C3a (recommended):** one schema-history table
  (`flyway_schema_history`), version numbers assigned in build order across all folders (`V2__corporate.sql`,
  `V3__shared.sql`, …, continuing from W-337a's `V1__auth_and_insurance.sql`); the **folders** are per module (D-929
  (3)'s point — a later move to per-module schemas, W-399, moves folders, not individual files), not separate
  migration histories. **C3b:** a separate Flyway configuration and history table per module — more moving parts,
  and W-399 (separate schemas) is explicitly "not now" (D-929).
