### Choices (recommended first)

**C1: the endpoint.** **(a) Recommended:** `POST /tax/user/{email}/drafts/{draftId}/optimise`, body
`{movable: [codes], residual: code, cashFloor: "rupees", verificationBreadth?: n}`, beside `compare-regimes` and
like it: read-only, nothing stored, the year's default regime as the start (the regime is chosen inside anyway,
A2.1). Engine refusals come back as 400 through `ControllerAdviser`. (b) A stored optimisation with a receipt: no
caller needs it, and it adds a collection, a retention row and a runbook entry.

**C2: the config key.** **(a) Recommended:** `app.tax.optimiser.exhaustive-breadth: 6` in all three yamls, bound by
an `OptimiserSettings` record. The request may name a breadth up to it; above it is refused with a 400 naming the
limit, so a request cannot undo O8's knob. The design's `app.taxplanning.` prefix would be a second word for the
same concept (CLAUDE.md §3); I record the rename in O10. (b) The design's literal key. (c) Use the config value only,
with no request field.

**C3: the facts per change.** A2.6 needs each change's rules and cash nature, and `taxplanning` cannot read the pack.
**(a) Recommended:** `Optimisation.Change` also publishes the component's pack facts: `kind`, `cashNature` and
`feedsInto` rule ids (facts, not rules, §4). The view adds `cashImpact` = −(suggested − current) for a `NON_CASH`
component and nil for a `CASH` one: a fact read off the pack, with no law in it. A2.6's `ruleIds` are the rules fed.
Its prose `conditions` (the scheme requirement, the cap headroom) have no fact behind them today, and the headroom is
A3.1's gap analysis. The view gives `conditions` as the rule ids only. `provisionsCited` (`TaxCalculator.java:171`)
spans every year and version, so it is not a source for one year's sections. (b) Expose `rules.component` as a named interface.
That widens a CLOSED module's surface for one caller.

**C4: liquidity and `hrSupportLikelihood`.** Neither has a source in the current code.
- **(a) Recommended: leave both out of W-238b and place them.** Liquidity, for example "locked until retirement", is
  law (the NPS and fund withdrawal terms). A label for it in Java breaks §4, so it belongs in the pack as a fact per
  component: **W-238e**. HR support is a product judgement with no legal source. It needs a table keyed by
  `ComponentCode`, with values the owner gives (C10: reported, never a veto): **W-238f**. Placed after W-238d, before
  the one deploy.
- (b) You give the HR-support values now, and I add them in W-238b as `taxplanning` product data. Liquidity still
  goes to W-238e.
- (c) Copy the legacy values: they use a different vocabulary, and W-159 deletes them. Not offered.

**C5: README.** **(a) Recommended:** no README change. It has no tax-planning section, and adding one here is
scope. The endpoint goes into api-collection (a new `Optimise a Draft.yml`) and `02-TECH-SPEC.md:99`. (b) Start a
tax-planning section in the README with this endpoint.
