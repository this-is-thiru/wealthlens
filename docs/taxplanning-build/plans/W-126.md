## Plan for W-126 — `Form130Parser`, layer L1 (structural)

> **Approved as recommended — C1a – C4a** (owner, session 102, 2026-11-16). Split recorded (D-729). Every path below was read on 2026-11-16 at `0b0a4eea`; grep each again before
> relying on it. No probe: nothing shared changes until C1 is chosen.

**What this item is for (one sentence, in my own words):** the first real parser — given a Form No. 130 PDF, find its
parts by their headings and each row by its statutory label, and return each row's text with its page and position, so
W-127 can read the numbers and W-128 can check the form's own arithmetic.

### What the design says

- `DR 06` G5.1 (`06-algorithms.md:472` – `:489`): "structural first, positional never". L1 extracts the text **with
  positions**, finds Part A / B / C "by their heading text", and rows "by their statutory label"; confidence 0.95+ on an
  exact label match. L2 (W-127) takes the number on the row; L3 (W-127) infers a missing cell from the form's sums.
- `01-rulebook.md` R21 (`:1498` – `:1570`), source **S4** (Income-tax Rules, 2026, G.S.R. 198(E), 20-03-2026,
  CG-DL-E-20032026-271092): Part A (`DOC-F130-A-001`), Part B (`DOC-F130-B-001`), Part C Annexure-I row A and rows
  1(a) – 21 (`DOC-F130-ROWS-001`), Annexure-II (`DOC-F130-C-B`). **The rulebook paraphrases the rows** ("Salary as
  per s.16"); the parser needs the **exact printed label**, which only the Gazette copy gives.
- `DOC-F130-PREFILL-001` (Note 8): layout varies by issuing system — hence labels, never coordinates.
- `DR 13` rows 71 – 72: a password or a scan without text is a `FAILED` reading with its reason (W-125's contract).

### Findings

1. **The row labels are law.** Form No. 130 is prescribed by the Rules; an amendment can change its text. CLAUDE.md §4:
   legal text and lists are tax-year-versioned data, never Java constants. Today the packs hold no `DOC-F130-*` row
   (`grep -rl DOC-F130 backend/src/main/resources/rulepacks` finds none), and `taxplanning` reads the packs only
   through `TaxCalculator` (`taxengine` is closed, D-048).
2. **The PDF library is already here.** `taxplanning/gazette/GazetteMatcher.java:3` – `:4` reads Gazette PDFs with
   iText 5 (`com.itextpdf.text.pdf.PdfReader`, `parser.PdfTextExtractor`; `backend/pom.xml:69` – `:70`). Its
   `parser` package also yields each text chunk with its page position, which L1 needs. No new dependency.
3. **No real Form No. 130 exists yet.** It certifies a whole tax year's salary; TY 2026-27 (the first year under the
   Rules, 2026) ends on 31-03-2027. Every fixture is therefore built from the Gazette's form text.
4. **The amendment chain.** Rules 2026 amendments are known to 12-11-2026
   (`sources/2026-11-15-evidence-of-claims.md` E4: G.S.R. 241, 286 (corrigendum), 646, 656, 822, 830, 871, 901, 961(E)).
   Which of them touch Form No. 130 has not been checked; the build checks each before using a label.
5. **Size.** Data from the Gazette, a pack layer (if C1a), and a parser with fixtures is more than one item (§7).

### Choices for the owner (recommended first)

- **C1 — where Form No. 130's layout lives** (each part's heading, each row's id, printed label and what it maps to,
  with its Gazette provenance):
  - **(a) in the pack**, a new layer `forms/certificates/` keyed by form, versioned by tax year like every rule, read
    through a new `TaxCalculator` method. The same layer can later say which certificate a year prescribes (so the
    upload can refuse a Form 16 for TY 2026-27 from data, W-131). Cost: a pack schema addition, its validator, a relock,
    and the test locks a new layer moves (11 last time, W-117).
  - (b) a `taxplanning` resource (`data/tax-planning/forms/form-130.json`), read at start like `HrSupportTable` —
    simpler, but law outside the packs, the pattern W-159 just removed.
- **C2 — the split** (finding 5):
  - **(a) W-126a — Form No. 130's layout as data:** read Part A's fields, the part headings and Annexure-I's row A and
    rows 1(a) – 21 verbatim from the Gazette copy of S4, check the amendment chain for any change to the form, record
    the source, and add them per C1 with their accessor and validator tests. **W-126b — the L1 parser:** text with
    positions (iText 5), the parts by heading, the rows by label, each row's text, page and box as an
    `ExtractedField` with no value yet (L2 is W-127), confidence 0.95 on an exact label match; `FAILED` with a reason
    for a password, no text layer or a broken file.
  - (b) one item.
- **C3 — what L1 covers now:**
  - **(a) Part A's identifying fields and Part C Annexure-I** (row A and rows 1(a) – 21) — what a draft can be seeded
    from. **Part B's quarterly table and Annexure-II** (the specified senior citizen's) placed as a new row, W-126c, after
    W-127.
  - (b) every part now.
- **C4 — the fixtures** (finding 3):
  - **(a) PDFs rendered in the test from the Gazette's form text** with the renderer the repo already uses for its own PDF
    (`ComputationReportService`, flying-saucer); one per case: labels as printed, labels re-flowed across lines, a
    password, no text layer. Replaced or joined by a real certificate once one exists (a placed row).
  - (b) wait for a real certificate (mid-2027).
