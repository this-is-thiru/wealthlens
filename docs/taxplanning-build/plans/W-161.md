## Plan for W-161 — the April – March year in one place

**What this item is for (one sentence, in my own words):** the financial year — 1 April to 31 March, labelled
`2025-2026` — is worked out by hand in seven places outside the engine, and again inside it by `TaxYearId`; this item
puts it in one type, so the boundary is stated once (D-315; audit T2; N2).

**Small to medium: one new `shared` type, about ten call sites, one test class moved to the type. No stored data or
API change: every label stays the same string.**

### What I read (session 35, 2026-10-25)

- W-161's row; the audit's T2 row (`reviews/2026-10-21-law-in-code-audit.md:172`); D-269 (`TaxYearId.containing`,
  the engine's one derivation); `TaxYearId` (whole); `TLocalDate.financialYear` (`:57–62`); the module dependencies
  (`shared` → `portfolio`; `taxengine` → `shared`; `portfolio` → `shared`, `brokercharges`, …).
- **Every place the April – March year is derived outside the engine** (grep for `financialYear(`, `Month.APRIL`,
  `MARCH`, `, 4, 1)` and `, 3, 31)`):

  | Place | What it does |
  |---|---|
  | `TLocalDate.financialYear` | date → `"2025-2026"`, by `month <= MARCH` |
  | 7 callers of it | `CapitalGainsAdapter:39`, `TradeOutcomeRecorder:141`, `TradeMatchingService:204`, `ProfitAndLossService:239`, `PortfolioService:783`, `ProfitAndLossV2Backfill:88`, `TradeOutcomeFinancialYearMigration:55` |
  | `CapitalGainsSummaryService:48`, `:62–64` | parses `"2025-2026"` itself, then builds the window as 31 Mar – 1 Apr (exclusive) |
  | `ProfitAndLossSplitReshape` (`FINANCIAL_YEAR`, `:131`) | parses the label again and builds 1 Apr – 31 Mar — **a copy I added in W-160d3** |
  | `YearlyChargeSummary:42` | orders months from `Month.APRIL` |

  The audit counted 8 callers. One of its 8 is now a Javadoc mention, and W-160d3 and W-172 added two derivations
  after the audit was written.
- **Why not `TaxYearId` for all of them:**
  - `portfolio` and `brokercharges` would need `taxengine :: id`;
  - `taxengine` may depend on `shared`, and `shared` depends on `portfolio`;
  - so the moment the engine imports anything from `shared`, that closes a cycle `ApplicationModules.verify()` refuses
    (the same constraint `plans/W-160.md` met);
  - and `portfolio` would then be reading a tax-side type to label its own records, against D-362's direction.
- **The engine today imports nothing from `shared`** (grep). Its `rules` vocabulary is pure `java.time`.

### Choices (recommended first)

- **C1 — the one place:**
  - **(a) recommended:** a `shared` type, `shared/util/time/FinancialYear(int startYear)`:
    - `containing(LocalDate)`, `parse(String)` (refuses anything but `2025-2026`), `startsOn()`, `endsOn()`;
    - `label()`, giving `"2025-2026"`, the stored form;
    - `positionOf(Month)` (April 0 … March 11).
    Every derivation in the table uses it, `TLocalDate.financialYear` goes, and `TaxYearId` stays as it is. The
    boundary is then stated twice: once for the engine, once for everything else. That is the cost of the engine
    staying free of `shared`.
  - **(b)** the same type, with `TaxYearId.startsOn()` / `endsOn()` / `containing` delegating to it. One statement
    repo-wide, but the engine's `rules` vocabulary then imports `shared`. It would be its first import from any
    other module, and the first step of the cycle above.
  - **(c)** keep `TLocalDate.financialYear` and add `parse` / `window` beside it. Fewest changes, but it is a static
    helper, not a type a year can be held in.
- **C2 — `TradeOutcomeFinancialYearMigration`:** it is removed after its prod run (W-149).
  - **(a) recommended:** switch its one call too, so nothing is left calling the removed method.
  - **(b)** leave it for W-149. It would then keep `TLocalDate.financialYear` alive.
