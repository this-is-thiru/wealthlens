## Plan for W-244 — eligibility condition sets in the timeline

**For:** a regime's eligibility (`RegimeSpec.eligibility`, the s.205(2) pattern) can be written as timeline data,
versioned by year, so a regime with conditions is a data change (W-146 F3).

### What I read (session 49)

- **The gap:** `RulePackCompiler.compile` always writes `"conditionSets": []` into `law/regimes.json`
  (`rules/timeline/RulePackCompiler.java:79`); `TimelineReader` knows no directory for them (`TimelineReader.java:59`).
- **What already reads them:** `RegistryJson.conditionSets` parses `{id, displayName, conditions, basis, provenance}`
  (`rules/json/RegistryJson.java:124` – `147`) into `ConditionSet` (`rules/pack/ConditionSet.java`); `RegimeOffers` bars
  a regime whose set has an unmet condition, naming it (`election/RegimeOffers.java:73` – `81`); `PackValidator` refuses
  an unknown set id (`:224`) and counts each set's `basis` as a reached row (`:110`, `:156`).
- **The pattern to mirror:** disallowance sets — one file per set under `law/disallowances/`, each with `versions`
  `{validity, …}`, overlap refused, the year's version projected into the pack (`DisallowanceSetVersions`, D-165).
- **Design:** `DR 10` sketches one unversioned `conditions.json` (`10-extensibility.md:212`); `DR 17` step 4 *"Add or
  reuse a `ConditionSet`"* is data (`17-regime-lifecycle.md:278`).
- **A second gap, found reading `RegimeOffers`:** eligibility is evaluated before any computation, on a
  `ConditionContext` with no node values (`pipeline/NodeContext.java:344`); `IncomeAtMost.holds` reads `valueOf(node)`,
  which throws when the value is absent (`ConditionContext.java:119` – `125`). So E8's *"total income below a
  threshold"* cannot be evaluated even once it can be written.
- **No shipped regime names an eligibility set** (both `law/regimes/*.json`: `"eligibility": []`), so the compiled
  `law/regimes.json` of both shipped years is unchanged and **no relock** is needed.
- **Erratum due:** W-244's row cites "I7"; I7 is *"every `ComponentCode` a rule references exists"*
  (`02-TECH-SPEC.md:226`), not this.

### Choices (recommended first)

**C1 — where a condition set lives.** (a) **`law/condition-sets/<ID>.json`, one file per set with `versions`
`{validity, displayName, conditions, basis, provenance}`**, as disallowance sets — a threshold that changes by year is a
new version, not a code change (facts, not rules). (b) One unversioned `law/conditions.json` as `DR 10` sketched — a
changed threshold would overwrite earlier years' law.

**C2 — the code.** (a) **Generalise `DisallowanceSetVersions` into one versioned-set reader serving both kinds**
(year projection, overlap refusal, per-version parse), so the two kinds of set cannot drift. (b) A parallel
`ConditionSetVersions` — about 70 duplicated lines.

**C3 — income-based eligibility.** (a) **Out of scope; place W-246** (eligibility that reads a computed income: offers
evaluated after computing under the regime), and an erratum to E8 so `SYN_FLAT`'s condition is one decidable before
computing — e.g. *no income under the head "profits and gains of business or profession"* (`HasIncomeUnderHead`
negated, as s.202(4)'s own binding uses). (b) Build it here — an election-time computation per regime, a design of its
own.

### Build (C1a – C3a)
1. `TimelineReader`: directory `law/condition-sets`, each file named for its id, every version read on load.
2. The versioned-set reader (C2a) serving `law/disallowances` and `law/condition-sets`; `Timeline` carries
   `conditionSetSources`; `RulePackCompiler` writes the year's versions into `conditionSets`.
3. Tests (`RulePackCompilerTest`, on a copy of the shipped timeline as its tests do):

   - `compile_whenTheShippedTimelineIsCompiled_holdsNoConditionSets` — the shipped law is unchanged.
   And one through the offers: a regime naming a set *"resident"* is barred for a non-resident with the condition
   named, available for a resident (`RegimeOffersTest`, built from the compiled copy).
4. Rows: W-246 placed; E8 erratum (C3a); W-244's I7 erratum.
