### Findings

1. **The graph cannot prove which nodes an input change reaches.** 39 files under `taxengine/node` read
   `EngineInputs` directly; none of those reads is a graph edge. That includes helpers like `LeaveTravelExemption` and
   cross-node statics like `OtherSourcesNode.dividendInterest`, which `SurchargeNode` calls. B5's
   `delta.affectedNodes()` has nothing to read it from.
   - A memo built today would rest on a hand-written map from inputs to nodes, which is exactly the unproven reuse
     the row forbids.
   - A wrong entry gives a silently stale number (CLAUDE.md standard 2; `D-NOSILENT`).
2. **A regime choice changes the `RegimeSpec`,** which every node reads through `ctx.inRegime` and `ctx.regime()`.
   So the regime election, the main case in W-084a, dirties everything. It would gain nothing even with input edges.
3. **No current caller needs it.** B5's caller is the F14 optimiser, which is Tier Next and has no item. The election
   resolver prices a handful of choices at a few milliseconds each. W-084a's product is regimes × house sets ×
   set-off orders. Even 2 × 7 × 6 = 84 whole runs at the measured ~3 ms is about 0.25 s. CLAUDE.md standard 2: no
   speculative code.
4. **Making the proof possible is a different, larger item.**
   - Every node would declare the `EngineInputs` parts it reads, as `rules()` declares rows.
   - `NodeContext` would enforce the declaration, which means a scoped inputs view.
   - About 25 nodes and their helpers would change, plus the runner itself.

   That is well over §7's 300 lines.
