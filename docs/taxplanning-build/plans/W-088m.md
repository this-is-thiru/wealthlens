## Plan for W-088m — rules chosen by facts in data, not by Java (split proposal)

**What this item is for (one sentence):** make which rule applies to which fact a matter of rule data. Then a new
regime, table column, entry kind or rate is added as rows, with no Java change (review E1, D-250).

**This plan proposes a split (§7: mis-sized). Approving it places W-088m1–m3 and writes W-088m1's plan; nothing is
built.**

### What I read (session 22, 2026-10-19)

- **How a node reaches a rule:**
  - `ComputationNode.rules()` returns a Java `Set<RuleId>`.
  - `NodeContext.rule(id)` (`pipeline/NodeContext.java:185`) refuses an id the node did not declare, because
    reachability (invariant I3) is computed from those sets.
- **Selection by regime is already data:**
  - Each version carries `RegimeApplicability` and `conditions`.
  - Nodes pick the one row that applies and refuse when none or several do:
    - `TaxByBasisNode.java:204–214` (`regime().rateTable()` plus conditional ladders);
    - `SalaryDeductionNode:193`, `ChapterEightNode:363`, `OtherSourcesNode:508`, `SurchargeNode:259`.
  - **But the candidates are a Java list.** Examples: `TaxByBasisNode.LADDERS` (`:71`), `SurchargeRows` per regime
    (`SurchargeNode:108`). A new regime's row needs a code edit to be seen at all.
- **Selection by item is Java.** Six maps from a category to a rule:
  - `MotorCarPerquisite.PARTLY` / `OWN_RUNNING` (`:51`, by `CarEngine`);
  - `PerquisiteNode.RULE_FOR_PROVIDER` (`:67`, by `AccommodationProvider`);
  - `RetirementNode.RULE_FOR_ENTRY` (`:57`) and `NotifiedRetirementLimits.AGGREGATE_FOR_ENTRY` (`:46`), by
    `RetirementEntry`;
  - `AssetPerquisite.WEAR_AND_TEAR` (`:43`, by `TransferredAssetKind`);
  - `TaxByBasisNode.SPECIAL_RATES` (`:79`, by `CapitalGainsPart`).
- **Conditions cannot test an item.** `Condition` (`rules/condition/Condition.java`) offers residence, age, person
  type, disability, income bands, heads, components, evidence and payment mode. Its `ConditionContext` is about the
  person; nothing describes the car, house or entry being computed.
- **The pack's shape:** 178 rule files, each with `ruleId`, `axis`, `midYearCombination`, `versions`,
  `headProvenance` and `_note`. Locks: `2025-26.lock.json`, `2026-27.lock.json`. The regime files name their
  `rateTable`.

### Proposed split (C0)

| Row | What | Why separate |
|---|---|---|
| **W-088m1** | **Rule families.** Each rule row names its `family`. A family file (`law/families/*.json`) states the family's selection: `EXACTLY_ONE` (refuse none or several), `ALL_THAT_APPLY`, or `FIRST_THAT_APPLIES` in a stated order. A node declares the families it evaluates, and `NodeContext.family(id)` returns the applicable rows, chosen by the existing regime applicability and conditions. Reachability (I3) counts family members. The validator refuses a family no node reads, and a row in no family that no node names. The regime-and-person sites move to families (ladders, surcharge, rebate, standard deduction, employer pension, family pension), and every other node's `rules()` set becomes a family declaration. **Behaviour unchanged:** golden cases identical; relocked. | Pure dispatch change, provable by unchanged results |
| **W-088m2** | **Conditions on the item.** The condition algebra gains item facts: a typed fact map the node supplies for the item it computes, as categorical codes and quantities, with conditions `ItemFactIs`, `ItemFactAtMost` and `ItemFactAtLeast`. The six category → rule maps become families whose rows state their item conditions. | New algebra and evaluation context; the dispatch rows change content |
| **W-088m3** | **The guard.** An ArchUnit rule: a node class reaches rules only through families (no `RuleIds.*` in `taxengine.node`, with a baseline that may only shrink, empty after m2). This stops the pattern returning. | Enforcement, after the migration |

**Then W-088n (raw facts):** `CarEngine` → capacity in cc plus electric; `PopulationBand` → population, with the
1.6-litre column and census bands as m2's item conditions. It stays its own row, after W-088m3, as placed.

### Choices (recommended first)

- **C0 — split:**
  - **(a) recommended:** W-088m1, m2, m3 as above, in that order, replacing W-088m's position.
  - **(b)** one item; it would cross the pack format, the algebra, every node and a relock at once.
- **C1 — where membership lives:**
  - **(a) recommended:** each row names its `family`, and the family file holds only the semantics. Adding a row is
    one file, and a row cannot silently belong to two families.
  - **(b)** the family file lists its members. That means two edits per new row, and the list can drift.
- **C2 — selection semantics:**
  - **(a) recommended:** declared per family in data (`EXACTLY_ONE`, `ALL_THAT_APPLY`, `FIRST_THAT_APPLIES` with an
    order). This covers today's sites: the ladders and standard deductions are exactly-one; additions such as Chapter
    VIII are all-that-apply.
  - **(b)** always exactly-one, with nodes combining. Rejected: the combining would move back into Java.

### How W-088m1 would be verified (detail in its own plan)

- **Every golden case and node test unchanged.** Unit and integration tiers green.
- **Relock:**
  - family membership is pack content, so both locks are recomputed, bumped once
    ([[rulepack-lock-recompute]]);
  - the diff must show only the family fields and the family files.
- **Bite probes:**
  - a row moved to a family no node reads is refused by the validator;
  - two rows applying in an `EXACTLY_ONE` family are refused at run time.

### What I am NOT doing

- Building any of it before the split is approved.
- Changing any figure, date or condition in the rule data.
- W-088n's raw facts (its own row).

### Risks or ambiguities

- **The family files are new pack content** under `law/`, so the pack compiler and the validator change.
- **Per-node declared rule sets feed the documented reachability report.** m1 must keep that report's meaning
  (unreachable = a family member no regime or condition can reach).
- **The trace names the applied row's id today.** Families must keep that (the row, not the family, goes in the
  trace), so receipts stay comparable.
