### Choices (recommended first)

**C1: use it or remove it.**
- **(a) Recommended: use it.** The runner runs each job as the job's own name (`auto-archive`, `staleness-sweep`,
  `retention-purge`, …, from each `name()`). A row then publishes a fact, "written by the retention purge",
  instead of a value that also covers any write nobody can account for. That makes runbook §2.0 / §2.2 look-ups
  and erasure audits answerable. The shape:
  - Replace the static `setSystemAuditor` / `clearSystemAuditor` with one instance method,
    `SecurityAuditorAware.runAs(String actor, Runnable work)`. It sets the thread-local, runs the work, and clears
    it in `finally`. A pooled scheduler thread can then never carry a job's name into a later write, which two
    separate static calls cannot guarantee.
  - `TaxJobRunner` gets the bean injected and calls `job.run(...)` inside `runAs(job.name(), …)`.
  - `taxplanning` already lists `auth` in `allowedDependencies`, so there is no module change.
- (b) Remove the thread-local and both methods. Job rows keep `"unknown"`. Less code, but a job's writes stay
  indistinguishable from a write with no known author.

**C2: `getAuditor()`.** It has no caller either.
- **(a) Recommended: remove it in this item.** It is the same finding in the same class (dead weight, CLAUDE.md §2).
- (b) Leave it, and place a row for it.

### Five roles

- **Architect:**
  - `taxplanning` → `auth` is already allowed, so there is no `allowedDependencies` change, and `ArchitectureTest`
    is unaffected (constructor injection, no repository from a controller).
  - Facts, not rules: the actor is a fact (which job wrote the row). No legal value is involved.
  - Wildcard effect: `runAs` affects only code inside it. Outside it, auditing is unchanged: the signed-in email,
    else `"unknown"`.
  - Seams touched: Spring Data auditing (`auditorAwareRef`) and the job runner. Since W-256, actors are stored
    through `SearchableIdentifier`, so a job's name is stored encrypted like any other actor (D-486 C2a).
- **Product:**
  - No response changes. The jobs write drafts, profile erasures and workspaces, and no API response exposes
    their `auditMetadata`. The `AuditMetadataDto` responses are for trades, assets, P&L and corporate actions,
    which no job writes.
  - Stored data: rows a job writes from now on carry the job's name. Rows already stamped `"unknown"` stay as
    they are, because no one can tell which of them a job wrote.
  - Docs: no api-collection or README change. In runbook §1.y (the background jobs, `:298-300`), I add one sentence saying a job's
    writes carry its name as `updatedBy` (§0.7 gives the stored form). That is a note, not an action.

### Risks

1. `runAs` on the main thread during `ApplicationReadyEvent`: it is cleared in `finally`, so nothing later in
   startup inherits it.
2. A job that ever ran on another thread inside `run` would lose the name. None does today: every job loops
   synchronously.
