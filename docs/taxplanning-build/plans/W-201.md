## Plan for W-201 — the `Export | Stocks - Long/Short` request, and its silent filter

**What this item is for (one sentence, in my own words):** a request in `api-collection` sends its filter under a key
the backend does not read, so it silently returns everything. The request is made to say what it does and to filter
as it claims, and the same fault is fixed wherever else it occurs.

**Source:** `03-WORK-ITEMS.md` W-201; `plans/W-193.md` C1; D-404.

**Board (R4):** `… W-193 D  W-201 ·  W-194 · …`. W-201 is the first open item. The resume check matched: last item
commit `1b2da384` (W-193), tree clean.

### What the probe showed (2026-10-30, a scratch integration test, deleted after the run, never committed)

Two assets were saved for one user, bought 2024-01-15 and 2025-01-15. The request's exact filter was posted to
`POST /portfolio/user/{email}/stocks/download`: `transaction_date GREATER_THAN 2024-06-22, isDateField true`.

| Key the filter was sent under | HTTP | Rows in the exported sheet |
|---|---|---|
| `"filters"` (as the request sends it) | 200 | **2**: the filter was silently ignored |
| `"queryFilters"` (the field `EntityExportRequest` has, `:15`) | 200 | **1**: the filter works |

So the backend accepts an unknown property without a word. No `spring.jackson` setting or mapper bean is
configured, so this is Spring Boot's auto-configured mapper.

### The same fault elsewhere in the collection

`"filters"` appears in three requests. Each posts to an endpoint whose body class has only `queryFilters`:

| Request | Endpoint | Body class | Key sent |
|---|---|---|---|
| `Portfolio/Export - Stocks - Long-Short.yml` | `POST …/stocks/download` | `EntityExportRequest` (`queryFilters`) | `filters`: ignored |
| `Complex Filters/Filter.yml` | `POST …/portfolio/user/:email/request2` | `BulkGetRequest` (`dateRange`, `queryFilters`) | `filters`: ignored |
| `Complex Filters/Assets more than 1 year.yml` | `POST …/request2` | `BulkGetRequest` | `filters`: ignored |

`Complex Filters/Transactions.yml` (`POST /transactions/user/:email`, `BulkGetRequest`) is not in the list: it sends
`queryFilters`.

### Choices (recommended first)

- **C1 — what `Export | Stocks - Long/Short` becomes:**
  - **(a) recommended:** a working date-filtered asset export, the collection's only export example with a date
    filter:
    - renamed `Export | Stocks - bought after a date`;
    - the key changed to `queryFilters`;
    - the filter itself unchanged (`transaction_date GREATER_THAN 2024-06-22`).
    - "Long/Short" is dropped because the term concept was removed (D-370): the date is a fact, the term was a
      label.
  - **(b)** Remove it as a duplicate of `Download | Portfolio`.
- **C2 — the two Complex Filters requests with the same fault:**
  - **(a) recommended:** fold them in here. Change only the key, `filters` → `queryFilters`, in both, so their filters
    take effect. Same defect, same one-word fix, same submodule commit.
  - **(b)** Place them as their own row.
- **C3 — the backend accepting unknown JSON properties silently** (the cause behind all three):
  - **(a) recommended:** place it as its own row, **W-202**, after W-201, as a decision for you: make request bodies
    refuse an unknown property with a 400, against CLAUDE.md's "Nothing silent". This is a behaviour change for every
    client. Any field a client still sends but the server no longer has would start failing. The clients are not
    surveyed here; W-202 does that. So it needs its own plan.
  - **(b)** No row. The collection fix is enough.
