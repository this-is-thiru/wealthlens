## Plan for W-084a — several elections resolved together

**What this item is for (one sentence):** price every combination of the choices the computation's elections offer
(regime, house specification, set-off order) and take the cheapest combination. Today each election is resolved
alone, and that is not jointly optimal (D-230: the regime changes what a house choice is worth). Per D-235 this runs
on whole runs.

**This plan raises choices C1–C4. Nothing is coded until you choose.**

### What I read (session 21, 2026-10-18)

- **The row:** *"the product of the choices of the elections a computation carries (regime, house specification,
  set-off order), priced jointly"*, with its D-235 erratum: on whole runs. `DR 15` C2 has elections priced by
  recomputation, never a heuristic.
- **`Election<T>`** (sealed: `HouseElection`, `RegimeElection`, `SetOffOrderElection`) has `candidates`, `stated`,
  `choosing`, `regimeFor`, `basis`, `node` and `describe`.
- **The three `choosing` methods touch disjoint fields:**
  - regime: `EngineInputs.regime`;
  - houses: `EnteredFacts.houseProperties` occupancy;
  - set-off: `EnteredFacts.absorptionOrder`.

  Each copies everything else, so applying them in sequence composes in any order. Only `RegimeElection.regimeFor`
  changes the `RegimeSpec`. The others return the regime being computed.
- **Candidates read only the original inputs:**
  - regime: `RegimeOffers.of(pack, inputs)`;
  - houses: the entered houses and `HP-OWN-RESIDENCE`;
  - set-off: `SETOFF-ACROSS-HEADS`.

  No election's candidates depend on another's choice.
- **`ElectionResolver.resolve`:** a stated choice is computed alone; otherwise every choice gets a whole run, the
  least `tax.netpayable` is taken, and a tie goes to the earlier choice, the default first. `ElectionOutcome<T>`
  holds the chosen choice, the mode and the priced alternatives. One MEASURE line per alternative, citing
  `basis(choice)` under `node()`, is appended to the chosen run's trace (`D-VIEWFROMTRACE`).
- **The tests:**
  - `ElectionResolverTest` uses a stub graph: one node prices the elected order from a table.
  - `GoldenCaseRunner.resolveRegime` / `resolveHouses` run the shipped engine.
  - `RegimeElectionPipelineTest` pins DR 08 T2-4: ₹5,00,00,000 nets 1,89,54,000 in the new regime and 1,92,56,250
    in the old.

### Findings

1. **The joint search is a product of each election's choice list,** taken in a fixed order with every default
   first, so the first combination is all the defaults. A tie goes to the earlier combination, so to the defaults
   where they are among the cheapest, as in `resolve`.
2. **An election's own outcome can still be stated without new types.** For each choice `c`, its price is the least
   net payable of the combinations that make `c`, with the other elections at their best for it. The jointly chosen
   combination's choice for that election has the global least, so `ElectionOutcome<T>` keeps its meaning and shape.
   The lines grow with the sum of the elections' choices, not with their product.

### Choices (recommended first)

- **C1 — the API:**
  - **(a) recommended:** `ElectionResolver.resolveTogether(List<Election<?>> elections, registry, pack, regime,
    inputs)` returns `JointResolution(List<ElectionOutcome<?>> outcomes, PipelineRunner.Result run)`.
    - The outcomes are in the elections' order.
    - It refuses fewer than two elections (`resolve` is for one) and two elections of the same kind.
    - A stated election contributes only its stated choice.
    - The regime is folded through each `regimeFor`.
    - `resolve` stays as it is.
  - **(b)** replace `resolve` with the joint method for any number of elections. That changes `resolve`'s line text
    and its tests, which is outside this item.
- **C2 — what each election's outcome and lines say:**
  - **(a) recommended** (finding 2): per choice, the least net payable over the combinations with it. Its line says
    *"`<choice>`: net payable, the other elections at their best for it (`<their choices>`); chosen / not chosen —
    priced jointly by recomputation against N combinations, the least taken, a tie going to the earlier, every
    declared default first"*. A stated election's line keeps `resolve`'s stated wording.
  - **(b)** one line per combination. That is N lines (84 for 2 × 7 × 6), and no single election's line can show
    its own alternatives.
- **C3 — the code shape:**
  - **(a) recommended:** a private generic helper captures each `Election<?>`'s type. Combinations are index
    vectors. The MEASURE-line construction in `withAlternatives` is extracted into one private method that both
    paths call, so the line is built once. `resolve`'s output stays byte-for-byte the same, and its tests prove it.
- **C4 — records:** D-236; the TS `election/` row and a Changes entry; `ElectionResolver`'s class Javadoc (one
  paragraph).
