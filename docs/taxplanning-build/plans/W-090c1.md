## Plan for W-090c1 — The facts r.164's conditions read: the split

**What this item is for (one sentence, in my own words):** every fact r.164(2) and (3)(e) read about a person, or about
their computed return, becomes something a form's condition can test. This plan sizes it and proposes a second split,
which D-523's row expected, because the facts fall into two groups with different sources.

**Findings (each read this session):**
- F1: the condition context is built in one place, `NodeContext.conditions()` (`pipeline/NodeContext.java:343` –
  `345`):
  - It fills residence as a boolean, `resident = residence() != NON_RESIDENT` (`:343`), plus person type, ages,
    disabilities and the declarations.
  - Nothing in main code fills `headsWithIncome` or `nodeValues` (grep outside `rules/condition` finds no filler). So
    `HasIncomeUnderHead` and `IncomeAtLeast` can hold today only in tests.
- F2: the person's own facts are already inputs:
  - Residence is `Assessee.ResidentialStatus` (`RESIDENT`, `RNOR`, `NON_RESIDENT`, `input/Assessee.java:47` – `50`).
  - The house properties are a list of `HouseProperty` (`input/HouseProperty.java:32`), each with an
    `ownershipShare`.
  - Brought-forward losses are entered as `CarriedHousePropertyLoss` and `CarriedCapitalLoss` (`input/`).
- F3: the computed facts are not on the result. `TaxComputation` holds `totalIncome`, `taxByBasis` and the trace only
  (`result/TaxComputation.java:52` – `61`). These stay inside the run:
  - capital gains by part, and the short- and long-term losses left after set-off (`CapitalGainsHead`,
    `pipeline/CapitalGainsHead.java:27` – `28`);
  - what `SetOffNode` leaves to carry forward under each head;
  - which s.93 clauses a deduction was allowed under (`OtherSourcesNode`, `DepositInterestDeduction`).

  Which capital-gains part is "long-term capital gains under section 198" is pack data. A part is a
  `CapitalGainsPart` code that CG-PARTS declares (`rules/definition/CapitalGainsPart.java:18`), so a condition can name
  parts without knowing the law.

**Choices for the owner:**
- **C1a (recommended): split W-090c1 into two.**
  - **W-090c1a, the person's own facts, filled now by `NodeContext`.**
    - Conditions: `IsOrdinarilyResident` (resident and not RNOR; the context keeps the status, not a second boolean),
      `HousePropertiesOwnedAtMost(n)` (every entered property counts, whatever the share, because r.164(2)(b) says
      "own", not "own wholly"), and `HasLossBroughtForward(head)`.
    - Each has a filler in main code from the day it lands.
  - **W-090c1b, the computed facts a return form reads, carried on the computation.**
    - `TaxComputation` gains the facts: income or loss by head, losses to be carried forward by head, capital gains by
      part, and the s.93 deduction rows applied.
    - Conditions read them: `HasLossUnderHead(head)`, `HasLossCarriedForward(head)`, `CapitalGainsOnlyInParts(parts)`,
      `CapitalGainsPartAtMost(part, limit)`, and `RuleAppliedOutside(set, rules)` for "a s.93 deduction other than
      93(1)(d)".
    - Each is a fact, never "ITR-1 eligible". It is published as data because W-092's schedules need the same
      figures.
    - Building a context from a computation stays W-091's (the selector), as it does for `totalincome` today. I will
      plan the s.93 reading against the rule set the rows belong to, and it may split again.
  - C1b: one item. It touches the condition algebra, `NodeContext`, `TaxComputation` and three nodes in one change.
- **C2a (recommended): co-ownership counts as owning.** r.164(2)(b) says "does not own more than two house property".
  A person with a half share owns that property, so any `ownershipShare` above nil counts. C2b: count only whole
  ownership. That reading has no support in the text I read.
