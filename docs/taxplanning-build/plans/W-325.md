## Plan for W-325 — the other rows' explanations (F37.2): split first

**What this item is for (one sentence, in my own words):** give every rule that can name a trace line a plain
sentence, as W-116 did for the 28 least-of rows. Each line's `in` and `out` are read from its node before any
sentence names them.

**Probe (run before this plan, then removed):** for one taxengine unit run (4,153 tests), I logged every `TraceLine` as
it was built: the rule, the node, the kind, and the types of `in` and `out`. `TraceLine.java` was restored afterwards,
and `git diff` shows it unchanged.

| Finding | Count |
|---|---|
| Rule ids that appear on a trace line | 199: 191 pack rules plus 8 test or synthetic ids |
| Pack rules on a line with no explanation yet | **163** |
| Pack rules that appear on **no** line in the run | 53 (condition and eligibility rows, rates read inside another rule, …) |
| (node, kind) groups the 163 fall into | 37. The largest are `salary.perquisites` INCOME 39, `chapterviii` DEDUCTION 22, `othersources.income` INCOME 14, `capitalgains.income` MEASURE 9, `tax.bybasis` TAX 8, `salary.base` MEASURE 7 |
| Lines whose `out` is not money | e.g. `salary.base` (`SalaryBases`) and `tax.bybasis` (`TaxByBasis`): their sentence can name no `{out}` |

Each sentence needs its node's meaning of `in` and `out`. That is about 37 node paths to read and 163 sentences to
draft, which is too large to review as one item.

**Choices for the owner:**
- **C1: how the work is split.**
  - **C1a (recommended):** four items by node family, each with its own plan, probe, review and commit:
    - **W-325a, salary:** `salary.perquisites`, `.base`, `.retirement`, `.exemptions`, `.gross`, `.income`, `.deductions`, `.medicaltravel` and employer-contribution charges. About 64 rows.
    - **W-325b, deductions and other heads:** `chapterviii`, `othersources.income`, `houseproperty.income`. About 59 rows.
    - **W-325c, the bill:** `tax.bybasis`, `.surcharge`, `.afterrebate`, `.cess`, rounding, `interest.and.fees`, `advance.tax`, `credits` and `setoff`. About 37 rows.
    - **W-325d, capital gains,** then the coverage pin (C2). About 12 rows.
  - C1b: one item for all 163. That is one review of 163 drafted sentences.
- **C2: the 53 rows on no line.**
  - **C2a (recommended):** W-325d classifies each one, by reading the code that reads it, as either "names a line on a path the tests do not reach" (that row gets a sentence) or "never names a line". The second kind is listed in the content file as `notALine` with the reason. `ExplanationCompilationTest` then pins that every rule of each year's pack is explained or listed. That makes full coverage a build check rather than a claim.
  - C2b: leave them out. F37.2's fallback to the rule ID already covers any line that does appear.
- **C3: lines whose figure is not money** (C3a, recommended): their `what` names no placeholder. The renderer already refuses a placeholder whose value is not money (W-116), so the build check holds.

**What I am NOT doing here:** any sentence. This plan only places W-325a – W-325d on the board in order, so that each is built and reviewed on its own (`batch-small-items` does not apply, because these are not small).

**Numbers I will use:** none.

**How I will verify:** board, `FinishedPlanTest` and `ParkedRowsTest`. Each sub-item names its own tests when it is
planned.

**Post-deployment actions (R15):** none.

**Roles:**
- **Architect:** no design change. W-116's catalogue, checks and renderer carry all four items.
- **PM:** each batch is a reviewable set of sentences, and users see the salary lines first (the most common).
- **Engineer and testers:** each sub-item gets its own red check and integration assertion.

**Risks:** the probe counts what the unit tests reach. A rule reached only on an untested path shows up under C2a's
classification rather than being silently missed.
