## Plan for W-091 – W-094 (one batch) — choosing the ITR form, then its schedules (`DR 21` I4, I5, I8)

**What this batch is for (one sentence, in my own words):** given a computed return, say which form the person files,
why every other form does not fit, and how they may furnish it (W-091). Then lay the form's schedules out as data
filled from the trace (W-092, W-093), proven by DR 21's T21 cases (W-094).

**Probe run first (memory `probe-before-plan`; throwaway, deleted, tree clean):** the four personas ran through the
full pipeline and a DR 21 I4 cascade over the shipped TY 2026-27 forms.
- Priya (salary ₹20,25,000) → ITR-1. Anand (pension and interest, ₹6,29,000) → ITR-1.
- Meera → ITR-2: ITR-1's ₹1,25,000 LTCG limit and r.164(3)(k), total income ₹50,50,000 over ₹50 lakh.
- Ravi → ITR-2: a short-term gain (₹40,000), and LTCG ₹1,50,000 over the limit.

Three facts the probe found, each a design point below:
1. **Nothing fills the form's computed facts.** `NodeContext.conditions()` (`NodeContext.java:342`) gives residence,
   ages, declarations and houses only. Bar (k) (`IncomeAtMost` on `round.totalincome`) and `HasIncomeUnderHead` read
   `nodeValues` and `headsWithIncome`, which no production code sets. The selector must set them from the run: the
   rounded total income, and the heads with income from `ReturnFacts`.
2. **The engine computes no business head.** `ReturnFacts.incomeUnder(BUSINESS_OR_PROFESSION)` throws "was not
   computed" (`ReturnFacts.java:65`). So the head is absent, never present, and "no business income" always holds.
3. **An unanswered declaration throws** ("an unanswered question is not a no", `Declarations.java:41`). A person who
   has not answered the year's questions cannot be put through ITR-1's bars.

**Sizing (said plainly, D-622):**
- **W-091 and W-094's selection cases are one build**, on data that exists.
- **W-092 and W-093 are not ready.** No form layout has been read: no sources file covers a schedule, and only the
  design docs name "Schedule S". DR 21 I5's example field paths ("S.1", node `salary.gross`, rule `SAL-HRA-001`) are
  illustrations, not read from a form. The schedules have to be read from the Gazette forms before any can be
  written: TY 2025-26's ITR-1 (2026/271423, pp.16 on) and ITR-2 (2026/271435, pp.38 on). TY 2026-27's forms under
  r.164 are not located. See C1.

**Files I will create (C1a):**
- `taxengine/rules/filing/ItrFormSelector.java`: the cascade (DR 21 I4). Candidates are filtered by person type and
  return kind and sorted by `cascadeOrder`. A form is excluded where an eligible earlier form is in its `excludes`.
  Otherwise it is eligible when no positive condition fails and no bar holds. The first eligible form is chosen.
- `taxengine/rules/filing/ItrSelection.java`, `FormVerdict.java`: every verdict, not only the winner.
  - Each verdict lists the failed positive conditions and the bars that held, each with its reason and provenance.
  - The selection carries the chosen form (`Optional`), the furnishing manners open to the person, and the
    unanswered questions (C3a).
- `taxengine/api/ItrFormChoice.java` (the API's answer) and `TaxCalculator.chooseForm(EngineInputs, ReturnKind)`:
  runs the computation and the selector, and builds the context from the run (point 1).
- `taxplanning/compute/controller/…`: `POST /tax/user/{email}/drafts/{draftId}/itr-form` beside `/compute`
  (`DraftComputationController.java:31`), body `{ "returnKind": "S263_1" }` (C2a). An api-collection request with it.
- `ItrFormSelectorTest` (synthetic packs: T21-12, 13, 16, and the cascade rules) and `ItrFormChoiceTest` (shipped
  packs, T21-1 – 5, 7, 9 – 11).

**Files I will modify:** `TaxCalculator.java` (one method); `DraftComputationController` and its service;
`api-collection` (submodule); `STATE.md`, `CHECKPOINT.md`. Plus `NodeContext.java` if the context is built there (the

**Choices for the owner:**
- **C1: the batch's scope.**
  - **C1a (recommended):** build W-091 now, with W-094's selection cases. W-092 / W-093 (and T21-14, T21-15) start
    with reading TY 2025-26's two Gazette forms into a sources file, then the schedule rows for the heads the engine

  - C1b: the whole batch in one build. The form reading comes first either way; C1b only holds W-091 back until it
    is done.
- **C2: where the choice is served.**
  - **C2a (recommended):** its own route, `POST …/drafts/{draftId}/itr-form`, with `returnKind` required. No input
    names the kind today (`ReturnKind`'s javadoc: "a return's inputs will name it"), and no default stands in for it.
  - C2b: added to the `/compute` response. That makes every compute name a return kind.
- **C3: unanswered questions.**
  - **C3a (recommended):** a form whose bar reads an unanswered question is **undetermined**, naming each question.
    No form is chosen while an earlier form in the cascade is undetermined: "answer these to settle ITR-1".
  - C3b: refuse the request with a 400 listing the unanswered questions.
- **C4: no shipped form fits** (business income or speculative trading need ITR-3, parked as W-090c3; an updated
  return needs ITR-UN, parked as W-090e).
  - **C4a (recommended):** answer 200 with no chosen form, every verdict, and the message "No form shipped for
    2026-27 serves this return; ITR-3 and ITR-4 are not modelled yet". T21-6 and T21-8 assert this until those forms
    ship.
  - C4b: DR 21's `NoApplicableItrFormException`, which answers 500 under `ControllerAdviser`.
