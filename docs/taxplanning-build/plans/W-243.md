## Plan for W-243 — a lone regime-chosen row is applied in a regime it excludes

**For:** a rule written `OnlyIn` or `ExceptIn` some regimes is never applied in a regime it excludes, whether its rule
set holds one row or several — so a regime added by data (W-146) cannot receive a deduction its law withholds, with no
word in the trace.

### What I read (session 49)

- **The defect** (`pipeline/NodeContext.java:291` – `305`): `chosen` returns a `REGIME`-ground set's rows untested when
  it holds one (`rows.size() <= 1 && set.ground() == SelectionGround.REGIME`); with two or more it keeps only those
  where `inRegime(...).applies()` (`appliesHere`, `:307` – `317`).
- **Why the shortcut exists:** W-088m2 kept *"one row, no test"* for `REGIME` sets when it made condition-chosen sets
  test even a lone row (`plans/W-088m2.md:60`, D-253). It lets a node receive a lone row that the regime **disallows**
  and write a nil line naming the provision: `SalaryDeductionNode.taxOnEmployment` (`node/SalaryDeductionNode.java:108`
  – `128`) and `entertainmentAllowance` (`:135` – `160`) read `inRegime` themselves — `ExcludedByRow` → no line,
  `Disallowed` → a nil line with `whyNot()`.
- **`inRegime`** (`NodeContext.java:364` – `379`) gives `ExcludedByRow` when the row's own `regimes` leave the regime
  out, `Disallowed` when a regime's disallowance set names the rule, else `Applies`.
- **Who is hurt:** every node that takes `ruleOf(set)` and does not ask `inRegime` — the standard deduction
  (`SalaryDeductionNode.standardDeduction`, `:197` – `204`) among them. W-146's probe applied `SYN-STANDARD-DEDUCTION`
  `ExceptIn(SYN_FLAT)` under `SYN_FLAT` (`plans/W-146.md` F4).
- **Exposure today:** none. No `REGIME`-ground set in TY 2025-26 or 2026-27 holds a lone row whose `regimes` is not
  `AllRegimes` (scan of `law/rules` against `law/rule-sets.json`, session 49) — so no shipped figure changes.
- **Tests:** `NodeContextRuleSetTest` (`ruleOf_*`, `optionalRuleOf_*`, `:131` – `:263`); `SalaryDeductionNodeTest`
  `evaluate_whenInTheNewRegime_deductsNoEntertainmentAllowanceAndSaysWhy` (`:304`), the `Disallowed` path.

### Choices (recommended first)

**C1 — the fix.** (a) **A lone row of a `REGIME` set is tested for the row's own regimes (`ExcludedByRow`) like any
other; a lone row the regime only disallows is still returned**, so the nodes that explain a disallowance keep doing so.
An `EXACTLY_ONE` set left with no row then refuses loudly, as it already does with several rows; an `AT_MOST_ONE` set
is empty. (b) Test lone rows fully (`applies()`), as several rows are — the disallowance nil lines then vanish and
`ruleOf` refuses on every disallowed `EXACTLY_ONE` set (tax on employment in the new regime), so nodes would have to be
rewritten. (c) Keep the shortcut and make every node ask `inRegime` — sixty nodes, and the next one forgets.

**C2 — the branches made unreachable.** Under C1a, `ExcludedByRow` can no longer reach `taxOnEmployment` or
`entertainmentAllowance`. (a) **Remove the two `ExcludedByRow` branches** (no dead code) and say in each method's
Javadoc that the set never yields an excluded row. (b) Keep them as a guard.

### Build (C1a, C2a)
1. `NodeContext.chosen`: a lone `REGIME` row is kept only where `version.regimes().appliesIn(regime)`; the Javadoc
   says why the disallowed lone row is still returned (the node names the provision).
2. `SalaryDeductionNode`: the two `ExcludedByRow` branches removed; Javadoc updated.
3. Tests in `NodeContextRuleSetTest`:
   - `ruleOf_whenTheSetsOnlyRowExcludesTheRegime_isRefused` — one row `ExceptIn(the running regime)`;
   - `optionalRuleOf_whenTheSetsOnlyRowExcludesTheRegime_isEmpty`;
   - `ruleOf_whenTheSetsOnlyRowIsDisallowedInTheRegime_isStillThatRow` — so the explanation path is held.
