## Plan for W-402 — store every time in UTC

> Planned in session 122 (2026-11-25), placed by D-954 (2), before W-337i. **Stop point (Stage 2 EXPLAIN):** nothing is
> built until the owner answers C1 – C6. **Revised after D-958** (the split: wire format and the published zone are W-403).

**What this item is for (one sentence, in my own words):** every time the application stores is written in UTC — today
audit times, the P&L "last updated" time and a transaction's submission time are the machine's local time while every other
stored time is UTC — and, widened by D-958, the JVM runs in UTC while one setting, `app.time.zone` (Asia/Kolkata), decides
"today", so nothing depends on the host's zone.

### Inventory (measured this session, HEAD of `w-337`)

| Stored time | Set by | Zone today |
|---|---|---|
| `created_at` / `updated_at` on every audited table (`AuditColumns.java:35, 39`) | JPA auditing: `@EnableJpaAuditing` names no `dateTimeProviderRef` (`PostgresJpaConfig`), so `CurrentDateTimeProvider.getNow()` → `LocalDateTime.now()` (spring-data-commons 4.1.0, read with `javap`) | **local** |
| `RealisedProfits.lastUpdatedTime` (in `profit_and_loss` JSON) | `LocalDateTime.now()`, `ProfitAndLossService.java:131, 420` — inside **static** methods (`:127`, `:415`), reached from `:90`, `:379`, `:398` and `ProfitAndLossRebuild.java:86` | **local** |
| `transactions.submitted_at` | `LocalDateTime.now()`, `TransactionService.java:101`; compared with `LocalDateTime.now()` at `:83` (the idempotency window) | **local** |
| every other stored `LocalDateTime` (25 fields: privacy, auth, tax planning, charges) | `LocalDateTime.now(clock.withZone(ZoneOffset.UTC))`, `JobContext.nowUtc()`, `TLocalDateTime.now()` (UTC) | UTC |
| `orderExecutionTime`, `AssetRequest.orderExecutionDateTime`, `BreachNotice.becameAwareAt` | entered by the caller — a fact, not "now" | not changed here |

Readers of the local times: `AutoArchive.java:43-44` (cutoff taken in local time *because* `updated_at` is — its own
comment); `ThirdPartyRetention.java:96-97` (audit time → the tax year it falls in); `GazetteCursorResponse.java:10` (shown to
an admin); `AssetsRebuild.java:167` (copied). Not stored but bare `LocalDateTime.now()`: `AnalyticsService.java:83` (a
response's `lastUpdated`), `EntityExportService.java:76` (an export's file name).

The `Clock` bean is `Clock.systemDefaultZone()` (`InvestmentTrackerConfig.java:36`) and 14 tax-planning services read
"today" from it (`LocalDate.now(clock)`, e.g. `DraftComputationService.java:88`, `DraftCalendarService.java:50`): an
Indian date.

### Probe (`probe-before-plan.md`): the core change applied, targeted tests run, reverted

Applied: a UTC `DateTimeProvider` on `@EnableJpaAuditing`; UTC at `TransactionService:83, 101`, `ProfitAndLossService:131,
420`; `AutoArchive`'s cutoff from `context.nowUtc()`. Ran 12 unit and 15 integration classes (machine zone Asia/Kolkata,
`/etc/localtime`). **One test moved:** `TransactionServiceIdempotencyTest.recordTransaction_whenNew_stampsTheFingerprintAndSubmissionTime`
(asserts against a local now). **Two will move at compile time** once `TransactionService` takes a `Clock`:
`TransactionServiceChargesTest.java:53`, `TransactionServiceIdempotencyTest.java:55, 200` construct it by hand. Everything else
green, **including the `AutoArchive` cases in `TaxJobsIntegrationTest` — which therefore cannot tell the cutoff's zone; a new
case must.** CI runs in UTC (GitHub's runners), where local and UTC are the same, so every new test pins a non-UTC clock
(`Clock.fixed(…, Asia/Kolkata)`, the way `TaxJobsIntegrationTest` already fixes its clock) or it proves nothing there.

### Decisions (for approval with this plan)

- **C1 — audit times.** **C1a (recommended):** a `DateTimeProvider` bean, `LocalDateTime.now(clock.withZone(ZoneOffset.UTC))`,
  named by `@EnableJpaAuditing(dateTimeProviderRef = …)` in `PostgresJpaConfig`. **C1b:** set the JVM's default zone to UTC
  at start — changes "today" too (C2); not recommended.
- **C2 — the `Clock` bean (D-958).** **C2a (recommended):** `Clock.system(app.time.zone)`, the setting in `application.yaml`
  as `Asia/Kolkata` (no per-profile copy), read through a small `@ConfigurationProperties` record that refuses a missing or
  unknown zone at start; stored times take `clock.withZone(ZoneOffset.UTC)`, as the 25 UTC fields already do. **C2b:** a UTC
  bean — between 00:00 and 05:30 IST every "today" in tax planning would be yesterday; not recommended.
- **C6 — the JVM's zone (D-958).** **C6a (recommended):** `TimeZone.setDefault(UTC)` as the first line of
  `WealthLensApplication.main` (the app is started only through it: `spring-boot:run`, `java -jar`), and
  `-Duser.timezone=UTC` on surefire's `argLine` (`pom.xml:195`, after `@{argLine}`) so tests run as the app does, locally as
  on CI. **C6b:** an `EnvironmentPostProcessor` setting it for app and tests alike — framework machinery for one line; not
  recommended.
- **C3 — the static P&L methods.** **C3a (recommended):** `ProfitAndLossService` takes the `Clock` and carries one UTC
  "now" into the static methods through the context objects they already receive (`InternalTransactionContext`,
  `InternalContext`); `foldSale` gains it as a parameter from `ProfitAndLossRebuild` (which takes the `Clock`).
  **C3b:** `LocalDateTime.now(ZoneOffset.UTC)` in place — not on the test-controlled clock; not recommended.
- **C4 — what callers see.** **C4a (recommended):** responses show the stored UTC time, as they already do for the 25 UTC
  fields; the P&L `lastUpdatedTime`, analytics `lastUpdated` and the Gazette cursor's `updatedAt` move 5 h 30 min earlier for
  an Indian caller. **C4b:** convert to IST at each response — every time-bearing response, and a zone to choose; not
  recommended here (a proposal if you want it).
- **C5 — the guard.** **C5a (recommended):** an `ArchitectureTest` rule: no main class calls `LocalDateTime.now()` without a
  clock (so `AnalyticsService:83` and `EntityExportService:76` move to `clock.withZone(UTC)` too), proven by a deliberate
  violation; plus a test of the provider with `Clock.fixed(2026-02-01T00:00 IST)` expecting `2026-01-31T18:30`. A
  `LocalDateTime.now(clock)` with a local clock cannot be seen statically, so the inventory above is the check for those.
  **C5b:** no rule — the next bare `now()` would go unnoticed; not recommended.

**Five roles:**
- **Architect:** stored time UTC, the JVM UTC, "today" the business zone's date — one setting, one `Clock` (D-958).
- **PM:** C4a's visible shift of three "last updated" times for an Indian caller; nothing else a user sees.
- **Senior engineer:** `AutoArchive`'s cutoff and the idempotency window move together with what they compare.
- **Automation tester:** every new test pins Asia/Kolkata, since CI's UTC hides the difference.
- **Manual tester:** after W-337i, a trade's P&L "last updated" read once against the clock.

**Risks or ambiguities:**
1. **"Today" moves on CI.** CI's `Clock` was UTC (its system zone); with C2a it is Asia/Kolkata. A test reading the real
   `Clock` near a date boundary could shift; the touched integration classes are run, and the full tiers on the pipeline.
2. **Logs** print times in UTC once the JVM is UTC (C6a) — today they follow the host (IST).
3. **One proposal open:** the `order_execution_time` column types (`TIMESTAMPTZ` on `transactions`, `TIMESTAMP` on
   `trade_outcomes`) — say if it should be placed as a row.
